A.1Logic Exercises · 逻辑练习

本节习题练习在关系逻辑中编写表达式与约束。它们不需要任何关于完整 Alloy 语言的知识，但其中许多展示了如何把表达式与约束嵌入一个 Alloy 模型，以便你能用 Analyzer 生成实例、获得具体反馈。

♥ A.1.1 Properties of Binary Relations · 二元关系的性质

下面这个 Alloy 模型把一个二元关系约束为具有一组标准性质：

module exercises/properties
pred show () {
  some r: univ -> univ {
    some r          -- 非空 nonempty
    r.r in r        -- 传递 transitive
    no iden & r     -- 反自反 irreflexive
    ~r in r         -- 对称 symmetric
    ~r.r in iden    -- 函数性 functional
    r.~r in iden    -- 单射 injective
    univ in r.univ  -- 全的 total
    univ in univ.r  -- 满的 onto
  }
}
run show for 4
题目

一个有限的二元关系不可能同时具有所有这些性质。哪些单个性质如果被消除，能让剩下的性质得到满足？对每一个被消除的性质，给出一个满足其余性质的关系的例子。

你可以用 Alloy Analyzer 来帮忙。run 命令指示 Analyzer 在至多 4 个原子的宇宙中搜索一个满足约束的实例。要消除某个性质，只需把它注释掉（在行首写两个连字符）。

点拨

这八条性质的写法本身就是第 3 章的浓缩复习：r.r in r 是传递性（自复合仍落在自身内）、no iden & r 是反自反（与恒等关系无交）、~r.r in iden 是「逆复合落在恒等里」= 函数性、r.~r in iden = 单射性、univ in r.univ 是「每个原子都在 r 的定义域里」= 全的、univ in univ.r = 满的。冲突的核心在于「反自反 + 对称 + 传递」三者同时成立时，r 只能是空关系（若 x->y in r，对称给 y->x，传递给 x->x，与反自反矛盾）——而空关系又与「非空」冲突。所以消掉「非空」即可全部满足；此外消掉「反自反」「对称」「传递」中任意一条也都能构造出解。

♥ A.1.2 Relational and Predicate Calculus Styles · 关系演算与谓词演算两种风格

A.1.1 中的性质是用关系演算（relational calculus）风格写的。把每一条改写成谓词演算（predicate calculus）风格。例如「非空」性质可以重新表述为：

some x, y: univ | x -> y in r

你的每一条改写都可以被铸成一个 Alloy 断言，于是你能用 Analyzer 来检验它。例如，要检验「非空」的改写，你会写：

assert ReformulateNonEmptinessOK {
  all r: univ -> univ |
    some r iff (some x, y: univ | x -> y in r)
}
check ReformulateNonEmptinessOK

然后执行这个 check，看是否有反例——即关系 r 的某个取值满足其中一种表述却不满足另一种。

点拨

这正是 3.3.1 讲的「两种风格等价」的机器验证版。注意断言里用 iff 而不是 implies——双向等价才能证明「改写」而非「弱化」。最容易写错的是 ~r.r in iden（函数性）与 r.~r in iden（单射性）的谓词演算形式：前者是 all x, y, z: univ | x->y in r and x->z in r implies y = z，后者要把量词顺序反过来（或改用 ~r 的表述）。

♥ A.1.3 Relational Properties in Modeling · 建模中的关系性质

假设你要把下列每一种关系建模为一个二元关系。你会期望它具有哪些性质（取自 A.1.1 的清单）？

#关系含义
(a)sibling同胞关系：父母相同的孩子们之间
(b)links链接关系：网络上的一个主机与它链接到的那些主机之间
(c)contains包含关系：文件系统中的一个目录与它的内容之间
(d)group分组关系：绘图程序中的图形元素与「组」（被一起选中/取消选中的元素集合）之间
(e)sameGroup同组关系：处于同一个组中的图形元素之间
(f)supersedes取代关系：一个文件系统中的文件与另一个文件系统中的文件之间，当第一个文件是第二个文件的更新版本时成立
(g)substitutableFor可替代关系：两个组件之间，当第一个可以在某类系统中的任何位置替代第二个时成立。例如一个电源可以替代另一个，只要它提供相同的电压和至少同样多的功率
点拨 · 参考答案
关系对称反自反传递说明
sibling✅❌（通常把自己也算作同胞，故自反）✅若不含自己则反自反且不传递
links看情况✅❌超链接通常不对称、不传递
contains❌✅看定义若是「直接包含」则不传递；若是「递归包含」则传递且非对称（antisymmetric）
group❌✅❌元素→组是函数性的（每个元素属于至多一个组）
sameGroup✅❌（自反）✅这是一个等价关系，= ~group.group
supersedes❌✅✅版本的「更新」是严格偏序
substitutableFor✅❌（自反）✅又一个等价关系——「提供相同电压且功率不小于」需要仔细推敲是否真对称

(d) 与 (e) 是同一对关系的两种视角：sameGroup = ~group.group。这道题的真正用意是让你体会「一个关系的性质往往由它与另一个关系的复合方式决定」。

♥ A.1.4 Refactoring Navigation Expressions · 重构导航表达式

在编写「导航表达式（navigation expressions）」时，你可能会注意到重复的子表达式可以被提取出来，使整个表达式更简洁。例如表示「p 的叔叔」的表达式 p.mother.brother + p.father.brother 可以改写成 p.(mother + father).brother。

这类化简依赖于「某些代数恒等式成立」这一假设，例如对给定的集合 s 与二元关系 p、q：

#候选恒等式名称
(a)s.(p + q) = s.p + s.qjoin 对并的分配律
(b)s.(p - q) = s.p - s.qjoin 对差的分配律
(c)s.(p & q) = s.p & s.qjoin 对交的分配律

对每一个候选恒等式，说明它是否成立；如果不成立，给出一个反例。

module exercises/distribution
assert union {
  all s: set univ, p, q: univ -> univ | s.(p + q) = s.p + s.q
}
check union for 4

这条命令让 Analyzer 在 4 个元素的宇宙中找反例。当你发现某个性质不成立时，试着通过缩小作用域（例如把 for 4 换成 for 2）来获得尽可能小的反例。

点拨 · 参考答案

(a) 成立，(b)(c) 都不成立。理由很直观：join 是「逐元取像」的操作，它对并天然分配（一个元组来自 p 或 q，那么它的像就在 s.p 或 s.q 中）；但对差和交不分配，因为像集合会「混合」来自 p 和 q 的贡献。

最小反例（作用域 2 即可）：令 s = {A}，p = {A->B}，q = {A->B}，再加一个 A->C 到 p。则 s.(p-q) 可能为空而 s.p - s.q 非空。交的情形同理。这正呼应了 3.2.5 里关于「join 分配律只对并成立」的提醒。

A.1.5 Characterizing Trees · 刻画树

树是一个满足某些性质的关系。这些性质究竟是什么？用关系逻辑把它们表达出来，并用几个例子加以说明。

module exercises/tree
pred isTree (r: univ -> univ) { … }
run isTree for 4

只需把省略号替换成对关系 r 的一些约束，然后执行命令来可视化一些样例实例。你可能需要加一些约束来让实例不平凡（nontrivial）。

点拨 · 树的四条特征
  1. 无环：no x: univ | x in x.^r；
  2. 每个节点至多一个父节点（函数性逆向）：~r.r in iden，或写作 all x: univ | lone ~r.x；
  3. 恰有一个根：one {x: univ | no ~r.x}；
  4. 连通：从根出发可达所有节点 all x: univ | x in root.*r。

「让实例不平凡」的技巧：加 some r（非空）、some x: univ | lone x.r and some x.r（存在恰好一个孩子的节点）、或者要求 #univ = 4 让树占满作用域。不加这些，Analyzer 很可能只给你一个空的或单节点的树。

A.1.6 Spanning Trees · 生成树

一个图的生成树（spanning tree）是一个覆盖所有节点的、树状的子图。把这个定义精确化，并给出一个具有两棵不同生成树的图的例子。

module exercises/spanning
pred isTree (r: univ -> univ) { … }
pred spans (r1, r2: univ -> univ) { … }
pred show (r, t1, t2: univ -> univ) {
  spans (t1, r) and isTree (t1)
  spans (t2, r) and isTree (t2)
  t1 not= t2
}
run show for 3
提示

由你决定把图和树看作有向的还是无向的。无向的情形更棘手一些，也更有意思。

生成树有什么用

生成树有许多用途。在网络中，它们常被用来建立连接。例如在 Firewire 协议中，一棵生成树被自动发现，而树的根成为协调通信的领导者（leader）。——这与 6.1 的环形领导者选举形成对照：同样是「选出一个协调者」，Firewire 靠生成树的根，环形协议靠最大标识符。

无向图在 Alloy 里怎么表示？用对称关系：r = ~r。spans(t, r) 则需说三件事：t 是 r 的子关系（t in r）、t 覆盖 r 的所有节点（t.univ + univ.t = r.univ + univ.r）、t 去掉方向后是一棵树。最后一条是难点：你要用 t + ~t 来做无环与连通判定，而不是直接用 t。

A.1.7 Characterizing Rings · 刻画环

一些通信协议把网络中的节点组织成一个环，节点到节点的链接构成一个圆圈。请尽可能简单、简洁地刻画 next（节点到节点的关系）上的约束，使其确保构成一个环。

module exercises/ring
sig Node {next: set Node}
pred isRing () {
  … 你的约束写在这里
}
run isRing for exactly 4 Node
点拨

第 6.1.1 节已经给出了标准答案：每个节点恰好一个后继（把声明改成 next: Node，或加 fact all n: Node | one n.next），加上「从任意节点出发反复跟随 next 可达所有节点」：

all n: Node | Node in n.^next

「尽可能简洁」的要点是：有了全称可达性，就不必再单独写「无环」和「唯一根」——它们在「每个节点恰好一个后继 + 全称可达」下自动成立。注意命令用了 for exactly 4 Node：4.2.3 说过，精确作用域能让「环恰好有 4 个节点」，否则 Analyzer 可能只给你一个 2 节点的环。

♣ A.1.8 Defining Acyclicity for an Undirected Graph · 为无向图定义无环性

一个无向图可以表示为一个被约束为对称的二元关系。为这样的关系写出排除环的约束。

module exercises/undirected
sig Node {adjs: set Node}
pred acyclic () {
  adjs = ~adjs
  … 你的约束写在这里
}
run acyclic for 4
点拨 · 为什么这题被标为 ♣

有向图的无环性很好写：no x | x in x.^r。无向图的陷阱在于对称性会让 adjs 自动包含 ~adjs，于是 x in x.^adjs 对任何有边的 x 都成立（x->y 且 y->x，两步就回到 x）。所以直接用闭包判环是无效的。

正确做法是先去掉自反对（adjs - iden 不影响，关键是长度 ≥3 的环），可以写成：

no x: Node | x in x.^^adjs.^adjs   // 思路示意，实际需仔细推敲

更实用的等价表述是「它是一片森林」：边数 = 节点数 − 连通分量数，或者「存在一个生成森林」。最简洁的写法往往是：all x: Node | x not in x.adjs（无自环）加上 「对任意非空节点集 S，S 内部至少缺一条边」：all s: set Node | some s and #(s.adjs & s) < #s * (#s - 1)。这类「计数式」约束正是 Alloy 允许乘法之外做基数的地方（# 运算符见附录 B）。

A.1.9 Axiomatizing Transitive Closure · 为传递闭包公理化

背景知识

传递闭包在一阶逻辑中不可公理化（not axiomatizable）。简而言之，这意味着如果你想表达它，你需要一个专门的运算符，因为它无法用其他运算符来定义。下面是一个伪造的（bogus）尝试；你的挑战是用 Alloy Analyzer 找出其中的破绽。

回想二元关系 r 的传递闭包是包含 r 的最小传递关系 R。我们说 R 是 r 的一个「传递覆盖（transitive cover）」，如果 R 是传递的且包含 r。为了确保 R 是最小的传递覆盖，我们可以说：从 R 中移除任何一个元组 a->b，得到的关系就不再是 r 的传递覆盖。把这个想法形式化，补全下面的模板：

module exercises/closure
pred transCover (R, r: univ -> univ) {
  … 你的约束写在这里
}
pred transClosure (R, r: univ -> univ) {
  transCover (R, r)
  … 你的约束写在这里
}
assert Equivalence {
  all R, r: univ -> univ | transClosure (R, r) iff R = ^r
}
check Equivalence for 3

现在执行这条命令，检查反例，并解释 bug 是什么。

历史注脚

UML 1.0 的官方定义就有这个问题。

点拨 · 破绽在哪

「移除任何一个元组后不再是传递覆盖」这个刻画只排除了「多余的传递边」，但没有排除「r 本身的边被传递性强制加回来的情形之外」的漏洞。真正的 bug 是：这个定义允许 R 包含 r 中没有、且移除后仍能靠传递性重新推出的元组——但只要 r 本身为空或结构特殊，最小性条件就可能被平凡地满足。

更根本的原因是逻辑上的：一阶逻辑无法表达「最小」，因为「最小」需要对所有子关系做全称量化，而一阶逻辑的量化范围是个体（原子与元组），不是关系——除非把关系也当作一阶对象（Alloy 通过 univ -> univ 类型做到了这一点，但代价是宇宙有限，而传递闭包的不可公理化恰恰是关于无限结构的定理）。所以在有限作用域下这个「伪造定义」可能看起来是对的，而 Analyzer 的反例会告诉你它在哪个具体的小结构上失效。

A.1.10 Address Book Constraints and Expressions · 地址簿的约束与表达式

这道题让你练习为一个简单的多级地址簿编写表达式与约束。考虑一个地址集合 Addr，和一个由两个不相交子集 Alias 与 Group 构成的名字集合 Name。从名字到地址的映射由关系 address 表示，但一个名字不仅可以映射到地址，也可以映射到另一个名字。

第一步：写出下列不变式

不变式（invariants）= 你期望地址簿始终满足的约束
  • (a) 没有环：如果你反复解析一个名字，你永远不会再次到达同一个名字。
  • (b) 所有名字最终都映射到一个地址。

第二步：写出下列模拟约束

模拟约束（simulation constraints）= 探索模型时为了看到更有趣的实例而添加的约束
  • (c) 地址簿至少有两层。
  • (d) 有些组是非空的。

第三步：写出下列表达式（不得使用集合理解式语法）

#要求
(e)作为组成员的那些名字的集合
(f)空的那些组的集合
(g)从别名到它们（直接或间接）所指地址的映射
(h)从名字到地址的映射，但当一个名字既直接映射到某些地址、又间接映射到另一些地址时，只包含那些直接地址
 
module exercises/addressBook1
abstract sig Name {
  address: set Addr + Name
}
sig Alias, Group extends Name {}
sig Addr {}
fact { … 不变式 … }
pred show () { … 模拟约束 … }
run show for 3

填写过程中不断执行 run 命令；工具会生成样例实例。然后，当你有了一个有趣的实例，把候选表达式输入求值器（evaluator），工具会向你显示它在那个特定实例上的值。你可能会发现需要添加更多模拟约束，才能得到一个能很好地说明某个表达式含义的实例。

点拨 · 参考答案
  • (a) all n: Name | n not in n.^address
  • (b) all n: Name | some n.^address & Addr
  • (c) some n: Name | some (n.address & Name).address
  • (d) some g: Group | some g.address
  • (e) Name.(~address) & Group.address.univ —— 更简洁：Group.~address & Name（被某个组指向的名字）
  • (f) Group - Group.address.univ —— 用域减去「有出边的组」，正是「不用理解式」的关键技巧
  • (g) (Alias <: address).^(address) & (Alias -> Addr)，或更直接 Alias <: ^address & (univ -> Addr)
  • (h) address & (univ -> Addr) —— 「只要直接的」就是用交把值域限制到 Addr，这一步极其简洁，正是「不用理解式」的示范

这道题的真正用意是让你体会：绝大多数「看起来需要集合理解式」的需求，都能用「交、差、域/值域限制」的组合来表达。这与 4.4.4 讲的 <:、:> 消歧义技巧一脉相承。

A.1.11 Modeling The Tube · 建模伦敦地铁

这道题让你先写出一些关于铁路线的通用约束，然后把它们应用到伦敦地铁上。

fig. A.1 的场景

fig. A.1 展示了伦敦地铁的一个简化片段（真实线路图见 http://tube.tfl.gov.uk/）。图中有三条线：

  • Jubilee 线：从 Stanmore 到 Waterloo，南北走向；
  • Central 线：从 West Ruislip 与 Ealing Broadway 到 Epping，东西走向；

A.2Extending Simple Models · 扩展简单模型

本节定位

本节的题目操练完整的 Alloy 语言，但会给你模型的初始结构。也就是说：你不需要从零设计 signature，而是要在别人搭好的骨架上补全约束、加操作、写断言。这恰恰是实际工作中最常见的建模任务形态。

A.2.1 Telephone Switch Connections · 电话交换连接

考虑下面这个电话网络连接模型：

module exercises/phones
sig Phone {
  requests: set Phone,
  connects: lone Phone
}

signature Phone 表示一组电话。对一部电话 p：

  • p.requests 是 p 正在请求与之连接的那些电话的集合，其中有些可能已被批准；
  • p.connects 是 p 当前连接到的那部电话（或者没有）。
#任务
(a)通过添加一个谓词并运行它来模拟这个模型。给谓词加一些约束以确保你不会得到无聊的情形；例如你可以说应该有一些请求和一些连接。
(b)添加两条不变式：每一个连接都有一个匹配的请求（假设请求不会消失，直到它们所派生的连接被拆除）；以及没有电话会议（conference calls），即没有一部电话参与多于一个连接。
(c)现在引入呼叫转移（call forwarding）：用一个从电话到电话的新关系 forward 来扩展状态，其中 p.forward 若非空，就是打进 p 的来电应当被转移到的那部电话。修改关联 requests 与 connects 的那条约束，以考虑转移。模拟一些有趣的呼叫转移例子，必要时添加额外的模拟约束。
点拨
  • (b) 的第一条：connects in requests —— 一行搞定，因为 connects 与 requests 都是 Phone -> Phone 的关系。这正是「关系包含」作为不变式的典型用法。
  • (b) 的第二条：「没有电话参与多于一个连接」要同时管住主叫侧和被叫侧：connects in ~connects 不够，应写 all p: Phone | lone connects.p + ~connects.p，或者更强：connects in ~connects and lone Phone.connects（后者说每部电话至多被一部电话连接）。
  • (c) 的陷阱：forward 可能形成环（A 转给 B，B 转给 A），于是「请求最终连到谁」需要闭包：connects in requests.^forward 或 connects = requests.*forward & ...。记得给 forward 加一条无环 fact，否则反例会全是循环转移。这也是 2.4 节「地址簿多级查找」的翻版。

A.2.2 Invariant Preservation in an Address Book · 地址簿中的不变式保持

题目设定

本题给你一个简单地址簿程序的模型，带有 add、delete、lookup 三个操作，以及一个刻画地址簿「良构性（well-formedness）」性质的不变式。你的任务是证明 add 和 delete 操作会破坏这个不变式，并通过强化它们的前置条件来修复。

module exercises/addressBook2
sig Addr, Name {}
sig Book {
  addr: Name -> (Name + Addr)
}
pred inv (b: Book) {
  let addr = b.addr |
    all n: Name {
      n not in n.^addr
      some addr.n => some n.^addr & Addr
    }
}
pred add (b, b': Book, n: Name, t: Name + Addr) {
  b'.addr = b.addr + n -> t
}
pred del (b, b': Book, n: Name, t: Name + Addr) {
  b'.addr = b.addr - n -> t
}
fun lookup (b: Book, n: Name): set Addr {
  n.^(b.addr) & Addr
}
不变式在说什么

注意名字既映射到地址，也映射到其他名字，从而产生多级查找（multilevel lookup）。

这个不变式说：① 没有任何名字应该直接或间接地映射到它自己；② 如果一个名字本身被（别的名字）映射到，那么这个名字必须直接或间接地映射到至少一个地址。

一个操作被称为「保持」一个不变式，如果它在任何满足该不变式的状态下被调用时，总是产生另一个满足该不变式的状态。

#任务
(a)不变式在谓词 inv 中被形式化定义。用文字非形式地解释这个不变式说了什么。
(b)生成一些满足不变式的地址簿例子，以及一些以不同方式违反它的例子。为此你需要添加谓词和运行它们的命令。
(c)生成一些操作执行的例子，同样通过添加并运行合适的谓词。
(d)找到反例，证明 add 与 delete 都不保持这个不变式。为此你需要定义调用操作与不变式的断言，以及检验它们的命令。必要时缩小作用域，以获得尽可能小的反例。
(e)为这两个操作添加额外的前置条件——对前置状态的约束——以确保不变式被保持，并重新运行保持性检验以证明你成功了。增大作用域以获得更多信心，并简要论证你对作用域的选择。
(f)重新运行 (c) 中的模拟，以检查你没有不小心把操作过度约束（overconstrain）。
点拨 · 完整解题路径

(d) 的断言模板（这正是 6.3.3「操作保持不变式」的原型）：

assert AddPreservesInv {
  all b, b': Book, n: Name, t: Name + Addr |
    inv(b) and add(b, b', n, t) => inv(b')
}
check AddPreservesInv for 3

反例的成因：add(b, b', n, n) 会让 n 映射到自己，直接违反①；add 一个「指向某名字 t，而 t 不指向任何地址」的映射会违反②。del 则相反：删掉一条边可能让某个原本「能到达地址」的名字变得「到不了地址」，违反②。

(e) 的强化：

// add 需要的前置条件
n not in t.*addr          // 不引入环（t 可达 n 就不能加 n->t）
t in Addr or some t.^addr & Addr   // t 自己能到达地址

// del 需要的前置条件
all m: Name | some addr.m => some m.^(addr - n -> t) & Addr

(e) 的作用域论证：参照 5.4 的准则——「对关系数量敏感，对原子数量不那么敏感」。这里只有一个二元关系 addr，所以作用域 3 已经覆盖 2⁹ = 512 种可能；升到 4（2¹⁶ = 65536）已足够有信心。但要注意：这个模型里 Name 与 Addr 是两个独立 signature，缩小其中一个可能刚好避开反例。

(f) 是本题最有教学意义的一步：强化前置条件后必须回头重跑模拟，确认操作仍然「可被调用」。一个把操作约束到永不发生的模型是空洞地正确的——这正是 5.3 讨论的「vacuity」陷阱。

A.2.3 Inmate Assignments · 囚犯分配

题目设定

需要一个程序，把囚犯分配到监狱的牢房里。如果两个囚犯属于不同的帮派，分配就必须避免把他们放在同一个牢房。

module exercises/prison
sig Gang {members: set Inmate}
sig Inmate {room: Cell}
sig Cell {}
pred safe () { … 你的约束写在这里 … }
pred show () { … 你的约束写在这里 … }
run show
#任务
(a)补全刻画「安全分配」的谓词 safe，并通过运行模拟谓词 show（在其中适当调用 safe 作为约束）来生成安全与不安全分配的例子。
(b)写一个新谓词 happy，说帮派成员只与同一帮派的成员共享牢房。一个安全的分配不一定是一个「快乐」的分配。通过编写一个断言和检验它的命令，找到一个反例，并解释为什么。
(c)添加一条作为 fact 的约束，确保安全性确实蕴含快乐性。重新运行你的模拟谓词，确保你没有引入不一致；并再次检验那个断言，确保它现在没有反例。
点拨 · safe 与 happy 的差别是全题的关键
  • safe：「不同帮派的两个囚犯不在同一牢房」，即 
    no disj i1, i2: Inmate, g1, g2: Gang |
  i1 in g1.members and i2 in g2.members
  and g1 != g2 and i1.room = i2.room
  • happy：「帮派成员只与同帮派成员共享牢房」——更强，因为它还要求同牢房的人必须同帮派。

(b) 的反例来自哪里？来自不属于任何帮派的囚犯！模型里 Gang.members 没有约束「每个囚犯必属于某个帮派」，所以一个「无帮派」囚犯可以和任何帮派成员同房——这不违反 safe（因为 safe 只谈两个不同帮派），但违反 happy。

(c) 的修复：fact { all i: Inmate | one i.~members }（每个囚犯恰好属于一个帮派），或者更弱一点：Inmate in Gang.members（每个囚犯至少属于一个帮派）。加上之后必须重跑 show 确认模型仍然可满足——这正是 (c) 后半句的用意。

方法论收获：「安全」与「满意」是两个不同的性质，而模型里的「未分类元素」常常是二者之间缺口的来源。这与 6.2.3 中 some o 那个额外假设的讨论同源——当你发现一个断言意外失败，先怀疑「模型允许了现实中不该存在的状态」。

A.3Classic Puzzles · 经典谜题

本节定位

本节的习题练习编写 Alloy 并组织小模型。它们的共同主题是：把一个「文字表述的推理」翻译成形式约束，然后让 Analyzer 告诉你翻译对不对——很多经典谜题的「妙处」恰恰在于自然语言的歧义，而形式化会迫使你把歧义摊开。

♥ A.3.1 A Surprising Syllogism · 一个令人惊讶的三段论

Doris Day 的一首歌

「Everybody loves my baby / but my baby don't love nobody but me.」
（人人都爱我的宝贝，但我的宝贝除了我谁都不爱。）

David Gries 指出，从严格的逻辑观点看，这蕴含着「我就是我的宝贝（I am my baby）」。

任务：把这首歌形式化为一些约束，把 Gries 的推论形式化为一个断言，然后检验它。接着修改约束，以表达 Doris Day 大概想说的意思，并证明这个断言现在有了反例。

点拨 
module exercises/day
sig Person {loves: set Person}
one sig Me, MyBaby extends Person {}
fact {
  Person in loves.MyBaby        // 人人都爱我的宝贝
  MyBaby.loves = Me               // 我的宝贝只爱我
}
assert ImMyBaby { Me = MyBaby }
check ImMyBaby

推理链条：Me 也是 Person，所以「人人都爱我的宝贝」蕴含 Me 爱 MyBaby，即 Me in loves.MyBaby，亦即 MyBaby in Me.loves；而「我的宝贝只爱我」给出 MyBaby.loves = Me，于是 Me ∈ Me.loves……更直接地：MyBaby.loves = Me 说明 Me 在 MyBaby 的爱的值域里；结合前一条，唯一能同时满足两者的赋值就是 Me = MyBaby。

Doris Day 大概的意思是「除了我之外人人都爱我的宝贝」，即把第一条改成 Person - Me in loves.MyBaby。这样断言立刻有反例——两个不同的人也能满足约束。

方法论收获：这是「形式化暴露歧义」的最纯粹示范。一句歌词的两种读法，一种推出荒谬结论，一种不会。建模的第一课就是：如果你写出的模型推出了你不想要的结论，先检查你是不是把话翻译错了。

♥ A.3.2 Ceilings and Floors · 天花板与地板

Paul Simon 的一首歌

「One man's ceiling is another man's floor.」（一个人的天花板是另一个人的地板。）

这是否蕴含「一个人的地板是另一个人的天花板」？

任务：在 Alloy 中形式化这两个约束，并检验「第一个蕴含第二个」的断言。如果你得到的反例因为隐含假设而讲不通，就把那些假设作为新约束加进去，再检验一次。

点拨 
sig Man {ceiling, floor: set Man}
fact { all m: Man | some n: Man | m.ceiling in n.floor }   // 第一句
assert Converse { all m: Man | some n: Man | m.floor in n.ceiling }
check Converse

第一句的形式化是 ceiling in ~floor（每个人的天花板都出现在某个人的地板里），而它的逆命题是 floor in ~ceiling。关系包含不蕴含其逆的包含，所以断言无效。

「隐含假设」是什么？现实中的天花板/地板关系应当是对称的——若 A 的天花板是 B，则 B 的地板就是 A。加上 ceiling = ~floor 这条 fact 后，断言就成立了。

方法论收获：题目最后一句「如果反例讲不通就加假设」是 Alloy 工作流的核心循环——跑 → 看反例 → 判断「这是真 bug 还是模型缺假设」→ 补约束 → 再跑。6.2.3 的 NoIntervening 正是这个循环的产物。

A.3.3 Barber Paradox · 理发师悖论

背景

考虑所有「不以自己为成员」的集合构成的集合。它包含自己吗？这个悖论由 Bertrand Russell 于 1901 年发现，揭示了 Frege 朴素集合论中的一个不一致性。

该悖论的一个变体（同样归于 Russell）问：在一个村子里，理发师给每一个不自己刮胡子的男人刮胡子，那么谁给理发师刮胡子？

module exercises/barbers
sig Man {shaves: set Man}
one sig Barber extends Man {}
fact {
  Barber.shaves = {m: Man | m not in m.shaves}
}
#任务
(a)用 Analyzer 证明这个模型确实是不一致的，至少对一个规模较小的村子而言。
(b)女性主义者指出，如果承认女性的存在，这个悖论就消失了。做一个新版本的模型，把村民分成男人（需要被刮胡子）和女人（不需要），并证明现在有一个简单的解。
(c)一个更激进的解法（由 Edsger Dijkstra 指出 [12]）是允许「没有理发师」这种可能性。相应地修改原模型，并证明现在有解。
(d)最后，试一个允许「多个理发师」的原模型变体，并证明同样有解。
点拨 · 三种「解悖」方式对应三种建模教训
  • (a) 直接 run {} for 3，Analyzer 会报告 No instance found——这就是「不一致」的证据。注意这只证明了「作用域 3 内不一致」；但对这个悖论而言，任何作用域都不一致，因为矛盾是关于 Barber 自身的，与村子大小无关：Barber in Barber.shaves iff Barber not in Barber.shaves。
  • (b) 关键是那条 fact 的值域：原本 {m: Man | ...} 把 Barber 自己也算进了被约束的范围。引入 Woman 并把「需要刮胡子的人」限定为男人，Barber 就可以是女人，或者可以给自己刮——悖论消解。
  • (c) 把 one sig Barber 改成 lone sig Barber。「不存在」时那条 fact 空洞地为真，模型立即可满足。
  • (d) 把 one sig 改成 sig Barbers（多个），fact 改成 all b: Barber | b.shaves = ... 或让理发师们分工：一个刮「不自己刮胡子且不被其他理发师刮」的人。多个理发师打破了自指的封闭性。

方法论收获：三种解法分别对应「扩大论域」「放松重数」「打破单指」——这正是修模型的三把基本扳手。而且 (a) 提醒你：「在小作用域下找不到实例」只是不一致的证据，不是证明；但对纯自指矛盾，任意作用域都成立。这与 5.2 的「小作用域假设」互为镜像。

♥ A.3.4 Halmos's Handshaking Problem · Halmos 的握手问题

题目（数学家 Paul Halmos 发明 [24]）

用构造逻辑论证来解决这个问题相当有挑战性，但用 Alloy 找到解很容易。

Alice 和 Bob 邀请了另外四对夫妻来家里参加聚会。他们中有些人彼此认识，有些不认识；有些人有礼貌，有些人没有。所以发生了一些握手，尽管并非每对客人都握了手（当然没有人握自己的手，也没有人握自己伴侣的手）。出于好奇，Alice 在聚会结束时挨个询问每个人握了多少次手。她从九个人那里得到了九个不同的答案。

Bob 握了多少次手？

#任务
(a)通过在 Alloy 中建模来解决这个问题，并用 Analyzer 找到一个解。
(b)为 10 个人求解会比为 4 个或 6 个人求解花更长时间，所以在你对模型的正确性有信心之前，先用较小的数字。
(c)是否可能存在另一个解，其中 Bob 握了不同数量的手？扩展你的模型以便检验这一点。你可能想稍微重构一下它，使得两个候选解不会导致两套几乎相同的约束。
点拨 · 建模骨架 
module exercises/handshake
abstract sig Person {shook: set Person}
one sig Alice, Bob extends Person {}
sig Other extends Person {}
fact { ^partner = iden }          // 需要 partner 关系（5 对夫妻）
fact { shook = ~shook }           // 握手是对称的
fact { no iden & shook }         // 没人握自己的手
fact { no shook & partner }      // 没人握伴侣的手
fact { // Alice 得到 9 个不同答案 ⇒ 除 Alice 外的 9 个人握手数互不相同
  all disj p, q: Person - Alice | not (#p.shook = #q.shook)
}

关键洞察：10 个人中每人握手数范围是 0–8（不能握自己和伴侣），恰好 9 个可能值；而「除 Alice 外有 9 个人」，所以这 9 个人恰好取遍 0,1,2,…,8 各一次。由此可推出握 8 次的人与握 0 次的人是一对夫妻，握 7 次与握 1 次是一对，依此类推——剩下握 4 次的那个人必然是 Alice 的配偶 Bob。答案：Bob 握了 4 次手。

(c) 的重构建议：把「候选答案」抽成一个参数化谓词 pred solution(k: Int) { #Bob.shook = k }，然后 run solution[4] 与 run solution[5] 分别试。这就是「用谓词参数代替复制粘贴约束」的重构——4.6 节函数与谓词参数的直接应用。

A.3.5 Goat, Cabbage, Wolf · 山羊、白菜、狼

题目

一个农夫想把一只山羊、一棵白菜和一只狼渡过河去，但他的船一次只够带一样东西。如果他把山羊和白菜留在一起，山羊会吃掉白菜；如果他把山羊和狼留在一起，山羊会被吃掉。他该怎么做？通过在 Alloy 中建模来解决这个问题，并用 Analyzer 找到一个解。

提示

Alloy 的标准发行版包含一个模块 util/ordering，它定义了一个全序。你可能会发现它在为农夫所采取的步骤排序时很有用。

点拨 · 这就是 6.1 的「迹 idiom」的缩小版 
open util/ordering[State] as TO
sig Item {}
one sig Goat, Cabbage, Wolf, Farmer extends Item {}
sig State { bank: set Item }      // bank = 此岸（左岸）上的物品集合
pred safe (s: State) {
  no s.bank.Farmer => {
    (Goat in s.bank iff Cabbage in s.bank) => false
    (Goat in s.bank iff Wolf in s.bank) => false
  }
}
fact {
  no TO/first().bank                       // 初始：全在左岸？（应为全部）
  TO/last().bank = Item                     // 目标：全到右岸 ⇒ bank 为空，按你的约定调整
  all s: State | safe (s)
  all s: State - TO/last() | let s' = TO/next(s) |
    lone s.bank - s'.bank and lone s'.bank - s.bank   // 每步至多移动一样
}
run {} for 8 State

建模要点：① 用「左岸集合」这一个字段表示全部状态（右岸 = 补集），状态数减半；② safe 用 iff 表达「山羊和 X 同在一岸」；③ 农夫必须与山羊/X 同岸才算安全，所以要加 Farmer in s.bank 的条件；④ 标准解需要 7 步（去-回-去-回-去-回-去），所以 Time 作用域至少 8。

方法论收获：这是 6.1 迹 idiom 的最小可运行版本——open util/ordering[State] + init + step + Traces fact + run。做完这道题，第 6 章的 fact Traces 就毫无神秘感了。

♣ A.3.6 Surgeon's Gloves · 外科医生的手套

题目（又一个 Paul Halmos 的著名问题）

一个外科医生必须给三个病人做手术，但只有两副手套。不能有交叉感染：医生不得接触任何病人的血液，任何病人也不得接触另一个病人的血液。医生需要两只手来工作。她该怎么做？

在 Alloy 中表达这个问题，并用 Analyzer 找到一个解。

提示

有 4 样东西需要被覆盖（3 个病人和 1 个外科医生）。手套提供 4 个资源。这个问题的形式化比握手问题棘手得多。你需要表达：

  • 外科医生必须能够（通过手套）处理病人这一约束；
  • 污染是如何被传递的；
  • 无污染条件本身。

你可能想为每一次手术关联一个前置状态和后置状态，每个状态都携带一个「污染关系」，说明什么污染了什么。

点拨 · 建模骨架 
sig Glove {inside, outside: set Person}   // 手套的两面各接触过谁
sig State { contaminated: Person -> Person } // 污染关系
sig Operation { pre, post: State, patient: Person,
                  worn: set Glove }             // 戴了哪些手套、什么顺序

核心难点有三个：

  1. 手套有「内外两面」，且可以叠加戴——所以 worn 必须是一个有序的集合（用 util/ordering[Glove] 或额外字段表示叠戴顺序）；
  2. 污染是可传递的：若 A 污染了手套内面，手套内面接触了 B，则 B 被污染。这需要 ^contaminated；
  3. 「翻转手套」这个动作（把内面翻到外面）是标准解法的一部分，必须能被表达。

经典解法：医生先同时戴两副手套给病人 1 做手术（此时外副手套外面被污染）；然后脱掉外副，用内副给病人 2 做手术；最后把外副翻过来套在内副外面（污染面朝外）给病人 3 做手术。「4 个需要覆盖的表面 vs 4 个手套表面」这个计数正是提示所指的。

为什么标 ♣：因为它要求你自己发明状态表示，而不是套用现成 idiom。这正是 6.4 抽象函数那节的预演——你需要一个「污染状态」的具体模型，然后用断言表达「安全性质」。

A.4Metamodels · 元模型

什么是元模型（metamodel）

元模型是「一组模型的模型」。它不必具备它所捕获的那些模型的品质。

例如：一个状态机的元模型自己不必是动态的——一个状态机只是一个「可以被赋予动态解释」的结构。

解读 · 这是全书最深的一个观念

「元模型不必具备被建模物的品质」这句话，是 Alloy 能用静态的一阶关系逻辑描述动态系统的哲学根据。6.1 的迹 idiom 就是一个状态机的元模型：Time 原子 + step 谓词构成的静态结构，被我们「读作」一条动态执行。本节习题要求你把这个手法反过来用：显式地为「状态机」这个概念本身建模。

A.4.1 State Machine Definition · 状态机定义

一个状态机有一个或多个初始状态，以及一个把每个状态连接到其后继的迁移关系。构造一个状态机的 Alloy 模型，并通过添加约束、让 Analyzer 求解，来生成各式各样的机器例子：

#要生成的机器
(a)一个确定性机器，其中每个状态至多有一个后继
(b)一个非确定性机器，其中某些状态有多于一个后继
(c)一个带有不可达状态的机器
(d)一个没有不可达状态的机器
(e)一个连通的机器，其中每个状态都可从每个其他状态到达
(f)一个带有死锁（deadlock）的机器：一个可达的、没有后继的状态
(g)一个带有活锁（livelock）的机器：存在一种无限执行的可能，其中一个「总是可达」的状态却永远不会被到达
点拨 · 骨架与七条约束 
sig State {next: set State}
sig Initial in State {}          // 初始状态集合（子签名）
fun reachable: set State { Initial.*next }

// (a) 确定性：      all s: State | lone s.next
// (b) 非确定性：    some s: State | some s.next and #s.next > 1
// (c) 有不可达：    some State - reachable
// (d) 无不可达：    State = reachable
// (e) 强连通：      all s: State | State in s.*next
// (f) 死锁：        some s: reachable | no s.next
// (g) 活锁：        some s: reachable | (some s.next) and s.next.*next = s.*next and s not in ...

(g) 活锁是七条中最难的。它的形式化要点是「存在一个无限执行路径，它始终待在一个循环里，而某个从该路径上任意点都可达的状态从未被经过」。在有限模型里，「无限执行」等价于「路径进入了一个循环」，所以可以写成：存在一个状态 s 和一个循环 C（C.next in C），使得从 C 中可达某状态 t，但存在一条只走 C 的无限路径永远不经过 t。简化写法：some s, t: State | t in s.*next and s in s.^next and t not in s.^next（s 在一个环上，t 从 s 可达但不在 s 的环里）。

(c)/(d)/(f)/(g) 都用到了「可达集」这个派生概念——把它写成 fun reachable 而不是在每个约束里重复 Initial.*next，正是 4.6「函数即宏」的实用价值。

♣ A.4.2 State Machine Simulation · 状态机模拟

考虑两个带有标记迁移的状态机 M1 和 M2。一个从 M1 的状态到 M2 的状态的关系 r，是 M1 在 M2 中的一个模拟（simulation），当且仅当：

模拟的两个条件
  • ① 迁移对应：只要 r 把 M1 中的状态 s1 关联到 M2 中的状态 s2，并且 M1 有一个从 s1 到 s1' 的、标记为 a 的迁移，那么 M2 也有一个从 s2 到某个 s2' 的、标记为 a 的迁移，其中 s2' 被 r 关联到 s1'；
  • ② 初始对应：只要 s1 是 M1 的一个初始状态，就存在 M2 的一个初始状态 s2，使得 s1 与 s2 被 r 关联。

如果此外 ~r 是 M2 在 M1 中的一个模拟，那么关系 r 就是一个双模拟（bisimulation）。

迹与行为

一个状态机的迹（trace）是一个有限的迁移标记序列，它通过从一个初始状态出发、沿着迁移走一条路径而形成。一台机器的行为可以由它所展示的迹的集合来描述。

#任务
(h)构造一个「带迹的状态机」与「模拟关系」的 Alloy 模型，并生成一些机器及其关联迹集的例子。
(i)加入「模拟」这个概念，并生成一些被模拟关系关联起来的机器的例子。
(j)如果两台机器之间存在模拟，它们必须有相同的迹集吗？用 Alloy 检验这个假设。双模拟呢？
点拨 · (j) 的答案

单向模拟不保证迹集相同——只保证「M1 的迹集 ⊆ M2 的迹集」。所以断言

assert SimSameTraces { simulation(r, M1, M2) => traces(M1) = traces(M2) }
check SimSameTraces for 3

会有反例：M2 可以有 M1 没有的迹（M2 更「自由」）。

双模拟则保证迹集相同。因为 ~r 也是模拟，于是两个方向的包含都成立。

这与 6.4.4 的「迹包含」标准完全同源：那里说「具体机器符合抽象机器，当且仅当它的迹集是抽象机器迹集的子集」——那正是一个单向模拟。而 6.4.4 也指出：迹包含不保证「做好事」（空迹集符合任何机器），这与这里「单向模拟不保证迹集相同」是同一个观察的两面。

建模骨架提示：用 sig Machine {states: set State, init: set states, trans: states -> Label -> states} 表示机器，sig Label {} 表示标记，trace 用 seq[Label]（Alloy 4 之后）或用 open util/ordering[Step] 自己搭。本题被标 ♣ 是因为你需要同时建模「机器」「迹」「模拟关系」三层结构。

A.4.3 Metamodel of Alloy · Alloy 的元模型

题目

写一个「Alloy 模型」的 Alloy 模型。把你的模型限制在 signature、字段以及它们之间的关系上。为了证明你的模型足够丰富到能描述它自己，添加模拟约束，让工具生成一个与之对应的实例。

点拨 · 「自描述」是本题的全部趣味 
sig Sig { field: set Field }
sig Field { decl: Sig,                  // 这个字段声明在哪个 signature 里
              target: set Sig,           // 它的类型指向哪些 signature
              mult: Mult }               // set / lone / one / some
sig Mult {}
one sig Set, Lone, One, Some extends Mult {}

fact SelfDescribing {
  // 要求生成的实例「就是」这个模型自己：
  // 存在一个 Sig 原子代表 Sig、一个代表 Field、一个代表 Mult……
  // 且 Field 原子的 decl/target/mult 恰如上面所声明
}

难点在 SelfDescribing 这条 fact：你要用存在量词「挑选」出实例中代表 Sig、Field、Mult 的那些原子，然后断言它们之间的 decl/target/mult 关系与模型声明一致。例如：代表 Field 的那个原子，它的 decl 必须是代表 Sig 的原子，它的 target 必须是 {代表 Sig 的原子, 代表 Mult 的原子}，它的 mult 必须是 Set。

方法论收获：这道题让你亲身体会 4.1 说的「模型即数据」——Alloy 模型本身就是一个关系结构，所以它能被 Alloy 描述。这与 A.3.3 理发师悖论形成有趣对照：自指在小规模、有限论域下是安全的，而 Russell 悖论的危险恰恰来自「所有集合的集合」这种无限自指。

A.4.4 Metamodel of Java · Java 的元模型

题目（分四步）
  1. 构造并探索一个 Java 的元模型。
  2. 首先，建模类/接口层次结构，把类和接口当作原子，它们之间由 extends 和 implements 等关系相互关联。
  3. 然后建模实例变量的声明，为每一个变量关联一个源类或接口和一个目标类或接口。
  4. 现在把堆（heap）本身建模为一个对象集合，每个对象都有一个被指派的运行时类型（runtime type），并写出确保堆是「良类型（well-typed）」的约束。用 Analyzer 生成一些有趣的例子。
点拨 · 三层结构 
// —— 第 1 层：类型层次 ——
abstract sig Type {}
sig Class extends Type { super: lone Class, impl: set Interface }
sig Interface extends Type { extendsI: set Interface }
fact { no c: Class | c in c.^super }        // 无环

// —— 第 2 层：字段声明 ——
sig Field { owner: Type, type: Type }        // 源 与 目标

// —— 第 3 层：堆 ——
sig Object { runtimeType: Class,
               value: Field lone -> Object }
fact WellTyped {
  all o: Object, f: Field, o': Object |
    o' in o.value[f] => {
      f.owner in o.runtimeType.*super + o.runtimeType   // f 在 o 的类型链上被声明
      o'.runtimeType in f.type.*(super + extendsI)      // o' 的类型是 f.type 的子类型
    }
}

「良类型」的两条本质：① 对象只能持有「它自己的类型（或其超类型）所声明的字段」的值；② 该值的对象的运行时类型必须是字段声明类型的子类型。第②条里的 *super 与 *extendsI 复合，正是「子类型」的形式化——这也是 Alloy 自己的 extends 语义的镜像（回想 4.2.3：子签名的原子集合是父签名的子集）。

有趣的例子怎么生成？加模拟约束，如 some o: Object | some o.value、some o, o': Object | o.runtimeType != o'.runtimeType and some o.value & (univ -> o')（存在跨类型的引用），或者要求堆里有一个循环引用 some o: Object | o in o.^value.univ。

本节定位

本节的习题涉及在明确界定的场景中构造小模型。与 A.2「给你骨架」不同，A.5 只给你问题描述，signature 由你自己设计——这是从「练习」到「建模」的分水岭。三题都被标为 ♣。

♣ A.5.1 Unix File System · Unix 文件系统

题目背景

这道题让你建模 Unix 文件系统中路径名是如何被解析的，并检验一些简单的性质。

在 Unix 文件系统中，每个文件由一个 inode 表示。inode 包含文件的一些基本属性（权限位、文件类型等），并有一个含十个地址的序列，指向存放文件数据的磁盘块。

此外还有三个间接地址：

  • 第一个涉及一层额外的间接：它指向一个存放「数据块地址」（而非数据）的块；
  • 第二个涉及两层间接：它指向一个地址块，该块又指向若干地址块，那些块再指向数据块；
  • 第三个涉及三层。

所有 inode 都存放在一个叫做 inode 表的数组里。一个给定 inode 在这个数组中的索引就是它的 inumber。

一个目录被表示为一个文件，其数据由「inumber/文件名」对的列表构成。根目录与某个固定的 inumber 相关联。

文件和目录都有路径名。空路径名 / 对应根目录。一般地，给定一个表示目录 d 的路径名 p，路径名 p/n 表示目录 d 中名为 n 的那个文件或目录。要解析一个路径名，文件系统从根目录出发，查找该文件路径名的前缀。这给出一个 inumber，它接着在 inode 表中查找这个 inumber。得到的 inode 要么是所要求的文件或目录（如果路径名没有剩余部分），要么是另一个目录，对该目录重复这个过程（作用于路径名的剩余部分）。

关键提示：这段描述故意包含了与「路径名如何被解析」无关的细节

例如，你需要考虑「inode 中地址的顺序是否重要」，如果不重要，那么什么比「序列」更简单的结构就足够了。

——这是全书反复强调的一课：规约里给的描述往往混入了实现细节，建模者的第一件事是识别哪些细节与要分析的性质无关，然后把它们抽象掉。这里的正确答案是：用集合 set Block 代替序列，因为路径解析只关心「哪些块属于这个文件」，不关心顺序。

#任务
(a)从构造 inode、inumber 与 block 的基本结构模型开始。忽略间接寻址。通过编写模拟约束来探索一些样例结构，并添加任何你发现自己遗漏了的不变式。
(b)构造一个路径名模型，把路径名当作一个列表，它由一个 name（第一个元素）和一个 pathname（其余部分）构成。通过编写模拟约束来探索一些样例路径名，并添加任何你发现自己遗漏了的不变式。
(c)现在你要把模型的两部分组合起来，并定义一个建模 lookup 的函数：给定一个路径名，它返回一个 inode 集合。你会想递归地定义 lookup，但 Alloy 的函数不能是递归的。取而代之，你可以声明一个对应于 lookup 的关系，它由一条「关系名出现在等式两边」的约束来定义。
(d)表述并检验两条断言：每个路径名至多解析到一个 inode；以及没有两个不同的路径名解析到同一个 inode。这两条中你原本期望哪一条成立？如果你的分析揭示了模型中的缺陷，就修正它们。
(e)最后，加入间接寻址的概念。试着以模块化的方式来做，对你的名字查找模型的扰动尽可能小。
点拨 · (c) 的「非递归」技巧是本题的核心

Alloy 函数不能递归（因为函数只是宏，展开会无限进行）。解决办法是把 lookup 声明为一个「字段/关系」，然后用一条自指的 fact 来定义它：

sig PathName { name: Name, rest: lone PathName, resolvesTo: set Inode }
fact {
  no p.^rest                                  // 路径名无环
  all p: PathName {
    no p.rest => p.resolvesTo = Root            // 基例：空路径 = 根目录
    some p.rest =>
      p.resolvesTo = {i: Inode |
        some d: p.rest.resolvesTo & Directory |
          p.name in d.entries.i }               // 递归步
  }
}

注意 p.rest.resolvesTo 出现在定义 p.resolvesTo 的约束里——这就是「关系名出现在等式两边」。Alloy 把它当作一条普通的一阶约束交给 SAT 求解器，于是「递归」被消解成了「联立方程」。这与 4.2.4 里 *@friends 那种「自引用字段声明」是完全不同的机制（后者是类型层面的，前者是约束层面的）。

(d) 的预期答案：「每个路径名至多解析到一个 inode」应当成立（前提是目录中不出现重名条目）；「没有两个不同路径名解析到同一个 inode」应当不成立——因为 Unix 支持硬链接（hard links）！如果你的模型让第二条也成立了，说明你遗漏了「一个 inode 可以有多个文件名」这个事实。这正是题目说的「如果分析揭示了模型中的缺陷，就修正它们」。

(e) 的「模块化」要求：间接寻址只影响「inode → 数据块」这一层，不影响「目录 → inumber → inode」的查找链。所以正确做法是把「inode 拥有哪些块」抽成一个独立的关系或函数，让 lookup 只依赖「目录条目」而不依赖「块结构」。这就是关注点分离——与 4.7「模块系统」和 6.4「用独立模块做检查」是同一个原则。

♣ A.5.2 Railway Switching · 铁路道岔

题目背景

这道题让你构造一个简单的铁路道岔系统模型，并检验「某个道岔策略能确保不发生碰撞」。你会做一些简化假设，例如一列火车一次只占用一个轨道段，但你会学到普遍适用的技术，特别是：

  • 如何建模一个「允许许多任意行为」的物理环境（在本例中是火车的移动）；
  • 如何把「需求」（不发生碰撞）与「假设」（司机遵守信号）分离开来。
解读 · 这两点正是第 6 章的方法论内核

「建模物理环境」= 6.1 中「token 池 + 任意选择」建模不可靠通信与并发调度；「需求与假设分离」= 6.2 中把 NoIntervening 写成 fact，而把 NoBadEntry 写成 assert。这道题实际上是要你独立复现第 6 章的整套方法论。

#任务
(a)把轨道布局建模为一个轨道段集合 Segment，带一个从 Segment 到 Segment 的关系 next。轨道段在物理上是不相交的，只在端点处相互接触，并且是有方向的，假定火车从一个端点行驶到另一个端点。不过端点并没有被显式表示出来；取而代之，我们用 next 把 s1 映射到 s2 来表示「s1 的出口端连接到 s2 的入口端」。生成一些样例布局，并用 Alloy Analyzer 获得一些漂亮的可视化。
(b)要建模碰撞的可能性，我们本可以简单地说「两列火车只有在同一段轨道上时才可能相撞」。为了一个更一般的概念——它允许「位于例如彼此平行的轨道段上的火车之间也可能相撞」——我们可以声明一个关系 overlaps，它非常抽象地表示轨道的物理布局：当一列火车在 s1 上、另一列在 s2 上会造成危险时，它把 s1 映射到 s2。你会期望这个关系具有哪些性质：它是自反的、对称的、传递的吗？把这个关系加进你的模型，外加一条记录你认为应当成立的性质的 fact。
(c)现在你要引入随时间变化的状态。声明一个 signature Train 表示一组火车，和一个 signature TrainState，带一个从 Train 到 Segment 的关系 on 表示它们的位置（记住每列火车只能占用一个段）。定义 TrainState 中一个额外的字段 occupied，它持有被火车占用的那些段的集合。生成并可视化一些样例状态；你大概会想用着色来标示被占用的段。
(d)为了描述所有物理上可能的火车移动，引入一个作用于 TrainState 的操作，它取两个火车状态（表示前置与后置状态）以及一组移动的火车作为参数，并约束这些火车状态，使得在这一步中，每列移动的火车都从一个段行进到它在 next 关系下的某个后继。生成并可视化这个操作的一些样例执行。
(e)为了建模信号系统，引入一个 signature GateState，带一个字段 closed，其值是一个段的集合，表示「火车不应越过的那些段」。注意没有必要把闸门或信号灯引入为显式的原子。写一个刻画合法移动的谓词，它的参数是一个 GateState、一个 TrainState 和一组移动的 Train。
(f)在 TrainState 上写一个安全条件，说火车绝不占用相互重叠的段，并生成一些满足与违反该条件的样例状态。
(g)最难的部分是设计那个机制——决定「闸门何时应当关闭」的策略。我们不想精确规定何时、哪些闸门应当关闭，而是想写一个施加某些「最小条件」的约束。这样，我们实际上是在检验「一整族可能的机制」。把这个策略写成一个谓词，参数是一个 GateState 和一个 TrainState。它可以说，例如：如果若干个被占用的段共享同一个后继，那么其中至多一个可以有一个打开的闸门。
(h)最后，把所有部分组装起来：写一个断言，说当火车移动时，如果机制遵守闸门策略、且火车的移动是合法的，那么碰撞就不会发生（即系统不会从一个安全状态迁移到一个不安全状态）。检验这个断言，如果你找到了反例，仔细研究它们，并调整你的模型。最有可能出问题的是你的闸门策略。
(i)当你满意闸门策略按预期工作（防止碰撞）之后，通过生成并可视化一些有趣的火车移动，来确保你没有把模型过度约束。
点拨
  • (b) 的性质答案：overlaps 应当是自反的（一段与自己重叠——同一轨道上两列车必然相撞）、对称的（若 s1 与 s2 危险，则 s2 与 s1 也危险）、但不应是传递的（平行段 A、B 重叠，B、C 重叠，不代表 A、C 重叠）。把「传递性」误加进去是这道题最典型的错误，它会让整个模型退化成「所有段都互相重叠」。
  • (c) 的 occupied 为什么是「额外字段」？因为它可以从 on 推导出来（occupied = Train.on 的值域）。把它显式声明出来是一种冗余——但题目要你这么做，是为了练习「冗余字段需要一条一致性 fact」这一课：fact { all ts: TrainState | ts.occupied = ts.on.univ }。忘了加这条 fact，模型就会有无穷多「不一致的」实例。这正是 4.2.4 里「依赖声明」想解决的问题。
  • (e) 「不必引入闸门原子」是关键洞见：一个「状态」不必由「实体」表示。closed: set Segment 这一行就够了。这与 6.1.1 中「进程原子本身就是标识符，不需要单独的 ID 概念」是同一思路——Alloy 让你只为「需要被区分的实体」造原子。
  • (g) 「检验一整族机制」是本题最深刻的一点：策略谓词应当是「机制必须满足的最小条件」，而不是「某个具体机制的定义」。这样 (h) 的断言一旦成立，就同时为所有满足该策略的机制提供了保证。这正是「underspecification（欠规约）」作为优点的典范——回想 5.4 的准则「宁可欠约束」。
  • (h) 断言的形状（把三层条件叠起来）： 
    assert NoCollision {
  all ts, ts': TrainState, gs: GateState, moved: set Train |
    policy (gs, ts) and legalMovement (gs, ts, moved) and move (ts, ts', moved)
    and safe (ts) => safe (ts')
}
check NoCollision for 4
  • (i) 与 A.2.2(f) 是同一个教训：证明「安全」之后，必须证明「模型仍然能做事」，否则你可能只是把系统约束到永不移动。

♣ A.5.3 Hotel Locking · 酒店门锁

题目设定（US Patent 4511946）

这道题让你构造一个与 6.2 节所述类似的酒店门锁方案的模型。在这个方案中：

  • 每张钥匙卡持有两个独立的、充当钥匙的号码。每把锁同样有两个钥匙。
  • 当卡上的第一个钥匙与锁中的第一个钥匙匹配，且卡上的第二个钥匙与锁中的第二个钥匙匹配时，锁打开。
  • 当卡上的第一个钥匙与锁中的第二个钥匙匹配时，门也会打开，但锁会被重新编码，使其第一个和第二个钥匙分别匹配卡的第一个和第二个钥匙。
  • 前台持有「每个房间最后发出的钥匙」的记录，此外还持有一个「已发出过的钥匙」的集合。
  • 一张新卡的形成方式是：用「最后发出的钥匙」作为第一个钥匙，用一个新鲜的钥匙作为第二个钥匙。
#任务
(a)构造这个方案的一个模型，带有入住、退房、进入房间的操作，并用 Alloy Analyzer 生成一些场景。
(b)表述一个捕获该方案目的——拒绝入侵者进入——的安全条件，并拿模型对照这个条件进行检验，报告你找到的任何反例。
(c)这个分析很可能揭示你的模型或安全条件中的错误。修正它们，检验安全条件得到满足；并且——为了确保你没有不小心把模型过度约束——重新生成你最初的那些场景（至少是那些仍然有效的）。
(d)假设酒店客人可以用「合法获得的卡上的钥匙」来制作新卡。相应地修改 entry 操作，并检验安全条件仍然成立。
(e)假设方案被改成「当卡上的第一个钥匙与锁中的第一个钥匙匹配时门就解锁（这种情况下忽略第二个钥匙）」。证明在这种情况下，该方案易受「一个制作新卡的不诚实客人」的攻击。

A.6Open-Ended Case Studies · 开放式案例研究

本节定位

这里是一些建模与分析的小型案例研究的想法。它们大致按难度排序，最容易的在前，每一个可能需要几小时到几天的工作，取决于研究的深度与所考虑特性的复杂度。

(a) Organizational Structure · 组织结构

建模你所在组织的结构，并生成该结构的样例实例。考虑针对不同类型的职能，可能存在不同的、横切的（cross-cutting）结构，并探索这些结构之间是如何相互关联的。

点拨这正是 6.3「catalogs that crosscut the directory structure」的组织学版本。难点在于：同一个人可以同时属于多个汇报线（实线/虚线），所以 reportsTo 不能是 lone 而应是 set，且需要区分职能维度（sig Function）。「横切结构之间的关系」通常表现为一条约束：某个职能线的主管必须在行政线上位于其下属之上——这条约束是否成立，正是值得用 Analyzer 检验的问题。

(b) Folders in an Email Client · 邮件客户端中的文件夹

建模一个邮件客户端的文件夹结构：邮箱（mailboxes）包含邮件（messages），文件夹（folders）包含邮箱，外加「在四处移动邮件」和「改变文件夹层次」的操作。仔细考虑如何处理特殊邮箱，例如接收来信的收件箱（inbox）、待发送与已发送邮件的箱子、草稿箱、已删除邮件箱。这些特殊箱子与常规箱子、以及它们彼此之间共享哪些性质？它们通常有额外的性质吗？

点拨核心问题是「特殊邮箱是子签名还是字段？」推荐用 abstract sig Mailbox 加 one sig Inbox, Outbox, Sent, Drafts, Trash extends Mailbox {}——这样每个特殊箱子的独有约束可以写成 signature fact（如 fact { no Drafts.messages.sent }）。「共享的性质」写成 Mailbox 上的 fact，「独有的性质」写在子签名里，这正是 4.2.3 子签名与 signature facts 的教科书用法。最有意思的断言是代数性质的：move(m, Inbox, Trash) 后再 restore(m) 是否回到原状？这与 6.3.3 的 CutPaste/PasteCut 是同构问题。

(c) Conference Calling · 电话会议

把一个电话系统看作「一组端点（endpoints）」加上「一个维护「哪些端点相互连接」信息的中心化数据库」。建模这个数据库的结构，外加那些在建立一次电话会议、添加与移除端点等情形下修改它的操作。模拟一些有趣的场景，并表述和检验一些断言。

点拨这是 A.2.1 电话交换的升级版——从「一对一连接」到「多方连接」。核心表示是 sig Conference {members: set Endpoint}，而不是 connects: Phone。值得检验的断言：① 对称性：若 A 与 B 在同一会议中，则 B 与 A 也在（平凡，但验证你的表示没有方向性错误）；② 无孤立端点：一个端点不能同时属于两个会议；③ 操作的原子性：add 与 drop 互逆。「有趣的场景」= 两人同时把对方加入自己的会议——这会暴露并发问题，正是 6.1.3「隐式并发」的动机。

(d) Do/Undo/Redo · 执行/撤销/重做

建模一个应用中撤销与重做动作的标准机制，并拿它对照一些「被表述为断言的基本性质」进行分析。

点拨这是 6.3.4 第三条洞见（「paste 让粘贴的资产保持选中，从而提供某种程度的撤销」）的正题化。标准机制是一个双栈（undo stack + redo stack）。基本性质：undo(do(s, a)) = s（撤销紧跟执行等于不变）；redo(undo(s)) = s；do(s, a) 之后 redo 栈必须被清空（这条最容易被漏掉，也是真实软件 bug 的高发地）。用 Alloy 建模时，栈可以用 seq[Action] 或用 util/ordering 自己搭；后者能让你练习「迹 idiom」。

(e) Trash · 废纸篓

建模一个操作系统的「废纸篓（trash）」或「已删除项目（deleted items）」文件夹，被删除的项目被移到那里，并且可以从那里被恢复（reinstated）。你可能想比较不同系统中的设计。在 Mac OSX 中，这个概念相当简单：项目可以被移出废纸篓，但没有「把一个文件或文件夹恢复到它原来的位置」的功能。相比之下，Windows 提供了更精细的功能。你能把「丢进废纸篓」的本质刻画为一组「以代数方式关联基本操作（例如创建、删除、取消删除等）」的断言吗？

点拨问题的实质是「恢复原位置」需要记住什么。Mac OSX 不记 ⇒ 只能「移出到用户指定的位置」；Windows 记 ⇒ 可以「还原」。在 Alloy 里这体现为 TrashItem 是否有一个 originalParent: Folder 字段。「以代数方式刻画本质」的断言集合：undelete(delete(x)) = x（Windows 版）vs 仅 contents(undelete(delete(x))) = contents(x)（Mac 版，内容相同但位置可能不同）；delete(delete(x)) 应当无意义或幂等；清空废纸篓之后 undelete 必须不可用（前置条件）。这正是 6.3.3「代数性质」那一类分析的完美练习题。

(f) Domain Name System · 域名系统

建模并分析标准域名系统中主机名的结构、DNS 数据库的结构，以及解析名字的机制。DNS 提供哪些种类的保证？

点拨三层结构：① 名字 = 标签的序列（sig Label {} + seq[Label] 或用 rest 链，像 A.5.1(b)）；② 数据库 = 分层授权的区（zone）树，每个区包含记录（sig Record {name, type, value}），并有委派（delegation, NS 记录）把子区交给别的服务器；③ 解析 = 从根出发沿委派链向下查询。值得检验的保证：解析终止（委派图无环——现实中这确实出过问题）、解析确定（每个名字至多一个权威区）、CNAME 链不产生环。「递归定义关系 + 无环 fact」的手法与 A.5.1(c) 完全相同。

(g) Elevator Control · 电梯控制

考虑一组服务于若干楼层的电梯。你能构造一个「纯粹用声明式规则来描述电梯如何响应请求」的模型吗？例如一条规则可能是：如果存在一个「来自电梯内部按钮按下」的、要求在某楼层停靠的请求，那么电梯不能在不停靠的情况下经过该楼层。

点拨「纯粹用声明式规则」是本题的挑战所在——不要写状态机，要写约束。核心表示：sig Request {floor: Floor, source: Source, served: set Time}，one sig Inside, Hall extends Source {}。规则的形式：all t: Time, e: Elevator, r: Request | r in unserved.t and r.source = Inside and r.floor between e.at.t and e.at.(next t) implies e.stops.t。「声明式」的判据是：你不描述「电梯如何决策」，只描述「什么样的行为是可接受的」——然后让 Analyzer 找出满足所有规则的行为（或证明不存在）。这与 6.1.2 用 fact 定义 elected 而不是用操作维护它，是同一种思维。值得检验的性质：每个请求最终被服务（活性，需要 progress 前件，参照 6.1.4）、电梯不会来回抖动（可加一条「方向一致性」规则）。

(h) Version Control · 版本控制

建模一个版本控制系统（例如 CVS 或 Subversion）背后的抽象视图，以及它所使用的机制。表述一些关键性质并检验它们。

点拨抽象视图的核心是「有向无环的修订图（revision graph）」：sig Revision {parents: set Revision, contents: File -> set Content} 加 fact { no r: Revision | r in r.^parents }。分支 = 有多个子节点的修订；合并 = 有多个父节点的修订。机制包括 checkout、commit、update、merge。关键性质：① commit 之后工作副本与仓库一致；② merge 是「对称差」的处理——两边都改了的文件产生冲突，只有一边改了的自动合并；③ update 保持本地未提交的修改（这条最难，也最接近 6.3 那种「特性交互」的分析）。②的形式化最能体现 Alloy 的价值：merge(a, b) = {f: File | a.contents[f] = b.contents[f] or ...}，然后用断言检验「合并结果在两个父节点的公共祖先之上同时包含两边的修改」。

(i) Layers in Photoshop · Photoshop 中的图层

构造一个 Adobe Photoshop 图层功能的抽象模型，其中一幅图像可以由一叠图层构成，每个图层要么由一个像素矩阵构成，要么由一个「应用于其下方图层的结果的变换函数」构成。

点拨本题的难点是「变换函数」这个概念在一阶关系逻辑中如何表示。Alloy 没有高阶函数，所以你不能真的写 f: Layer -> Layer 并应用它。可行的抽象办法有两种：① 把变换建模为「一个作用于图层栈的关系」：sig Transform {appliesTo: set LayerKind, effect: Layer -> Layer}——但 effect 本身就是一个函数关系，所以「应用」退化成 join；② 只建模结构与顺序，不建模像素语义：sig Layer {above: lone Layer, kind: Kind, visible: Bool}，然后分析「图层顺序改变会如何改变结果」这类性质。推荐走第二条路——它符合「抽象模型只保留与要分析的性质相关的细节」这一原则（A.5.1 的那句提示）。值得检验的性质：可见性切换与顺序交换是否可交换（一般不可交换，这正是 Photoshop 用户的常见困惑源）；「调整图层」只影响其下方图层这一约束是否被正确建模。

附录 A 小结

  1. 六个节构成一条清晰的能力阶梯：A.1 纯逻辑表达式 → A.2 在给定骨架上补全 → A.3 把自然语言谜题形式化 → A.4 为「模型本身」建模 → A.5 自主设计小型案例 → A.6 完全开放的研究项目。难度标记 ♥（容易）与 ♣（挑战）帮助你安排练习节奏。
  2. A.1 只需第 3 章背景，但作者强烈建议边做边用 Analyzer，并为此提供了模板——模板的作用是「让你在不掌握完整语言的情况下就能获得具体反馈」。除 A.5.3（引用第 6 章）外，其余各节读完第 3、4 章即可尝试。
  3. A.1.1 的八条关系性质是第 3 章的浓缩复习；核心洞察是「反自反 + 对称 + 传递 ⇒ 只能是空关系」，所以消掉「非空」即可让全部性质共存。A.1.2 要求把每条改写成谓词演算并用 iff 断言机器验证——「双向等价」才能证明是改写而非弱化。
  4. A.1.4 的分配律：join 只对「并」分配，对「差」和「交」都不分配。理由是 join 是逐元取像，像集合会混合来自两个关系的贡献。发现性质不成立时，应缩小作用域以获得最小反例。
  5. A.1.9「传递闭包不可公理化」是一个深刻的逻辑事实：一阶逻辑无法表达「最小」，因为那需要对所有子关系做全称量化。UML 1.0 的官方定义就栽在这里。Alloy 通过把关系当一阶对象部分绕过了这个限制，但代价是宇宙有限——而不可公理化恰恰是关于无限结构的定理。
  6. A.1.10 的真正用意：让你体会「绝大多数看似需要集合理解式的需求，都能用交、差、域/值域限制的组合来表达」。例如「空的组」= Group - Group.address.univ，「只要直接地址」= address & (univ -> Addr)。
  7. A.1.11 伦敦地铁：核心告诫是「不要作弊——不要直接录入实例」，因为那样得到的模型无法容纳额外的中间车站，而且你会错过用 Analyzer 发现通用约束中错误的机会。第 (h) 问「登上 L 线列车最终会到达 S2」在有分支的线上为假——这与 6.1.4 中活性断言需要 progress() 前件是同一个教训。
  8. A.2.2 是「不变式保持」分析的标准练习，也是 6.3.3 的原型：写 inv(b) and op(b,b') => inv(b')，找反例，强化前置条件，然后必须回头重跑模拟确认没有过度约束——一个让操作永不发生的模型是空洞地正确的。
  9. A.2.3 的「safe vs happy」教你识别「未分类元素」：安全分配不蕴含快乐分配，反例来自「不属于任何帮派的囚犯」。修复办法是加 all i: Inmate | one i.~members。通用教训：当断言意外失败，先怀疑「模型允许了现实中不该存在的状态」。
  10. A.3 的共同主题是「形式化暴露歧义」：Doris Day 那句歌词的严格读法确实推出「我就是我的宝贝」，而加上「除了我之外」就解除了；理发师悖论的三种解法（承认女性 / 允许无理发师 / 允许多个理发师）恰好对应修模型的三把扳手：扩大论域、放松重数、打破单指。
  11. A.3.4 握手问题的关键计数：10 人中每人握手数范围是 0–8（不含自己与伴侣），恰好 9 个值；「除 Alice 外 9 人答案互不相同」⇒ 取遍 0…8 ⇒ 握 8 次者与握 0 次者是一对，握 7 与握 1 是一对，握 6 与握 2 是一对，握 5 与握 3 是一对，剩下握 4 次者必是 Alice 的配偶 Bob。答案是 4 次。第 (c) 问的「重构」建议是把候选答案参数化为 pred solution(k: Int)。
  12. A.3.5 山羊白菜狼是 6.1 迹 idiom 的最小可运行版本：open util/ordering[State] + init + step + Traces fact + run。用「左岸集合」单一字段表示状态可让状态数减半；标准解需要 7 步，所以 State 作用域至少 8。A.3.6 外科医生手套（♣）则要求你自己发明状态表示——4 个需覆盖的表面 vs 4 个手套表面，解法包含「翻转手套」这一动作。
  13. A.4 的核心观念：元模型不必具备它所捕获的模型的品质——状态机的元模型自己不必是动态的，因为一个状态机只是「一个可被赋予动态解释的结构」。这是 Alloy 能用静态一阶关系逻辑描述动态系统的哲学根据，也是第 6 章迹 idiom 的理论基础。
  14. A.4.2 的模拟/双模拟直接呼应 6.4.4 的迹包含：单向模拟只保证「M1 的迹集 ⊆ M2 的迹集」，不保证相同；双模拟（~r 也是模拟）才保证迹集相同。而 6.4.4 也指出迹包含不保证「做好事」——空迹集的机器符合任何抽象机器。两处是同一观察的两面。
  15. A.4.3「Alloy 的元模型」要求自描述：用存在量词挑出实例中代表 Sig/Field/Mult 的原子，断言它们之间的关系与模型声明一致。A.4.4 Java 元模型的「良类型」两条本质：对象只能持有「自己类型或其超类型所声明的字段」的值；该值的对象的运行时类型必须是字段声明类型的子类型——后者的 *super 与 *extendsI 复合正是 Alloy 自己 extends 语义的镜像。
  16. A.5.1 Unix 文件系统最重要的提示是「描述故意包含了无关细节」：inode 中十个地址的顺序对路径解析无关紧要，所以应当用集合而非序列。(c) 的「非递归」技巧是全题核心：Alloy 函数不能递归，但可以声明一个关系并用一条「关系名出现在等式两边」的 fact 来定义它——递归被消解成联立方程交给 SAT 求解器。(d) 中「没有两个不同路径名解析到同一 inode」应当不成立，因为 Unix 支持硬链接。
  17. A.5.2 铁路道岔要求你独立复现第 6 章的整套方法论：overlaps 自反、对称、但不传递（误加传递性会让模型退化成「所有段都互相重叠」）；「不必引入闸门原子」体现了「一个状态不必由实体表示」；(g)「检验一整族机制」是本题最深刻的一点——策略谓词应当是「机制必须满足的最小条件」而非「某个具体机制的定义」，这是欠规约作为优点的典范；(i) 与 A.2.2(f) 同样要求「证明安全之后再证明模型仍能做事」。
  18. A.5.3 与 6.2 的方案同构但更强：双钥匙 + 双记录（lastKey 与 issued）。(e) 揭示的漏洞与 6.2 的漏洞同源——「验证条件弱于状态更新条件」：改成「第一钥匙匹配即开门」后，重编码只在另一条分支发生，于是旧卡可反复开门。建议直接以 examples/hotel 模块为起点改造，迹约束与 NoBadEntry 断言几乎可原样复用。
  19. A.6 的九个开放题目按难度递增，每个需数小时到数天。它们共同的方法论是：先决定「哪些细节与要分析的性质相关」，把其余抽象掉（A.5.1 的提示在这里同样适用）。特别地，(i) Photoshop 图层揭示了一个语言边界：Alloy 没有高阶函数，所以「变换函数」只能通过关系或「只建模结构与顺序」来近似——认清工具的表达边界，本身就是建模能力的一部分。
