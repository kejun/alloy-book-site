6.1Leader Election in a Ring · 环形领导者选举

问题与协议

许多分布式协议需要一个进程扮演领导者角色来协调其他进程。预先指派领导者不可行，所以需要某种机制，让一组运行同一程序的通信进程能够动态地「选举」出一个领导者。

考虑进程构成一个环的情形。由于通信拓扑是对称的，我们必须到别处寻找可利用的不对称性。我们假定进程有唯一的、全序的标识符——例如它们所在机器网卡的序列号（所谓的 MAC ID）。领导者将是标识符最大的那个进程。

协议 [8]

进程把自己的标识符当作 Token，沿环朝某个方向（比如顺时针）传递。每个进程检查它收到的每个标识符：

  • 标识符小于自己的 ⇒ 消费掉这个 token；
  • 标识符大于自己的 ⇒ 把 token 继续传下去；
  • 标识符等于自己的 ⇒ 它知道 token 已经绕环一整圈，于是选举自己为领导者。
建模分布式算法的原则：尽量少做假设

建模分布式算法时，你要对通信与调度做尽可能少的假设。显然算法必须对进程执行的所有交错（interleaving）都成立，因为进程是并发的。理想情况下，即使消息在进程之间被缓冲、被重排序、甚至被丢弃，它也应该成立。

作者的取舍：不建模进程之间的显式消息缓冲区，而是给每个进程一个 token 池（pool）。在一步中，一个 token 可以从一个进程的池里取出、移到它在环中的后继的池里。token 的选择是任意的（以建模重排序），参与某一步的进程的选择也是任意的（以建模并发）。消息投递是可靠的，但要修改模型以允许消息被丢弃是很容易的。

6.1.1 Topology and State Components · 拓扑与状态组件

首先命名模块并导入全序库模块，把它分别应用到表示时间步的 signature 和表示环中进程的 signature：

module examples/ringElection
open util/ordering[Time] as TO
open util/ordering[Process] as PO
sig Time {}
一个巧妙的省略

不需要「进程标识符」这个特殊概念——代表进程的那个原子本身也就充当它的标识符。这是 Alloy「原子无解释」特性的直接收益：你不必为「ID」再造一个 signature。

sig Process {
  succ: Process,             // 后继进程（环中一侧的邻居）
  toSend: Process -> Time,  // 待沿环发送的「进程标识符」池
  elected: set Time        // 它认为自己被选为领导者的那些时刻
}
「加上 Time 列」= 让关系变成动态的（本章最核心的 idiom）

Time signature 没有出现在 succ 字段的声明中，因为拓扑是静态的。给一个关系加上一列 Time，就使它变成动态的。

字段没有 Time 列加上 Time 列
toSend只是进程之间的关系，p.toSend 表示一个进程集合变成关系，p.toSend.t 是在时刻 t 与 p 关联的进程集合
elected会是一个进程集合变成关系，elected.t 是在时刻 t 被选为领导者的进程集合；p.elected 是进程 p 被选中的那些时刻的集合

进程要构成一个环。succ 的声明已确保每个进程恰好有一个后继，所以只需再加一条约束：从任意进程出发反复跟随 succ，所有进程都可达：

fact Ring {all p: Process | Process in p.^succ}
module examples/ringElection
open util/ordering[Time] as TO
open util/ordering[Process] as PO
sig Time {}
sig Process { succ: Process, toSend: Process -> Time, elected: set Time }
fact Ring {all p: Process | Process in p.^succ}

pred init (t: Time) {all p: Process | p.toSend.t = p}
pred step (t, t': Time, p: Process) {
  let from = p.toSend, to = p.succ.toSend |
    some id: from.t {
      from.t' = from.t - id
      to.t' = to.t + (id - PO/prevs(p.succ))
    }
}
pred skip (t, t': Time, p: Process) {p.toSend.t = p.toSend.t'}

fact Traces {
  init (TO/first ())
  all t: Time - TO/last() | let t' = TO/next (t) |
    all p: Process |
      step (t, t', p) or step (t, t', succ.p) or skip (t, t', p)
}
fact DefineElected {
  no elected.TO/first()
  all t: Time - TO/first()|
    elected.t = {p: Process | p in p.toSend.t - p.toSend.(TO/prev(t))}
}
assert AtMostOneElected {lone elected.Time}
check AtMostOneElected for 3 Process, 7 Time

pred progress () {
  all t: Time - TO/last() | let t' = TO/next (t) |
    some Process.toSend.t =>
      some p: Process | not skip (t, t', p)
}
assert AtLeastOneElected { progress () => some Elected.Time }

pred looplessPath () {no disj t, t': Time | toSend.t = toSend.t'}

6.1.1 Discussion

Q：为什么要为「排序」这么简单的概念导入库模块？

把标准概念抽取到库里总是好的：它降低理解模型的认知负担（模型使用标准词汇与概念时），并降低犯错的风险——即使是简单的排序也可能写错。

在这个例子里还有性能优势：应用于 util/ordering 的对称破缺被硬连线进了 Analyzer 的实现，它依赖排序的某个性质，而这个性质很难从库模块的文本中推断出来。

Q：为什么时间在字段声明中显式出现？

替代方案是在 Alloy 中引入「可变字段」的概念。那会让语言复杂化，并且把用户绑死在某一种特定的 idiom 上。

当时刻像任何其他原子一样出现在关系里时，整套关系算子的 repertoire 都能被应用。例如表达式 elected.Time 表示「在任意时刻被选中的进程集合」。声明约束也能用来表达动态性质：

elected in Process lone -> Time   // 任意时刻至多一个进程被选中
toSend: (Process lone -> Process) -> Time
// 任意时刻，每个进程标识符至多驻留在一个进程的发送池中
Q：为什么把 Time signature 放在字段声明的末尾？

乍看之下，把 Time 列放在开头似乎更自然：

sig Process {toSend: Time -> Process}   // 而非 Process -> Time

大多数情况下唯一的差别只是 join 参数的位置：进程 p 在时刻 t 的池中的进程，前者写作 p.toSend[t]（或 t.(p.toSend)），后者写作 p.toSend.t。

但注意

在第一种写法中，因为字段声明在 Process 内，toSend 是一个第一列为 Process 的三元关系——所以 Time 列出现在中间而不是末尾。当你用关系算子写表达式时，这就成了不便。

用第二种声明形式，表达式 toSend.t 表示一个从 Process 到 Process 的关系：当 p 在时刻 t 的池中持有 q 的标识符时，它把 p 映射到 q。这让写这类约束变得容易：

toSend.t = Process <: iden   // 该关系是进程上的恒等关系（正是 6.1.2 的初始化条件）

类似地，如果环拓扑是动态的（sig Process {succ: Process -> Time}），无环条件可以从

fact Ring {all p: Process | Process in p.^succ}

轻松扩展为

fact Ring {all t: Time, p: Process | Process in p.^(succ.t)}

若 Time 列在中间，这些约束就没法写得这么方便——你不得不写类似 {p, q: Process | p -> t -> q in succ} 的东西，而不能写 succ.t。

简言之，问题的实质是：Time 列出现在关系的外侧还是中间。如果在中间，你就无法写一个简单的 join 表达式来表示「关系在给定时刻 t 的值」。

Q：为什么不把 Time signature 放在关系的最前面？

所以更好的问题是：为什么 Time 列写在最后而不是最前。确实，在这个模型里，写成下面这样几乎没差别：

sig Process { succ: Process }
sig Time { toSend: Process -> Process, elected: set Process }
动态字段挂在 Process 上（本书用法）动态字段挂在 Time 上
风格渊源令人想起面向对象编程大多数传统建模语言（如 Z 和 VDM）使用的 idiom；这种情况下叫 State 比叫 Time 更合适
特点把单个对象的所有静态与动态方面打包在一起；允许用 signature 扩展对对象分类有一个全局状态；更干净地分离静态与动态方面；支持一种状态被增量地增长的建模风格（在 Z 中常见）
书中用在哪6.1、6.26.3 的媒体资产例子

6.1.2 Protocol Dynamics · 协议动态

协议本身分三个阶段描述。

① 初始条件：每个进程只准备好发送自己的标识符
pred init (t: Time) { all p: Process | p.toSend.t = p }
② 允许的状态迁移：从池中任取一个标识符，移到后继的池里
pred step (t, t': Time, p: Process) {
  let from = p.toSend, to = p.succ.toSend |
    some id: from.t {                 // 任意选一个标识符
      from.t' = from.t - id           // 从 p 的池中移除
      to.t' = to.t + (id - PO/prevs(p.succ))   // 加入后继的池（或被消费）
    }
}
id - PO/prevs(p.succ) 在做什么

它从「只含标识符 id 的单例集合」中减去所有先于 p.succ 的标识符。这就建模了 token 的消费：如果 token 中的标识符大于接收进程的标识符，它就被放进池中等待转发；否则它被丢弃。

不要被这里的两个不同的排序搞混：一个是进程绕环的排序，一个是标识符的排序。表达式 p.succ 表示 p 在环中的标识符后继；对它应用函数 PO/prevs，得到的是在标识符空间中先于它的那些进程标识符的集合。

③ 被选中进程的指定
fact DefineElected {
  no elected.TO/first()                    // 第一个时刻没有进程被选中
  all t: Time - TO/first()|
    elected.t = {p: Process |
      p in p.toSend.t - p.toSend.(TO/prev(t))}   // 「刚刚收到自己标识符」的进程
}

我们本可以像对待 token 池那样处理 elected——在 init 里初始化它、在 step 里更新它。但这样定义能给出更干净的「关注点分离」，并避免了对框架条件（frame conditions）的需要。

Q：为什么「被选中」这个概念不是粘性的（sticky）？

你可能已经注意到，这个选举定义只让一个进程在它收到自己标识符的那一个时刻处于「被选中」状态。在下一个时刻，它就不再被视为被选中了。如果你不喜欢这样，你可以修改模型，让选举变得「粘性」——一旦被选中就保持被选中。

但没那么简单

这不只是「把集合理解式里的第二项去掉」的问题，即把定义改成

elected.t = {p: Process | p in p.toSend.t}

而不是

elected.t = {p: Process | p in p.toSend.t - p.toSend.(TO/prev(t))}

如果你不确定为什么，试着在 Alloy Analyzer 里运行这些命令，看看会发生什么。

6.1.3 Introducing Traces · 引入迹

我们想检验两个性质：至多一个领导者被选出，以及最终有某个领导者被选出。

路线做法
传统的归纳分析（Alloy 可以自动化它）对第一个性质：构造一个不变式，用 Alloy 检验「不变式蕴含该性质」且「不变式在每一步都被保持」。对第二个性质：找某个整数度量，用 Alloy 检验「它在每步递减」且「归零蕴含选举发生」。
本书采用的路线需要更少的洞见（insight），并允许直接检验性质。目前的模型实例涉及一组状态；只需添加一条 fact，就能把这些状态串成一条执行迹。然后就可以直接对迹表述断言。如果断言无效，反例就是一条展示它如何被违反的迹。
 
fact Traces {
  init (TO/first ())
  all t: Time - TO/last() | let t' = TO/next (t) |
    all p: Process |
      step (t, t', p) or step (t, t', succ.p) or skip (t, t', p)
}

它说：初始条件在第一个时刻成立；对任何后续时刻，每个进程 p 要么自己走一步，要么它的前驱 succ.p 走一步，要么什么都不做。「什么都不做」被建模为一个操作：

pred skip (t, t': Time, p: Process) { p.toSend.t = p.toSend.t' }
Q：为什么迹约束允许前驱走一步？

当进程 p 从时刻 t 走到 t' 时，谓词 step(t, t', p) 成立。这意味着一个标识符从 p 的池移到它后继进程的池。那个后继进程因此也经历了一次状态变化。它的状态变化由同一个 step 谓词描述，只是应用于它的前驱。

如果没有第二个谓词调用，约束就不可能被满足——因为那个后继进程要么必须 skip，要么必须自己作为 token 转移的源头，而这两者都与「作为 token 转移的目标」不相容。run 命令会抓住这个错误并报告不一致。

或者，作者本可以写一个更简单的迹约束：

some p: Process |
  step (t, t', p) and all p': Process - (p + p.succ) | skip (t, t', p)

意思是「每步有一个进程移动，除这个进程和它的后继外，其他任何进程都没有状态变化」。这种表述的缺点是它一次只允许一对进程移动。

隐式并发的价值

原版本的隐式并发（implicit concurrency）除了更一般之外，还有一个优势：它允许更短的迹里发生更多事情，因此在更小的作用域下做的分析更有意义。

Q：为什么一个操作必须取两个时间参数？
既然 step 和 skip 总是被应用于一个时刻及其后继，你可能会问为什么不声明单个参数 t、然后在谓词体内把 t' 定义为 TO/next(t)。这里的动机是关注点分离：与其在每个操作里都承诺使用「迹」这个 idiom，不如只在一个小小的地方承诺它，这样换成另一种 idiom 就会很容易。

6.1.4 Dynamic Analysis · 动态分析

第一步：先跑个简单模拟，确认模型没有过度约束 
pred show () { some elected }
run show for 3 Process, 4 Time

作者选了三个进程的作用域——最小的有趣环——和四个时刻，因为领导者的 token 必须绕环一整圈，所以时刻数必须比进程数至少多一。生成的样例迹见 fig. 6.4：进程 P2 的标识符一路绕完一圈，而在此之前没有发送任何其他标识符（初始状态在左上的面板，执行按顺时针穿过各面板）。

确认模型至少是一致的之后，就可以着手检验性质了。协议的目的，是到达一个「恰好一个领导者被选出」的状态。

方法论：把性质拆成子性质，分别检验

在可能的时候，最好把一个性质拆分成子性质并分别检验。这样在某个性质不成立时，更容易诊断出了什么问题。所以我们分别考虑两个性质：至多一个与至少一个被选中的进程。

① AtMostOneElected —— 有效

assert AtMostOneElected { lone elected.Time }
check AtMostOneElected for 3 Process but 7 Time
解读：elected.Time 比 all t: Time | lone elected.t 更强

表达式 elected.Time 表示在任意时刻被选中的进程集合。所以这条断言不仅说了「任意时刻至多一个进程被选中」（那可以写成 all t: Time | lone elected.t），而是更强地说：选举不会从一个进程变成另一个进程。

作用域把分析限制在 3 个进程、7 个时刻的环上。AtMostOneElected 断言是有效的，找不到反例。

② AtLeastOneElected —— 无效，然后修复

assert AtLeastOneElected { some t: Time | some elected.t }
check AtLeastOneElected for 3 but 7 Time
第二个断言无效：反例里「什么都没发生」

它有一个反例，其中什么事情都没发生。问题出在包含了 skip 操作——它允许每个进程在每一步都 skip！

修复办法：强制进展（progress）——坚持「只要某个进程有一个非空的标识符池，某个进程（不必是同一个）就必须移动」。写成谓词：

pred progress () {
  all t: Time - TO/last() | let t' = TO/next (t) |
    some Process.toSend.t =>
      some p: Process | not skip (t, t', p)
}

然后把断言以这个谓词成立为条件：

assert AtLeastOneElected { progress () => some Elected.Time }
check AtLeastOneElected for 3 Process, 7 Time
解读 · 「公平性假设作为断言前件」是通用套路

注意这里的处理模式：把「活性（liveness）」性质写成 公平性假设 => 想要的结论，而不是把公平性写成 fact。这样模型依然允许什么都不发生的迹（用于其他分析），但断言只在满足进展假设的迹上被要求成立。这正是 5.1.3 Discussion 里提到的、CTL 无法表达的「公平性性质（fairness properties）」。

7 个时刻实际上是能保证产生领导者的最小作用域。作者找到它的方法很朴素：从更小的作用域开始，逐步增大，直到断言不再产生反例。

6.1.4 Discussion

Q：进程总是按标识符顺序被放进环里的吗？

不是。它们在 fig. 6.4 中以那个顺序出现，是因为 Alloy Analyzer 的对称破缺优化（见 5.2.1 后的讨论）。由于原子是可互换的，你可以取一个命令的任意实例（或反例），通过置换原子造出另一个。

数学家会说：把进程绕环排成 P0、P1、P2……是「不失一般性」的，因为这个方案的描述从未提及特定原子。Analyzer 利用这一点来减少搜索——对 succ 施加一个约束。util/ordering 模块的排序关系用了同样的技巧：这就是为什么迹中的时刻总是按顺序出现。

如果模型显式比较这两个关系，对称破缺就会退让

如果模型显式地比较这两个关系，那么在两处都破缺对称性就不再有效，Analyzer 会退让（back off），不再包含对 succ 的对称破缺约束。要看到这一点，加上：

fact DifferentOrder { all p: Process | p.succ != PO/next(p) }

模拟就会显示一个标识符乱序出现的环。

Q：AtLeastOneElected 怎么可能是有效的？作用域不是允许更短的迹吗？

与排序模块相关的对称破缺实际上会强制被排序的集合包含「作用域所允许的最大数量」的原子。所以我们的两条命令的效果，与写成精确作用域时相同：

check AtMostOneElected  for exactly 3 Process, exactly 7 Time
check AtLeastOneElected for exactly 3 Process, exactly 7 Time
Q：这违反了作用域单调性吗？如果违反了，要紧吗？

是的，它违反了；是的，它要紧（至少在某些方面）。

  • 对检验 AtLeastOneElected 而言，signature Time 需要精确作用域；这类「最终性（eventuality）」性质永远不是作用域单调的。
  • 对检验 AtMostOneElected 而言，精确作用域并不可取，因为可以设想存在「坏迹」（两个进程被选中）无法被延长到作用域要求的完整长度。不幸的是，无法检验这种情况不会发生（见 5.3 节）。
  • 精确作用域对两条命令都有的另一个不良后果是：它强制环中进程数恰好是某个数。

不过很容易调整模型，使得作用域 k 下的分析考察所有「至多 k 个进程」的环——引入一个子签名：

sig Process {}
sig RingProcess extends Process {
  succ: RingProcess,
  toSend: RingProcess -> Time,
  elected: set Time
}
fact Ring {all p: RingProcess | RingProcess in p.^succ}

从而只把 succ 的重数约束和 Ring fact 施加在「出现在环中的那部分进程」上。

6.1.5 Computing Machine Diameter · 计算机器直径

为什么需要这一节

作用域内的穷尽分析由小作用域假设证成，通常看起来是捕获大多数 bug 的合理办法——例如如果这个协议在五节点的环上没有反例，它似乎不太可能藏着 bug。但「给迹设界」这件事说服力就弱一些。

  • 对 AtLeastOneElected：我们找的是选举的见证者，所以增加迹长不会产生新的反例。
  • 对 AtMostOneElected：我们有理由担心漏掉一个只在更长迹中才显现的 bug。

关于作用域是否充分，我们可以问的一个问题是：我们考察的迹是否长到足以覆盖所有可达状态？如果是，就可以放心：分析 AtMostOneElected 这样的断言时，不会因为迹长不足而漏掉 bug——因为该断言是关于状态的声明，而每个可达状态都会被考察到。

直径（diameter）的定义

一个状态机的直径，是一个状态距初始状态的最大距离，其中两个状态之间的距离是能把你从一个带到另一个的最少执行步数。一般来说，用 Alloy 计算一个被建模状态机的直径是不可能的，但我们常常能找到一个上界。

做法是：写一个谓词，它的实例是「无环路径（loopless path）」——即给定状态至多被访问一次的迹。我们协议的行为只依赖于标识符池，所以当两个时刻的池相等时，我们就认为它们的状态等价：

pred looplessPath () { no disj t, t': Time | toSend.t = toSend.t' }

然后对递增的迹长求这个谓词的实例：

命令结果
run looplessPath for 3 Process, 12 Time✅ 产生一个解
run looplessPath for 3 Process, 13 Time❌ 不产生解
结论

不存在含 13 个时刻且无环的迹。因此我们可以断定：对三节点环，Time 的作用域 12 足以到达该协议的所有状态。换句话说，当 Process 的作用域为 3 时，再增大 Time 的作用域不会有任何收获——就 Time 而言，分析是完备的。

6.1.5 Discussion

Q：Alloy 的迹断言与时序逻辑相比表达力如何？

由于模型的实例是迹，这些断言可比于线性时序逻辑（LTL），而不是计算树逻辑（CTL）——后者需要实例是树结构。

任何 LTL 性质都能轻松用一阶逻辑表达，这由「LTL 归约到可满足性」（即所谓的有界模型检查（bounded model checking） [5]）所证明。一阶逻辑比时序逻辑更有表达力，尽管那额外的能力——至少在时序方面——似乎并不必要。

把迹过滤到那些满足 progress 性质的迹，是一类叫「公平性性质（fairness properties）」的经典例子，而这类性质在 CTL 中不可表达。一般来说，LTL 似乎比 CTL 更适合描述软件的时序性质。

6.2Hotel Room Locking · 酒店房间门锁

问题背景

如果你住过酒店，你可能会好奇门锁是怎么工作的。锁用一次性的钥匙——不像大多数锁那样，它们无法被反复用同一把钥匙开启。这就提出了一个问题：当房间被分配给新客人时，如何阻止旧客人再进入？

可重编码锁（recodable locks）

可重编码的锁解决了这个问题，酒店从 1980 年代起就在使用——先是机械式的，现在是电子式的。它们的工作方式是：给下一位住客发新钥匙时，锁会被重新编码，于是先前的钥匙停止工作。

锁是一个独立的、电池供电的单元，其内存中持有当前的钥匙组合（current key combination）。一个硬件装置——比如反馈移位寄存器（feedback shift register）——生成伪随机数。锁既可以用当前组合打开，也可以用它的后继组合打开；把后继组合插入锁，就使它成为当前组合。

关键在于：前台与锁之间不需要通信。只要初始同步一次，加上两边运行同一个伪随机数生成器，双方的记录就能保持同步。

6.2.2 Hotel Operations · 酒店操作

init —— 初始化

pred init (t: Time) {
  no Guest.keys.t
  no FrontDesk.occupant.t
  all r: Room | FrontDesk.lastKey.t [r] = r.currentKey.t
}
初始化并不容易实现

这是唯一一个需要「锁 ↔ 前台」之间通信的操作。实践中通常靠一张特殊的重置卡（reset card）完成。其他所有操作都靠双方运行同一个伪随机生成器来保持同步。

entry —— 客人开门

1 pred entry (t, t': Time, g: Guest, r: Room, k: Key) {
2   k in g.keys.t                                    // 前置：g 在 t 时持有 k
3   let ck = r.currentKey |
4     (k = ck.t and ck.t' = ck.t) or                 // k 就是当前组合 ⇒ 锁不变
5     (k = nextKey(ck.t, r.keys) and ck.t' = k)      // k 是后继组合 ⇒ 重编码
6   noRoomChangeExcept (t, t', r)                    // 框架条件
7   noGuestChangeExcept (t, t', none)
8   noFrontDeskChange (t, t')
9 }

三个框架条件谓词

pred noFrontDeskChange (t, t': Time) {
  FrontDesk.lastKey.t = FrontDesk.lastKey.t'
  FrontDesk.occupant.t = FrontDesk.occupant.t'
}
pred noRoomChangeExcept (t, t': Time, rs: set Room) {
  all r: Room - rs | r.currentKey.t = r.currentKey.t'
}
pred noGuestChangeExcept (t, t': Time, gs: set Guest) {
  all g: Guest - gs | g.keys.t = g.keys.t'
}
解读 · 这就是 5.1 里说的「框架问题」的具体样子

「框架条件（frame condition）」= 明确写出「其他所有状态组件都不变」。这里把三个组件的框架条件各封装成一个谓词，每个操作只需一行调用——这是应对框架问题的常规工程手法，也正好为 6.2.4 的 Reiter 式改写做了对照。

注意 noRoomChangeExcept(t, t', r) 里的参数：「除了 r 之外」。这就是框架条件的「例外表」写法。

checkout —— 退房

pred checkout (t, t': Time, g: Guest) {
  let occ = FrontDesk.occupant {
    some occ.t.g                 // 前置：g 确实住过某个房间
    occ.t' = occ.t - Room -> g  // 从名册中移除 g 的所有条目
  }
  FrontDesk.lastKey.t = FrontDesk.lastKey.t'
  noRoomChangeExcept (t, t', none)
  noGuestChangeExcept (t, t', none)
}

checkin —— 入住

1  pred checkin (t, t': Time, g: Guest, r: Room, k: Key) {
2    g.keys.t' = g.keys.t + k                // 客人拿到钥匙 k
3    let occ = FrontDesk.occupant {
4      no occ.t [r]                          // 前置：房间 r 当前无住客
5      occ.t' = occ.t + r -> g               // 名册登记
6    }
7    let lk = FrontDesk.lastKey {
8      lk.t' = lk.t ++ r -> k                // 覆盖式记录最后发出的钥匙
9      k = nextKey (lk.t [r], r.keys)        // k 是上一个钥匙的后继
10   }
11   noRoomChangeExcept (t, t', none)         // ★ 锁本身不变！
12   noGuestChangeExcept (t, t', g)
13 }
第 11 行是本例 bug 的根源

checkin 不修改房间锁的当前钥匙——前台只是在记录里推进了一步，而锁要等到新客人真正插入新卡时（entry 的第 5 行）才会被重编码。这个「时间差」正是 6.2.3 中反例的来源。

迹约束

fact Traces {
  init (TO/first ())
  all t: Time - TO/last() | let t' = TO/next (t) |
    some g: Guest, r: Room, k: Key |
      entry (t, t', g, r, k) or checkin (t, t', g, r, k) or checkout (t, t', g)
}
对比 6.1 的迹约束：这里没有 skip，也没有并发

6.1 的 Traces 是 all p: Process | step(...) or step(...succ...) or skip(...)——每个进程都要表态，允许隐式并发。这里是 some g, r, k | ...——每步恰好发生一个操作。这不是疏忽：酒店场景里三个操作天然互斥于「前台」这一串行资源（entry 由锁独立完成，但它只改锁、不改前台，所以串行化不丢失可达行为）。这正是「迹 idiom 可以按场景调整」的示范。

Q：「被拒绝进入」这件事在哪里被建模了？

哪里都没有。它被 entry 的前置条件排除掉了（第 2 行 k in g.keys.t 加上第 4/5 行的分支，意味着只有能开门的钥匙才会触发 entry）。

这样处理是必要的，因为我们的目标是「未授权进入」，而失败的开门尝试不会改变任何状态。如果要建模锁的审计功能（记录谁试过开门），那就需要显式建模被拒绝的进入。

Q：为什么 checkin 的前置条件被分散在各处，而不是集中写成一个前置块？

因为这里的约束是围绕「状态组件」来组织的，而不是被切分成「前置条件 / 后置条件」。这样写避免了重复 let 语句，或者把它们的作用域扩得很大。

解读 · 声明式规约的组织方式

这是声明式规约与传统「前置/后置条件」规约的一个实质差别：在 Alloy 里，约束是按「涉及哪个状态组件」聚合的，而不是按「时序阶段」聚合的。一个 let 块里既可以放前置条件也可以放后置条件，读的时候要自己把两者分开。作者在 init、entry 等谓词中一律如此。

修复：加一条关于世界的假设

结论是：「阻止未授权进入」这个保证，只在「入住与开门之间没有插入其他事件」的假设下才成立：

fact NoIntervening {
  all t: Time - TO/last() | let t' = TO/next (t), t" = TO/next(t') |
    all g: Guest, r: Room, k: Key |
      checkin (t, t', g, r, k) => (entry (t', t", g, r, k) or no t")
}

读作：每次 checkin 之后紧接着的一步，必须是同一客人、同一房间、同一钥匙的 entry（除非已经到迹的末尾）。

Q：这个修复是不是在说「必须把新住客一路拖到房间门口」？

不是。NoIntervening 这条 fact 只是记录了一个关于世界的假设。如果这个假设不成立，那么安全性保证就被削弱了。这正是「建模涉及环境中其他行动者」的典型情形——规约不能只描述自己的机器，还要显式写出对世界的假设。

Q：some o 这个额外假设是干什么的？

它存在的原因是：这套方案保护的是「住客彼此之间」，而不是「酒店免受住客侵扰」。

如果去掉它，就会得到反例：一个客人退房之后立刻又用自己的钥匙重新进入。从酒店角度看这也许不算 bug（他已经付过费了），但从「名册为空时不许进入」的角度看它是违反断言的。

Q：问题的本质真的是「住客在首次进入之前并不拥有房间」吗？

是的。而且「住客身份（occupancy）」完全可以用「首次进入」来定义——就像领导者选举协议里用「收到自己的标识符」来定义 elected 一样。这样就不需要那条额外的 NoIntervening 假设了。

解读 · 「用定义代替假设」是更优雅的做法

这与 6.1.2 的 fact DefineElected 是同一个思路：与其在初始化和每步操作里维护一个状态组件（从而背上框架条件、并可能因假设不足而得到反例），不如把它定义成其他状态的函数。被定义出来的量天然满足框架条件，也不会引入额外的世界假设。作者在这里选择保留「假设 + 显式维护」的版本，是为了示范「如何为环境中的其他行动者写假设」这一课。

Q：这个问题是不是太「脏」了？真实的建模也会这样吗？

是的，它很脏——而且它代表了绝大多数「 situated in the real world（身处真实世界之中）」的需求。

传统上把需求当作「更高层的规约」来处理的做法无法应对这种情况。Michael Jackson 的「问题框架（problem frames）」理论 [38, 39] 解释了这一点，也解释了「简单可观察的事件」（进入房间）与「更适合用定义来刻画的事件」（获得住客身份）之间的区别。参见他的文章 “Definitions”“Designations”“Domains”“Machines”“Requirements”。

实用结论：入住后第一次开门，请一定用你自己的钥匙

如果行李员用万能钥匙放你进房，那么锁就没有被重编码，你的贵重物品在你下次自己进门之前都处于风险之中。

6.2.4 An Event-Based Variation · 事件式变体

Alloy 没有固定的状态机 idiom

这一节把同一个酒店模型换一种写法：状态空间和迁移完全相同，但用事件（events）而不是操作（operations）。

每个操作一个谓词声明一个 signature，它的原子就是事件

操作的参数（t, t', g, r, k）变成字段；signature 层次结构可以把公共的部分抽取出来

abstract sig Event { pre, post: Time, guest: Guest }
abstract sig RoomKeyEvent extends Event { room: Room, key: Key }

sig Entry extends RoomKeyEvent {} {
  key in guest.keys.pre
  let ck = room.currentKey |
    (key = ck.pre and ck.post = ck.pre) or
    (key = nextKey(ck.pre, room.keys) and ck.post = key)
}
sig Checkin extends RoomKeyEvent {} {
  keys.post = keys.pre + guest -> key
  let occ = FrontDesk.occupant {
    no occ.pre [room]
    occ.post = occ.pre + room -> guest
  }
  let lk = FrontDesk.lastKey {
    lk.post = lk.pre ++ room -> key
    key = nextKey (lk.pre [room], room.keys)
  }
}
sig Checkout extends Event {} {
  let occ = FrontDesk.occupant {
    some occ.pre.guest
    occ.post = occ.pre - Room -> guest
  }
}

事件式版本明显更短

断言从 4 个量词（t, r, g, k）缩到 1 个（e）；NoIntervening 从嵌套的 let t' / t" 缩到直接说 e.pre = c.post。因为事件本身就是原子，「哪两个时刻之间发生了什么」不再需要用 t/t' 的算术来表达。

事件式的最大优势：可视化

因为事件是原子，很容易看出 Analyzer 生成的每条迹的每个快照里发生的是哪个事件。fig. 6.13 展示的反例与 fig. 6.6 相同（在省略 NoIntervening 时产生）；可视化器被设置为「在事件的前置状态中显示事件」，也就是显示即将发生的那个事件。

Q：事件式写法有哪些吸引力？
  • 更好的可视化；
  • 更简洁、更直接的性质表述；
  • signature 扩展（signature extension）能把事件的公共属性抽取出来。这里抽取的只是参数声明，但也可以在事件类之间共享传统的框架条件——在 signature 之间共享比在谓词之间共享更容易，因为谓词是显式参数化的，而 signature 扩展（像面向对象继承和 Z 的 schema 包含一样）是用自由变量来工作的。
Q：这里本来可以用传统的框架条件吗？

可以，一字不改地照搬。之所以选用这种不寻常的写法，是为了强调「一门没有固定 idiom 的语言」的灵活性。

Q：Reiter 式框架条件与传统式相比，孰优孰劣？

这个想法出自 Ray Reiter [57]，并由他与 Alex Borgida 和 John Mylopoulos [7] 为软件建模进一步阐发。是否合算，取决于状态组件数 m、操作数 k，以及每个操作改动多少组件：

场景传统式（写等式）Reiter 式（写蕴含）谁更省
m 个状态组件，k 个操作，每个操作只改一个组件k × (m−1) 个等式只需 m 个蕴含式（「如果这个组件变了，那么它的操作必定发生了」）Reiter 大胜
每个操作改动除一个之外的所有组件只需 k 个等式需要 m 个蕴含式，每个都要列出 k−1 个操作名传统式大胜

就这个简单对比而言，Reiter 方案等价于「modifies 子句」（就像许多编程语言所提供的），但它的优势在于：

  • 不需要任何逻辑之外的概念（no extra-logical notions）；
  • 能容纳更复杂的形式，例如依赖于调用状态（invocation state）的框架条件。

6.3.4 Insights · 洞见

① 选中项不只是一个集合

它要么是 Undefined，要么是一个含 ≥1 个资产的集合。这带来两个好处：

  • 阻止「选中零个资产」——那毫无意义；
  • 阻止在什么都没选中时执行 show-selected，而那会把所有资产都隐藏掉！

② show/hide 的不对称反映了另一个不对称

选中项始终是「正在显示的资产」。

如果 show 是增补而不是替换 showing，那么它将完全没有任何效果！

换个说法：这两个命令其实都是关于「隐藏」的——hide 隐藏被选中的资产；show 隐藏「显示着但未被选中的」那些资产。

③ paste 让粘贴进来的资产保持选中

这提供了某种程度的撤销——紧接着做一次 cut 即可。但这个撤销是不完整的，因为原来的选中项丢失了。

这正解释了 6.3.3 中 PasteCut 为什么会失败：失败的不是目录集内容，而是选中项。

④ 缓冲区与目录集共享资产的情形出奇地微妙

作者一开始写错了，写成：

cs'.showing = cs.showing + buf
cs'.selection = buf

（用整个 buf 而不是 buf - cs.assets）结果 PasteNotAffectHidden 和 PasteCut 都因意外原因失败了：

  • 前者：粘贴一个已经被隐藏的资产会使它变成显示的（把它从 hidden 中移除）；
  • 后者：此外，产生的选中项包含了原本就在目录集里的资产，于是后续的 cut 会让目录集比 paste-cut 序列开始之前拥有更少的资产。

在 Media Pro 上做实验揭示了 paste 那个更复杂（但正确）的设计，它看起来是明智的，因为它保住了大多数用户所期望的代数性质 PasteCut（至少忽略选中项时）。

6.3.4 Discussion

Q：cut 和 paste 里的存在量词是为了「分配一个新状态」吗？

不是。在声明式规约里根本不需要「分配」这个概念。你完全可以改写成：

let cs' = xs'.catalogState [xs.currentCatalog] | cs'.assets = 表达式
all c: Catalog - xs.currentCatalog |
  xs'.catalogState [c] = xs.catalogState [c]

用存在量词之所以方便，是因为它允许使用关系覆盖算子 ++——即第 9/23 行的 xs'.catalogState = xs.catalogState ++ xs.currentCatalog -> cs'，一行就替代了上面那条「所有其他目录集状态不变」的全称量词。

Q：这些洞见是不是很琐碎（trivial）？

也许是。它们当中没有一个是「showstopper」——即没有一个是日后无法修补的。但要做出一个可靠且可用的应用，你最终必须把所有这些事情都做对。

Q：可用性问题能在抽象层面处理吗？

有些问题确实无法在抽象层面解决，但这并不构成在设计阶段忽略它们的理由。

  • 早期聚焦可用性能捕获许多问题，并省下返工的成本；
  • 可用性研究作为「检验一个假设的实验」时最有效，而没有一个抽象干净、连贯的设计，你就没有假设。
本章金句

「You can't tweak an incoherent user interface design into a usable and elegant one any more than you can test a pile of spaghetti code into a robust code base.」

你无法通过微调把一个不连贯的界面设计调成可用而优雅的，正如你无法通过测试把一堆面条代码测成一个健壮的代码库。

6.4.1 Abstract Memory · 抽象内存

模块被 Addr（地址集合）和 Data（可存储的数据值集合）参数化。Memory signature 表示内存的可能状态。

module examples/abstractMemory [Addr, Data]
sig Memory { data: Addr -> lone Data }
fact Canonicalize {
  no disj m, m': Memory | m.data = m'.data
}
pred init (m: Memory) { no m.data }
pred write (m, m': Memory, a: Addr, d: Data) {
  m'.data = m.data ++ a -> d
}
pred read (m: Memory, a: Addr, d: Data) {
  let d' = m.data [a] | some d' implies d = d'
}
fig. 6.18 简单抽象内存。
要点说明
data 是偏函数Addr -> lone Data：每个地址至多映射到一个数据值。
init内存初始为空，完全没有任何映射。（6.4.3 会把这个模型与一个「每个地址一开始就任意地有一个值」的更具体的模型关联起来。）
write新内存 m' 的 data 映射 = 旧内存 m 的 data 映射被 a -> d 覆盖。
read更有趣：如果被查询的地址有关联的数据值，就返回那个值；否则该值不受约束，任何值都可能被返回。这就是非确定性。
Canonicalize确保「内容相同的内存由同一个原子表示」——即 Memory 的原子与其 data 映射之间是双射。

两条可施加于此模型的检查

// ① 读一个地址返回刚刚写入的值
assert WriteRead {
  all m, m': Memory, a: Addr, d1, d2: Data |
    write (m, m', a, d1) and read (m', a, d2) => d1 = d2
}
check WriteRead

// ② 执行第二次相同的写没有效果
assert WriteIdempotent {
  all m, m', m“: Memory, a: Addr, d: Data |
    write (m, m', a, d) and write (m', m”, a, d) => m' = m“
}
check WriteIdempotent
解读 · WriteRead 为什么成立，全靠 Canonicalize

没有 Canonicalize，两个内容相同的 Memory 原子可以同时存在，那么 WriteIdempotent 里的 m' = m“ 就会失败——尽管它们在语义上无法区分。这就是「规范化」的实用价值：让外延相等与内涵相等重合。

Q：为什么要把内存值规范化（canonicalize）？

替代方案是引入一个谓词，比如 sameMemory，当应用于两个 data 映射完全相同的内存时求值为真，然后用它来取代等号测试。

两种做法都能正常工作，但规范化稍微更方便一些，原因是：

  • 避免了「忘记使用等价谓词而误用等号」这个错误；
  • Analyzer 生成的实例更容易理解，因为名字不同的内存总是在结构上不同的。
Q：为什么 read 不取第二个内存参数？

因为 read 不改变内存的状态，所以没有必要用第二个参数（比如 m'）来表示后置状态。

不过有时加上它反而更好。在一个「read 操作可能把数据从主存加载到缓存」的更具体的模型里，第二个参数是必需的。而为了拿那个模型与这个抽象模型做对比，在抽象模型里也带上第二个参数会很方便——这样就不必单独检验「加载式的 read 不影响抽象状态」了。

pred load (c, c': CacheSystem) {
  some addrs: set c.main.Data - c.cache.Data |
    c'.cache = c.cache ++ addrs <: c.main
  c'.main = c.main
}
pred flush (c, c': CacheSystem) {
  some addrs: some c.cache.Data {
    c'.main = c.main ++ addrs <: c.cache
    c'.cache = c.cache - addrs -> Data
  }
}

非确定性load 和 flush 是非确定的：它们不指定某个具体的缓存策略，而是通过「把「哪些条目被加载 / 被换出」这个问题悬而不决」来覆盖所有策略。

反面对照：如果把 load 写错

假设我们在规约 load 时犯了错，允许任意条目从主存被复制到缓存，而不管它们的地址是否与缓存中已有条目的地址相符：

pred load (c, c': CacheSystem) {
  some addrs: set Addr |        // ★ 少了 c.main.Data - c.cache.Data 的约束
    c'.cache = c.cache ++ addrs <: c.main
  c'.main = c.main
}

Analyzer 现在会找到一个反例，展示「缓存中的新鲜值（尚未被 flush 出去）被覆盖掉了」。

解读 · addrs <: c.main 的读法

<: 是域限制（domain restriction）：把关系 c.main 限制到定义域 addrs 内。所以 c.cache ++ addrs <: c.main 的意思是「只把 addrs 中那些地址的主存内容覆盖进缓存」。flush 里的 addrs <: c.cache 同理，方向相反。正确版 load 里 addrs 的类型是 c.main.Data - c.cache.Data——「在主存有值、但在缓存还没有值」的那些数据，正好排除了覆盖脏数据的可能。

Q：为什么缓存版本没有对内存值做规范化？

这个模型（不同于前面的抽象内存模型）没有包含规范化 fact。原因是：我们的例子不涉及对缓存内存的比较，但它会涉及对抽象内存的比较——即当我们检验「加载与刷新没有抽象层面的效果」时。

解读

规范化只在「需要对状态本身做相等比较」时才必要。6.4.5 的 LoadOK / FlushOK 断言里有 m = m'，比较的是抽象内存——而抽象内存已经规范化过了。缓存系统本身从不被拿来互相比较，所以省下这条 fact 是合理的（也让模型更简洁）。

6.4.3 Fixed-Size Memory · 定长内存

在 6.4.1 的抽象内存模型中，内存会随着对新地址的写入而动态增长，尽管可能地址的集合是固定的。对于一个用硬件实现的内存，更真实的模型是每个状态下每个地址都有一个值。

module examples/fixedSizeMemory [Addr, Data]
sig Memory { data: Addr -> one Data }   // ★ lone 变成 one
pred init (m: Memory) { }                  // ★ 空的！
pred write (m, m': Memory, a: Addr, d: Data) {
  m'.data = m.data ++ a -> d
}
pred read (m: Memory, a: Addr, d: Data) {
  d = m.data [a]                            // ★ 不再区分地址是否存在
}

与抽象内存的差别说明
lone → one初始化谓词现在是空的：允许任意初始的数据值指派，只要遵守 data 字段声明的重数，从而每个地址都有一个确定的数据值与之关联。
read 简化不再区分「地址是否存在」的情形，只是返回给定地址的数据值。读一个从未被写过的地址，会返回初始化时留下的任意「垃圾值」。

这个模型可以接受与抽象内存模型同样种类的内部分析——这里没有任何新东西。真正的新内容在 6.4.4 之后：如何证明这个更具体的模型符合那个更抽象的模型。

6.4.4 A Quick Introduction to Abstraction Functions · 抽象函数速览

我们现在已经看到内存模型的三个变体：一个抽象内存模型，和两个更具体的模型（一个容纳任意初始化，一个描述缓存）。如果我们观察后两者的行为，我们会期望它们符合抽象模型。也就是说：如果你唯一能看到的是「哪些操作发生了、传给它们的地址、以及传入 write / 传出 read 的数据值」，那么每一个具体系统的执行都将与抽象系统的某个执行无法区分。

第一步：同一状态空间内的精化

要判定一个具体操作

pred concreteOp (s, s': State) {…}

产生的行为是否被抽象操作

pred abstractOp (s, s': State) {…}

所接受，可以断言「具体操作的每一次迁移都是抽象操作的一次迁移」：

assert Refinement {
  all s, s': State | concreteOp (s, s') => abstractOp (s, s')
}
书中的例子

检验抽象模型的 write

pred write (m, m': Memory, a: Addr, d: Data) { m'.data = m.data ++ a -> d }

是否满足这个更抽象的描述

pred writeWeak (m, m': Memory, a: Addr, d: Data) { m'.data [a] = d }

——后者（没什么帮助地）允许除被写入的那个地址之外的每个地址都被破坏：

assert WriteRefinement {
  all m, m': Memory, a: Addr, d: Data |
    write (m, m', a, d) => writeWeak (m, m', a, d)
}

第二步：跨状态空间就需要抽象函数

简单做法失效

但要跨内存模型做比较，这个简单办法行不通：被比较的操作作用于不同的状态空间。

Tony Hoare 的一篇经典论文 [28] 提出了一个如今广为人知、被广泛使用的解决方案：定义一个把具体状态映射到对应抽象状态的「抽象函数」。

假设我们的操作是

pred concreteOp (s, s': ConcreteState) {…}
pred abstractOp (s, s': AbstractState) {…}

那么我们尝试找一个抽象函数

fun alpha (s: ConcreteState): AbstractState {…}

使得下面这条断言有效：

assert AbstractionRefinement {
  all s, s': ConcreteState |
    concreteOp (s, s') => abstractOp (alpha(s), alpha(s'))
}
这样做的意义

如果能找到这样的抽象函数，那么具体模型的可观察行为——其中「除了状态本身之外的一切都是可见的」——就将符合抽象模型。

Q：这里的「符合（conformance）」究竟是什么概念？

我们用「迹包含（trace inclusion）」作为衡量标准。

  • 迹（trace）是一段执行历史：一个事件序列，每个事件代表某个操作触发的一步；
  • 一个事件可以由「操作的名字 + 这一步中输入与输出所取的值」完整描述。注意前置状态与后置状态不是事件的一部分，因为它们被视为从外部不可见；
  • 每台机器（抽象的和具体的）都有一个迹集（trace set）来概括它的行为；
  • 具体机器符合抽象机器，当且仅当它的迹集是抽象模型迹集的子集。
Q：迹包含是不是太强 / 太弱的「符合」标准？

如果具体机器以这种方式符合，它就永远不会做坏事。但另一方面，符合并不保证它会做任何好事。特别是：

空迹集的机器符合任何抽象机器！

一个完全没有任何迹的具体机器，符合任何抽象机器。

为了确保「好事会发生」，符合的概念需要被扩展。如果每个操作代表一次服务请求及其履行，我们或许可以要求具体操作具有同等的可适用性（just as applicable）：只要抽象机器中的某条迹可以被某个事件延长，具体机器中就有对应的事件（或更一般地，一个合适的事件序列）。这就确保具体机器绝不会拒绝回应一个抽象机器本会回应的请求。

这种扩展在 Alloy 中不容易表述或检验，因为它需要对状态做无界的全称量化。我们需要的断言大致是说：对每一个具体的前置状态，只要对应的抽象操作可适用，具体操作就可适用（即存在一个满足操作约束的具体后置状态）。这个「对具体后置状态的存在量词」在被否定以求反例时，会变成一个无界的全称量词，所以 Alloy 无法处理它。详见 5.3 节。

Q：抽象函数方法总是行得通吗？

这个方法是「健全的（sound）」——意思是：如果你能找到一个满足精化条件的抽象函数，那么就可以推出具体机器符合抽象机器。

但它不是「完备的（complete）」：仅仅因为具体机器符合，并不意味着抽象函数就存在。标准方法出问题的情况很少见，发生在抽象机器与具体机器在不同的点上表现出非确定性、但可观察效果相同的时候。

有两种办法可以让它变得完备：

办法做法评价
① 泛化为抽象关系允许一个具体状态对应多个抽象状态这对 Alloy 并不可取，因为它需要一个无界的全称量化
② 用额外的状态变量增广具体模型以不改变可观察行为的方式加入变量，使抽象函数变得可寻两类变量：历史变量（history）与预言变量（prophecy），取决于那个「麻烦的非确定性」是在具体机器中更早还是更晚被消解。历史变量的用法见 6.4.6。
Q：如果挑错了抽象函数怎么办？

挑哪个函数都无所谓，只要它满足精化条件，外加一个条件：它必须是「全的（total）」，即为每一个具体状态都给出一个解释。

这个「全性」条件在 Alloy 中不容易检验，因为它需要一个无界的全称量词（见 5.3 节）。但你常常可以把抽象函数写成一眼就能看出它是全的形式，而且你可以「模拟」它——只需在 Alloy Analyzer 里运行这个函数——来检验它是一致的。

Q：抽象函数真的必须映射每一个具体状态吗？

不一定。你可以引入一个不变式（invariant）。只要每个具体操作都保持这个不变式——这在 Alloy 中很容易检验（见 6.3.1 的 HidePreservesInv 模式）——那么精化条件就可以被限制在「满足该不变式的那些前置状态」上，于是抽象函数只需要映射它们。

解读 · 这把 6.3 与 6.4 串起来了

6.3.3 的「操作保持不变式」分析在这里派上了新用场：不变式 + 保持性证明 = 缩小抽象函数的定义域。这也正是 Hoare 式论证的标准结构——「不变式 + 精化」两件套。

6.4.5 Abstraction Function for Cache Memory · 缓存内存的抽象函数

为了拿缓存模型与抽象模型做对比，我们新建一个 Alloy 模块：

module examples/checkCache [Addr, Data]
open cacheMemory [Addr, Data] as cache
open abstractMemory [Addr, Data] as amemory

然后声明一个抽象函数，说明「与一个缓存系统相关联的抽象内存」是这样得到的：取主存的内容，再用缓存的内容覆盖它：

fun alpha (c: CacheSystem): Memory {
  {m: Memory | m.data = c.main ++ c.cache}
}
解读 · 为什么是 c.main ++ c.cache

++ 是关系覆盖：c.cache 里的条目覆盖 c.main 里的同地址条目。这精确对应了缓存语义——缓存中的值（可能是脏的、尚未 flush 的）是权威值，主存里的是旧值。这一行就是整个精化论证的实质。
注意 alpha 依赖于抽象内存的 Canonicalize fact：正因为「内容相同 ⇒ 同一个原子」，集合理解式 {m: Memory | …} 才恰好返回一个单例集合，从而 alpha 真的是一个函数。

read 与 write 的精化

assert ReadOK {
  all c: CacheSystem, a: Addr, d: Data, m: Memory |
    cache/read (c, a, d) and m = alpha (c)
      => amemory/read (m, a, d)
}
check ReadOK

assert WriteOK {
  all c, c': CacheSystem, a: Addr, d: Data, m, m': Memory |
    cache/write (c, c', a, d)
    and m = alpha (c) and m' = alpha (c')
      => amemory/write (m, m', a, d)
}
check WriteOK

load 与 flush：与「什么都不做」的抽象操作对比

关键思路

load 和 flush 在抽象模型中没有对应物；从抽象视角看，它们的效果甚至应当是「不可察觉的」。所以我们拿它们与「什么都不做的那个抽象操作」做对比：

assert LoadOK {
  all c, c': CacheSystem, m, m': Memory |
    cache/load (c, c')
    and m = alpha (c) and m' = alpha (c')
      => m = m'
}
check LoadOK

assert FlushOK {
  all c, c': CacheSystem, m, m': Memory |
    cache/flush (c, c')
    and m = alpha (c) and m' = alpha (c')
      => m = m'
}
check FlushOK
解读 · 「不可观察」= 「抽象状态不变」

这就是把「某个内部操作对外界不可见」这句话形式化的标准方式：该操作前后，抽象函数的值相等。注意 LoadOK 正是 6.4.2 那条 Discussion 所预告的检验——「加载与刷新没有抽象层面的效果」。

也正因为这两条断言里有 m = m' 这个对抽象内存原子的相等比较，抽象内存模型才必须有 Canonicalize；否则内容相同的两个抽象内存会是不同原子，断言就会假失败。

6.4.6 History Variables · 历史变量

困境

只靠一个抽象函数，无法证明「定长内存符合抽象模型」。但定长内存确实是符合的：

  • 那些任意的初始值，对应于抽象内存中「没有关联数据值」的那些地址；
  • 当 read 操作返回这样一个任意值时，抽象模型也会允许它——因为在抽象的设定下，那个地址本来就不在映射里，而这种情况下抽象的 read 操作对返回值不做任何约束。

不幸的是，在初始状态之后，你就再也无法通过观察定长内存的「地址/数据」映射，来判断哪些地址被写过、哪些仍然持有它们的初始垃圾值。

解决这个两难的办法，是给模型增加一个额外的状态组件来维持这个区分。

module examples/fixedSizeMemory_H [Addr, Data]
open fixedSizeMemory [Addr, Data] as memory
sig Memory_H extends memory/Memory {
  unwritten: set Addr
}
pred init (m: Memory_H) {
  memory/init (m)
  m.unwritten = Addr                 // 初始时所有地址都「未被写过」
}
pred read (m: Memory_H, a: Addr, d: Data) {
  memory/read (m, a, d)              // read 不改变 unwritten
}
pred write (m, m': Memory_H, a: Addr, d: Data) {
  memory/write (m, m', a, d)
  m'.unwritten = m.unwritten - a     // ★ 写过的地址从集合中移除
}
fig. 6.21 用历史变量扩展定长内存模型。
历史变量（history variable）

这个状态组件 unwritten 被称作历史变量，因为它保存了关于行为的额外历史——在这个例子中是「尚未被写入的地址集合」。

注意它完全不影响可观察行为：它既不是任何操作的输入，也不是输出。这正是 6.4.4 里说的「以不改变可观察行为的方式增广具体模型」。

现在，使用增广后的状态，我们就能表述一个抽象函数，并像之前那样检验各操作，只不过用的是增广后的具体模型而不是原来的模型：

module examples/checkFixedSize [Addr, Data]
open fixedSizeMemory_H [Addr, Data] as fmemory
open abstractMemory [Addr, Data] as amemory

pred alpha (fm: fmemory/Memory, am: amemory/Memory) {
  am.data = fm.data - (fm.unwritten -> Data)   // ★ 抹掉所有未写过的地址
}

assert initOK {
  all fm: fmemory/Memory, am: amemory/Memory |
    fmemory/init (bm) and alpha (bm, am)
      => amemory/init (am)
}
check initOK

assert readOK {
  all fm: fmemory/Memory, a: Addr, d: Data,
      am: amemory/Memory |
    fmemory/read (fm, a, d) and alpha (fm, am))
      => amemory/read (am, a, d)
}
check readOK

assert writeOK {
  all fm, fm': fmemory/Memory, a: Addr, d: Data,
      am: amemory/Memory |
    fmemory/write (fm, fm', a, d)
    and alpha (fm, am) and alpha (fm', am')
      => amemory/write (am, am', a, d)
}
check writeOK
fig. 6.22 抽象函数与精化断言。
原书 fig. 6.22 有几处排印错误

照抄原文时要注意：initOK 里写成了 bm，而量词声明的是 fm；readOK 里多了一个右括号 alpha (fm, am))；writeOK 里用了 am'，但量词只声明了 am。这些都是书本身的笔误，不影响方法的正确性——修正后即可运行。

解读 · alpha 这一行怎么读

fm.data - (fm.unwritten -> Data)：先构造「所有未写过的地址 × 所有数据值」这个关系，再从 fm.data 中减掉它。结果就是「只保留被写过的地址的映射」——而这正好就是抽象内存的语义（未写过的地址不在映射里）。一个减号，就把「垃圾值」翻译成了「缺失」。

注意这里 alpha 被写成了谓词（两个参数）而不是函数（一个参数），原因见下方 Discussion。

6.4.6 Discussion

Q：定长内存为什么也需要抽象函数？它的状态难道不与抽象内存的状态相匹配吗？

缓存模型的状态显然与抽象模型的状态不同，因为它把内存分成了两个映射。但你可能想知道定长内存的状态是否不同：像抽象内存一样，它的状态只由一个叫做 data 的字段构成，把地址映射到数据值。答案是：仍然需要抽象函数，有两个理由。

第一，不同的 signature 代表不同的原子集合，即使它们的字段同名。能用同名字段是一种便利——一种 Alloy 自动消解的重载（overloading）。Alloy 不允许两个同名的不同 signature；尽管这两个都叫 Memory，但它们声明在不同的模块里，所以它们的全名是唯一的（abstractMemory/Memory 与 fixedSizeMemory/Memory）。

第二，即使我们改写模型，让定长内存与抽象内存共享同一个状态 signature，抽象函数仍然是需要的。考虑检验初始化谓词：抽象内存要求「地址/数据映射初始为空」，而定长内存要求它是「满的」！

本质

问题的实质是：即使两个状态空间的名字匹配、并且由同一组原子表示，一个状态在两个模型中也可以有不同的解释（interpretation）。

事实上，要用抽象内存的术语来解释定长内存的一个状态，我们需要区分「已被写入的地址」和「仍然持有初始化时任意值的地址」。这正是我们引入历史变量的原因。

即使没有历史变量，当两个状态空间的「解释」不同时，也需要一个抽象函数来在它们之间架桥。再举一个例子：拿一个算术实现去测试另一个「字节序不同」的实现——测试框架将需要施加转换，尽管两个实现都把一个整数表示为一个字节。

Q：为什么把抽象函数写成谓词而不是函数？

纯粹是为了示范一种不同的风格；它仍然是一个函数，尽管它是被隐式定义的。谓词形式或许更可取，因为它不使用集合理解式（set comprehension）。

反直觉的一点：fun 关键字并不保证它是抽象函数

你可能以为「把抽象函数定义成一个 Alloy fun（像 6.4.5 那样）」就能确保它真的是一个从具体状态到抽象状态的函数。不幸的是，这不是真的：

如果理解式的性质写得不好，单个具体状态可能会映射到一个含有多于一个抽象状态的集合。那样你仍然有一个「Alloy 关键字意义上的函数」（因为结果是一个抽象状态的集合），但你没有一个抽象函数，因为「状态到状态」的映射不是一一的。

解读 · 呼应 4.6「函数只是语法糖」

这正是第 4 章反复强调的那一点：Alloy 的 fun 返回的是一个「集合」，不是数学意义上的单值。所以要真正确保 alpha 是函数，必须靠模型里的其他 fact（这里是 Canonicalize），而不是靠关键字。

第 6 章小结

  1. 四个案例，四种不同的建模范式：分布式算法（领导者选举）、涉及环境行动者的需求（酒店门锁）、真实软件的特性交互（媒体资产管理）、经典形式化方法问题（内存抽象）。这一章的用意是说明 Alloy 不局限于「算法验证」。
  2. 「加一列 Time 使关系变成动态的」是全书最重要的建模 idiom。Time 列放在末尾，这样 r.t 就能取出「关系在时刻 t 的值」；放在中间则必须写 {p,q | p->t->q in r}。
  3. 拓扑静态、状态动态：succ 不带 Time 列（环是固定的），toSend/elected 带 Time 列。要支持动态拓扑，只需给 succ 也加上 Time 列，Ring fact 改成 all t, p | Process in p.^(succ.t)。
  4. 用「定义」代替「维护」可以消除框架条件：fact DefineElected 用集合理解式定义 elected，而不是在 init/step 中更新它，既实现了关注点分离，又避免了框架条件。
  5. 两种框架条件风格各有适用场景：传统式写「除 X 之外都不变」的等式，Reiter 式写「若 X 变了则必是这些操作」的蕴含。m 个组件、k 个操作、每个只改一个组件时 Reiter 大胜（m 条 vs k×(m−1) 条）；每个操作改掉几乎所有组件时传统式大胜。Reiter 式的额外好处是不需要任何逻辑之外的概念。
  6. 事件式建模的三大好处：可视化更好（事件是原子，每个快照一眼看出发生了什么）、性质表述更简洁、signature 扩展可共享公共部分（比谓词间共享更容易，因为它靠自由变量而非显式参数）。
  7. 活性性质要写成「公平性假设 ⇒ 结论」：progress() => some Elected.Time。直接写 some t | some elected.t 会得到「什么都没发生」的反例，因为 skip 允许每步都跳过。这类公平性过滤在 CTL 中不可表达。
  8. 拆分子性质分别检验：lone elected.Time（至多一个，且选举不换手）与 some elected.Time（至少一个）分开，更容易诊断问题。
  9. 机器直径给出迹长的完备性保证：pred looplessPath () {no disj t,t': Time | toSend.t = toSend.t'}，逐步加大 Time 作用域直到无解。3 节点环在 Time=12 时有解、13 时无解 ⇒ 就 Time 而言分析是完备的。
  10. 对称破缺会强制「精确作用域」，这既是帮助也是陷阱：它让 AtLeastOneElected 成为有效（最终性性质本来就不满足作用域单调性，精确作用域正是它需要的）；但它对 AtMostOneElected 不可取（短坏迹无法延长，而这种情形无法被检验）。用 sig RingProcess extends Process 可以让「至多 k 个进程的环」都被考察到。
  11. 需求存在于真实世界中，就必须为其他行动者写假设：fact NoIntervening 记录的不是代码，而是对世界的假设；假设为假，安全保证就失效。Michael Jackson 的「问题框架」理论正是为处理这类情形而生。实用结论：入住后第一次开门一定要用自己的钥匙。
  12. 没有单一性质能抓住设计的本质，但许多简单的合理性检查能暴露错误：媒体资产例子用两类断言——「操作保持不变式」与「代数性质（cut/paste 互逆）」。后者的失败揭示了三条微妙设计：选中项要么未定义要么非空、show 与 hide 其实都是「隐藏」、paste 用 buf - cs.assets 而不是整个 buf。
  13. 用「注释掉相等式」定位反例来源：把 sameApplicationState / sameCatalogState 中的某条相等式注释掉，若反例消失，则失败正是由该组件引起。
  14. 「可用性研究是检验假设的实验」——没有一个抽象干净的设计，你就没有假设。「你无法通过微调把一个不连贯的界面设计调成可用而优雅的，正如你无法通过测试把一堆面条代码测成一个健壮的代码库。」
  15. 精化的两种层次：同一状态空间内直接断言 concreteOp ⇒ abstractOp；跨状态空间则必须借助抽象函数：concreteOp(s,s') ⇒ abstractOp(alpha(s), alpha(s'))。这是 Hoare 的经典方案 [28]。
  16. 「符合」的衡量标准是迹包含：事件 = 操作名 + 输入输出值（前后状态不算，因为外部不可见）；具体机器的迹集是抽象机器迹集的子集。迹包含保证「不做坏事」，但不保证「做好事」——空迹集的机器符合任何抽象机器。补足这一点需要「可适用性」条件，而它在 Alloy 中不可检验（否定后产生无界全称量词，见 5.3）。
  17. 抽象函数方法是健全的但不完备。补全的两条路：泛化为抽象关系（Alloy 不可取，需无界全称量词），或用历史变量 / 预言变量增广具体模型（不改变可观察行为）。定长内存需要历史变量 unwritten，抽象函数写作 am.data = fm.data - (fm.unwritten -> Data)——一个减号把「垃圾值」翻译成「缺失」。
  18. 「内部操作不可观察」的形式化 = 抽象状态不变：load / flush 在抽象模型中没有对应物，因此断言 m = m'。这也解释了为什么抽象内存必须有 Canonicalize——否则内容相同的两个原子会让断言假失败。
  19. fun 关键字不保证「真的是函数」：Alloy 函数返回的是一个集合，若理解式写坏了，一个具体状态可能对应多个抽象状态。要确保单值，得靠别的 fact（如 Canonicalize）。抽象函数还必须是「全的」；全性在 Alloy 中不易检验（无界全称），但可以写成一眼可辨的形式并在 Analyzer 里运行它来验证一致性。若有不变式且各操作都保持它，抽象函数只需定义在满足不变式的状态上。
  20. 模块系统在这里承担了真正的架构职责：abstractMemory / cacheMemory / fixedSizeMemory 各自独立且被 Addr, Data 参数化，checkCache / checkFixedSize 是专门用来关联它们的第三方模块——模型与「关于模型的检查」分离。fixedSizeMemory_H 更用 extends memory/Memory 在原模型上做增广，示范了「不重写、只扩展」的复用方式。
