五家共同点

共性 · 这几条把「形式化建模」整体与编程语言区分开
  • 都提供比编程语言更简洁、更直接的记法来捕捉软件抽象。
  • 尽管语法语义各异，都把状态看作经典数学结构（集合、关系等）。
  • 都用约束以声明式方式描述行为。
  • 都存在轻量级工具：用具体案例求值约束；且每家都有新项目在大幅扩展其能力与适用范围。

差异与代价

维度原文结论
风格B 更偏操作式（operational）：其记法更像「抽象编程语言」而非规格语言。
语法OCL 的语法与其他几家截然不同，令人想起 Smalltalk。
状态机绑定B 与 VDM 把某种特定状态机观念写死在语言里，Z 与 OCL 也某种程度上如此；Alloy 则被设计成支持多种习语（idiom），每种习语表达起来的难易程度互不相同。
证明 vs 分析B、VDM、Z 更以「证明」为设计目标，因而由专用定理证明器支撑；Alloy 与 OCL 不是。
年代这些语言都早于 Alloy；Alloy 从中受益甚多，面向类似应用，但把重心放在自动分析上。
Alloy 的核心取舍：为分析而减法的语言

「Alloy 被削到只剩结构化建模的基本要素，并与它的分析工具手牵手发展。任何会妨碍分析的特性都被排除在外。」

后果是 Alloy 的分析比其余方法的轻量分析更强。原书列出三条机制级差异 —— 除 ProB 之外，其余工具基本上是「动画器（animator）」，只能在给定的测试案例上执行模型；而 Alloy Analyzer：

  1. 不要求用户提供初始条件与输入；
  2. 不把语言限制在可执行子集内；
  3. 覆盖作用域内的整个空间，因而更擅长揪出隐蔽的 bug。

而且「分析」这个想法被内建进语言本身：断言可作为规格的一部分记录，界定分析的作用域只出现在命令里；其余方法靠的是工具专属的语言扩展。

「小而简」换来了什么

原文的第二个设计目标是异常地小和简单：概念数少于其他语言，且某些方面更灵活。四个例子：（1）一切数据结构统一在「关系」这一个概念之下；（2）同一个关系连接同时用于索引、解引用结构和应用函数；（3）signature 能模拟 Z 的 schema 和 OCL 的 class；（4）assertion 能表达不变式保持、精化和基于轨迹的时序性质。

Alloy 明确承认的短板（务必读，选型时最要紧）

「这些好处当然有代价。Alloy 的表达力不如其他语言。」

  • Alloy 的结构严格是一阶的；而 B、VDM、Z 都支持高阶结构与高阶量化。
  • 原文举 Carroll Morgan 著名的电话交换局规格 [54] 为例：它把「通话连接」表示成端点集合的集合（set of sets of endpoints）。这种结构在 Alloy 中无法直接表示，只能把连接建模为「端点之间的关系」或「连接原子集合，每个映到它的端点」。
  • 更狠的是：Morgan 用一个高阶公式约束「连接结构必须极大（maximal）」来刻画交换机行为的那个巧妙做法，在 Alloy 中根本无法表达。
  • 还有一个「更显著但不那么根本」的缺陷：Alloy 对序列和整数的支持相对薄弱（呼应第 5.3 节与附录 B.7.7 的 Int 简陋）。

E.1An Example · 基准例题：可重编码的酒店门锁

为什么用这一道题

用一个酒店门锁（recodable hotel-door lock）方案贯穿全部五种方法 —— 「类似于但比第 6 章那个方案更简单」。建模与分析的目的是判断该方案能否有效阻止未授权进入。

对每家方法：由该领域的专家亲手建模，配一张「状态声明」+ 一张「操作」+ 一段工具说明。因为篇幅限制，收录不全：原文特别交代，Gogolla 还写了第二个 OCL 模型，证明 OCL 也能容纳 Alloy 规格里的「时间instant」习语（而不只是标准 pre/post 习语），并构造了一个 ASSL 过程来自动生成测试案例；Woodcock 则用 Z/Eves 证明了所有操作的前条件定理，并证明了 NoIntruder 断言 —— 这两项工作没能进书。

图 E.1 · Alloy 版：状态空间声明与初始化

module hotel
open util/ordering [Time]

sig Key, Time {}

sig Card {
  fst, snd: Key
}

sig Room {
  key: Key one->Time
}

one sig Desk {
  issued: Key->Time,
  prev: (Room->lone Key)->Time
}

sig Guest {
  cards: Card->Time
}

pred init (t: Time) {
  Desk.prev.t = key.t
  no issued.t and no cards.t
}
行 5：每张门卡上刻有两个密钥（fst、snd）
这些刻印是固定的，不随时间改变 —— 所以 Card 的两个字段没有 Time 列。这正是「卡是物理物件」的建模表达。
行 8 / 11 / 12 / 15：其余部件都是随时变化的
判据就是声明里有没有 Time 列：房间当前的钥匙（8）、前台「迄今已发出哪些钥匙」的记录（11）、前台「上一次 checkin 中哪个房间发的是哪把钥匙」的记录（12）、每位客人手上持有的卡集合（15）。
行 12 的三层结构
(Room -> lone Key) -> Time：外层再套一个 Time 列，使「房间→至多一把钥匙」这个关系本身随时间变化 —— 这就是全书反复使用的「把关系变成关系的时间序列」手法（附录 B.7.3 的嵌套标注在此派上用场）。
初始化（18、19）
前台「房间→钥匙」的记录与锁里当前的钥匙一致（18）；没有发出过任何钥匙，也没有客人持有卡（19）。

图 E.2 · Alloy 版：操作、轨迹与断言

pred checkin (t, t': Time, r: Room, g: Guest) {
  some c: Card {
    c.fst = r.(Desk.prev.t)
    c.snd not in Desk.issued.t
    cards.t' = cards.t + g->c
    Desk.issued.t' = Desk.issued.t + c.snd
    Desk.prev.t' = Desk.prev.t ++ r->c.snd
  }
  key.t = key.t'
}

pred enter (t, t': Time, r: Room, g: Guest) {
  some c: g.cards.t |
    let k = r.key.t {
      c.snd = k and key.t' = key.t
      or c.fst = k and key.t' = key.t ++ r->c.snd
    }
  issued.t = issued.t' and prev.t = prev.t'
  cards.t = cards.t'
}

fact Traces {
  init (first())
  all t: Time - last() |
    some g: Guest, r: Room |
      checkin (t, next(t), r, g) or enter (t, next(t), r, g)
}

assert NoIntruder {
  no t1: Time, disj g, g': Guest, r: Room |
    let t2 = next(t1), t3 = next(t2), t4 = next(t3) {
      enter (t1, t2, r, g)
      enter (t2, t3, r, g')
      enter (t3, t4, r, g)
    }
}

check NoIntruder for 3 but 6 Time, 1 Room, 2 Guest
checkin 的语义（行 1–10）
客人在前台办理某房间的入住 ⇒ 给他一张卡：该卡的第一把钥匙 = 该房间上一次发出的那把钥匙（3）；第二把钥匙是全新的（4，未出现在已发出集合中）。前台记录相应更新（6、7）。锁里的钥匙不发生任何变化（9）。
enter 的语义（行 11–19）
只要客人手上有一张卡（12），其第一或第二把钥匙与房间锁当前钥匙相符，即可进入。若是第二把钥匙相符，锁的钥匙保持不变（14）；若是第一把相符，锁就用第二把钥匙重编码（15）。前台记录（17）与客人所持卡集合（18）都不变。
为什么没有 checkout
「为缩短示例，没有给出退房操作。新客人使用钥匙应当使先前发出的钥匙失效，因此每当一位客人办理入住，上一位住客就被隐式退房了。」
Traces（行 20–25）
引入内建 util/ordering [Time]（图 E.1 行 2）就得到 Time 上的全序；Traces 用这个序把「初始化成立于首状态」与「除末状态外，每个状态与其后继之间必是 checkin 或 enter」钉住 —— 这就是第 5 章的「轨迹习语」。
NoIntruder（行 26–33）
断言：同一房间上不可能连续发生三次进入，其中间那次由一位客人执行、第一次和第三次由另一位客人执行。换句话说，两位客人不能同时使用同一个房间。注意 disj g, g' 与 let 三个后继时刻的写法。
原文特意为「还没读完全书的人」写了四条注解
  • signature 引入一个集合，以及若干以该集合为第一列的关系。例：sig Card 引入门卡集合 Card 与两个从 Card 到 Key 的关系 fst、snd。
  • 关系上的重数有时是隐含的，有时用关键字显式写出。fst、snd 就是隐含地把一张 Card 映到一把 Key；key: Key one->Time 则显式声明「对给定房间，每个 Time 时刻对应一个 Key」。lone 意为「至多一」（可读作「小于等于一」），所以 prev 的声明说的是：给定 Desk、给定 Time，每个 Room 至多关联一把 Key。
  • 点算子就是关系连接。标量在语义上被当作单元集，集合被当作一元关系。故 cards.t 是在时刻 t 把 Guest 关联到 Card 的关系，c.fst 是卡 c 的第一把钥匙，r.key.t 是房间 r 在时刻 t 的当前钥匙。
  • -> 是笛卡积（在操作里用来构成元组），+ 是并，- 是差，++ 是关系覆盖（override）。

第一次分析：2 秒出反例，六个状态的轨迹

check 命令的真实语义

「命令指示分析器考虑所有涉及 3 张卡、3 把钥匙、6 个时刻、1 个房间、2 位客人的轨迹。」注意 for 3 but 6 Time, 1 Room, 2 Guest 的读法：3 是每个顶层 sig 的默认上界，but 之后覆盖其中三个（附录 B.7.5）。

执行在 2 秒内（在一台 PowerMac G5 上）产生一个反例轨迹，其步骤如下（图 E.3 是可视化器输出：每个面板对应一个状态；执行从左上角开始，先读完左页到底部，再接右页顶部）。

  1. 初始：Room0 的锁里是 Key0，前台也把该房间关联到这把钥匙，但没有任何「已发出钥匙」的记录。房间里带标签 NoIntruder_r —— 它就是断言中被量化变量 r 充当时，将见证这次违反。
  2. 第二状态（一次 checkin 之后）：Guest0 拿到一张卡，其第一、第二把钥匙分别是 Key0 与 Key1；前台把 Key0 记为已发出。该客人被标为 NoIntruder_g（扮演断言里的 g）。
  3. 第三状态（又一次 checkin）：第二位客人 Guest1 拿到一张卡，第一、第二把钥匙分别是 Key1 与 Key0 —— 与 Guest0 的卡是同样两把钥匙，只是次序相反；前台把 Key1 记为已发出。这位客人被标为 NoIntruder_g'，即扮演 g' 的入侵者。
  4. 第四状态：第一次进入发生（Guest0），房间钥匙被改成 Key1。
  5. 第五状态：第二次、也就是非法的进入发生（Guest1），房间钥匙被改回 Key0。
  6. 第六（末）状态：第三次进入发生（又是 Guest0），房间钥匙被改回 Key1。
第 1 号缺陷在初始化里，而不在操作里 
pred init (t: Time) {
  Desk.prev.t = key.t
  Desk.issued.t = Room.key.t and no cards.t
}

「错在初始条件。因为 Room0 的初始钥匙 Key0 没有被记为已发出，它就有可能被发出两次，从而搭起这个循环。锁里已有的那些钥匙本应在初始时就被记为已发出。」

这条修复极有代表性：反例的成因往往不在「哪一步做错了」，而在「初始世界少了一条约束」。改完后再跑，分析器穷尽整个空间都找不到反例。

也就是说：轻量分析与形式证明不是 rival 而是接力棒 —— 作用域爬升到「足够可信但仍非证明」的那一点，正是把断言交给定理证明器的交接点。这与第 5.3 节「Alloy 无界全域问题难以证明」相呼应。

E.2B

来历：B 由 Jean-Raymond Abrial 设计 —— 他正是 Z 的最早贡献者之一。B 包含一门语言（AMN）和一套方法：通过逐步精化（stepwise refinement）从抽象模型得到实现。从一台极抽象的机器出发，一层层加细节，直到得到一台可直接翻译成代码的机器。若每一步精化都有效，则最终代码被保证满足顶层规格。

定位：主要面向关键系统（critical systems）的开发，已有若干工业项目。迄今最著名的应用是巴黎地铁的制动系统。

文献：标准参考是 Abrial 的书 [1]；另有入门教材 [61, 76, 46] 与案例集 [62]。

E.2.1 B 的建模概念

一句话抓住 B 的取向

B 的规格语言叫 AMN（Abstract Machine Notation），它的名字就暴露了它的焦点：系统被（与 VDM、Z 一样）看作一台带有作用于全局状态之上的操作的机器。

一个 B 模型由五部分组成
一串集合声明（相当于 Alloy 的 signature、Z 的 given set）；状态成分（称为「变量 variables」）的声明；一个状态上的不变式；一个初始化条件；一组操作。
状态结构与类型检查
状态成分用集合与关系构造（同 Z）；与 Alloy 不同，允许高阶结构。AMN 不把类型约束与更具表达力的其他不变式分开，因此类型检查带有一种启发式（heuristic）味道。
后条件是替换，不是公式（B 最独特之处）
像 VDM 一样，操作的前条件是显式的。但与其余所有方法都不同：后条件不是一段逻辑公式，而是一组「替换（substitution）」。替换类似赋值语句，可以改变某个状态变量的整体值，也可以在某一点上更新一个关系的值。要部分地约束某状态变量，可以给它赋一个从「由公式刻画的那个集合」中取出的任意值。
为什么这样设计（四条理由 + 两条代价）
理由：① 使定理证明更容易 —— 在语法上操纵操作时，后条件可被按字面当作替换来处理；② 更操作式的风格对程序员更熟悉；③ 它把非确定性的存在表达得更明白；④ 因其编程式风格，更容易直接转换成命令式程序。
代价：与其他语言相比灵活性更差，对增量式建模的支持更弱 —— 你必须为每一个状态变量都给出一个替换；而在 Alloy 里，即便只为部分状态成分写了约束，也能模拟出一个操作。

E.2.2 B 版样例模型（图 E.4–E.6）

B 版走了「先抽象、后精化」这条 Alloy 版没有的路线

B 的酒店门锁模型跨三张图：图 E.4 是顶层抽象机器，图 E.5/E.6 是一个精化。抽象模型只有一个状态成分 —— 房间占用名册（alloc），由 Checkin 更新、并守卫（guard）Enter。名册决定谁能进，钥匙与锁根本还没出现。这与后文 Z 的第一版模型（E.12–E.14）策略完全一致，也正是 Alloy 版没走的路。

图 E.4 · 最抽象的 B 机器

MACHINE hotel1
SETS

 ROOM  = {r1,r2}

INVARIANT
 alloc : ROOM +-> GUEST
INITIALISATION alloc := {}

 THEN skip

读这张图的四个要点

  • +-> 表示偏函数。原文提醒：B 与 Z 用「一组特殊箭头」来代替 Alloy 与 OCL 的重数标注 —— 这是两套记法传统的第一处正面冲突。
  • precondition ≠ guard。B 区分二者：在 guard 为 false 的状态里调用操作会「阻塞（blocks）」；而前条件说的是「不该在前条件不成立时调用；若真调用了，任何结果都可能」。Enter 的前条件只要求参数是一位客人和一个房间；guard 才要求「该客人在这间房的名册里」。
  • 基本集合被赋予具体值（g1,g2 / r1,r2）是为了给 ProB 的分析定界。原文：「这和 Alloy 的作用域声明一模一样，只不过它是全局设定的，而不是逐命令设定的。」
  • skip 表示「什么都不改」 —— 与 Alloy 中「未提及即不受约束、要表达不变必须显式写等式」形成对照。

「精化」本身就是一条待工具检验的断言
原文：「图 E.5 与 E.6 中的精化模型具有完全相同的结构。『这个模型 hotel2 精化了更抽象的那个 hotel1』这一论断，是一条要由工具来检验的断言。」 —— Alloy 语言里没有对应的内建概念（Alloy 表达「精化」要靠 assertion 手工编码）。
POW(e) 与冒号的读法（B 的高阶性在此现形）
POW(e) 是 e 的幂集（从 e 取元素构成的「集合的集合」）；每个声明里的冒号表示集合成员关系。所以 key: POW(KEY) 等价于 Alloy 的 key: set Key —— 原文紧接着补那记关键限定：「即便 B 里的这个右端表达式是高阶的，而 Alloy 里的不是。」
>-> 与 ->
分别表示单射函数与全函数。
行 13 是不变式而非声明，但顺序仍然要紧
!c.(c: cArd => ckey1(c) /= ckey2(c))：一张卡的两把钥匙必须不同。把它放进不变式意味着「期望各操作保持它」。原文点出一个极实用的怪癖：语义上这条不变式与它前面的 ckey1/ckey2 声明毫无区别，但类型检查会区分二者 —— 若把顺序颠倒（不变式放在声明之前），类型检查会失败。
为什么把 ckey1/ckey2 声明成变量而非常量
声明为状态变量 ⇒ 就可以定义一个「改变卡上钥匙」的操作；若像 Alloy、OCL、VDM 三个版本那样声明为常量，就排除了这种可能。这是刻意的建模分歧，不是笔误 —— 它正是「卡会不会被黑客改写」这一攻击面在不同语言里的不同暴露方式。
初始化示范了非确定性
ANY 子句把「任意一把钥匙集合」绑给 ks、「任意一个从房间到钥匙的函数」绑给 f；f 声明里的那个箭头使它是单射的，保证没有一把钥匙被指派给两个房间。子句体把 ks 赋给 key、把 f 赋给 lock 和 prev。
与 Alloy 的精确等价
原文特意对齐：「注意：把非确定选出的 f 同时赋给这两个变量，其效果等同于 Alloy 模型里的那条等式 Desk.prev.t = key.t」 —— 都表示「无论它是什么，前台的房间—钥匙记录必须与实际锁里的钥匙相符」。
Enter 被拆成两个操作
精化模型里 Entry 被拆成两个操作。注意此处原书正文与代码的标注相互对调，须留意：正文写「Enter1 对应正常情形，Enter2 对应锁被重编码的情形」，而图 E.6 的代码恰恰相反 —— Enter1 的条件是 ckey1(c) = lock(r) 且执行 lock(r) := ckey2(c)（这才是重编码），Enter2 的条件是 ckey2(c) = lock(r) 且执行 skip（这才是正常进入）。本页按代码语义注释。与 Alloy 版 enter 里那个 or 的两个分支一一对应。原文另说：「在其他方法里这用析取表达；在 B 里也可以用非确定性选择算子达到同样效果。」

E.2.3 B 的工具

两个商业工具 + 一个「异类」ProB

Atelier B（来自 Steria）与 B-Toolkit（来自 B-Core）：都聚焦定理证明与代码生成，同时也提供一个用于轻量分析的动画器。

ProB [49] 是一个非常不同的工具：它提供的功能与 Alloy Analyzer 极为相似；在与这些「其他方法」相关联的全部工具当中，它是唯一能完全自动生成断言反例的工具。

ProB 的细节原文与解读
B 没有「定义任意断言」的设施因此 ProB 聚焦于检验由不变式与精化声明所生成出的证明义务。即：ProB 能反例化，但可检查的命题集合是语言替你先定好的（不变式保持、精化成立），不像 Alloy 能对任意谓词写 check。
精化沿轨迹检验，而非归纳检验「精化是在轨迹上（over traces）被检验的，而不是在操作上作归纳式检验的，因此用户无需去找一个归纳不变式。」这是 ProB 相对证明器路线最实在的减负。
跨方言精化ProB 还能检验「一个 B 模型」与「一段用 CSP 进程代数写成的更抽象描述」之间的精化关系。
B 与 Alloy 的五处正面碰撞（本页归纳）
  1. 后条件：替换 vs 公式。B 的后条件是「一组赋值」，Alloy 的 pred 体是逻辑公式 ⇒ Alloy 可以只约束一部分状态成分，B 必须逐变量给替换。
  2. 重数记法：特殊箭头 vs 关键字。B 用 +->（偏函数）、>->（单射）、->（全函数）；Alloy 用 lone/one/some + 箭头组合。箭头族更易读但组合能力弱：Alloy 的 X one->one Y（双射）在 B 里要用两个记号叠加。
  3. 作用域：全局 vs 逐命令。B 靠给基本集合列举具体元素来定界，一次设定全局生效；Alloy 的 for 3 but 6 Time 每条命令独立。后者可直接对同一模型问不同规模的问题。
  4. 非确定性：ANY…WHERE vs some c: Card {…}。结构完全同构：都是「存在一个满足条件的值，用它来构造结果」。
  5. 精化：内建 vs 自理。B 有 REFINES + 证明义务；Alloy 只能靠 assertion 自行编码不变式保持。

E.3OCL

来历：OCL（Object Constraint Language）是 UML 的约束语言，由 Jos Warmer 与 Anneke Klepper 在 Steve Cook 与 John Daniels 的 Syntropy 语言 [10] 以及 IBM 的建模工作之上开发。他们的书 [73] 提供了易读的概览。作为 UML 的一部分，OCL 是 OMG 标准；最新规格可在线获取 [53]。

一段耐人寻味的历史：OCL 早期设计对精确语义的重视不如其他方法。许多研究者（尤其是 Precise UML Group）致力于为它建立形式语义，但因为语言已经标准化，为时已晚，无法再消除它的复杂性。所以 —— 原文的讽刺句 —— 「尽管 OCL 是怀着『要比 VDM 和 Z 更简单』的期望设计的，它最终反而更复杂了。」

本书用的是哪个变体：由 Mark Richters 与 Martin Gogolla 设计的一个 OCL 变体 [59, 58] —— 它有形式语义、有支持子类型的类型系统，并配有一个强大的动画与测试工具 USE。

一个标准带来的尴尬：OCL 被纳入 UML 标准时，被视作「UML 类图上的注释语言」，因此没有为自己的声明部分配备文本记法。按标准，一个 OCL 模型必须附上一张 UML 图来声明类与关系 —— 「一个不便，对小模型尤其如此」。USE 变体补上了文本声明记法，从而解决了这个问题（下文图 E.7 用的就是它）。

E.3.1 OCL 的基本概念

模型构成
一个状态空间描述（由类、属性、关联给出）+ 若干不变式 + 一组操作。和 VDM 一样，操作分离前条件与后条件，并隐式包含不变式。
但 OCL 也能「打包任意谓词」
这一点上它与 Alloy 更为相近；原文断言：「Alloy 模型所用的那套显式时刻（time instant）习语，可以相当容易地搬进 OCL。」（这也解释了开头提到的 Gogolla 第二模型。）
最关键的一处语义分歧：to-many 是「到集合的函数」，不是平坦关系
与 Alloy 一样，OCL 也用集合与关系来建模状态。然而出人意料的是：一个「某物对多个」的关系 —— 即把一个原子映射到不止一个原子 —— 在语义上不被当作平坦关系，而被当作「到集合的函数」，其结果是一种更接近 VDM 而非 Alloy 或 Z 的模型风格。
由此引出的方向性：关联不能被反向遍历
「这给了 OCL 的关系一种强烈的方向性；它们无法被反向遍历。」因此一个关联不是作为单一关系被访问，而是作为从它派生出来的一对「角色（roles）」，每个方向一个，供导航之用。
重数进入类型（这是 OCL 与 Alloy 的第二大分歧）
角色的重数是其类型的一部分。导航就是函数应用，依重数不同而返回集合或标量 —— 与之相对，Alloy 中导航是关系映像（relational image），永远返回集合。原文给出三面评价：
  • 优点：类型检查器能揪出「某次导航假定的重数与声明不符」这类错误。
  • 缺点 1：重数与「说出同一件事的显式约束」行为不同。
  • 缺点 2：改变一个角色的重数就改变了它的类型，可能要求在它被使用处做补偿性修改。
  • 缺点 3：需要在集合与标量之间做转换。
没有传递闭包，于是引入递归 ⇒ 后果严重
OCL 没有传递闭包算子。为允许多步穿越一个关系，它允许把谓词和函数定义为递归的。这带来有用的表达力，但有代价：谓词不再有简单的逻辑解释，而需要「最小不动点语义」。结果：OCL 工具无法采用 Alloy Analyzer 或 ProB 那种约束求解器，因为那会产生对应于「非极小解」的伪案例（spurious cases）。
OCL 与其他方法的两处根本不同
  1. 语法风格：OCL 以 Smalltalk 的方式层层堆叠变量绑定，并把运算符的第一个参数当作特殊地位处理。相应地，它有一个「上下文（context）」概念 —— 在这个上下文里，对「某个类的原型成员（archetypal member）」的引用是隐含的。（下文 self 即由此而来。）
  2. 类 ≠ 该类的对象集合：像面向对象编程语言一样，OCL 区分二者。这使得反射（reflection）成为可能，对元建模很有用，但也让语言变复杂了。
一个被低估的架构差异：基本数据类型放在哪里

OCL 的底层数据类型定义在库模块里，扮演 Z 的「数学工具包（mathematical toolkit）」类似的角色；而在 Alloy、B、VDM 中，基本类型是内建在语言里的。

「这个决定对类型系统有一些微妙影响。例如，与 Alloy 的类型检查器不同，OCL 的类型检查器无法利用集合与关系算子的含义，只能依赖它们声明的类型。」

这条正好和附录 B.6 的表述对上：Alloy 的类型检查是关系性地推理的（知道 ~r 的域是 r 的值域），而 OCL 只能语法性地查表。

OCL 的表达力天花板：表达式不能表示关系

「一个表达式的值必须属于某种库类型。由于关系不在其中，这意味着：与其他语言不同，表达式不能表示一个关系。」

原文随即给出公允评价：「这并不降低语言的表达力，因为允许任意量化；但它确实使某些约束更啰嗦。」

对照 Alloy：「一切皆关系」让「表达式与约束共用一套代数」；OCL 把关系排除在值域之外，代价是无法把关系当作一等公民传递、命名或组合 —— 这正是 Alloy 在导言里自夸的第一条统一性。

为什么要额外造一个 Desk 类
「类 Desk 的引入是为了给『代表已发出钥匙集合的那个状态成分』提供一个上下文。」和 Alloy 版一样只有一台前台，这个约束被记为不变式 oneDesk。
Desk.allInstances 与那条「非法写法」
原文警告：写 Desk->size=1 是非法的，因为 Desk 表示一个类而不是一个集合 —— 必须用 Desk.allInstances 取「该类的那些实例的集合」。这条就是上面「类 ≠ 对象集合」之区别的直接落地。
关联是关系，可以有任何元数 —— 用「角色个数」表示
「一个关联是一个关系，它可以有任何元数，由角色的数目表明：fst 和 snd 有两个角色，因此是二元的；而 prev 是三元的。」
命名约定 c4a
本模型遵循：关联 a 中指向类 c 实例的那个角色，命名为 c4a。所以 key4prev 就是「prev 关联里指向 Key 的那个角色」。
三元关联的角色到底表示什么（最容易读错的一条）
二元关联的两个角色互为转置的二元关系。但三元关系中，一个角色表示「一对二元关系」—— 每个可能的导航源一个（因为涉及另外两个类）；一般地，有 k 个角色的关联，每个角色表示 k−1 个不同的二元关系，具体哪一个由上下文选定。
原文给的例子
给定一台前台 d，d.key4prev 表示「d 作为某些房间的前钥匙而持有的那些钥匙的集合」；同样 d.room4prev 表示「在 d 处有前钥匙与之关联的那些房间的集合」。
角色的表达力不足，以及 OCL 的补救办法
「角色只提供了高阶关系的一个简化视图，并不完全具有表达力。」例：若有多台前台，就写不出 Alloy 的 d.prev[r]（在某台前台处、某个房间的前钥匙）。所幸本模型只有一台前台，问题没暴露。当 OCL 真的需要一个高阶关系时，必须改用另一套做法：把该关系显式表示为「元组的集合」 —— 原文指向 Richters 论文 [58] 第 4.9.2 节。
操作声明在 Room 上下文中 ⇒ 隐式 self，且可省略
这让每个操作都带一个可用 self 引用的隐式参数；与 Alloy 的 this 不同，它可以被省略：第 5 行的 self.key4prev 可写作 key4prev。而 Alloy 里没有这种简写，因为裸写 key4prev 表示的是整个关系。
前后条件可拆成「有名字的子句」
「以便工具在检查一个测试案例违反模型时，能反馈究竟是哪一条子句被违反。」这是 OCL 面向「测试案例校验」而非「求解」取向的语法体现 —— 对照 Alloy：check 给的是反例轨迹，而不是「第几条 post 挂了」。
@pre 标记
后条件中，引用前状态值的角色和属性加后缀 @pre。例：g.card4cards = g.card4cards@pre->including(c) 说的是「后状态里该客人的卡集合 = 前状态那个集合加上卡 c」。Alloy 用两列 t / t' 达到同一效果，OCL 用 @pre —— 因为它把状态机写死了。
全附录最烧脑的一则辨析：为什么 Set{c.key4snd} 的 Set 并非多余 
self.key4prev = Set{c.key4snd}   // checkin 后条件（图 E.8 行 20）

Set 关键字把元素 c.key4snd 提升为一个集合。「你可能以为这里不必用它，因为角色 key4prev 与 key4snd 的重数分别是 [0..1] 和 [1]，类型上是兼容的。」

但原文紧接着给出正确的道理：「对于一个三元关系，角色 r 的重数并不表示 x.r 可能表示的那个集合的大小；它表示的是与「其他那些类型的实例的某种组合」相关联的该类型实例有多少个。」

结论：若存在多台前台，self.key4prev 尽管有那个重数，仍可能包含多把钥匙；因此任何与它作等式的值必须是集合而非标量。

这条对读 Alloy 同样关键，因为它正是附录 B.7.3 嵌套标注所解决的问题的镜像：多层箭头上的重数描述的是「对每个已定的其他坐标」的像的大小，而不是任意切片视图的基数。把 prev 的前导坐标（Desk）当成「固定的那一个」，是这类误读的根源。

E.3.3 OCL 的工具

两类工具，功能差别像两个时代

常规类：不少工具可用。有些是独立工具，如 Octopus（来自 Anneke Kleppe 创办的 Klasse Objecten 公司）；有些是更大的模型驱动开发套件里的组件，如 Borland Together Designer 的 OCL 组件。典型功能：语法与类型检查、在具体测试案例上解释（interpret）OCL 约束、从 OCL 表达式生成 Java/SQL 等代码。

设计期分析类：支持设计期分析的工具较少；这一类中最强的似乎是不来梅大学的 USE 工具 [71]。它提供一个环境，让建模者亲手构造测试案例并在其上求值 OCL 表达式与约束。

USE 的新能力：最近加入了一个「用用户提供的生成器枚举快照（snapshots）」的设施 [18]，「它允许在有限案例空间上作 Alloy 风格的穷尽搜索」。其界面把 OCL 与 UML 图形对象模型整合，支持声明的可视化编辑、快照与执行的图形展示。

最有说服力的一句

「借助 USE 工具，Martin Gogolla 得以模拟场景并发现了缺陷 —— 包括 Alloy 模型第一版中的那个初始化错误。」

也就是说：本节 E.1 里那个「Key0 未记为已发出」的漏洞，不是只有 Alloy 能发现 —— 一个基于生成器的快照枚举器同样抓到了它。这把导言里「其他方法基本只能做动画」的论断补上了一个诚实的例外，也印证了「穷尽有限空间」这一思想的普适性。

E.4VDM

名字来历：VDM 代表 Vienna Development Method（维也纳开发方法），因为它生长于 1970 年代 IBM 维也纳实验室在编程语言定义方面的工作。该方法由 Cliff Jones 与 Dines Bjørner 发展，包含一门规格语言 + 一套把规格精化成代码的路子。

历史地位：「逻辑式规格（logic-based specification）的许多基本原理与想法，最早就是出现在 VDM 里。」

今天的所指与标准：如今「VDM」通常指那门语言，经典参考是 Jones 的书 [41]。最新版本 VDM-SL（VDM Specification Language）由 ISO 在 1990 年代标准化 [47]；它有两套语法：一套基于 ASCII（多数 VDM 工具用它），一套使用特殊数学符号。

工业应用：电子交易系统、安全智能卡，以及荷兰花卉拍卖系统。

教材：两本讲 VDM 建模过程的书：[16] 用标准语言 VDM-SL，[17] 用带面向对象特性与并发支持的扩展 VDM++；两本都含案例研究，都强调用轻量级工具技术促进工程师与领域专家之间的对话。Jones 的一篇论文讨论 VDM 的设计原理 [42]。

E.4.1 VDM 的基本概念

状态机 + 可实现性检查
一个 VDM 规格描述一台状态机：一组状态 + 一组操作。状态由一个顶层声明给出，并可用辅助声明引入它使用的任何复合类型；每个声明都可配一个不变式。
「implementable（可实现）」这条独特规则
操作有分离的前/后条件。每个操作都必须可实现：对每个满足前条件的前状态，其后条件至少容许一个后状态。若操作以显式风格（postcondition 由「对后状态各成分的赋值」构成）书写，则它「by construction」自动可实现。
不变式与 Alloy 相同地隐式并入
「不变式，如 Alloy、OCL、Z 中一样，被隐含地包含进前条件与后条件之中。显式操作必须保持不变式。」
操作引用（operation quotation）↔ Alloy 的一对谓词
一个操作的前后条件可以被另一个操作使用，机制叫操作引用，它「把该操作几乎当作一对 Alloy 谓词来对待」。
验证猜想 = Alloy 的断言，但不在语言里
「验证猜想（validation conjectures）扮演着 Alloy 断言的角色，但它们是用工具专属的语言扩展来表达的，而不是用 VDM 语言本身。」—— 这条与导言「其他方法使用工具专属扩展，而 Alloy 把分析内建进语言」严格呼应。
VDM 最独特的设施：帧条件（frame conditions）
「与 Alloy、B、OCL、Z 都相反（也和 JML [48]、Larch 接口语言 [23] 这类更侧重描述代码接口的语言相同），VDM 有帧条件，标明某操作可以读或写哪些状态变量。」
  • 好处：让操作大幅简短（不必提及不变化的成分），也许更容易一眼读懂。
  • 坏处：帧条件假定了一种比 Alloy、Z 之类语言所容许的更受限的规格形式 —— 「你不能往状态里加一些由其他成分定义的冗余成分，而不必修改所有操作。」
帧条件那条坏处值得展开：它直接封死了 Alloy 的核心手法

Alloy 里「冗余成分」是常规武器：第 6.4 的 inv 不变式把「所有有效 Inv」打包成一个字段供断言引用；A.5.1 的 bijection、第 6.2 的 Room <: keys 都是「由别的成分定义的派生成分」。它们的存在只是为了让断言更好写，而每个操作都必须去「维护」它们 —— 在 VDM 的帧条件下这是不可接受的。

这就是「声明式规格（Alloy/Z）vs 接口式规格（VDM/JML/Larch）」的分水岭：前者说「世界应当是什么样」，后者说「这个操作有权碰哪些格子」。

types

end

图 E.10 · VDM 操作（隐式风格）

operations
 CheckIn(g:Guest,r:Room)
  ext wr desk : Desk
     wr guests : map Guest to set of Card
  pre r in set dom desk.prev
  post exists new_k:Key &
    new_k not in set desk~.issued and
    let new_c = mk_Card(desk~.prev(r),new_k) in
     desk.issued = desk~.issued union {new_k} and
     desk.prev = desk~.prev ++ {r |-> new_k} and
     if g in set dom guests
      then guests = guests~ ++ {g |-> guests~(g) union {new_c}}
      else guests = guests~ munion {g |-> {new_c}};

 Enter(r:Room,g:Guest)
  ext wr locks : map Room to Key
     rd guests : map Guest to set of Card
  pre r in set dom locks and g in set dom guests and
    exists c in set guests(g) &
      c.fst = locks(r) or c.snd = locks(r)
  post exists c in set guests(g) &
    c.fst = locks(r) and
      locks = locks~ ++ {r |-> c.snd} or
    c.snd = locks(r) and locks = locks~;

CheckInExpl(g,r) ==

token 类型 = Alloy 的无字段 sig
类型声明以 Key、Room、Guest 三个 token 类型开篇，意即「表示无解释原子的集合」—— 对应 Alloy 的 sig Key, Room, Guest {}。而 Card 和 Desk 被声明为记录（record）类型；对应全局状态的 Hotel 也是记录类型。
类型不变式 ↔ Alloy 的字段约束
Desk 的不变式（行 11）说的是：「有前钥匙的那些房间的集合，是已发出钥匙所属房间集合的子集」（rng d.prev subset d.issued）。各类型都可后跟一个不变式。
记录类型：一条好处与两条代价
Alloy 相反，没有复合类型（除了关系）。用记录的好处：可以用构造器造出一个新值（如行 8 的 mk_Card(...)），而 Alloy 需要一个集合概括式或存在量词（如 Alloy 版 checkin 里 some c: Card {…}）。代价：
  • 额外的记法：「注意 VDM 里 c.fst 用点，而 locks(r) 用括号」—— 同一件事两套存取语法。
  • 给分析制造问题（下条）。
「记录没有独立于其值的身份」⇒ 无界全域问题（这是本附录与第 5 章最重要的一次勾连）
原文：「记录常能在 Alloy 里用 signature 表示，但缺少构造器这一点，正是 5.3 节所述『无界全域问题（unbounded universals problem）』的核心所在。」紧接着：「一个记录没有区别于其值的身份，因此这个 VDM 模型不会区分由不同客人持有、却恰好带有相同两把钥匙的两张卡。」
VDM 的高阶性在状态不变式里现形（行 16–19）
那条 dunion {{c.fst, c.snd} | c in set dunion rng h.guests} subset h.desk.issued 说的是「客人们所持卡上的第一、第二把钥匙都必须已被前台记录为发出」。因为 h.guests 是「客人 → 卡的集合」的函数，它的值域 rng h.guests 是集合的集合，必须先取一次分布并（dunion）摊平，才能判断卡 c 是否属于。
同一条件的 Alloy 写法（原文逐字对照）
all t: Time | Guest.cards.t.(fst + snd) in Desk.issued.t —— 「在 Alloy 里，集合的集合是不可表达的」，于是把高阶摊平换成一条沿 Time 的量化。
时间变量与状态变量的角色互换
「时间变量 t 扮演着 VDM 规格里状态变量 h 的角色。它的位置是所选习语的产物 —— 若把状态建模成一个 signature（如第 6 章的内存例子或媒体资产例子），它就会出现在字段名之前而不是之后。」
帧条件如何缩短后条件
「注意帧条件如何缩短其所属的后条件：在 Enter 中，因为只有 locks 成分是可写的，就不必像 Alloy 版（图 E.2 第 17、18 行）那样为其余成分写等式。」这正是 Alloy 必须写 issued.t = issued.t' and prev.t = prev.t' cards.t = cards.t' 的原因。
显式前条件的一害（原文给的实证）
显式前条件让「操作何时适用」更易看清，但可能更啰嗦：「注意 Enter 的前条件（行 17）在后条件里被重复了一遍，因为存在量词无法横跨两者。」Alloy 不存在这个问题 —— 谓词体是一整个公式，量词自然覆盖全部。
~、& 与「状态是可变的顶层记录」
VDM 的前/后条件就是逻辑公式，像 Alloy 谓词体一样。但与 Alloy 不同、与其他方法（Z 相对轻些）相同：VDM 假定某种特定状态机习语并为之提供专门语法。状态声明不像其他类型声明 —— 它定义了一个可变结构，其各成分在操作的前状态与后状态中各有其值；成分 c 在前状态的值写作 c~，后状态写作 c。特殊符号 & 分隔量词的约束部分与主体（exists x & body）。
「所有变异都被限制在状态的顶层成分」
「这很方便，但不如 Alloy 的路子灵活。你不能把 cards 变成可变的，以便建模『黑客修改既有门卡』 —— 而在 Alloy 里，只要给 Card 的关系加一列 Time 就行了。不过 VDM++ 允许所有结构都可变。」
VDM 区分集合与关系（映射）—— 一个 + vs union/munion
「Alloy 对所有并运算都用同一个 +，而 VDM 对集合用 union、对映射用 munion。」作为高阶语言，VDM 还需要集合构造括号来区分映射与元组、集合与其元素：
  • 初始化行 21 把「客人→卡集合」映射的值域等同于 {{}} —— 只含空集的那个集合；若写成 {} 意思就完全不同了。
  • 扩充 guests 与 locks 两个映射时，一个需要集合括号（{r |-> new_k}）一个不需要（{g |-> {new_c}}）。
显式风格：为动画器而改写
「要把动画器（如 VDMTools 的那个）应用于一个操作，该操作必须写成显式形式。」图 E.11 即 CheckIn 的显式版本：存在量词被换成 let 语句；后条件的各约束被换成赋值；帧条件不再必要。原文判语：「这个记法与 B 非常相似。」—— 恰好闭合了本节开头「VDM 支持显式与隐式两种建模」这句评价。

E.4.3 VDM 的工具

VDMTools 与 Overture

在 Peter Gorm Larsen 的指导下，丹麦公司 IFAD（1990 年代提供 VDM 咨询）开发了 VDMTools —— 同时支持 VDM-SL 与 VDM++ 的工具箱。它包含一个类型检查器和一个定理证明器，并针对 VDM 的一个可执行子集提供规格模拟与测试设施，外加一个代码生成器。该工具箱现归日本 CSK 公司所有。

面向 VDM++ 的新工具支持正在 Overture 开源计划下开发。

注意那句限定：「针对 VDM 的一个可执行子集」 —— 这正好落在导言批评的点上：动画器要求可执行子集，而「Alloy Analyzer 不把语言限制在可执行子集内」。VDM 的显式风格（图 E.11）就是「为进入那个子集而做的改写」。

E.5Z

来历与战绩：Z 于 1980 年代在牛津大学开发。它在教学与研究上影响极深，并成功应用于若干大型项目：牛津大学与 IBM 在 CICS 系统上的合作、Praxis Critical Systems 的一串项目，以及 NatWest 银行开发的 Mondex 电子钱包的安全验证 —— 这是史上第一个获 ITSEC Level 6 认证的产品 [69, 68]。

与 Alloy 的血缘：「Z 那干净而简单的语义基础，是 Alloy 设计的一个灵感来源。」

标准与主流教材：语言已由 ISO 标准化 [30]，但 Mike Spivey 的书 [65] 所描述的那个版本至今仍最流行。关于 Z 的书写得很多：教材 [40, 56, 74, 75]、案例集 [26]、风格指南 [3]。

E.5.1 Z 的基本概念

一句最要紧的对照：Z 只有一个打包构造，Alloy 有两组

「Z 和 Alloy 一样，骨子里就是一套逻辑，加上若干语法构造以便描述软件抽象。在 Alloy 里，这些构造是 signature（用来打包声明）与 facts / predicates / functions（用来打包约束）。在 Z 里，同一个构造 —— schema —— 既用来打包声明，也用来打包约束。schema 的语言（schema calculus）足够丰富，能支持广泛的习语。」

「Oxford style」已经变成事实上的语言的一部分
实践中，某一个习语 —— 又称 IBM style 或 「established strategy」[3] —— 自最早期起就被几乎所有 Z 规格采用。围绕它生长出一整套语法约定，并已成为语言事实的一部分。铁证：「按顺序组合操作的算子就假定了这一习语的使用；没有它，该算子不会具有预期的含义。」
Z 没有内建精化，但有一套成熟的精化理论
与 B 不同，Z 没有内建的精化概念；事实上许多 Z 用户把它当作系统建模语言，根本不打算证明代码与模型的符合性。不过 Z 有一套确立良好的精化理论，语言也很适合逐步精化的开发 —— Woodcock 的书 [74] 是该途径的易读入门。
schema 声明的两段结构与「隐式并入」
一个 Z 规格由一串 schema 声明搭成。每个声明有两部分：一串变量声明 + 一个约束它们的谓词。当引用一个先前声明过的 schema 时，它的变量声明和谓词都被隐含地并入。表示状态的 schema 通常在既有状态 schema 上添加新成分并用额外不变式进一步约束状态；表示操作的 schema 可以并入前状态与后状态两个状态 schema，也可以扩展一个既有操作 schema、追加约束使其行为更具体。
「简洁到神秘」：三种语言共享同一种力量
「因为并入一个 schema 会把它声明的变量带入作用域，schema 谓词里出现的变量常常没有显式声明。结果 Z 规格可以极其简洁 —— 有时简洁得近乎神秘。」原文随即把这种力量横向对比：「完全相同的力量、同样的简洁与同样的隐晦，出现在面向对象编程语言的继承机制中，也出现在 Alloy 的 signature 扩展机制里 —— 顺带一提，那个机制正是刻意为支持 schema 式结构化而设计的。」
Oxford 风格下的不变式与前条件
状态不变式与状态声明一起声明，因而被隐含并入操作（如 VDM）；这与 B 形成鲜明对照 —— B 中不变式必须被证明为操作所保持。操作的前条件不与后条件分离。把前条件显式写在操作 schema 里被视为良好风格，但并非必需。
用「前条件定理」替代 VDM 的可实现性检查
「取代 VDM 的可实现性检查，Z 规格师从一个操作 schema 推导出一个前条件，再与他期望的前条件相比较。」
集合与关系：Z 与 B 同源，而 Alloy 来自另一支血统
集合与关系是 Z 的主导数据类型。这一点 Z 与 B 相似（不足为奇 —— B 的发明者 Abrial 早年是 Z 的开发者之一，更早前还研究过数据库语义）。对 Z 和 B 而言，集合是基本的、关系是派生的；Z 这个名字就来自它的根基 ZF（Zermelo–Fraenkel）集合论。
Alloy 的血统：Tarski 与 Codd
「Alloy 同样基于集合与关系，但它的逻辑更多地受 Tarski 的关系演算 [70] 与 Codd 的关系数据库模型 [9] 这些关系式形式化传统的影响 —— 在 Alloy 里，集合被视作关系的一个特例。」这是全书关于 Alloy 血统最明确的一段自述。
schema 类型：比 signature 多了构造器，少了子类型
和 VDM 一样，Z 也包含记录类型：同一个语法上用于「把声明分组」的 schema 构造，语义上可用来声明一种「schema 类型」，其值是「字段名 → 值」的绑定。
  • 比 Alloy signature 更强的地方：提供构造器。
  • 更弱的地方：schema 没有子类型。一个 schema 可定义为另一个 schema 的扩展，但两者的类型互不相关。原文的例子：若你声明了一个「文件系统对象」schema，并扩展成「文件」与「目录」两个 schema，那么你无法把文件 schema 或目录 schema 的实例放进一个声明在文件系统对象之上的集合或关系里。
对照 Alloy：B.7.2 的 extends 天生带子类型关系与签名事实的自动适配，Z 在此处需要手工处理。
外观
Z 有独特的视觉外观：schema 四周画框，并有自己的一套数学符号。本附录采用「水平式（horizontal form）」—— 原文自嘲：「虽然不那么优雅，但不必专门的排版工具就能排出来。」

given set、全局常量与 datatype
首行 [Guest, Key, Room] 把三者声明为 given sets：无解释的原子集合，成为类型检查的基础（对应 Alloy 的无字段 sig）。全局变量 initkeys 表示「把房间锁关联到其钥匙初始值」的那个函数。Msg 是一个 datatype 声明，表示操作可能的结局。
箭头的种类即重数
Hotel 引入三个变量：firsttime（房间的集合）、key（房间→钥匙的函数，代表某状态下各锁里的钥匙）、guest（房间→客人的函数，即占用名册）。「箭头的种类表明重数：key 是偏单射，guest 是偏函数。」（↣ / ↛）
firsttime 为什么在 Alloy 版里不存在
因为本模型要精确说明「何时该允许进入、何时该重编码锁」（后续精化才描述「靠查钥匙来决定进入」这一机制）。firsttime 用来标记「此后被进入时应当重编锁」的那批房间 —— 因为将有新客人第一次进入。
装饰（decoration）：撇号
Hotel 只有变量声明、不含谓词，InitHotel 则声明与谓词都有；其声明部分通过提及 schema 名并入 Hotel。注意名字后的撇号：「这称为装饰（decoration），其效果是并入并非完全等于 Hotel 的那些声明，而是每个变量 likewise 加撇的版本」—— 撇号变量在 Z 中用于指「操作执行后的状态成分取值」。
schema 谓词只是约束的合取，等号不是赋值
「schema 谓词就是一个约束，由各行约束合取而成。每行的约束是一个简单数学公式，等号表示相等（不是赋值）。所以这些等式里各项的次序没有语义意义，把每个等式左右颠倒也不改变含义。」
那为什么本例还要把撇号变量写在左边
「本规格被写成暗示其可执行方式的形式：撇号变量在左。这使它可以用 Jaza 之类的工具做动画。同样的道理也解释了为什么初始化把 key' 等同于先前声明的 initkeys —— 正如 B 模型里对应成分被初始化那样（图 E.5 行 23）。而更传统的 Z 风格会干脆不提 key'，让它的值不受约束。」—— 一段极佳的「为工具而牺牲纯度」的实例。
Δ 与 Ξ（读 Z 操作的钥匙）
Checkin0 与 EnterFst 提到 Δ Hotel：这是一个由约定隐式定义的 schema，包含 Hotel 与 Hotel'，从而为每个状态变量引入「普通版 + 撇号版」，代表执行前后。EnterSnd 提到 Ξ Hotel：类似的 schema，也含 Hotel 与 Hotel'，但额外带一条「每个状态变量等于其撇号版本」的约束 —— 因此它的使用表示一个对状态毫无影响的操作。注意 EnterSnd 的体内确实一条 x' = x 都不用写，对比 Alloy 必须在 enter 里逐条写出未变化等式。
输入 ? / 输出 !：语法糖而非语义
「每个操作还声明了一些带问号装饰的变量。按约定它们代表输入参数；在语义上，它们与表示状态成分的变量毫无区别。」当操作 schema 在别处被使用时，这些参数由一次语法替换绑定 —— 把 schema 里参数变量的每次出现替换为新上下文中的变量名。
与 Alloy 显式参数化的得失
不便：「表达式不能替换变量，所以若实参还没有对应的变量存在，就必须用存在量词把它声明出来。」方便：「当实参与形参同名时不必替换，产出的文本不会被参数列表弄乱。」
Z 不在语法上区分前后条件
「Z 不在语法上区分前条件与后条件，而且根本无须显式写出前条件。把前条件完整列在属于后条件的那些约束之上，被视作良好风格。」例：Checkin0 的前条件是「r? 不在 guest 的域中，且 g? 不在其值域中」—— 即所指房间尚未被占用，且该客人尚未被指派到别的房间。
这条风格规范为什么工具查不了，以及 Alloy 的替代方案（重要）
「这条风格指南一般无法用简单语法手段检查，因为显式前条件可能容纳一些『后条件无法满足』的状态，从而使实际的前条件更强。」对策：可构造一条「该操作具有所期望的前条件」的定理（就是 Theorem preCheckin0）。而原文接着承认：「Alloy 无法表达这类定理，正如 5.3 节所解释的。非意图性的过度约束改由『模拟该操作』来缓解。」
操作谓词本身
Checkin0 往 guest 关系里加上「r? ↦ g?」；EnterFst 用 ⊕（覆盖）把 key 关系改写为「r? ↦ 新钥匙 k?」来重编锁 —— 与 Alloy 的 ++、VDM 的 ++ 一一对应。原文：「注意，与 Alloy 和 OCL 一样，未被提及的状态变量是不受约束的，所以若某成分不变，就需要一条显式等式（如第 24 行）。」（guest' = guest）
异常情形与组装 —— Z 把「操作 = 公式」贯彻到底
Success 只引入输出参数 m! 并令其等于 okay；随后两个 schema 说明「进入应被视为不允许」的条件（房间根本未分配 / 尝试进入的客人不是合法住客），以前条件形式表达，并配上把消息值约束为相应取值的后条件。最后 Enter 用一个纯 ∧/∨ 的表达式把各情形拼起来，描述「尝试进入某房间」的全部场景。
全书在此处给 Alloy 记的一功
「注意它仅用析取与合取就完成了组装。这种简洁是『操作不过就是逻辑公式』这一事实的后果。Alloy 从 Z 借来了这个想法，因而支持同一种结构化。」

E.5.3 Z 的工具

证明器为主，动画器为辅

大多数 Z 工具支持集中于定理证明。最广泛使用的证明工具是 ProofPower（Lemma 1 Ltd）与 Z/Eves —— Eves 定理证明器的前端（ORA Canada）。本附录的样例模型就是用 Z/Eves 分析的。

Z/Eves 能做的三件事：计算前条件；执行「域检查（domain checks）」（确保偏函数绝不越出其定义域被应用）；一般性定理证明。「虽然证明中的许多步骤可自动执行，复杂定理往往需要有经验的用户给予引导。」

动画器：Z 也造了不少动画器。样例模型用 Jaza [72] 测过 —— Waikato 大学 Mark Utting 开发的动画器。Jaza 能执行以显式风格写成的操作，并能在小域上做一定程度的约束求解；上面整个样例模型都能交给 Jaza 处理。

原文回扣 E.5.2 那个「传统 Z 风格不会写 key' = initkeys」的选择：「我们注意到初始化把全局函数 initkeys 赋给 key' 而不听任它不受约束；这使得在用户给出 initkeys 的一个取值时，初始化就能被执行。」

与 USE、VDMTools 的动画器一样，Jaza 能求值表达式、检查给定状态是否满足不变式、检查转移是否符合操作，并能在用户挑选操作的情况下模拟一条执行轨迹。

Z/Eves 与 Alloy Analyzer 的分工，一句话讲清

Z/Eves 会自动推导前条件并证明定理（例如「实际前条件 = 期望前条件」，这是 Alloy 语言表达不了的）；Alloy Analyzer 会搜索反例（例如 NoIntruder 的那条六状态轨迹，这是 Z/Eves 做不动的）。两边各自的短板恰是对方之长 —— 这正是本节末尾「关键场景下应当转而尝试证明」那句话的技术根据。

  1. 「同一道题」被五种语言各写一遍，但只有 Alloy 版故意留了那个漏洞。原文说明 Alloy 用 check 在 2 秒内给出反例轨迹，也说明Gogolla 用 USE 模拟场景同样「发现了缺陷，包括 Alloy 模型第一版中的那个初始化错误」。值得注意的对照是（本页归纳，非原文断言）：四个专家版本在写法上都预先避开了那一坑 —— OCL 的 init 后条件 issued_eq_room_key: Desk.allInstances.key4issued = Room.allInstances.key4key 与 VDM 的 init h == h.desk.issued = rng h.locks 恰好就是 Alloy 的修复方案；B 干脆不设「已发出」记录，把「全新」定义为 k /: key；抽象 Z 模型则把「全新」定义为 k? ∉ ran key。换言之：漏洞之所以在 Alloy 版里出现，是因为它被写成「教学用的第一版」，而不是语言差异所致。
  2. 四种「其他方法」的差异，绝大多数可以归约到一个轴：把状态机写死 vs 留给习语。B、VDM（及一定程度上 Z、OCL）在语言层面固定了「状态 / 前状态 / 后状态」；Alloy 只给关系与公式，状态习语（时间列、pre/post、动态块）随你挑。本附录里 Alloy 最反直觉的一点也由此而来：它没有 @pre、没有 Δ、没有撇号、没有帧条件，只有「多一列 Time」。
  3. Alloy 承认的两处真实短板在四个样例里都留下了痕迹：（a）一阶限制 —— Morgan 电话局的极大性高阶公式无法表达；本附录中 VDM 的 rng h.guests（集合的集合）在 Alloy 里被改写为沿 Time 的量化。（b）没有构造器 —— VDM/Z 用 mk_Card/schema 类型直接构造新值，Alloy 必须写存在量词或概括式；且这一缺失「正是 5.3 无界全域问题的核心」。看到「Alloy 写起来更绕」的地方，几乎总能归因到这两条之一。

附录 E 小结

  1. 本附录的定位：由 Butler / Fitzgerald / Gogolla / Larsen / Woodcock 五位专家分头建模同一个酒店门锁问题，供选型参考与「他山之石」对照。因篇幅所限收录不全（Gogolla 的第二个 OCL 模型、Woodcock 的全部前条件定理与 NoIntruder 证明均未入书）。
  2. 选这四家的标准：能简洁而抽象地刻画复杂结构，知名且有活跃社区；模型检查器整体不入榜，因为除 FDR 外对数据结构化支持初级。
  3. 五家共性：记法比编程语言更简洁直接；状态被视为经典数学结构（集合、关系）；行为以约束声明式描述；都有求值具体案例的轻量工具；都有新工具项目。
  4. 五家差异：B 偏操作式（像抽象编程语言）；OCL 语法像 Smalltalk；B、VDM 把某种状态机观念写死（Z、OCL 也部分如此），Alloy 支持多种习语；B/VDM/Z 为证明而设计，配专用定理证明器，Alloy 与 OCL 不是。
  5. Alloy 的设计公式：语言削到只剩结构化建模的基本要素，与分析工具同步发展，任何妨碍分析的特性一律排除。
  6. Alloy 分析强于他人的三条机制：不要初始条件与输入；不限制到可执行子集；覆盖作用域内整个空间 ⇒ 更擅长隐蔽 bug。另加两条：断言是规格的一部分、作用域只在命令里（他人靠工具专属扩展）。
  7. 「小而简」换来的四处统一：一切数据结构统一为关系；同一个连接兼作索引/解引用/函数应用；signature 可模拟 Z 的 schema 与 OCL 的 class；assertion 可表达不变式保持、精化与轨迹上的时序性质。
  8. 代价（明说）：Alloy 不如其他语言表达力强；结构严格一阶，而 B/VDM/Z 支持高阶；Morgan 电话局的「连接=端点集合的集合」与那条极大性高阶公式在 Alloy 中不可表达；对序列与整数支持较弱。
  9. 四家独门优势（明说）：B 通往实现更直接；OCL 与 UML 集成；VDM 显式与隐式双支持；Z 的高阶特性利于大规格结构化。
  10. E.1 的 Alloy 基准模型：Card 的两把钥匙是固定刻印（无 Time 列），其余成分（房间当前钥匙、前台发出记录、前台上次入住的房间→钥匙、客人持卡）都带 Time 列。初始化只对齐了「prev 与锁一致」，却漏了「锁里已有的钥匙须记为已发出」。
  11. 分析节奏：for 3 but 6 Time, 1 Room, 2 Guest ⇒ 2 秒出反例（六状态轨迹）；修 init 后穷尽无解；for 4 but 7 Time, 2 Guest, 1 Room ⇒ 又出一例（同一客人两次入住，中间夹他人）；把 cards.t' = cards.t + g->c 改为 ++（覆盖而非追加）⇒ for 6 but 12 Time, 3 Guest, 3 Room 一分钟内穷尽。
  12. 方法论落点：「我们并未证明断言成立，更大作用域里仍可能有反例（虽不太可能）；关键场景下此时应尝试证明」，而定理证明器对本附录所有方法都可适用。
  13. B（E.2）：AMN = 语言 + 逐步精化方法；最著名应用为巴黎地铁制动系统。模型五段（SETS/VARIABLES/INVARIANT/INITIALISATION/OPERATIONS）；后条件是替换而非公式（利于证明、像程序、须逐变量给出，故增量性差）；precondition 与 guard 有别（后者导致阻塞）；用列举基本集合元素来定界，且全局生效；POW 体现高阶；不变式与声明语义无别但类型检查在意次序。
  14. B 的工具：Atelier B、B-Toolkit 重证明与代码生成；ProB 是唯一能全自动生成反例者，检验不变式/精化的证明义务，沿轨迹而非归纳地检验精化（无需归纳不变式），还能比对 B 与 CSP 描述的抽象。
  15. OCL（E.3）：UML 的约束语言（Warmer–Klepper，源自 Syntropy 与 IBM）；先标准化、后补形式语义 ⇒ 想简单却更复杂；标准未给声明配文本记法（USE 变体补上）；to-many 语义上是「到集合的函数」⇒ 关系有强方向性、不可反向遍历 ⇒ 关联以「角色」成对暴露；重数进入类型（导航返回集合或标量，改重数即改类型）；无传递闭包 ⇒ 允许递归 ⇒ 需最小不动点语义 ⇒ 无法使用约束求解器（会产生非极小解的伪案例）；类 ≠ 对象集合（故须 allInstances）；表达式不能表示关系；基本类型在库模块里 ⇒ 类型检查器只能依赖声明类型，无法利用算子含义。
  16. OCL 样例的坑：prev 是三元关联；k 个角色的关联中每个角色表示 k−1 个二元关系；角色视图不完全具有表达力（多前台时写不出 d.prev[r]，须把关系显式表示为元组集合）；Set{c.key4snd} 的 Set 并非多余 —— 三元关系中角色重数说的是「其他类型的某种实例组合对应多少个该类型实例」，不是 x.r 那个集合的大小。
  17. OCL 工具：Octopus / Together 组件做语法类型检查、测试案例解释、代码生成；USE 最强，新增「用户生成器枚举快照」后可按 Alloy 风格穷尽有限空间，并据此复现了 Alloy 第一版的初始化错误。
  18. VDM（E.4）：维也纳开发方法（Jones、Bjørner），逻辑式规格的许多原理首现于此；VDM-SL 由 ISO 标准化，两套语法（ASCII 与数学符号）；工业案例含电子交易、安全智能卡、荷兰花卉拍卖。
  19. VDM 的概念：状态机 + 每声明可带不变式；「可实现性」检查（显式风格自动满足）；不变式隐式并入前后条件（同 Alloy/OCL/Z）；操作引用 ≈ 一对 Alloy 谓词；验证猜想 = 断言，但用工具专属扩展表达；独有帧条件 ext rd/wr（更简短、更好读，但排斥「由其他成分定义的冗余状态成分 —— 而这恰是 Alloy 的常用手法）。
  20. VDM 样例的洞见：token = 无解释原子；mk_Card 构造器是 Alloy 所缺；「记录无独立于值的身份」⇒ 两张同钥匙的卡不可区分，这「正是 5.3 无界全域问题的核心」；状态不变式里的 dunion rng h.guests 是集合的集合，Alloy 须写成沿 Time 的量化 all t | Guest.cards.t.(fst+snd) in Desk.issued.t；时间变量 t 扮演 VDM 状态变量 h 的角色，位置只是习语的产物；帧条件省掉了 Alloy 必须显式写的一串「未变化」等式；Enter 的前条件被迫在后条件里重复一遍（存在量词无法横跨两者）；c~ 表前状态、& 分隔量词约束与主体；变异仅限状态顶层成分（不能把 cards 变可变来模拟黑客改卡；VDM++ 可以）；区分 set 与 map（union/munion）且需集合括号区分 {{}} 与 {}；动画器要求显式风格：存在量词→let、约束→赋值、帧条件可省 —— 该记法与 B 极像。
  21. VDM 工具：IFAD 的 VDMTools（类型检查 + 定理证明 + 可执行子集的模拟测试 + 代码生成），现属 CSK；VDM++ 的新支持在 Overture 开源计划下开发。
  22. Z（E.5）：牛津 1980s；CICS、Praxis、Mondex（首个 ITSEC Level 6 产品）；其干净简单的语义基础是 Alloy 的灵感来源；已 ISO 标准化但 Spivey 的版本最流行。
  23. Z 的概念：一个 schema 同时打包声明与约束（Alloy 分 sig 与 fact/pred/fun）；schema calculus 丰富到足以支持多种习语，但Oxford style 的约定已成语言事实的一部分（顺序组合算子离开它就失去预期含义）；无内建精化但有成熟精化理论；引用 schema 即隐式并入其声明与谓词 ⇒ 变量常无显式声明 ⇒ 简洁到神秘，此力量与 OO 继承、Alloy 的 extends 同源（后者正是为 schema 式结构化而设计）；不变式随状态声明隐式并入操作（与 B 的「须证明保持」相反）；不区分前后条件，显式前条件只是风格；以「推导前条件并与期望比较」的定理取代 VDM 的可实现性检查。
  24. Alloy 的血统声明（本页最重要的一段史料）：Z/B 视集合为基本、关系为派生（Z 之名来自 ZF 集合论）；Alloy 虽也用集合与关系，但其逻辑更多受 Tarski 关系演算与 Codd 关系数据库模型影响，把集合当作关系的特例。
  25. Z 的 schema 类型 vs Alloy 的 signature：多了构造器，少了子类型 —— 扩展 schema 与被扩展 schema 类型互不相关，故文件系统对象的实例无法放进声明在「文件系统对象」上的集合/关系里（Alloy 的 extends 无此限制）。
  26. Z 样例的要点：given sets [Guest,Key,Room] 作类型检查基础；initkeys 是全局常量、Msg 是 datatype；箭头种类表重数（↣ 偏单射、↛ 偏函数）；firsttime 是 Alloy 版没有的成分，用来标记「下次进入即须重编锁」的房间；撇号 = decoration（并入逐变量加撇的声明）；schema 谓词只是各行合取，= 是相等不是赋值，等式两侧可互换；之所以把撇号写在左边是为了可动画，且「更传统的 Z 风格会干脆不提 key'」；Δ=前后两套变量，Ξ=再加「每变量等于其撇号版」⇒ 表示无影响的操作；?/! 只是约定，语义上与普通变量无异，绑定靠语法替换（故表达式不能替换变量，无对应变量时须用存在量词声明）。
  27. Z 的两处「Alloy 做不到 / Alloy 抄了 Z」：「这类前条件定理在 Alloy 中不可表达（见 5.3），非意图性的过度约束改由模拟操作来缓解」；反之「操作不过是逻辑公式，故可用 ∧/∨ 组装 —— Alloy 从 Z 借来此想法并支持同类结构化」。另注意：未被提及的状态变量不受约束、需要显式等式，原文明说这一点 Z 与 Alloy、OCL 相同。
  28. Z 工具：重心在证明 —— ProofPower、Z/Eves（能算前条件、做域检查确保偏函数不越域应用、一般定理证明，复杂定理需老手引导）；动画器 Jaza（Utting，Waikato）能执行显式风格操作并在小域上做一定约束求解，整个样例模型皆可处理；与 USE、VDMTools 动画器一样可求值表达式、校验状态与转移、按用户选操作模拟轨迹。
  29. 选型口诀（本页归纳）：要一路做到代码 ⇒ B；要在 UML 上贴约束 ⇒ OCL；要接口式、显隐双轨 ⇒ VDM；要高阶结构化 + 定理证明 ⇒ Z；要最快找到隐蔽 bug、语言最小、可自由选习语 ⇒ Alloy。
  30. 全书终章的一句话精神：这些语言都早于 Alloy，Alloy 从它们的经验中大大受益；差异不在优劣，而在「表达力 ↔ 可分析性」这条光谱上各占一点。
