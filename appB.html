B.1Lexical Issues · 词法问题

允许的字符

允许的字符是 ASCII 字符集中的可打印字符，但以下两个除外：

  • 反斜杠 \
  • 反引号 `

而在 ASCII 非打印字符中，只有空格、水平制表符、回车和换行被允许。由于换行的编码在不同平台上有差异，Alloy Analyzer 接受回车与换行的任何标准组合。

非字母数字符号

非字母数字符号被用作运算符或标点，但以下这些除外：

符号用途
$ 美元符保留给语言的未来版本使用
% 百分号
? 问号
_ 下划线可以用在标识符中
' 和 " 单双引号
小心「智能引号」

单引号与双引号（ASCII 编号 39 和 34）不应与排版引号（typographic quote marks）和撇号（prime mark）混淆，后者不是可接受的字符。如果文本是在文字处理器中准备的，请确保「智能引号（smart quotes）」功能没有开启，因为它可能从简单引号生成排版引号。

注释

三种注释形式
  • -- 到行尾
  • // 到行尾
  • /* 到 */

多行注释不可以嵌套。

Token 切分

非注释文本被下列分隔符切分成 token：

  • 空白字符（空格、制表符、换行）；
  • 非字母数字字符（下划线与引号除外）。
三条重要规则
  • 文本的含义与其格式无关；特别地，换行被当作空白处理，就像空格和制表符一样。（所以 Alloy 不靠换行分隔语句，这与 Python 完全不同。）
  • 关键字和标识符是大小写敏感的。
  • 标识符可以包含任何字母字符，以及（除了作为第一个字符之外）数字、下划线、问号、感叹号和引号。连字符不能出现在标识符中，因为它被当作一个运算符。
  • 数字常量由一串 0–9 的数字构成，其第一个数字不为零。

被识别为单个 token 的字符序列

Token含义
::双冒号，用于接收者语法（receiver syntax）
=>蕴含运算符
>= =<整数比较运算符
->积箭头（product arrow）
<: :>限制运算符（域限制 / 值域限制）
++关系覆盖运算符
&& ||合取与析取
-- // /* */注释标记
一个有用的细节

取反的运算符（例如 !=）不被当作单个 token，所以它们可以在取反符与比较符之间写空白——即 a ! = b 与 a != b 等价，原书中大量使用的 not = 写法正是这一点。

B.2Namespaces · 命名空间

每个标识符属于且仅属于一个命名空间。共有三个命名空间：
  1. 模块名与模块别名；
  2. signature、字段、段（fact、函数、谓词、断言）以及绑定变量（函数与谓词的参数，以及由 let 和量词绑定的变量）；
  3. 命令名。

不同命名空间中的标识符可以共享名字而没有名字冲突的风险。

同一命名空间内的规则与唯一例外

在一个命名空间内，同一个名字不得用于不同的标识符，只有一个例外：绑定变量可以相互遮蔽（shadow），也可以遮蔽字段名。

适用常规的词法作用域（lexical scoping）：最内层的绑定生效。

解读 · 为什么这个设计很重要

「命令名单独一个命名空间」意味着你可以写 run show 而 show 既是谓词名又是命令名。「模块名单独一个命名空间」意味着模块可以叫 Process 而不会与 signature Process 冲突（B.7.1 明确重申了这一点）。而「绑定变量可以遮蔽字段名」是 Alloy 中一个常见的意外来源：如果你在 let addr = b.addr | ... 中用了与字段同名的变量，那么在该 let 的作用域内 addr 指的是变量而不是字段——A.2.2 的 inv 谓词正是有意这样写的（let addr = b.addr）。

B.3Grammar · 语法

BNF 约定

语法使用标准的 BNF 运算符：

  • x* — x 的零次或多次重复；
  • x+ — x 的一次或多次重复；
  • x | y — 选择 x 或 y；
  • [x] — 可选的 x。

此外：

  • x,* 表示零个或多个以逗号分隔的 x；
  • x,+ 表示一个或多个以逗号分隔的 x。

为避免与语法符号混淆，方括号、星号、加号和竖线在被解释为终结符时以粗体排版。

每个以 Id 结尾的名字都是一个标识符，应当被当作终结符处理。终结符 number 表示一个数字常量。

模块与段

module    ::= header import* paragraph*
header    ::= module [path] moduleId [ '[' sigId,+ ']' ]
path      ::= directoryId / [path]
import    ::= open [path] moduleId [ '[' sigRef,* ']' ] [as aliasId]

paragraph ::= sigDecl | factDecl | funDecl | predDecl | assertDecl
            | runCmd | checkCmd

signature 声明

sigDecl ::= [abstract] [mult] sig sigID,+ [extends sigRef] sigBody
          | [mult] sig sigID,+ in sigRef sigBody
sigBody ::= { decl,* } [constraintSeq]

各类段声明

factDecl   ::= fact [factId] constraintSeq
assertDecl ::= assert [assertId] constraintSeq
funDecl    ::= fun [sigRef ::] funId ( decl,* ) : declExpr { expr }
predDecl   ::= pred [sigRef ::] predId ( decl,* ) constraintSeq

runCmd     ::= [commandId :] run funRef [scope]
             | [commandId :] run predRef [scope]
checkCmd   ::= [commandId :] check assertRef [scope]

scope      ::= for number
             | for [number but] typescope,+
typescope  ::= [exactly] number scopeable
scopeable  ::= sigRef | int

声明

decl        ::= [part | disj] varId,+ : declExpr
letDecl     ::= varId = expr
declExpr    ::= declSetExpr | declRelExpr
declSetExpr ::= [mult] expr
declRelExpr ::= declRelExpr' [mult] -> [mult] declRelExpr'
declRelExpr'::= declRelExpr | expr
mult        ::= lone | one | some

表达式

expr ::= [@] varId | sigRef | this
       | none | univ | iden
       | unOp expr | expr binOp expr | expr '[' expr ']'
       | { decl,+ | [constraint] }
       | let letDecl,+ | expr
       | if constraint then expr else expr
       | Int intExpr
       | [expr ::] funRef ( expr,* )
       | ( expr )

intExpr ::= number | '#' expr | sum expr | int expr
          | if constraint then intExpr else intExpr
          | intExpr intOp intExpr
          | let letDecl,… | intExpr
          | sum decl,+ | intExpr
          | ( intExpr )
intOp   ::= + | -

约束

constraintBody ::= constraintSeq | '|' constraint
constraintSeq  ::= { constraint* }
constraint     ::= expr [neg] compOp expr
                 | quantifier expr
                 | intExpr [neg] intCompOp intExpr

                 | constraint thenOp constraint [elseOp constraint]
                 | quantifier decl,+ constraintBody
                 | let letDecl,+ constraintBody

assertRef ::= [moduleRef] assertId

B.4Precedence and Associativity · 优先级与结合性

逻辑运算符的优先级（从最紧开始）

优先级运算符
1（最紧）取反：! 和 not
2合取：&& 和 and
3蕴含：=>、<=>、implies 和 iff
4（最松）析取：|| 和 or

表达式运算符的优先级（从最紧开始）

优先级运算符名称
1（最紧）~ ^ *一元运算符
2.点连接（dot join）
3<: :>限制运算符
4[ ]方括号连接（brackets join）
5->箭头积（arrow product）
6&交
7++覆盖
8（最松）+ -并与差
特别注意：点比方括号绑得更紧

a.b[c] 被解析为 (a.b)[c]，而不是 a.(b[c])。这是最常见的解析意外之一。

结合性

除蕴含外，全部左结合

所有二元运算符都向左结合，蕴含是例外，它向右结合。所以：

  • p => q => r 被解析为 p => (q => r)
  • a.b.c 被解析为 (a.b).c

在一个蕴含中，else 子句与其最近的 then 子句相关联。所以约束

p => q => r, s

被解析为

p => (q => r, s)
解读 · 「就近 else」与编程语言中的「悬挂 else」是同一个约定

这与 C/Java 里 if-else 的悬挂 else 规则一致。实践建议：只要用了 else（或逗号形式的 else），就加括号明确意图，不要依赖解析规则。

B.5Semantic Basis · 语义基础

B.5.1 Instances and Meaning · 实例与含义

核心定义

一个模型的含义是「若干组实例（several collections of instances）」。一个实例是「把值绑定到变量」。

通常，单个实例代表一个状态，或一对状态（对应一个操作的执行），或一条执行迹。然而语言中没有内建的状态机概念，所以一个实例不必代表这些东西中的任何一个。

指派给一个模型的实例组有三类：

组定义变量
① 核心实例（core instances）与模型的 facts 以及signature 声明中隐含的约束相关联的实例集合。它们把值绑定到变量上，使 facts 与声明约束为真。signature 及其字段
② 每个函数或谓词一组那些「整个模型的 facts 与声明约束为真，且额外地该函数或谓词的约束也为真」的实例集合。核心实例的变量，再加上该函数或谓词的参数
③ 每个断言一组那些「整个模型的 facts 与声明约束为真，但该断言的约束为假」的实例集合。同上
三组的「健康状态」判读
对象没有实例意味着
模型不一致（inconsistent），并且几乎肯定是有错误的
函数或谓词同样不一致，并且不太可能有用
断言这正是我们所期望的！实例就是反例，它们表明该断言并不从 facts 推出
有界搜索的根本限制

Alloy Analyzer 通过在有限界内搜索来自动找到模型的实例（界由用户指定为作用域，见 B.7.5）。因为搜索是有界的，未能找到实例并不必然意味着实例不存在。但被找到的实例保证是有效的。

——这句话是第 5 章全部内容的规范表述：Alloy 是「反例可信、无反例不可信」的工具。

B.5.2 Relational Logic · 关系逻辑

Alloy 是一阶关系逻辑

指派给变量的值，以及在给定实例的上下文中求值的表达式的值，都是关系。这些关系是一阶的：也就是说，它们由「其元素是原子（而不是本身也是关系）」的元组构成。

概念在 Alloy 中就是
集合（set）一个一元关系
标量（scalar）一个单例的一元关系
元组（tuple）一个单例关系

Alloy 没有显式的「集合」「标量」或「元组」概念。类型系统区分集合与关系（因为它们有不同的元数），但不区分元组、标量与更一般的关系。

没有「函数应用」运算符

关系 join 被用来替代它，而且它在语法上比「一个区分集合与标量的语言」中会更干净。

例如，给定一个函数性的关系 f，以及被约束为标量的 x 和 y，约束

x.f = y

把 x 在关系 f 下的像约束为集合 y。只要 x 在 f 的定义域内，这个约束就与「把点解释为函数应用、把 f 解释为函数、把 x 和 y 解释为标量类型变量」时具有相同的含义。

但如果 x 不在 f 的定义域内，表达式 x.f 将求值为空集，而由于 y 被约束为一个标量（即单例集合），整个约束将为假。

这是 Alloy 的一个设计优势

在一个有函数应用的语言里，取决于如何处理偏函数，各种含义都是可能的。Alloy 方法的一个优势是它绕开了这个问题。

声明语法被设计成「让熟悉的形式具有预期的含义」

因此，当 X 是一个集合时，量化约束

all x: X | F

让 x 遍历标量值。也就是说，约束 F 是在「x 被绑定到 X 的单例子集」时求值的。

Alloy 语法实际上允许高阶量化

例如「join 在二元关系上是结合的」这个断言可以写成：

assert {all p, q, r: univ -> univ | (p.q).r = p.(q.r)}

许多这类约束在被提交分析时会变成一阶的，因为（像这里一样）被量化的变量可以被 Skolem 化掉。如果一个约束仍然是真正高阶的，Alloy Analyzer 会警告用户「分析可能不可行」。

——这解释了为什么 A.1.1 能写 some r: univ -> univ { ... }，也解释了 5.2.2 中 Skolem 化的重要性。

整数的初步支持

Alloy 提供对整数的初步（rudimentary）支持。有一类表达式，其值是整数。整数值不能被绑定到实例中的变量上，但有一类特殊的「整数原子」，它们与原始整数值相关联，并且可以像任何其他原子一样出现在被绑定到变量的关系中。详见 B.7.7。

B.6Types and Overloading · 类型与重载

Alloy 类型系统的设计目标与编程语言不同

建模语言中没有「运行时错误」这个概念，所以「类型健全性（type soundness）」不是一个问题。取而代之，类型系统被设计为：

  • 允许尽可能多的合理模型，而不产生虚假警报；
  • 同时仍然在分析之前捕获那些「仅凭已声明字段与变量的类型就能解释」的错误。
用户视角的承诺

我们期望大多数用户能够忽略类型系统的微妙之处。

  • 报告「某个表达式类型不良」的错误信息从来不是虚假的，并且总是对应一个真实的错误。
  • 报告「无法解析一个重载的字段引用」的信息，总是可以通过一个「小的、系统性的修改」来处理，见下文。

B.6.1 Type Errors · 类型错误

错误种类含义例子
① 元数错误
arity error		 表明试图把一个运算符应用于一个元数不对的表达式，或试图组合元数不兼容的表达式 对一个非二元关系取闭包；把一个关系限制到一个非集合；对不同元数的两个关系取并、交、差，或用相等或子集来比较
② 不相交错误
disjointness error		 表明表达式中两个关系被以「结果将总是空关系（无论它们的值如何）」的方式组合 对两个不相交的关系取交集；join 两个没有匹配元素的关系；用一个与之不相交的集合来限制一个关系。
把覆盖运算符 ++ 应用于不相交的关系也会产生 disjointness 错误——即使结果可能不是空关系，因为这些关系被期望是重叠的（否则用并集就够了）
③ 冗余错误
redundancy error		 表明一个表达式（通常出现在并表达式中）是冗余的，可以在不影响外围约束值的情况下被丢弃 诸如 (a + b) & c 这样的表达式，以及诸如 c in a + b 这样的约束，其中 a 或 b 之一与 c 不相交
重要例外：不相交类型的并是被允许的

注意，不相交类型的并是被允许的，因为它们可能并不是错误的。因此表达式 (a + b).c 将是类型正确的，即使 a 和 b 的类型不相交——只要 c 的最左列的类型与 a 和 b 两者的右列的类型重叠。

这正是 4.4.4 中「只有 s.r 的不相交情形被拒绝」的规范表述。

B.6.2 Field Overloading · 字段重载

规则

signature 的字段可以被重载。也就是说，两个不同的 signature 可以有同名字段，只要这两个 signature 不代表重叠的集合。字段引用被自动解析。

重载的解析利用表达式的完整上下文，并使用与类型检查器相同的信息。每一种可能的解析都会被考虑：

  • 如果恰好有一种不会产生类型错误，它就被选中；
  • 如果多于一种，就产生一条报告「引用有歧义」的错误信息。
与 Java 字段解引用的对比

解析利用了关于可能解析项的类型的全部已知信息，包括元数，以及所有列（不只是第一列）的类型。

因此，与面向对象语言（如 Java）中用于字段解引用的那种解析不同，表达式 x.f 中对 f 的引用不仅可以利用 x 的类型来解析，还可以额外利用「整个表达式所出现的上下文」来解析。例如，如果外围表达式是 a + x.f，f 的引用可以由 a 的元数来解析。

无法解析时的标准修法：S <: f

如果一个字段引用无法被解析，修改表达式使它可被解析是很容易的。如果字段引用 f 意在指「在 signature S 中声明的那个字段 f」，你可以把对 f 的引用替换为表达式 S <: f。

这个新表达式有相同的含义，但保证能解析这个引用，因为只有「在 S 中声明的那个 f」才会产生非空的结果。

注意这不是一种特殊的类型转换（casting）语法。它只依赖于域限制运算符的标准语义。（等价于 (S -> univ) & f。）

B.6.3 Subtypes · 子类型

类型系统包含一个子类型的概念。这允许捕获更多错误，并允许字段有一个更细粒度的命名空间。

类型的结构
  • 任何表达式的类型都是一个「联合类型（union type）」，它由若干关系类型的并构成。
  • 一个关系类型是若干基本类型的积。
  • 一个基本类型要么是「signature 类型」，要么是预定义的全类型 univ，要么是预定义的空类型 none。
  • 基本类型构成一个格（lattice），以 univ 为其最大元、none 为其最小元。这个格是这样得到的：取已声明的 signature 类型构成的森林（trees 的集合），再加上「顶层类型与 univ 之间」以及「none 与所有 signature 类型之间」的子类型关系。
一个精细的区分

「由零个关系类型构成的并」被用在类型检查中，用来表示「类型不良的表达式」，它与「由一个「全是 none 的积」的关系类型构成的并」是不同的——后者用于用常量 none 构造的表达式，代表一个「有意为空的关系」。

子类型的语义非常简单
  • 如果一个 signature 是另一个的子类型，它就代表一个子集。
  • 一个 signature 的直接子类型是互不相交的。
  • 因此，两个子类型只有在「其中一个是另一个的（直接或间接）子类型」时才重叠。
  • 类型系统为一个表达式计算出的类型是其值的一个近似（approximation）。

考虑 join e1 . e2，其中子表达式具有类型：

e1 : A -> B
e2 : C -> D
join 的类型规则
  • 如果基本类型 B 和 C 不重叠，这个 join 就产生一个 disjointness 错误。
  • 否则，B 或 C 中必有一个是另一个的子类型。整个表达式的类型将是 A -> D。
不需要任何类型转换（cast），无论向上还是向下

如果字段 f 声明在 signature S 中，而 sup 和 sub 分别是类型为「S 的超类型」和「S 的子类型」的变量，那么 sup.f 和 sub.f 都是类型良好的。

  • 两种情况下表达式都不必然为空。
  • 两种情况下它都可能为空：如果 sup 不在 S 中，或者 f 被声明为偏的且 sub 在其定义域之外。
  • 另一方面，如果 d 是一个其类型 D 与 S 的类型不相交的变量——例如因为 S 和 D 都是某个其他 signature 的直接子类型——那么表达式 d.f 将是类型不良的，因为它必然总是求值为空关系。

B.6.4 Functions and Predicates · 函数与谓词

一条容易踩坑的规则

函数与谓词的调用是这样被类型检查的：确保实际参数表达式与形式参数不相交。（即检查「实参类型与形参类型有重叠」。）形式参数的类型不被用来解析实际表达式中字段名的重载。

函数与谓词的参数声明中隐含的约束，在「运行」该函数或谓词时会被合取到体约束上。然而当函数或谓词被「调用」时，这些隐含约束被忽略。

因此你不应该依赖这类声明约束具有语义效果；它们的意图是「冗余的文档」。Alloy 的未来版本可能会包含一种检查方案，用来判定实际表达式是否具有与形参的声明约束相容的值。

解读

这条规则的实际后果是：写 pred p (x: set S) {...} 时，set S 里的 set 在被调用时不起作用——它只在 run p 时生效。所以不要指望「形参的重数声明」在调用点帮你做校验；如果需要，就在体内显式写约束。

B.6.5 Integers and Type Checking · 整数与类型检查

语法层面的区分，而非类型层面的

只有整数表达式才取原始整数值。解析器区分关系表达式与整数表达式，所以解析 + 和 - 运算符的重载时不需要类型信息——它们在整数表达式中充当加法与减法，在关系表达式中充当并与差。

在这样一个约束中：

# S + S = 1

加号将被解析为一个关系运算符（而 # 运算符将被应用于整个左侧），因为否则整个约束在语法上就不合法了。

Int 类型（它代表「承载整数的对象」的预定义 signature）被类型系统当作任何其他基本类型一样处理。它与所有其他基本类型都不相交，除了全类型 univ。

关键字解释

one恰好一个
some一个或多个
记忆窍门（原文提供）

要记住 lone 意味着「零或一」，可以把这个词想成是 “less than or equal to one” 的缩写。

这些关键字被用在五种上下文中：

#上下文例子与含义

②量化表达式中的量词lone e — 说表达式 e 表示一个「至多含一个元组」的关系

B.7.1 Module Structure · 模块结构

本节涉及的生产式 
module    ::= header import* paragraph*
header    ::= module [path] moduleId [ '[' sigId,+ ']' ]
path      ::= id / [path]
import    ::= open [path] moduleId [ '[' sigRef,* ']' ] [as aliasId]
paragraph ::= sigDecl | factDecl | funDecl | predDecl | assertDecl
            | runCmd | checkCmd
sigRef    ::= [moduleRef] sigId | Int | univ
moduleRef ::= [path] moduleId [ '[' sigRef,* ']' ] / | aliasId /
funRef    ::= [moduleRef] funId
predRef   ::= [moduleRef] predId
assertRef ::= [moduleRef] assertId
模块与模型
  • 一个 Alloy 模型由一个或多个文件组成，每个文件含有一个模块。其中一个「主（main）模块」被提交分析；它直接（通过自己的 import）或间接（通过被导入模块的导入）引入其他模块。
  • 一个模型可以完全包含在一个模块中，此时不需要任何导入。
  • 没有任何段的模块在语法上合法，但毫无用处。

七类段（paragraph）

段在分析中的角色
signature表示集合，并在分析中被赋值 —— 因此其角色类似于编程语言中的「静态变量」
fact / fun / pred都是约束的封装（packagings of constraints）
run / check 命令用来指示 Alloy Analyzer 执行各种分析
导出规则（决定了「命令不可 import」）

一个模块导出的组件是「除命令之外的所有段」；只有主模块的命令在一次分析中是相关的。

路径、文件与根目录

文件系统约定
  • 模块由「一个路径 + 一个模块标识符」命名，并可被一个或多个 signature 形参参数化。
  • 路径必须对应「模块文件相对于某个默认根目录的目录位置」。一组根目录可以在 Alloy Analyzer 中指定，以便把库与特定领域的模型保存在不同的位置。
  • 模块标识符为 m 的模块必须存放在名为 m.als 的文件中。

导入与实例化

每个被导入模块需要一个独立的 import

它给出被导入模块的路径与名字、其形参的实例化（若有），以及一个可选的别名：

open [path] moduleId [ '[' sigRef,* ']' ] [as aliasId]
  • 被导入模块的每一个形参都必须有一个实例化的 signature 形参。实例化 signature 可以是类型、子类型或子集，也可以是预定义类型 Int 与 univ。
  • 如果被导入模块声明了一个「是某形参的扩展」的 signature，那么用「子集」或 Int 来实例化那个形参将是一个错误。
  • 同一个模块可以被导入多次。其结果不是创建该模块的多份拷贝，而是让同一个模块以不同的名字可用。
解读 · 「不产生多份拷贝」为什么关键

第 4 章的结论由此获得语言层面的保证：同一个 signature 无论被 open 多少次，在分析中都只有一个解释。这就是第 6.1.3 中 open util/ordering[Time] as TO 与 open util/ordering[Time]（后者在第 6 章的不同位置被反复引用）能够共存、且 Time 始终是同一个集合的原因。

限定名（qualified name）

何时必须限定

被导入模块的一个组件通过限定名引用，即「模块引用 + 组件名」：

sigRef  ::= [moduleRef] sigId | Int | univ
funRef  ::= [moduleRef] funId
predRef ::= [moduleRef] predId
assertRef ::= [moduleRef] assertId
  • 当一个组件引用会产生歧义时，它必须被限定。在「引用发生的模块」中声明的组件不必限定。
  • 模块在导入时也可以被赋予别名，以得到更简洁的限定名。一旦声明了别名，就不能再使用常规的模块名。
  • 模块引用可以是「导入语句中原样出现的路径 + 模块标识符 + 实例化形参」，也可以是「导入时声明的别名」。两者都以 / 结尾：moduleRef ::= [path] moduleId [ '[' sigRef,* ']' ] / | aliasId /

这正是 6.1 中 TO/first、PO/prevs、KO/min 的语法依据；也解释了 4.7 里 RoomKeyEvent extends hotel.Event 式引用为何需要带模块前缀。

顺序、预定义与封装

四条规则
  • 段在模块中可以任意顺序出现。没有「先定义后使用」的要求。import 语句之间的顺序也无关紧要，即使一个 import 为另一个提供实例化形参。
  • signature Int 是一个代表整数的特殊预定义 signature，可以在没有显式导入的情况下使用。
  • 一个模块不得引用「它没有导入的另一个模块」的组件，即使那个模块在别处与它一起被导入。（模块封装：可见性只沿自己的 import 图传播。）
  • 模块名占据自己的命名空间，因此可以与 signature、段、参数或变量的名字相同而没有冲突。

B.7.2 Signature Declarations · signature 声明

生产式 
sigDecl ::= [abstract] [mult] sig sigID,+ [extends sigRef] sigBody
          | [mult] sig sigID,+ in sigRef sigBody
sigRef  ::= [moduleRef] sigId | Int
sigBody ::= { decl,* } [constraintSeq]
mult    ::= lone | one | some
signature 表示原子的集合，共两种
  • 用 in 关键字声明的是「子集 signature（subset signature）」：sigID,+ in sigRef sigBody
  • 其余全部是「类型 signature（type signature）」：[abstract] [mult] sig sigID,+ [extends sigRef] sigBody

类型 signature → 一片森林

层级结构
  • 类型 signature 在类型系统中扮演「类型或子类型」的角色。
  • 不扩展任何其他 signature 的类型 signature 是「顶层 signature」，其类型是「顶层类型」。
  • 扩展了另一个 signature 的 signature 称为被扩展者的「子 signature（subsignature）」，其类型是被扩展者类型的子类型。
  • 一个 signature 不得直接或间接地扩展自身。
  • 因此类型 signature 形成一个类型层级，其结构是一片「森林」：以顶层类型为根的若干棵树的集合。
不相交规则（决定一切 disjointness 判断）

顶层 signature 表示互不相交的集合，且一个 signature 的各个子 signature 之间互不相交。因此任意两个不同的类型 signature 都是不相交的 —— 除非其中一个直接或间接地扩展了另一个，此时它们重叠。

子集 signature → 一个 DAG

与类型 signature 的三点关键差异
  • 子集 signature 表示的集合是「其所有父集（声明中列出的 signature）之并」的一个子集。父集可以是子集 signature，也可以是类型 signature。
  • 子集 signature 不得被扩展；并且同一个 signature 的各个子集之间不必互不相交。
  • 子集 signature 不得直接或间接地成为自身的父集。
  • 因此子集 signature 与其父集构成一个「有向无环图（DAG）」，以类型 signature 为根。
  • 子集 signature 的类型一般是一个「顶层类型或子类型的并（union）」，由「作为类型的父集」加上「作为子集的父集们的类型」构成。

——「子集之间不必不相交」正是 A.2.3 地铁线路题（Jubilee、Central、Circle 三个 sig ... in Station 可以共用车站）的语言依据。

抽象 signature

abstract

标记为 abstract 的 signature 被约束为「只包含属于某个扩展它的 signature 的元素」。

  • 如果没有扩展，这个标记没有任何效果。
  • 其意图是：抽象 signature 代表一种「由更『具体』的 signature 进一步细化的元素分类」。
  • 如果一个抽象 signature 没有扩展，abstract 关键字很可能是在提示「模型是不完整的」。
与 B.7.5 的作用域规则联动

因为抽象集被强制等于扩展之并，抽象 signature 的对象数 = 其各子 signature 对象数之和，所以作用域里抽象 signature 的界是推导出来的而非独立指定的。这就是 6.1.5 中「要表达『至多 k 个环』必须让 RingProcess extends Process，并给抽象父 Process 一个不小于子之和的界」的规范表述。

signature 上的重数

[mult] sig ...

任何重数关键字（lone/one/some）都可以关联到一个 signature，用来约束该 signature 集合的元素个数。

唯一的例外是 set —— 它没有效果，因此不能用在 signature 上。（注意这与 B.7.3 中 set 在集合声明里的作用不同。）

段体：字段声明 + signature 事实

sigBody ::= { decl,* } [constraintSeq]

signature 声明的体由「字段声明」加上「一个可选的、约束该 signature 元素的 signature 事实」组成。

  • 子类型 signature 继承它所扩展的 signature 的字段，以及那个 signature 所继承的字段。
  • 子集 signature 继承其父集 signature 的字段，以及父集们的继承字段。
两条字段名冲突禁令
  1. 一个 signature 不得声明一个「名字与某个继承字段名冲突」的字段。
  2. 如果两个子集 signature 的类型有重叠，它们不得声明同名字段。

原文的理由：这保证了「同名的两个字段只能声明在互不相交的 signature 中」，并且「总存在某个上下文使得两个同名字段能够被区分」。若非如此，某些重载将永远无法被解析。

一次声明多个 signature = 各自单独声明

在单条 signature 声明中一次声明多个 signature，等价于逐个单独声明。因此声明

sig A, B extends C {f: D}

引入了 C 的两个子 signature A 与 B，并为每一个声明一个字段 f。（注意：由于 A 与 B 是同一父集的子 signature，它们互不相交，因此同名字段 f 是合法的重载 —— 呼应上面的冲突禁令。）

signature 事实：隐式量化与隐式解引用

原文的精确定义

像任何其他 fact 一样，signature 事实是一个「总是成立的」约束。但不同于其他 fact 的是：signature 事实被「隐式地对该 signature 集合量化」。给定 signature 声明

sig S {…} { F }

signature 事实 F 被解释为仿佛写出了这样一条显式 fact：

fact { all this: S | F' }

其中 F' 与 F 相同，但把其中对 S 的每个字段 f（无论声明的还是继承的）的引用都替换为 this.f。在字段名前加特殊符号 @ 会抑制这一隐式展开。

sig Person {friends: set Person} {no friends & iden}
   ≡  fact { all this: Person | no this.friends & iden }

sig Person {friends: set Person} {no @friends & iden}
   ≡  fact { all this: Person | no friends & iden }  -- 引用字段本身
解读 · A.3.3 第五题的官方答案就在这里

「什么时候需要 @？」—— 当你在 signature 事实里想谈的是字段关系整体（例如把它与另一个字段比较、或对它做闭包）而不是「当前原子的像集」时。B.7.6 也再次重申：「在字段名被隐式解引用的上下文中 —— 即 signature 声明表达式与 signature 事实 —— @ 前缀阻止解引用」。

B.7.3 Declarations · 声明

生产式 
decl         ::= [part | disj] varId,+ : declExpr
letDecl      ::= varId = expr
declExpr     ::= declSetExpr | declRelExpr
declSetExpr  ::= [mult] expr
declRelExpr  ::= declRelExpr' [mult] -> [mult] declRelExpr'
declRelExpr' ::= declRelExpr | expr
mult         ::= lone | one | some
一套声明语法，三种用途

同一套声明语法同时用于：signature 的字段、函数与谓词的参数、以及量化变量 —— 下文统称「变量」。字段的解释略有不同，放在最后说明。

声明的两种效果

语义效果 + 类型效果
  • 语义上：约束变量可取的值。「左边所表示的关系」被约束为「右边声明表达式所表示的关系」的子集。
    • 当一次声明多个变量时可用 disj 与 part：disj 约束被声明变量互不相交；part 额外约束它们「对声明表达式所表示的关系构成一个划分」。
    • 下文的重数约束会进一步约束变量的值。
  • 为了类型检查：声明给变量一个类型。先为声明表达式求出类型，再把该类型赋给变量。
    • 声明表达式中出现的任何变量必须「已经被声明过」：或者在本声明所在的声明序列中更早，或者在其他地方更早。具体地：
      • 对量化变量 —— 指在一个外层量词之内；
      • 对 signature 的字段 —— 指该字段是继承来的；
      • 对函数/谓词参数 —— 指在外围函数或谓词的参数声明中。
注意

signature 中字段声明的声明表达式，不得引用「在其他 signature 中声明的字段」，除非它们是继承来的。

集合（一元）声明与默认标量

declSetExpr ::= [mult | set] expr

声明表达式是任意表达式。若它表示一个集合（一元关系），可以用重数关键字作前缀；省略关键字时，被声明变量默认被约束为「标量」（即单例集合）。四种写法的效果：

写法效果
省略约束为标量（单例集合）
set消除这个约束（可以是任意集合）
lone把约束弱化，允许变量表示一个「可选项（option）」：单例集合或空集
some约束变量表示非空集合
one没有效果，等价于省略

若表达式不表示集合（元数 ≥ 2），则不得用重数关键字作前缀。

箭头两侧的重数标注

declRelExpr ::= declRelExpr' [mult] -> [mult] declRelExpr'

若声明表达式形如 e1 m->n e2（m、n 为重数关键字），该箭头表示的关系，其元组是 e1 的元组与 e2 的元组的串接。此时：

  • 若标注 n 存在：所声明变量表示的关系，对 e1 中的每个元组 t1，被要求含有 n 个「以 t1 开头」的元组。
  • 若标注 m 存在：对 e2 中的每个元组 t2，被要求含有 m 个「以 t2 结尾」的元组。
  • 标注解释：lone = 零或一；one = 恰好一；some = 一或多。

当 e1、e2 是一元时，这些就退化为熟悉的概念：

声明含义
X -> one Y从 X 到 Y 的全函数（total function）
X -> lone Y从 X 到 Y 的偏函数（partial function）
X one -> one YX 到 Y 的双射（bijection）

这就是 6.2.1 中 Room <: keys : Room lone -> Key（偏函数）与 A.5.1 中 one -> one（双射）的读法。

嵌套箭头声明的展开

嵌套标注产生「逐像」约束

形如

r: e1 m -> n (e2 m' -> n' e3)

的声明既产生由 m、n 描述的约束，也产生由 m'、n' 描述的额外约束。嵌套部分的约束与「顶层箭头表达式的重数约束」相同，但施加于「所声明关系在某个元组之下的像」—— 即每个能产生嵌套表达式取值的像。展开式：

  • e1 表示集合时，等价于声明
    all x: e1 | x.r : e2 m' -> n' e3
  • e1 不是集合时，量化必须遍历相应的元组。例如 e1 为二元时，等价于声明
    all x, y: univ | x->y in e1 => x.(y.r) : e2 m' -> n' e3

——第 6.4.2 中把 data: set Addr -> set Data 精化为 data: Addr -> Data（即「每个地址至多映射一个数据」）正是这种「逐列重数」的应用；而 6.3 中 selection: Window -> set Asset 的嵌套标注同理。

字段声明：约束 this.f，类型为 S -> e

signature 内声明的核心差异

signature 内的声明本质上解释相同，但对字段 f 而言，声明约束适用于 this.f，而不是 f 本身 —— 即「用 f 解引用 signature 的某个元素所得的值」。因此：

sig S {f: e}

并不约束 f 是 e 的子集（若 f 是普通变量则会），而是蕴含

all this: S | this.f in e
  • 此外，e 中出现的任何字段都按「signature 事实的规则」展开（见 B.7.2）。
  • 重数约束与 disj/part 也做同样处理。例如若 e 表示一元关系，隐式的重数约束将使 this.f 成为一个标量，从而 f 本身表示「在 S 上的全函数」。
  • 字段的类型检查具有同样的风格：f 不被赋类型 e，而被赋类型 S -> e。即关系 f 的定义域类型是 S，而 this.f 与 e 类型相同。
这正是 6.2.1 那个「声明式子集」写法的存在理由

字段声明 keys: Room -> set Key 只约束「每个房间有若干钥匙」（从 Room 视角），无法表达「每把钥匙至多属于一个房间」（从 Key 视角）。要补上后者，必须写成约束形式的声明约束 Room <: keys : Room lone -> Key —— 详见 B.7.8 的「声明约束」小节。同理，第 6.4.2 中「缓存是内存的函数」也必须写成 cache: Mem -> lone Data 之类的显式约束来补足反向重数。

B.7.4 Constraint Paragraphs · 约束段

生产式 
factDecl   ::= fact [factId] constraintSeq
predDecl   ::= pred [sigRef ::] predId ( decl,* ) constraintSeq
funDecl    ::= fun [sigRef ::] funId ( decl,* ) : declExpr { expr }
assertDecl ::= assert [assertId] constraintSeq
constraintSeq ::= { constraint* }
constraint ::= … | [expr ::] predRef ( expr,* )
expr       ::= … | [expr ::] funRef ( expr,* )
段原文定义可被 Analyzer 做什么
fact一个「总是成立的」约束参与每一次分析（被合取进 F and D）
pred一个「可在不同上下文中实例化」的约束模板可被模拟（simulated），即 run
fun一个「表达式模板」可被调用；也可 run
assert一个「预期应从模型 facts 推出」的约束，因而是一种「有意的冗余（intentional redundancy）」可被检验（checked）；pred 与 fun 可被模拟
命名规则
  • fact 可以为了文档目的而命名。
  • assert 可以命名也可以匿名；但由于「检验一个断言的命令必须指名它」，所以匿名断言无法被检验。
  • 函数与谓词必须总是命名。
约束以序列给出，隐式合取

fact 由「可选的名字 + 一个以约束序列给出的约束」组成，序列中的约束被隐式合取：

fact Transitive {
  all a, b, c: univ | a in b.r && b in c.r => a in c.r
  no iden & r
}

谓词声明由「谓词名 + 若干参数声明 + 一个以约束序列给出的约束」组成，序列同样隐式合取。

匿名接收者参数 pred S::f

形式参数中的「第一个匿名参数」

参数声明可以包含一个以匿名形式声明的第一个参数。当谓词以下列形式声明时：

pred S::f (…) {…}

第一个参数被取为「signature S 上的一个标量」，并在谓词体内用关键字 this 引用它 —— 就好像声明本写成：

pred f (this: S, …) {…}

函数声明类似：它由「函数名 + 若干参数声明 + 一个表达式」组成；参数声明包含一个用于「函数结果」的声明表达式，它对应于表达式的值；第一个参数同样可以匿名声明，规则与谓词完全一致。

调用 = 文本内联

语义

谓词可以为每个参数提供一个表达式而作为约束被调用；函数 likewise 可以为每个参数提供一个表达式而作为表达式被调用。

调用可以被视为「文本内联（textual inlining）」：

  • 谓词调用得到的约束 = 取谓词体的约束，把形参替换为调用中相应的表达式；
  • 函数调用得到的表达式 = 取函数体的表达式，把形参替换为调用中相应的表达式。
两个直接推论

① 不支持递归调用。这是第 4.4.3 中 pred path 必须借助传递闭包 ^ 来表达的深层语言原因，也是第 6.1.4 中 send 谓词不能自递归的原因。

② 因此每次调用都拥有自己的局部变量 —— 内联把形参换成调用点的表达式，不存在「同名参数互相冲突」的危险，嵌套调用也各自独立。

接收者语法与解耦

p(a,b,c) 与 a::p(b,c) 等价

函数或谓词调用可以把它的第一个参数放在「接收者位置」。因此除了写 p (a, b, c)，还可以写 a::p (b, c)。

调用的形式不受声明形式的约束。虽然常见做法是「既用匿名接收者参数声明、又用接收者语法调用」，但这并非必需：

  • 第一个参数可以不论声明格式而以接收者形式呈现；
  • 第一个参数也可以不论使用格式而匿名声明。
  • 特别地：当第一个参数不是标量时，用接收者形式调用函数或谓词往往是方便的 —— 尽管在那种情况下它不能用接收者语法来声明。（因为 pred S::f 的接收者被定义为「S 上的一个标量」。）

——第 6.4 中 c.mem.load [a]、第 6.1 中 p.toSend 这类「接收者不是标量也能用」的写法，其规范依据正是这一条。

段的名字唯一性

在一个模块内，不得有两个约束段声明同名；一个约束段也不得与某个 signature 同名。（注意：这与「run 命令必须指名断言」共同决定了 assert 的命名策略。）

B.7.5 Commands · 命令

生产式 
runCmd   ::= [commandId :] run funRef [scope]
           | [commandId :] run predRef [scope]
checkCmd ::= [commandId :] check assertRef [scope]

scope      ::= for number
             | for [number but] typescope,+
typescope  ::= [exactly] number scopeable
scopeable  ::= sigRef | int
sigRef     ::= [moduleRef] sigId | Int | univ
命令是什么

命令是「指示 Alloy Analyzer 执行一次分析」的指令。分析就是「求解约束」：寻找一个满足约束的实例。

  • run 命令让分析器搜索一个「见证某个函数或谓词之一致性（consistency）」的示例；
  • check 命令让它搜索一个「表明某个断言不成立」的反例。
命令名的用途与唯一性

命令名在图形界面（或命令行）中用于选择要执行的命令。在 GUI 中命令从弹出菜单里选取；命令名存在的唯一理由，是当同一个断言/函数/谓词有很多命令时，让命令更容易被识别。一个模块内不得有两个命令同名。

三种命令各自解出的约束

核心表格（F = 所有 facts 之合取，D = 所有声明约束之合取）
命令被求解的约束说明
run 体为 P 的谓词 P and F and D D 包含该谓词「参数声明」的约束。
注意：当谓词体为空时，约束就只是「模型的 facts 与声明约束」
run 体表达式为 E、名为 f 的函数 f = E and F and D 这里变量 f 代表「该表达式的值」；D 同样包含函数参数的声明约束
check 体为 A 的断言 F and D and not A 也就是 F and D implies A 的否定；此处 D 是所有声明约束之合取
原文给出的实用建议

空谓词常常是「分析的有用起点」，用来判定模型是否一致；若一致，还可以检视它的若干实例。即写 run {}。

反复强调的那条不对称规则（此处再次出现）

注意：谓词或函数的「声明约束」在「该函数或谓词被 run 时」会被使用，但在「该谓词或函数被调用（invoked）时」会被忽略。

与 B.6.4 的表述完全一致 —— 因此形参声明中的 set/one/lone 只是文档，不构成调用点的校验。

被找到的实例给哪些变量赋值

三类变量
  • 模型的 signature 与字段；
  • 若实例来自谓词或函数：该谓词/函数的各个参数 —— 其中若第一个参数是匿名声明的，会有一个名为 this 的参数；
  • 若实例来自函数：一个代表「表达式值」的变量，其名字与函数本身相同。

分析器还可能给「Skolem 常量」赋值，作为存在量词的见证。是否这样做，以及「全称量词内部的存在量词」是否也被 Skolem 化，取决于用户设定的偏好（preferences）。

——这就是第 5.2.2 中「Skolem 化既减少搜索空间、也可能改变可视化」的规范来源。

作用域：什么被定界

只有类型 signature 被定界

命令的作用域规范「对赋给类型 signature 的集合的大小设定上界」，从而把搜索变为有限。

只涉及类型 signature；子集 signature 不得在作用域规范中被定界。

本节余下内容中，「signature」应读作与「类型 signature」同义。

界的确定规则（四条，按顺序）

写法结果
不给作用域规范使用「3 个元素」的默认作用域：每个顶层 signature 被约束为「至多表示含 3 个元素的集合」
for N默认值改为 N
for N but ...but 之后列出的每个 signature 受其给定界约束；任何未给出界的顶层 signature 由默认值 N 定界
没有默认值的显式列表列出的每个 signature 受其给定界约束

隐式界（四条，按顺序）

条件隐式界
抽象 signature 无显式界，但其子 signature 都有界（隐式或显式）它的界 = 其各子 signature 界之和
抽象 signature 有界（显式或默认），且其子 signature「除一个之外」都有界剩下那个子 signature 的界 = 抽象 signature 的界 − 其余子 signature 界之和
例：for 4 but 3 A, 1 B, 1 C（A、B、C 扩展 abstract sig X）⇒ X 为 5，且未指定的那个扩展被定界为 1
用重数关键字 one 声明的 signature界为 1
若按上述规则无法为某 signature 确定隐式界该 signature 没有隐式界
原文紧接的一条兜底规则

如果按上述规则无法为某个 signature 确定隐式界，那么该 signature 就没有隐式界。（这通常会使作用域不满足下面要求的「完备性」而被 Analyzer 拒绝。）

exactly：把上界变成「上下双界」并向上传播

若作用域规范使用了关键字 exactly，该界就被当作「对该 signature 基数的上界与下界」。隐式界的规则相应调整。例如：一个「其子 signature 被 exactly 约束」的抽象 signature，也将同样被 exactly 约束。

解读 · 为什么第 6 章反复用 exactly

第 6.1.5 中「用 exactly 让恰好 k 个环成立」、第 6.2 中「exactly 1 Guest 逼出更小的反例」、第 6.4 中「exactly 固定内存大小」都是同一条规则的应用：exactly 既收紧了搜索空间（消掉「更少元素」的等价实例），又通过对抽象父集的自动传播避免了不一致的作用域报错。

作用域必须满足的三条性质

原文列表
性质原文含义
一致（consistent）「至多有一个界可以与任何 signature 相关联」 —— 无论该界是隐式的、显式的、还是默认的。
完备（complete）每个顶层 signature 都必须有一个界。
均匀（uniform）一个「没有界的 signature」不得拥有「有界的子 signature」。
解读 · 三条性质各自防的是什么

一致防「同一个 signature 被两个不同的界夹击」（默认 N 与显式列表重叠时会发生）；完备防「某个顶层集无上界 ⇒ 搜索空间无限」；均匀」防「界在层级中出现空洞」—— 若父集未定界而子集已定界，那么搜索空间里出现的「父集比子集大」的实例，并不对应原模型的任何一个合法解释（因为父集的元素数不可能少于其各不相交子集之和），得出的结论也就失去意义。这就是第 6.1.5 中给 RingProcess 定界时必须连带给抽象父 Process 定界的直接原因。

整数作用域：Int 与 int

两个不同的东西
  • Int（大写）是一个 signature（承载整数的对象集合），因此可以出现在 sigRef 中，被当作普通 signature 定界。默认情况下 Int 被定界为 3 个对象；由于这些对象被期望取不同的整数值，这意味着界内可用的值是 0、1、2。
  • int（小写）是一个「可定界的类别（scopeable）」，出现在 scopeable ::= sigRef | int 中。对 int 指定界 k 会把可用的原始整数值限制在 0 … 2^k − 1（含两端）。整数界的默认值是 5 —— 也就是说，在没有显式整数界时，可用的原始整数值是 0 到 31。
实践后果：这是最容易踩的坑

第 6.1.7 中「机器直径 12 有解、13 无解」这类基数结论，必须配合足够大的 Int 界与 int 界；否则「找不到更大的实例」完全可能只是整数空间不够造成的假阴性。附录 A.4.2 明确要求「显式地定界整数」，理由就在这里。回顾 B.1 的关键字表：Int 与 int 是两个不同的保留字。

B.7.6 Expressions · 表达式

生产式 
expr ::= [@] varId | sigRef | this
     | none | univ | iden
     | unOp expr | expr binOp expr | expr '[' expr ']'
     | { decl,+ | [constraint] }
     | let letDecl,+ | expr
     | if constraint then expr else expr
     | Int intExpr
     | [expr ::] funRef ( expr,* )
     | ( expr )

letDecl ::= varId = expr
binOp   ::= + | - | & | . | -> | <: | :> | ++
unOp    ::= ~ | * | ^
两类表达式

Alloy 中有两类表达式：关系表达式与整数表达式。当不加限定时，术语「表达式」指的是「关系表达式」。

每个关系表达式都表示一个关系。集合被表示为「元数 1 的关系」，标量被表示为「单例集合」，元组是「单例关系」。

Alloy 的分析涉及「求约束的解」。对于任何一个可能作为该约束之解的候选实例，约束中的每个表达式都有一个值，该值由「实例对变量所赋的值」给出。

简单表达式：变量、signature 引用、this

expr ::= [@] varId | sigRef | this
  • 若变量是一个字段名，其值 = 在被求值的实例中绑定给该字段的值。
    在「字段名被隐式解引用」的上下文中 —— 即 signature 声明表达式与 signature 事实 —— @ 前缀阻止解引用（见 B.7.2）。若存在多个同名字段，该引用会被解析；若有歧义则被拒绝（见 B.6）。
  • 若变量是量化变量或 let 绑定变量，其值由该绑定决定。
  • 若变量是某个函数或谓词的参数：当前的分析必须是对该函数或谓词的一次 run —— 因为若函数或谓词被调用，其含义已由内联取得，参数早已被替换掉 —— 而在搜索期间，该变量的值被「试探性地（speculatively）」绑定到每一个可能的值。

三个关系常量

none / univ / iden
常量含义
none空的元数 1 关系，即「不含任何元素的集合」
univ全域的元数 1 关系，即「含每个元素的集合」
iden恒等关系，即「把每个元素与自身相关联」的二元关系
一个极易出错的点（原文特意提醒）

注意 univ 与 iden 是在「全体原子的宇宙」上被解释的。所以像

iden in r

这样的约束将不可满足，除非关系 r 的类型是 univ -> univ。要说「r 是自反的」，你更应当写

t <: iden in r

例如，其中 r 的类型是 t -> t。

——这正是 A.1.2/A.1.3 中「自反性必须写成 t<:iden in r」的规范出处，也是本章多处的 <: 用法的根由。

^ee 的传递闭包

  • 前三个（一元运算符）要求 e 是二元的。

  • 限制运算符要求其参数 e2 是一个集合。
  • 注意 e1[e2] 等价于 e2.e1，但点运算符与方括号运算符有不同的优先级（点在 B.4 中优先级 2，方括号是 4）。

每个运算符的精确定义

原文逐条
  • 转置是关系的镜像：把每个元组反转所得的关系。
  • 传递闭包是「包含它的最小的传递关系」（传递 = 只要存在 b 使关系把 a 联到 b、b 联到 c，就把 a 联到 c）。
  • 自反-传递闭包是「包含它的最小的、既传递又自反的关系」（自反 = 包含恒等关系）。
  • 并、差、交是标准的集合论运算符，施加于「被视作元组集合的关系」：并含 e1 或 e2 中的每个元组；交含两者都有的元组；差含「在 e1 中但不在 e2 中」的元组。
  • 连接（join）：取「第一个关系的每个元组」与「第二个关系的每个元组」的每种组合，若第一个元组的最后一个元素与第二个元组的第一个元素匹配，则把两个元组串接、并省略匹配的那个元素。
  • 积（product）：取两个关系元组的每种组合，并纳入它们的串接。
  • 域限制：e1 对 e2 的域限制含「e1 中所有以 e2 的某个元素开头」的元组；值域限制含「e1 中所有以 e2 的某个元素结尾」的元组。这两个运算符在解析重载时特别好用（见 B.6）。
  • 关系覆盖：e1 ++ e2（e1 被 e2 覆盖）含 e2 的全部元组，此外还含 e1 中那些「第一个元素不是 e2 中任何元组的第一个元素」的元组。
解读 · 覆盖定义与 6.3 的 ++ 用法严丝合缝

注意覆盖的定义只看「第一个元素」，因此 ++ 只适用于二元关系。第 6.3 中 buf' = (buf - cs.assets) ++ (cs.selection ++ ...)、第 6.4 中 m.data' = m.data ++ (a -> d) 之所以能用覆盖来表达「除被改写的地址外保持不变」，正是因为「同键覆盖、异键保留」就是这条定义的直接后果；而 B.6.1 之所以规定「对不相交关系用 ++ 报 disjointness 错误」（即使结果非空），也是因为覆盖的语义预设了两边会重叠，否则你该用 +。

演绎（comprehension）表达式

expr ::= { decl,+ | [constraint] }

表达式

{x1: e1, x2: e2, … | F}

表示这样的关系：取所有形如 x1 -> x2 -> … 的元组，其中 x1 从集合 e1 中选取、x2 从 e2 中选取，依此类推，且约束 F 成立。

  • e1、e2 等必须是元数 1 的（unary）；
  • 且不得带重数关键字作前缀；
  • 更一般的声明形式不允许，唯一的例外是 disj 与 part 关键字的使用。

这就是 6.1.4 中 {p: Process | ...}、以及 B.7.7 中把 Int ie 定义为 {i: Int | int i = ie} 的语法基础。

let 表达式

expr ::= let letDecl,+ | expr

表达式

let v1 = e1, v2 = e2, … | e

等价于表达式 e，但其中每个绑定变量 v1、v2 等被其赋值的表达式 e1、e2 等替换。

  • 出现在 let 声明表达式中的变量必须早先已被声明。
  • 不允许递归绑定。

if 表达式与其余形式

三条收尾
  • if 表达式：if F then e1 else e2 在约束 F 为真时取值 e1，否则取值 e2。
  • 调用表达式 [expr ::] funRef ( expr,* ) 的含义在 B.7.4 解释；整数表达式 Int intExpr 的含义在 B.7.7 解释。
  • 括号：( expr ) 可用来强制某种特定的运算符应用次序。

B.7.7 Integers · 整数

生产式 
constraint ::= intExpr [neg] intCompOp intExpr
expr       ::= Int intExpr

关键不变式：不同的整数对象绝不携带相同的原始整数值

Distinct integer objects never carry the same primitive integer value. 所以下面的断言恒真：

assert IntegersCanonical {no disj i, j: Int | int i = int j}
解读 · 这就是第 6.4 记忆模型能work的前提

第 6.4 中 Canonicalize（「没有两个内存具有相同的 data」）是需要显式写出的 fact；而对 Int 而言，「值 → 对象」的单射性是语言保证的，无需 fact。因此 A.5.2 中「one sig 表示常量」能成立，也正因为每个原子有唯一的身份。原书用 IntegersCanonical 这个名字点明它与内存正规化的同构关系。

从关系表达式取得原始整数值

sum expr 与 int expr

两种运算都返回「与关系表达式 e 所表示集合中的整数对象所关联的整数值之和」。int e 与 sum e 之间没有语义差别。

  • 意图是：用 sum 来明确标示「该表达式被预期不是单例」。
  • 通常 int 会应用于「表示单个整数对象」的表达式，但它被定义在「整数对象的集合」上，以便它总是有值。（空集上的和是 0 —— 因此 int 永不失败。）
实践提示

这解释了为什么第 6 章里 #(set) 与 sum 常被混用：两者都是「把关系折算成整数」的桥，而 int e 在 e 恰好为单例时与直接取该原子的值一致。写 int 而实际得到多元素集合时结果会是「求和」而不是报错 —— 这是一个静默陷阱。

# expr：基数

原始整数值也可以从「任意类型的关系表达式」通过基数字符串表达式取得：#e 的值对应于 e 的基数 —— 即「关系表达式 e 所表示的关系中元组的个数」。

注意是「元组个数」而非「原子个数」：因此 #(A -> B) 是 |A|·|B|，而不是 |A|+|B|。这与第 6.1.7 中「用 # 数环上的进程数」时必须先降为一元关系相呼应。

数值常量

数值常量可以作为整数表达式使用：intExpr ::= number。一个数值常量是一串一个以上的数字，其第一位不是零。（即不允许 007 这类写法；0 本身是单个数字且第一位非零的情形由「一位数」满足 —— 原文的表述严格来说排除了前导零。）

算术与比较

intOp ::= + | -

i + j 求值为整数表达式 i 与 j 的值之和；i - j 求值为 i 的值减 j 的值。

注意加号与减号是重载的：它们在整数表达式中充当「算术运算符」，在关系表达式中充当「并与差」。

比较为真的条件
i = j两个整数表达式有相同的值
i < ji 小于 j
i > ji 大于 j
i =< ji 小于等于 j
i >= ji 大于等于 j
为什么是 =< 而不是 <=

「小于等于」运算符被非常规地写成「等号在前」，以免它看起来像一个箭头，从而可能与逻辑蕴含混淆。

——这条设计说明与 B.1「=> 与 -> 都是单 token」互为因果：Alloy 里箭头家族太重要，不能让 <= 被误读成 < 加 = 或某种箭头变体。

没有 !=、没有 <>：不等只能通过取反表达。比较运算符取反的形式

e1 not op e2

等价于把否定移到外面：

not e1 op e2

否定运算符 ! 与 not 含义相同。

sum decl,+ | intExpr：区间求和

整数表达式

sum x: X, y: Y, … | ie

求值为「对 x、y 等的所有不同绑定，整数表达式 ie 所能取的诸值之和」。

  • 最一般的声明形式都被允许；
  • 不过当绑定不是一阶的时候，分析可能不可行。
if 与 let 也可用于整数表达式 
intExpr ::= if constraint then intExpr else intExpr
          | let letDecl,… | intExpr

含义与关系表达式相同，只是值换成整数值。

从值回到对象：Int 运算符

expr ::= Int intExpr

表达式 Int ie 表示「与整数表达式 ie 的值相关联的那个整数对象」；它等价于

{i: Int | int i = ie}
  • 有可能在某次具体分析中，作用域太小而未能提供这样一个整数。在那种情况下，Int ie 表示空集。
  • 注意：由于没有两个整数对象持有相同的整数值，它绝不会表示含多于一个对象的集合。
这是「找不到反例」的又一来源

Int ie 在界外静默地返回空集而不是报错。所以「Int 40」在默认的 Int 界 3（可用值 0/1/2）下是 none。第 6 章凡是用 Int k 或依赖整数计数的地方，都必须同时检查 Int 与 int 两个作用域 —— 与 B.7.5 末尾的提醒完全一致。

语法上 Int 出现在 expr（关系表达式）的产生式中 —— 即 Int ie 是一个关系表达式（返回集合），而 int e 是一个整数表达式（返回原始值）。这一对「往返」是 Alloy 整数机制的全部。

总纲

基本约束（elementary constraints）由「把量词应用于关系表达式」或「比较关系表达式或整数表达式」构成。

量化表达式（对表达式施加量词）

constraint ::= quantifier expr
约束为真的条件
no ee 求值为「不含任何元组」的关系
some ee 求值为「含一个或多个元组」的关系
lone ee 求值为「至多含一个元组」的关系
one ee 求值为「恰好含一个元组」的关系
all e被静态语义检查拒绝：它没有含义。
解读 · 为什么 all e 无意义而其余四个有

这四个量词都是关于「关系里元组个数」的基数谓词，可以直接对表达式求值；而 all 语义上是「对所有绑定成立」，必须搭配一个声明（范围）才有意义 —— 所以它只出现在 all decl,+ constraintBody 那条产生式里。这就是第 5 章中「all r 会被报错、而 lone r/no r 是合法的表达式级断言」的规范解释，也是 Traces 里 no r.elected & ... 这类写法合法的原因。

比较约束

constraint ::= expr [neg] compOp expr，compOp ::= in | =
约束为真的条件
e1 in e2e1 求值所得的关系是 e2 求值所得关系的子集
e1 = e2e1 与 e2 求值为同一个关系

  • 取反形式 e1 not op e2 等价于 not e1 op e2；! 与 not 含义相同。
  • 对整数表达式的比较在 B.7.7 中讲述。（注意 BNF 中 compOp 只有 in 和 =，： 在「声明约束」那一条单独出现。）

否定与逻辑组合

constraint ::= neg constraint | constraint logicOp constraint

not F 在 F 为假时为真，反之亦然；not 与 ! 可互换。

约束为真的条件
F and GF 真且 G 真
F or GF 与 G 中有一个或两个为真
F iff GF 与 G 同假或同真
F implies GF 为假，或 G 为真
F implies G else H「F 与 G 都真」或者「F 假且 H 真」

逻辑运算符可以用符号可互换地书写：&& 代替 and，|| 代替 or，=> 代替 implies，<=> 代替 iff，逗号 , 代替 else。

两个必须记住的组合后果

① 逗号就是 else：所以 all x: X | F, G 里的逗号不是「合取的分隔」，而是「F 蕴含 G 否则……」。要写合取请用 { }（约束序列）或 &&。
② else 结合最近的 then（B.4），因此 p => q => r, s 解析为 p => (q => r, s)。

约束序列

constraint ::= constraintSeq，constraintSeq ::= { constraint* }

约束

{ F G H … }

等价于合取

F and G and H and …

如果序列中不含任何约束，则该约束为真。（空体 {} 恒真 —— 这正是 run {} 只检查模型一致性的语法基础。）

量化约束

constraint ::= quantifier decl,+ constraintBody

它由「一个或多个声明」加上「一个体」构成。体是「竖线加单个约束」还是「约束序列」并无区别 —— 提供两种形式是为了让「体是多个约束时可以省略竖线」。原文列出四种等价写法：

all x: X | { F }        -- 有些用户偏好永远写竖线
all x: X { F }          -- 有些用户偏好永不写竖线，即使序列只含一个约束

这些形式都可接受且可互换。

五种量词的含义（关于「绑定的个数」）
约束为真的条件
all x: e | FF 对 x 的所有绑定为真
no x: e | FF 对 x 的没有任何绑定为真
some x: e | FF 对 x 的一个或多个绑定为真
lone x: e | FF 对 x 的至多一个绑定为真
one x: e | FF 对 x 的恰好一个绑定为真
多声明：后声明可以引用先声明

绑定变量的范围与类型由其决定（见 B.7.3）。在声明序列中，每个被声明的变量可以被其声明本身、或此前已声明的变量绑定。例如约束

all x: e, y: S - x | F

中，x 遍历表达式 e 的值（假定 e 表示一个集合），而 y 遍历集合 S 中除 x 之外的所有元素。

多声明不是嵌套量词的简写（原文重点澄清）

当声明多个变量时，量词在「所有变量的绑定」上被解释。因此

one x: X, y: Y | F

为真，当且仅当恰好存在一个「给 x 和 y 赋值并使 F 为真的绑定」。

所以，尽管「带多个声明的量化约束」对某些量词而言可以看作嵌套的单声明约束的简写，但一般来说并不成立。具体地：

all x: X, y: Y | F   ≡ 是   all x: X | all y: Y | F
one x: X, y: Y | F   ✗ 不是   one x: X | one y: Y | F
这是全书最容易写错的一条

all 与 no 可以拆开，one/some/lone 不可以。第 6.1.4 中 one p: Process | ... 与第 6.2 中「恰好一个操作」的写法依赖的正是「绑定数」而非「每个变量的取值数」。写 some x: X, y: Y | F 时，只要有一对 (x,y) 使 F 为真即成立；而嵌套写法则要求「存在某个 x，使得存在某个 y……」——两者在 F 非对称时完全不同。

高阶量化

一个量化约束可以是高阶的（higher-order）：即它可以把「非标量的值」绑定到变量上。该约束是否可分析，取决于分析器能否对它做 Skolem 化，以及若不能，作用域有多大。（与 B.5.2 表述一致。）

let 约束

constraint ::= let letDecl,+ constraintBody

let 约束允许引入一个变量，用来「突出一个重要的子表达式」或「通过提取重复出现的子表达式使约束更短」。

let x1 = e1, x2 = e2, … | F

等价于把约束 F 中每个绑定变量 x1 的出现替换为表达式 e1、x2 替换为 e2，依此类推。

  • 与所有声明一样，let 声明按顺序解释，且不得递归。
  • 谓词调用在 B.7.4 中讲述。

附录 A.2.2 的 inv 谓词（let addr = b.addr | ...）与第 6.4 中大量 let 用法都受此条约束：let 是纯文本替换，不引入新的绑定，也不改变量词范围。

声明约束（declaration constraint）—— 本节最重要的补充工具

constraint ::= expr : declExpr 
declExpr ::= [mult | set] expr
           | expr [mult] -> [mult] expr

声明约束有两个用处。

用处一：把重数约束施加到「任意表达式」上

声明本身只允许把重数约束加在变量上；声明约束则可以加在任意表达式上。例如

p.q : t one -> one t

就说「p 与 q 的连接（join）是一个双射」。

用处二：表达「声明无法表达」的额外重数约束

考虑类型 A -> B 的关系 r，它可以被声明为 A 的字段：

sig A {r: set B}

由于声明约束适用于 this.r，它们无法从 B 的视角约束该关系的重数。要说「r 至多把一个 A 映到每个 B」，可以添加如下作为 fact 的声明约束：

fact {r: A lone -> B}
这条正是第 6.2.1 那个「反常写法」的官方解释

酒店模型里的 Room <: keys : Room lone -> Key（「每把钥匙至多属于一个房间」）不能写进字段声明，只能以声明约束的形式出现在 fact 里。第 6.4.2 中「缓存/内存的反向重数」同理。同时注意：这里必须用 <: 把关系限制到 Room，否则「lone」会被判为对整个 keys（含 Undefined 等部分）施加约束，从而产生过强约束 —— 呼应第 5.4 的「宁欠勿过」。

用处三：突破「声明只允许一个箭头」的限制

声明的另一个缺陷是它们只允许给出「一个箭头周围」的重数。对类型 A -> B -> C 的关系 p，形如

all r: A -> some (B -> C) | …

的声明使 r 在 A 上是全（total）的。而「R 把 A -> B 中的一个对映到 C 的每个元素」这一约束无法在该声明中表达，因为它需要对表达式做不同的解析 —— 让箭头向左结合而非向右结合。要表达它，可以用这样的声明约束：

all r: A -> some (B -> C) | r : (A -> B) some -> C  => …
解读

请注意这条示例的写法本身：「声明约束」被放在一个 all 量化里，用 => 与体相连 —— 因为它是一条约束而不是声明，所以在任意约束位置都能出现。这正是第 6.3 中「对每个窗口，选中集是若干资产的对」这类三元重数唯一可行的写法。

括号

一个约束可以加括号以强制特定的运算符应用次序：constraint ::= ( constraint )。

  24. 嵌套箭头标注逐像展开：r: e1 m -> n (e2 m' -> n' e3) ⇒ all x: e1 | x.r : e2 m' -> n' e3；e1 非集合时须遍历元组。X one->one Y = 双射，X -> lone Y = 偏函数。
  25. 字段声明约束 this.f 而非 f，字段类型是 S -> e —— 这是「反向重数必须写成声明约束」的根本原因。
  26. 四种段：fact 恒真 · pred 约束模板 · fun 表达式模板 · assert 是「有意的冗余」；匿名 assert 无法被 check；模块内段名唯一且不得与 sig 同名。
  27. 调用 = 文本内联 ⇒ 不支持递归；每次调用有独立局部变量。pred S::f 的接收者是 S 上的标量，但调用形式不受声明形式约束，且接收者不必是标量。
  28. 命令解出的约束：谓词 P and F and D；函数 f = E and F and D；断言 F and D and not A。空体谓词 = 模型一致性检验的标准形式。各命令相互独立，实例之间不要求相容。实例还会给 Skolem 常量赋值（依用户偏好）。
  29. 作用域：只定界类型 sig，默认 3；for N、for N but ...、显式列表三种写法；抽象界 = 子之和，「除一外全有界 ⇒ 余者为差」，one sig 界为 1，显式优先，推不出则无隐式界。
  30. exactly 使界成为上下双界并自动传播给抽象父集 —— 第 6 章用它收敛搜索空间。
  31. 作用域必须一致 / 完备 / 均匀：任一 sig 至多一个界；每个顶层 sig 有界；无界的 sig 不得有有界的子。
  32. 整数界：Int 默认 3 个对象 ⇒ 可用值 0、1、2；int 默认 5 位 ⇒ 原始值 0–31。
  33. 表达式即关系；none/univ/iden 三常量定义在全体原子上，所以「自反」必须写 t <: iden in r，iden in r 除非 r: univ->univ 否则不可满足。
  34. 运算符语义全部以「元组」定义：join 省略匹配元素、积做串接、限制要求右侧是集合、覆盖只看第一个元素（故 ++ 只适用于二元）。
  35. 演绎表达式 {x1: e1, ... | F} 中各 e 必须一元且不得带重数前缀，声明形式除 disj/part 外一律不许。
  36. let 是纯文本替换，不得递归，被绑定的变量必须早先声明；if F then e1 else e2 是表达式级的。
  37. 两类整数：对象 vs 原始值。对象可作原子、可量化、不可直接运算；原始值不可作原子、不可量化。Int ie 是关系表达式（界外静默返回空集），int e/sum e 是整数表达式；int 定义在集合上故永不失败。
  38. 不同整数对象必持不同值（IntegersCanonical 恒真）；=< 而非 <= 是为了不像箭头；没有不等运算符，只能 not op。
  39. #e 数的是元组个数，不是原子个数。
  40. 量化表达式：no/some/lone/one e 都是元数无关的基数谓词；all e 被静态检查拒绝。
  41. 相等是外延的；in 是子集；! 与 not 互换；else 可用逗号书写（陷阱！）；空约束序列恒真。
  42. 多声明量词不是嵌套量词的简写：all x:X, y:Y | F 是简写，one x:X, y:Y | F 不是 —— 它数的是「绑定」的个数。这是本附录最容易写错的一条。
  43. 声明约束 expr : declExpr 的三个用处：对任意表达式施加重数（p.q : t one->one t）、补足字段声明无法表达的反向重数（r: A lone -> B）、突破「声明只允许一个箭头」从而改变箭头结合方向（r : (A -> B) some -> C）。
  44. 高阶量化被允许但可能不可分析：能否 Skolem 化决定可行性，否则受作用域大小编译。
