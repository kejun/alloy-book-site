2.0为什么选地址簿这个例子

选它是因为「对大多数读者都熟悉」。但 Jackson 借机说了一段关于模型规模的重要论断：

十行模型 vs 十行程序

「A ten-line program can't do very much, and has almost nothing in common with a thousand-line program. But a ten-line model can be very useful, and doesn't differ that much from a hundred-line model, which is often all that's needed to explore a difficult design issue.」

十行程序做不了什么，跟一千行程序几乎没有共同点； 但十行模型可以非常有用，跟一百行模型差别不大——而一百行往往就足以探索一个困难的设计问题。 模型的价值不随规模线性增长，这是轻量级方法可行的根基。

地址簿的领域概念

概念含义关键性质
address book一个小数据库，把邮件地址与更好用的短名字关联起来—
alias（别名）为某个联系人创建的昵称，可代替其地址使用地址变了，别名不必变
group（组）像别名，但关联一整个联系人集合（比如一个家庭）一对多
埋下的伏笔：间接引用

用户定义 group 时，常常插入 alias 而不是真实邮件地址，这样某人邮箱变了只需在一处修改， 即使它隐式出现在许多 group 里。——这正是第 1 章说的 indirection，也是后面所有麻烦（和所有价值）的来源。 名字可以指向名字，形成任意长度的命名链（naming chains）。

2.1Statics: Exploring States · 静态：探索状态

第一个模型：三行声明

module tour/addressBook1

sig Name, Addr {}

sig Book {
  addr: Name -> lone Addr
}

「That's a complete Alloy model.」——这就是一个完整的 Alloy 模型。它引入了三个 signature（签名）： Name、Addr、Book，每个代表一个对象集合。Book 有一个字段 addr。

最关键的语义：字段是「多一路」的关系

addr 事实上是一个三元映射（three-way mapping），关联 book、name、address， 当「在书 b 中，名字 n 映射到地址 a」时，它包含元组 b -> n -> a。

而表达式 b.addr 表示「书 b 的从名字到地址的映射」。 也就是说：x.f 这个点操作符做的事，是把关系中最左列为 x 的那些元组取出来、并去掉最左列。 这是理解 Alloy 全部导航表达式的唯一钥匙，第 3.4 节会严格化为 join 算子。

addr 关系的实际内容（三元组）
Book0→Name0→Addr0
Book0.addr 求值后（二元组）
Name0→Addr0
图 2-B　字段是「隐式带上接收者」的关系（对应原书 fig. 2.1 实例）

重数（multiplicity）：lone

声明中的关键字 lone 表示重数——这里是「每个名字至多映射到一个地址」。 现在只建模简单别名，group 留到后面。

重数含义数量范围
（缺省）恰好一个= 1
lone至多一个0 或 1
one恰好一个（显式写出）= 1
some至少一个≥ 1
set任意（含空）≥ 0

没有命令 = 没法分析

要点

「This model contains no commands, so there's no analysis that can be done (beyond simple static semantic and type checks).」
模型只声明结构时，分析器只能做语义与类型检查。要有分析，必须有 run 或 check 命令。

第一次模拟：空谓词 + run

pred show () {}
run show for 3 but 1 Book
  • 谓词体为空——后面会往里加约束。
  • 命令指定了一个 scope（作用域）来限定实例搜索：每个签名至多 3 个对象， 但 Book 限为 1 个，因为现在只想看单个地址簿。
极易混淆的一点

「The scope is for the purpose of analysis alone; the model doesn't limit the size or number of address books.」
scope 只服务于分析，模型本身并不限制地址簿的大小或数量。 换句话说：for 3 不是模型的一部分，它只是「这次搜索请只看 3 个对象以内」的指令。 把 scope 误当成模型约束，是初学者最常见的理解错误。

关于「工具选了哪个实例」

运行后得到 fig. 2.1 的实例。输出可以是多种文本或图形形式；作者选择图形显示，并让分析器 project（投影）到 Book 上——即为每个 book 对象显示一张单独的图。

Q：为什么偏偏选中这个实例？

工具对实例的选择是任意的（arbitrary），甚至可能因偏好设置不同而在多次运行间变化。

但实践中，第一个生成的实例往往是个小实例。这很有用，因为小实例常常是病理性的（pathological）， 因此更可能暴露微妙的问题。

你可以要求工具产生一系列不重复的实例，但本章的 tour 里我们总是只用第一个。

用约束「引导」模拟：三次迭代

第一次的实例只有一条链接。想看更多链接，就往谓词里加约束。这个「加约束—跑—看图—再加」的循环就是 Alloy 的日常。

迭代 ①：要多于一条关联

pred show (b: Book) {
  #b.addr > 1
}

为了能谈论某个特定的书，给谓词加了参数 b: Book。b.addr 是这本书的名字→地址映射， #b.addr 是这个映射中关联的数量（# 是基数算子）。

结果（fig. 2.2）：模型允许两个名字映射到同一个地址（这个实例里是三个！）。

迭代 ②：一个名字能映射到两个地址吗？——探测模型边界

pred show (b: Book) {
  #b.addr > 1
  some n: Name | #n.(b.addr) > 1
}
分析器的回答：inconsistent

分析器告诉你谓词 show 现在是不一致的——至少在这个 scope 内——没有实例。 这不奇怪，因为加的约束与 addr 声明里的重数（lone）矛盾。

这是一种非常有价值的诊断手段：用 run 去问「模型允不允许 X」， 如果回答 inconsistent，就说明你的模型排除了 X。可能是好事（本来就该禁止），也可能是意外（约束写过头了）。

注意 n.(b.addr) 的写法：括号是必需的，因为 . 的结合性会让 n.b.addr 被解析成 (n.b).addr。 这里的语义是「在书 b 的映射里查名字 n」。

迭代 ③：换成更弱的约束——确保地址簿里能有多个地址

pred show (b: Book) {
  #b.addr > 1
  #Name.(b.addr) > 1
}
Alloy 的一个漂亮特性：算子定义得极其一般

坏约束用 n.(b.addr) 查单个名字 n；好约束用 Name.(b.addr) 查整个名字集合。 后者表示「所有可能由查找得到的地址的集合」。

原文：「any operator that can be applied to a scalar can also be applied to a set.」 ——任何能作用于标量的算子，也能作用于集合。这消灭了大量「单值版 / 集合版」的重复 API， 是 Alloy 语法「特别简单而统一」的具体体现。同样的道理适用于 #Name.(b.addr)、Alias.(b.addr)、Name -> a 等等。

结果 fig. 2.3。这类小模拟为什么有用？作者给了两条理由：

  1. 以用户极小的代价，确认模型没有意外地排除掉显而易见的情况；
  2. 呈现出一些你可能压根没想过的情况。

2.2Dynamics: Adding Operations · 动态：加入操作

用约束表达一个操作

pred add (b, b': Book, n: Name, a: Addr) {
  b'.addr = b.addr + n -> a
}

add 和 show 一样，只是一个约束。只不过它代表一个操作，描述动态行为。 四个参数：添加前的书 b、添加后的书 b'、名字 n、要映射到的地址 a。 约束说：新书的地址映射 = 旧书的地址映射 加上 一条从名字到地址的链接。

本章最重要的概念转折：声明式 vs 操作式

原文：如果你习惯命令式编程语言、又没见过建模语言，这种写法大概会让你觉得奇怪。

  • 这里没有显式的 mutation（状态修改）。前后两个状态被赋予不同的名字（b 和 b'）， 操作的效果由一个关联二者的性质捕捉。
  • 程序中的过程是操作式的（operational）：描述如何通过修改状态分量来产生状态变化。
  • Alloy 是声明式的（declarative）：描述如何检查一个状态变化是否有效，办法是比较前后的值。

「Even though Alloy is declarative, it can still be executed much like an operational language.」 ——虽然是声明式的，它仍然可以像操作式语言那样被「执行」。这正是 SAT 求解带来的能力。

「执行」这个操作

run add for 3 but 2 Book

这次把 Book 限制为 2 个（分别对应前值和后值）。结果 fig. 2.4 中， prestate（操作前的状态）显示在上方，poststate（操作后）在下方： prestate 里书是空的；poststate 里多了一条从 Name0 到 Addr0 的链接。

注意图上的标签：add_n / add_a

name 节点被标上 add_n、address 节点被标上 add_a， 用以显示哪些对象被绑定到了 add 操作的参数 n 和 a 上。

这些标签后面会变得更重要——它们会显示断言被违反时的「见证者」（witnesses）。 这是 Alloy 可视化极其实用的一点：反例不只告诉你「有 bug」，还精确指出「是哪几个对象造成的」。

把「操作本身」与「探索用的约束」分开

pred showAdd (b, b': Book, n: Name, a: Addr) {
  add (b, b', n, a)
  #Name.(b'.addr) > 1
}
run showAdd for 3 but 2 Book

新谓词 showAdd 「调用」了已有谓词 add——效果与直接把 add 的约束内联进来没有区别， 但这样更模块化。加的约束要求：操作后的地址簿有多于一个地址被映射到。

一个反直觉但极有用的事实

「Note that it's just as easy to constrain the state after as constraining the state before: the analyzer is “executing” this operation backward.」

约束后置状态和约束前置状态一样容易——分析器是在反向「执行」这个操作。 命令式语言里这几乎不可能（你得手写逆操作），而声明式 + SAT 天然支持双向求解。 这解释了为什么 Alloy 操作不需要写成可执行风格。

删除与查找：pred 与 fun 的区别首次出现

pred del (b, b': Book, n: Name) {
  b'.addr = b.addr - n -> Addr
}

fun lookup (b: Book, n: Name): set Addr {
  n.(b.addr)
}
  • del：后书 = 前书 去掉所有从名字 n 到任意地址的链接。 注意 n -> Addr 里的 Addr 是整个地址集合——又一次体现「算子对集合一视同仁」。
  • lookup 写成函数而非谓词：它的体是一个表达式而不是一个约束， 说明查找的结果就是名字 n 在 b 的 addr 映射下所映射到的那组地址。
predfun
体的内容公式 / 约束（boolean）表达式（relation）
返回真 / 假一个关系（值）
返回类型声明不需要需要，如 : set Addr
用在哪作为约束参与合取嵌入到表达式中

断言：delUndoesAdd 与第一个真 bug

接下来作者换了个玩法：不模拟单个操作，而是写关于操作组合（序列）行为的断言。第一个断言说「删除是添加的撤销操作」：

assert delUndoesAdd {
  all b,b',b": Book, n: Name, a: Addr |
    add (b,b',n,a) and del (b',b",n) implies b.addr = b".addr
}
check delUndoesAdd for 3
assert / check 的语义

断言是一个「意在有效」（intended to be valid）的约束——即对所有可能情形都为真。
check 命令指示分析器不去找例子，而是找反例——一个断言被违反的场景。

它确实找到了（fig. 2.6）。奇怪的是，这个场景里只有两个不同的状态。 如图所示，b 和 b'（第一、第二状态中书的值）都是 Book0。原因是：

反例的根因

要添加的那条 name/address 链接本来就已经存在，所以 add 的执行没有任何效果（b 和 b' 是同一个对象）。 而 del 的执行却把这条链接删掉了，得到空书。

于是「add 再 del」≠「什么都不做」。这不是模型的 bug，而是断言写得太宽。

Jackson 在这里插入了一句非常诚实、非常值得记住的话：

关于「事后显而易见」

「At least, it's not surprising in retrospect. Many of the issues raised by analysis are like bugs in code— perfectly obvious once you've already seen them.」
很多分析揭示的问题就像代码里的 bug——一旦你已经看见它们，就完全显而易见。 这句话既是对「这些问题不是很 trivial 吗」这类质疑的预防性回答，也点出了自动分析的真正价值： 它把「事后显而易见」提前成了「事前可见」。

修复断言：加上前置条件

assert delUndoesAdd {
  all b,b',b": Book, n: Name, a: Addr |
    no n.(b.addr) and add (b,b',n,a) and del (b',b",n)
      implies b.addr = b".addr
}

把断言限定到「名字 n 原本没有条目」的情形（no n.(b.addr)）。现在 check ... for 3 找不到反例了。

关键反思：找不到反例 ≠ 断言有效

必须内化的一条

「The assertion may still be invalid, though.」——断言仍可能是无效的。 因为分析器只考虑了三本书、三个名字、三个地址的情形，涉及更多的反例是可能存在的。

于是调大 scope。三本书以上没意义，但名字和地址各给到 10：

check delUndoesAdd for 10 but 3 Book

这次耗时更长（在 2GHz Macintosh G5 上约 3 秒）。作者顺手做了一个极有说服力的算术：

scope=10 到底有多大？

  • 10 个名字和地址，每个名字有 11 种可能（映射到 10 个地址之一，或不映射）；
  • 所以仅起始状态就有 1110 种可能取值；
  • 而且因为操作不必写成可执行风格，工具必须搜索全部三本书的可能取值—— 于是共有超过 1030 个案例要考虑。

「Now you can see why this kind of analysis is more effective than testing.」——现在你能明白为什么这种分析比测试更有效。

Q：1030 个案例，怎么可能在 3 秒内查完？

当然，分析器不会逐个构造并检查每个案例。即使每个案例只用一个处理器周期， 1030 个案例所需的时间也超过宇宙的年龄。

它靠的是剪枝可能性之树（pruning the tree of possibilities）—— 能够排除大片子空间而无需完整检查它们。这正是 SAT 求解器（DPLL/CDCL）的核心能力。

Small Scope Hypothesis · 小作用域假设（全书的思想基石）

原文表述

「We still haven't proved the assertion is valid.」——我们仍没有证明断言有效。但直觉上， 如果真有问题，它却无法在一个只有 10 个名字和地址的反例中展示出来，这是非常不可能的。

走多远是建模者必须做的实用主义判断（pragmatic judgment）。随着 scope 增大，分析终将变得不可处理（intractable）。 这个权衡在原则上与「决定程序测得够不够」时面对的权衡并无不同。但实践中， 穷尽 scope=10 所提供的模型覆盖度，超过手写测试用例所能达到的任何程度。

为什么？「Most flaws in models can be illustrated by small instances, since they arise from some shape being handled incorrectly, and whether the shape belongs to a large or small instance makes no difference.」
模型中的大多数缺陷都能用小实例来说明，因为它们源于某个「形状」（shape）被处理错了—— 而这个形状属于大实例还是小实例，毫无区别。所以如果分析考虑了所有小实例，大多数缺陷就会被揭示。
这一观察被称为 small scope hypothesis（小作用域假设），是 Alloy 分析所依赖的根本前提。

解读：「shape」是理解小作用域假设的关键词

想想 delUndoesAdd 的那个反例：它需要的「形状」只是一条已存在的链接—— 3 个名字就够了。真实系统里可能有百万个联系人，但 bug 的形状不会因此改变。 这与测试的差别是本质性的：手写测试用例只能覆盖你想到的形状， 而 scope 内的穷举覆盖所有能在这个规模下构造的形状。第 5 章会把这套论证严格化，并诚实指出它失效的边界（5.3 节）。

两个「代数风格」的断言

// ① add 是幂等的：重复添加没有效果
assert addIdempotent {
  all b,b',b": Book, n: Name, a: Addr |
    add (b,b',n,a) and add (b',b",n,a) implies b'.addr = b".addr
}

// ② add 是局部的：给名字 n 加条目，不影响查另一个名字 n' 的结果
assert addLocal {
  all b,b': Book, n,n': Name, a: Addr |
    add (b,b',n,a) and n != n' implies lookup (b,n') = lookup (b',n')
}

两个都没有反例。（addLocal 在 2.3 节引入间接引用后会失败，那是本章第二个重要发现。）

模拟谓词与断言 = 测试驱动与桩

fig. 2.7 的最终模型包含了模拟谓词、断言以及它们配套的命令。 原文：「These play the same role that test drivers and stubs play for code; they are an integral part of the development.」

它们扮演代码中测试驱动与桩的角色，是开发不可分割的一部分。 当你修改模型时，你可以重新 check 断言、重新 run 模拟，就像改完代码跑回归测试一样。 ——这是把 Alloy 纳入日常工程流程的具体做法。

fig. 2.7　简单地址簿的最终模型（完整）

module tour/addressBook1
sig Name, Addr {}
sig Book {addr: Name -> lone Addr}

pred show (b: Book) {
  #b.addr > 1
  #Name.(b.addr) > 1
}
run show for 3 but 1 Book

pred add (b, b': Book, n: Name, a: Addr) {b'.addr = b.addr + n -> a}
pred del (b, b': Book, n: Name) {b'.addr = b.addr - n -> Addr}
fun lookup (b: Book, n: Name): set Addr {n.(b.addr)}

pred showAdd (b, b': Book, n: Name, a: Addr) {
  add (b, b', n, a)
  #Name.(b'.addr) > 1
}
run showAdd for 3 but 2 Book

assert delUndoesAdd {
  all b,b',b": Book, n: Name, a: Addr |
    no n.(b.addr) and
      add (b,b',n,a) and del (b',b",n) implies b.addr = b".addr
}
assert addIdempotent {
  all b,b',b": Book, n: Name, a: Addr |
    add (b,b',n,a) and add (b',b",n,a) implies b'.addr = b".addr
}
assert addLocal {
  all b,b': Book, n,n': Name, a: Addr |
    add (b,b',n,a) and n != n'
      implies lookup (b,n') = lookup (b',n')
}
check delUndoesAdd for 10 but 3 Book
check addIdempotent for 3
check addLocal for 3 but 2 Book

2.3Classification Hierarchy · 分类层次

真实的地址簿应用里：你可以给一个地址建别名，然后把那个别名当作另一个别名的目标； 而且一个别名可以命名多个目标，于是一组地址可以用单个名字引用。

作者选择从头开始重写（而非在旧模型上改造），按需复用旧模型的片段。先是分类层次：

关键变化：Book 的 addr 字段现在把名字映射到 target。 一个 target 要么就是一个地址（同以前），要么本身就是一个名字；而名字要么是 group 要么是 alias。

解读：这就是 Composite 模式的关系化

Name extends Target 这一行是全部魔法所在。因为 Name 是 Target 的子类型， addr: Name -> Target 就自动允许名字指向名字，无需任何特殊机制。 同时 abstract sig 保证 Target 和 Name 没有「裸」实例——每个 target 必是 Addr 或 Name， 每个 name 必是 Alias 或 Group。这正是第 1 章许诺的「有子类型和并集但不需要向下转型」的类型系统。

分析器给出 fig. 2.9 的实例：一个别名映射到了它自己。 「This is the first simulation we've done that clearly reveals a flaw to be remedied.」 ——这是我们做的第一次明确揭示出待修缺陷的模拟。

体会一下这件事

只写了 some b.addr（要一本非空的书）这么一句约束，工具就主动递给你一个自环实例。 没有人想到要测「别名指向自己」这种情形——它不在任何测试计划里。 这正是前言所说的「模拟会呈现你压根没想过的情况」。自环意味着 lookup 会陷入无限递归。

修复：用传递闭包表达「不可达自身」

fact {
  all b: Book | no n: Name | n in n.^(b.addr)
}

fact 是「假定永远成立」的约束。这条说：对任何书，不存在某个名字， 它属于从它自身出发可达的 target 集合。

核心算子：传递闭包 ^

n.^(b.addr) 表示从 n 出发可达的 target，用的是书 b 的地址映射的传递闭包 ^(b.addr)。

作者的直观解释：
· x.r = 从对象 x 出发，经过一次关系 r 的应用所到的导航结果；
· x.^r = 从对象 x 出发，经过一次或多次 r 的应用所到的导航结果。

signature fact：更地道的写法

像这种适用于某签名的每个成员的 fact，更好的写法是签名事实（signature fact）—— 量词和对具体成员的引用都是隐式的：

sig Book {addr: Name -> Target}
 {no n: Name | n in n.^addr}
两处隐式化，务必看清

① 像面向对象程序中接收者（receiver）的字段引用一样，addr 现在隐式指 this.addr—— 即一个原型书（archetypal book）的地址映射；
② all b: Book | 这个量词消失了。

注意 n.^addr 不再需要括号，因为 addr 是单个标识符， 而之前 ^(b.addr) 必须加括号是因为 b.addr 是个复合表达式。

空查找问题：把它变成显式的断言

fig. 2.12 意味着：你查一个名字，可能一个地址都拿不回来，尽管这个名字确实在地址簿里！ 作者补了一句现实观察：许多地址簿应用允许这种情况，然后（很不帮忙地） 只在稍后发送消息时才报告失败。

先把 Book 签名细化，让「书中包含哪些名字」显式化——加一个 names 字段， 并把 addr 的声明改成「只映射这个集合中的名字，且每个至少映射到一个目标」：

sig Book {
  names: set Name,
  addr: names -> some Target }
 {
   no n: Name | n in n.^(addr)
   all a: Alias | lone a.addr
 }
一个高级技巧：用字段名作为关系定义域

addr: names -> some Target 中的 names 不是一个签名，而是同一签名内的另一个字段。 Alloy 允许用字段来约束另一个字段的定义域，语义是「对每本书 b，b.addr 的定义域 ⊆ b.names」。 这种「字段引用字段」的能力让模型能表达非常精细的依赖关系。

然后加断言，声称「书中每个名字的查找都会产生结果」：

assert lookupYields {
  all b: Book, n: b.names | some lookup (b,n)
}

检查它会得到一个跟 fig. 2.12 一样的反例。这个问题不容易修： 我们可以简单加一条 fact 说「group 不能为空」，但如何维持这样的性质并不显然，所以先搁置，稍后回来（→ 2.4 节）。

解读：这里体现的建模判断力

「group 非空」是一条不变式（invariant），而 add 可以随手创建空 group， del 可以随手把 group 掏空。要用 fact 维持它，就得给每个操作加前置条件—— 但作者此时还不确定该加什么。承认「先放着」是成熟建模者的标志： 与其草率加一条 fact 把模型搞得更难懂，不如先去 2.4 节用轨迹分析看清这个问题是怎么产生的，再对症下药。

更新操作以匹配新模型

pred add (b, b': Book, n: Name, t: Target) {b'.addr = b.addr + n -> t}
pred del (b, b': Book, n: Name, t: Target) {b'.addr = b.addr - n -> t}
fun lookup (b: Book, n: Name): set Addr {n.^(b.addr) & Addr}

作者说「差别很小」，但每一处都值得看：

  • add 现在接受一个 target 而非 address（因为可以加别名/组）。
  • del 现在除名字外还接受一个 target。
    一个由工具驱动的设计发现

    「At first I didn't see the need for the second argument of del, but while exploring the model with the analyzer, I realized that without it you wouldn't be able to remove just one target from a group.」
    作者一开始没看出 del 需要第二个参数，是在用分析器探索模型时才意识到： 没有它，你就无法只从 group 中移除一个目标。 ——这是一个绝佳例证：模型的工具化探索会反过来修正 API 设计。

  • lookup 现在有意思多了，被推广到任意深度： 它跟随地址映射任意多次（而非仅一次）得到一组 target， 然后与地址集合求交（&），从而返回从该名字可达的所有地址。
值得背下来的一行

n.^(b.addr) & Addr

「沿关系走任意步，然后与某个类型求交」——这是 Alloy 里过滤出特定子类型的标准惯用法。 由于类型系统不需要向下转型，这种「闭包 + 交集」的组合就是类型收窄的全部手段。第 3 章会把 ^ 和 & 严格定义。

结论：这次不修模型

「Now that we have indirection, changing the binding of one alias or group can affect another. This seems reasonable, and we decide that the model doesn't need to be fixed.」

既然现在有了间接引用，改变一个别名或组的绑定本来就可能影响另一个。 这看起来是合理的，所以我们决定模型不需要修改（是断言不再适用了）。

解读：反例的三种命运

本章已经完整展示了面对反例时的三种正确反应，这个分类非常有用：
(a) 修断言——delUndoesAdd：模型合理，断言漏了前置条件；
(b) 修模型——自环、别名多目标：断言/直觉合理，模型缺约束；
(c) 撤销断言——addLocal：引入间接引用后这个性质本来就不该成立。
第 (c) 类最考验判断力：你必须能说出「为什么这个性质在新设计下不该成立」， 而不是因为懒得修就把它删掉。

2.4Execution Traces · 执行轨迹

回到空查找问题。这次不只看坏状态，还要看它是怎么产生的。 于是不再考虑单个步骤的效果，而是考虑整条轨迹——由从初始状态出发的多个步骤组成。

改动量惊人地小

「The body of the model remains unchanged.」——模型的主体保持不变。 需要做的只是：给地址簿加一个排序，并约束它，使得 ① 第一本书满足某些初始条件；② 排序中任意相邻的两本书由某个操作相关联。

逐行拆解

open util/ordering [Book]
排序由库模块 util/ordering 提供。这个模块是泛型的——它可以对任意类型的集合排序—— 所以打开时必须用一个类型实例化（这里是 Book）。 模块有自己的签名和字段，但通过三个函数访问：first（序中第一个元素）、 next（给定元素的后继）、last（最后一个）。
pred init (b: Book) {no b.addr}
给出初始条件：地址簿是空的。
init (first ())
轨迹中的第一本书满足初始条件。
all b: Book - last ()
「除最后一本外的每本书」。- 是集合差算子。
let b' = next (b) |
let 引入一个局部别名，把 b 的后继命名为 b'，避免后面反复写 next(b)。
some n: Name, t: Target | add(...) or del(...)
b 与其后继 b' 由 add 或 del 的约束相关联。 some 是存在量词：存在某个名字和目标使得这一步成立。 注意——具体是哪个 n、哪个 t、用的是 add 还是 del，全由分析器自己选。
解读：这就是 Shlyakhter 的那个发明

前言致谢里说 Ilya Shlyakhter「发明了通过给每个关系加一列状态原子来表达动态的建模范式」。 这里看到的正是它：「轨迹」不是一种新的语言构造，只是 Book 集合上的一个全序 + 一条 fact。 Alloy 里没有 transition、event、state machine 这些关键字， 动态性完全由静态的关系结构承载。这也是为什么「模型主体保持不变」—— 加动态不需要重写任何东西。第 2.5.1 节的最后一个问答会进一步解释这个设计选择。

看一条样例轨迹

最后一次添加很有意思

最后一步（让 Group0 成为 Group1 的成员）很有趣：它创建了通往同一个地址的两条路径。 「Again, we see how simulation generates cases that are thought-provoking, even when they don't expose obvious flaws.」
模拟生成的案例发人深省，即使它们没有暴露明显缺陷。

多条路径通向同一地址在真实邮件系统里意味着重复收件—— 这不是「错」，但确实是个需要产品层面决策的问题。工具没有判断它，只是把它摆到你面前。

断言与之前完全一样，但这次书集合被约束成一条轨迹， 所以反例（fig. 2.16）展示了一系列操作如何导致一个坏状态。

  • 违反实际上在第一步之后就发生了，在状态 Book1 中——所以作者省略了另外两个状态。
  • 「A smaller scope would have sufficed.」——更小的 scope 本来就够了。
根因

问题在于 add 允许把一个无意义的别名（one that refers to nothing，即不指向任何东西）加进一个 group。

修复 ①：给 add 加前置条件

pred add (b, b': Book, n: Name, t: Target) {
  t in Addr or some lookup (b,t)      // ← 前置条件
  b'.addr = b.addr + n -> t
}

前置条件说：给定的目标要么是一个地址，要么在查找时至少解析出一个地址。

再次检查断言，得到 fig. 2.17 的反例。这次问题出在删除上：我们删掉了一个 group 的最后一个成员。

修复 ②：给 del 加前置条件

pred del (b, b': Book, n: Name, t: Target) {
  no b.addr.n or some n.(b.addr) - t    // ← 前置条件
  b'.addr = b.addr - n -> t
}

前置条件说：n 本身没有被映射到（no b.addr.n），或者除了 t 之外它还映射到别的目标（some n.(b.addr) - t）。

作者的自我评价：draconian（严苛）

「We can fix this, albeit in a rather draconian manner, by forbidding such a deletion with a precondition.」 ——用前置条件禁止这种删除，虽然是相当严苛的办法。

这个自我批评很重要：真实产品里你应该允许删除 group 的最后一个成员（用户就是想清空它）， 然后在 lookup 返回空时给出友好提示。模型这里选择「禁止」只是为了让断言通过、把讨论推进下去。 建模者必须时刻分清「模型的简化」与「设计的结论」。

顺带注意 no b.addr.n 这个写法：b.addr.n 是从 book 出发经 addr 到 n 的导航， 它非空意味着「有某个名字映射到了 n」。所以 no b.addr.n = 「n 不是任何人的目标」。 这种情况下删除 n 的出边是安全的（n 反正查不到，谈不上 lookupYields）。

确认修复：把 scope 拉到 6

check lookupYields for 6

现在找不到反例了。于是把 scope 提到 6，分析所有涉及 6 个 target 和 6 本地址簿的场景。 「This is a much larger space, and analysis takes almost 2 minutes, but still no counterexample is found.」 ——这是个大得多的空间，分析花了将近 2 分钟，但仍然没有找到反例。

解读：两个数字构成的现实图景

把本章的耗时数据串起来看：for 3 → 瞬间；for 10 but 3 Book（单步分析）→ 3 秒； for 6（带轨迹，6 本书 6 个 target）→ 近 2 分钟。

这说明两件事：① 加轨迹会让分析代价急剧上升（因为要搜索整条执行，而不是一次转移）， 这也解释了作者为什么说「实践中通常一次只分析一个操作就够了」； ② 2006 年 2GHz G5 上的 2 分钟，在今天大致是秒级——印证了前言的赌注：求解器变快，Alloy 就变快。

2.5Summary · 小结

本章的目的（作者澄清）

这段短 tour 的目的不是展示这种建模风格能完成多少东西。 读完本书并做些练习后，你将能为更有趣的事物写出更精巧的模型。 它的目的是展示：要为一个软件设计问题获得洞见，你实际需要做的事有多么少。 我们最复杂的模型只有一页长，但这已足以探索一个真实系统中出现的若干问题。

接着是一句关于「trivial」的辩护，也是全书的态度宣言：

关于「这些问题太琐碎」

「It's easy to dismiss the kinds of issue we looked at as trivial and obvious. They often are—in retrospect, at least.」
把我们看过的问题当作琐碎显然的东西而不予理会，这很容易。它们往往确实如此——至少事后看来。

「Indeed, the hardest, and most rewarding, challenge in software design is reducing a mass of complicated, incongruous details to a few simple generalities. Simplicity is the key to good software design.」
软件设计中最困难、也最有价值的挑战，是把一大堆复杂而不协调的细节归约为少数几条简单的通则。 简洁是好软件设计的关键。

「回顾这次建模练习，更有教益的是回想我们没有做什么」

这是本章的点睛之笔。六条「没做」，每一条都是对传统方法的对比：

#我们没做的事细节与含义
1 没有先写一个精细的模型再分析 我们的第一次分析，施加在一个不到十行的模型上。模型是随着用分析器探索而增量开发的。
2 没有用任何复杂数学或陌生符号 Alloy 语言基于基本逻辑的简单概念，加上一个用于沿关系导航的特殊的点算子—— 它类似于（但比）Java 的解引用点更灵活。
3 没写任何可执行代码就能拿到样例状态、甚至样例轨迹 这一点有个本次 tour 没有利用到的重大优势：你可以写出一个操作的非常局部的描述， 允许许多不同的行为。（即：规格说明可以是欠定的，这在命令式语言里不可能。）
4 没有写任何测试用例 我们写的断言像是测试预言机（test oracles），用来检查结果。 写一个断言很少比写单个测试用例更麻烦，但它拥有一个大到无法想象的测试套件的覆盖度。
5 没有以任何方式引导分析器 除了给一个 scope 来限定分析范围之外，什么都没做。 没有证明步骤、没有引理、没有需要建议的启发式。（直接对比定理证明）
6 不必担心误报（false alarms） 虽然断言的分析可能找不到反例（因为反例只存在于更大的 scope 中）， 但它绝不会报告一个虚假的反例。
（当然，反例仍可能是不相关的——因为断言不是我们本来的意图， 或者模型没有表达我们心里想的行为。这是建模错误，不是工具误报。）
第 6 条是最强的保证，务必分清两件事

Alloy 分析的可靠性是单边的：
· 报出反例 → 100% 是真的（在模型的意义下）。绝不会有无中生有的警报，所以你不会浪费时间 chasing 幽灵。
· 没报反例 → 不保证没问题，只保证「在这个 scope 内没问题」。

这个不对称性是 Alloy 相比「近似分析 / 静态启发式检查器」的根本优势： 它的信噪比是完美的。而括号里那句补充同样重要——如果反例不相关， 那不是工具的错，而是你的断言或模型写错了，这本身也是有价值的发现。

两种对照实验

如果全程用纸笔做？

「Without extraordinary discipline and perseverance, it's hard to motivate yourself to explore tricky issues.」 ——没有非凡的自律和毅力，你很难有动力去探索棘手的问题。

而且即便真的探索了，我们大概也不会把它们表述得足够精确， 以至于可以与他人分享（或者供我们自己日后回忆）。 ← 这一点常被忽略：模型的价值不只是发现 bug，还是可传递的设计文档。

如果用代码（比如 Java）做？

· 至少需要 5 个文件（仅仅为了表示那个分类层次）；
· 一行的 lookup 操作会需要一个循环或递归、访问一个 hashtable、 并把结果累积到另一个数据结构里；
· 我们唯一能做的分析就是执行几个固定的测试用例—— 没有任意样例的生成、没有界内的穷举检查、没有结果的可视化显示。

2.5.1Questions · 四个问答

Q1：这种建模风格是新的吗？

不是。四条历史线索：

  • Jim Horning 与 John Guttag 在 1980 年的一篇论文里描述了一个非常相似的方法， 其中用定理证明器来交互式地回答关于候选设计的问题 [21]。 那篇论文是 Alloy 的主要灵感来源之一。 （前言里也说这篇论文「至今仍没有获得它应得的知名度」。）
  • Z 记法 [65]，1980 年代在牛津发展起来，其设计初衷就是鼓励增量式规格说明， 许多已发表的 Z 例子都证明了这一点。
  • 若干工具能动画化（animate）规格说明：用于 UML 的 USE 工具 [71] 和 VDMTools [2]， 它们从给定的初始状态出发执行操作并求值约束。

Alloy 的新意不在风格，而在分析引擎：把定理证明换成 SAT，从而做到全自动、无需引导。

Q2：你探索的问题不是很琐碎吗？

「With hindsight, most software design problems are trivial. But if you don't address them head-on, trivial issues have a nasty habit of becoming nontrivial.」
事后看来，大多数软件设计问题都是琐碎的。但如果你不正面处理它们， 琐碎的问题有个讨厌的习惯：变得不琐碎。

一个扎心的现实例证（写书当时）：作者所知的大多数邮件客户端都没有优雅地处理空查找问题。 比如 Apple 的邮件客户端：它允许你在地址簿里创建空的 group 和 alias， 但（没有任何解释性警告）拒绝让你把它们放进邮件头。 而如果你创建一个唯一成员是空 alias 的 group，它允许你把这个 group 放进邮件头， 然后把一条格式错误的消息传给 SMTP 服务器，结果被退信。

解读：这个例子的分量

这不是随手举的例子，而是精确复现了本章 lookupYields 断言所捕捉的那个 shape： 局部检查（alias 非空）通过，但组合后（group 的唯一成员是空 alias）全局性质失败。 一个世界级的工程组织，在一个日常功能上，犯了一个 30 行 Alloy 模型 + 一次 check 就能抓到的错。 这就是「琐碎问题变得不琐碎」的实证。第 6.2 节的酒店房卡锁是同一论证的加强版——那是个真实的安全漏洞。

Q3：如何为 Alloy 分析选择 scope？

每个命令（check 断言或 run 谓词）都指定一个 scope，给每个签名的元素数量设上界。存在权衡：

  • 小 scope：可能漏掉实例；
  • 大 scope：分析更慢，而且倾向于产生更大、更难理解的实例。

推荐工作方式：从小 scope 开始，如果找不到实例再逐步增大。
另外，某些签名的 scope 往往是明确的。例如：分析「从地址簿的一个值到另一个值的单次状态变化」这类转移， 只需要两本书。（这正是本章反复出现 but 2 Book 的原因。）

Q4：为什么 Alloy 里没有内建「执行」的概念？

不把某个特定的执行概念硬编码进语言，使得这个记法可以用于许多不同的惯用法（idioms）。

举例：在第 6 章里，酒店锁方案的模型被开发了两个版本——

  • 一个用本章的惯用法：执行步骤满足具名的操作，但操作名本身不是执行的一部分；
  • 另一个用的惯用法是：执行就是一系列具体的、具名的事件。
解读：这是「机制 vs 策略」的经典取舍

Alloy 提供的是机制（关系 + 算子 + 排序库模块），不提供策略（什么叫「一次执行」）。 对比一下：模型检查语言（SMV、Promela/SPIN）把「状态机 + 转移」硬编码进语言， 于是你只能用那一种方式思考行为。Alloy 让你自由选择：

  • 状态对（本章 2.2）：一次分析一个操作，最便宜；
  • 全序轨迹（本章 2.4）：util/ordering，看整条执行；
  • 具名事件序列（第 6 章酒店）：事件本身是原子，可以携带类型与参数；
  • 偏序 / 并发：自己定义因果序，适合分布式协议（第 6.1 节环上选举）。

一句话总结第 2 章

用不到十行声明一个结构，用 run 让工具主动递给你想不到的实例， 用 assert + check 让工具在数十亿案例里替你找反例， 用反例上的 witness 标签定位根因，然后修模型 / 修断言 / 撤销断言—— 如此循环，一页纸的模型就能探索一个真实系统的设计问题。 全过程不需要：可执行代码、测试用例、数学符号、证明引导， 也不会有误报。这就是 lightweight formal methods 的手感。
