3Logic · 逻辑

原书 p. 33–81 · Alloy 的语义地基：一种把一阶逻辑量词与关系演算算子结合起来的关系逻辑。本章是全书的「字典」，也是理解一切 Alloy 代码的前提。

开篇的三个要求

每个建模语言的核心都是一种提供基本概念的逻辑。它必须小、简单、富有表达力（small, simple, and expressive）。 但一种为「表达抽象」而设计的「工作逻辑」（working logic），与为理论研究设计的逻辑不同， 不可能完全极小——它必须足够灵活，允许同一个想法用不同的方式表达。

本章的四个设计决定

作者在开头就用一段话交代了这套逻辑区别于传统逻辑的关键特征，值得逐条列出：

决定内容带来的好处
① 关系的 join 被推广 这是它区别于传统逻辑的关键特征。像关系数据库一样，关系是元组的集合。 —
② 集合是单列关系，标量是单元素集合 Sets are represented as relations with a single column, and scalars as singleton sets. 于是同一个 join 算子可以作用于标量、集合和关系。
③ 改变重数不影响约束 在声明中改变一个关系的「重数」（即它把一个元素映射到标量还是集合），不需要改动它出现的那些约束。 模型可以无痛演化——这是「增量细化」的技术基础。
④ 取消集合与标量的区分 Dispensing with the distinction between sets and scalars. 约束更统一、更好写；而且消除了偏函数应用问题，因此不需要特殊的「未定义」值。
还有两点

· 逻辑被刻意保持不含任何会把它绑定到特定编程语言或执行模型的概念；
· 另有少量新意，比如声明中可以嵌套重数（nested multiplicities，见 3.6.5）。

3.1Three Logics in One · 三种逻辑合一

本章介绍的是一种关系逻辑（relational logic），它把一阶逻辑的量词与关系演算的算子结合起来。 「It's easy to learn—especially if you're familiar with basic set theory, or with relational query languages—and surprisingly powerful.」

这套逻辑支持三种不同的风格，可以随意混合与变换。同一个约束—— 「一个地址簿（由从名字到地址的关系 address 表示）把每个名字至多映射到一个地址」——可以写成三种样子：

① 谓词演算风格
predicate calculus

只有两类表达式：用作谓词的关系名，以及由量化变量构成的元组。

all n: Name, d, d': Address |
  n -> d in address and
  n -> d' in address
    implies d = d'

② 导航表达式风格
navigation expression

表达式表示集合，由量化变量出发沿关系「导航」构成。

all n: Name |
  lone n.address

← 最常用

③ 关系演算风格
relational calculus

表达式表示关系，而且完全没有量词。

no ~address.address - iden

读作：「不存在两个不同的地址被同一个名字映射到」

作者的取舍结论

「The predicate calculus style is usually too verbose, and the relational calculus is often too cryptic. The most common style is therefore the navigational one, with occasional uses of the other styles when appropriate.」

谓词演算风格通常太啰嗦，关系演算风格常常太隐晦。 因此最常用的风格是导航式，另两种在合适时偶尔使用。

Discussion · 五个问答

Q：这个约束你实际上会选哪种写法？

都不选。这类重数约束太常见了，所以我们的逻辑有特殊语法，允许把约束直接写进声明里。 这种情况下你会写：

address: Name -> lone Address

→ 这就是第 2 章 addr: Name -> lone Addr 的由来。详见 3.6.2。

Q：谓词演算风格用在哪里？

一个常见用途是集合构造表达式（comprehension expressions），它允许你从一个约束构造出一个集合或关系。 例如，若关系 r 关联来自集合 A、B、C 的三个元素，而你想要列的顺序变成 B、A、C，可以用集合构造定义一个新关系：

r' = {b: B, a: A, c: C | a -> b -> c in r}

谓词演算风格在写非常微妙的约束时也有吸引力，因为它具体而直白， 而且量词化往往与自然语言表述一一对应。

Q：关系演算风格用在哪里？

有经验的建模者发现它对某些反复出现的约束很有用，因为这样能写得更简洁。例如：

no ^r & iden      // 关系 r 是无环的（acyclic）

另外，你可能先用导航风格写一个约束，然后注意到某个量化变量可以被「消掉」（cancelled out）。例如：

// 导航风格
all p: Person | p.uncle = p.parent.brother

// 关系演算风格，更简洁
uncle = parent.brother

前提条件：uncle 和 parent 只映射 Person 集合的成员 （so long as uncle and parent only map members of the set Person）。

Q：这些风格的表达力等价吗？

不等价。导航风格表达力最强。

  • 谓词演算缺少传递闭包，所以可达性性质无法表达。
  • 关系演算没有量词，而且并非谓词演算中量词的所有出现都能纯关系式地表达。
解读：这条问答的技术含金量最高

「谓词演算缺少传递闭包 → 可达性无法表达」是数理逻辑里的一个经典事实： 一阶逻辑无法定义「传递闭包」/「可达性」（这需要无穷多个公式或二阶量词）。 Alloy 通过在关系演算一侧把 ^ 和 * 作为原语算子加进来， 得到了一个严格强于一阶逻辑的系统——却仍然可判定（在有界作用域内）。 这是 Alloy 表达力/可分析性平衡的核心：用导航语法糖 + 闭包原语，而不是用高阶量词。 这也解释了为什么第 2 章的 no n: Name | n in n.^addr 那类约束在纯一阶逻辑里根本写不出来。

Q：风格会影响分析的性能吗？

一般不会。关于「用多少个关系、每个关系多少列」的基本建模决策， 影响要大得多。（Basic modeling decisions about how many relations to use, and how many columns each relation has, have a far bigger impact.）

3.2Atoms and Relations · 原子与关系

本节的一句话

「All structures in our models will be built from atoms and relations, corresponding to the basic entities and the relationships between them.」
模型中的所有结构都由原子和关系构成，分别对应基本实体与它们之间的关系。

3.2.1 Atoms · 原子

原子是一个原始实体（primitive entity），具有三个性质：

indivisible
不可分

不能被拆成更小的部分。

immutable
不可变

它的性质不随时间改变。

uninterpreted
无解释

没有任何内建性质——不像数字那样。

作者立刻承认：除了基本粒子，现实世界里几乎没有东西是原子的；这是一种建模抽象。 那么如果你想建模可分的、可变的、有解释的东西怎么办？

统一答案

「You just introduce relations to capture these properties as additional structure.」
引入关系，把这些性质捕捉为额外的结构。3.2.3 节会给出三种情形的完整配方。

3.2.2 Relations · 关系

关系是一个关联原子的结构，由一组元组构成，每个元组是一个原子的序列。 可以把关系想成一张表，表中每个条目是一个原子。

规则说明
列的顺序重要The order of the columns matters.
行的顺序不重要but not the order of the rows.
每行每列都必须有值Each row must have an entry in every column.（关系是「平坦」的，没有空洞）

size 与 arity

arity（元数 / 列数）关系的列数必须是 1 或更多（不能为 0）

1 且至多 1 个元组option要么是标量，要么为空

示例：从集合到三元关系

// 集合（一元关系），各 size 为 3、3、2
Name = {(N0), (N1), (N2)}
Addr = {(D0), (D1), (D2)}
Book = {(B0), (B1)}

// 标量（只含一个元组的一元关系）
myName   = {(N0)}

// 二元关系：只有一个地址簿的世界（因此无需显式建模地址簿）

// 三元关系（第 2 章用的那种）：多个地址簿，各有自己的映射
addr = {(B0, N0, D0), (B0, N1, D1), (B1, N1, D2), (B1, N2, D2)}

option 的实用场景

一个邮件应用可能存储用户的邮件地址， 以及可选地一个用于消息「reply-to」字段的不同地址。 前者可以建模为标量 userAddress，后者建模为 option replyAddress—— 它要么包含一个地址，要么为空。

术语约定：tuple = 单例关系

在 Alloy 逻辑中所有值都是关系，所以一个元组由包含它的那个关系来表示， 正如一个标量由一个单例集合表示。因此本书用 tuple 一词来描述单例关系——恰好包含一个元组的关系。

myName    = {(N0)}        // 标量
myAddress = {(A1)}        // 标量
myLink    = {(N0, A1)}    // 关联二者的元组

3.2.3 Expressing Structure with Relations · 用关系表达结构

本节的总纲

「With relations, you can express structures in space and time, overcoming the apparent limitations of atoms as a modeling construct.」
借助关系，你可以表达空间和时间上的结构，从而克服原子作为建模构造的表面局限。

本节给出了三个「原子的限制 → 关系的解法」配方，这是整章最实用的部分之一：

配方 ①　原子不可分 → 用关系绑定组件（组合对象）

虽然逻辑中唯一的对象是不可分的原子，但你可以用原子表示组件、用一个关系把它们绑在一起，来建模一个复合对象。

例：目录包含文件

引入关系 contents，把目录映射到它包含的文件。 当目录 D0 包含文件 F0 和 F1 时，它包含元组 (D0, F0) 和 (D0, F1)。

例：酒店房卡（两个密钥）

每张房卡持有两个加密密钥。建模为： 卡集合 Card、密钥集合 Key，以及两个从 Card 到 Key 的关系 fst 和 snd。

fst = {(C1, K11), (C2, K21)}
snd = {(C1, K12), (C2, K22)}

→ 这正是第 6.2 节酒店案例的核心数据结构，此处已埋伏笔。

当对象的内容本身是一个关系时，就用 multirelation 来建模包含关系。 例如上一节的 addr 关联地址簿、名字、地址——每本地址簿都可以看作包含一张 name/address 表。

配方 ②　原子不可变 → 把「身份」与「值」分成不同原子（变化）

虽然原子不可变，但你可以通过把对象的身份（identity）与它的值（value）分离成不同的原子， 并把身份、值、时间三者关联起来，从而建模mutation（对象值随时间变化）。

// 股票取值的历史：value 含 (S0, V0, T0) 表示股票 S0 在时刻 T0 取值 V0
value = {(S0, V0, T0), (S0, V1, T1), ...}

// 地址簿内容的变化：addrT 定义在名字、地址、时间上
addrT = {(N0, D0, T0), (N1, D1, T0), (N2, D2, T1)}
回头理解第 2 章的 Book

作者点出一个关键事实：第 2 章的 addr 关联 book、name、address， 它本来可以用来建模「一个静态世界，其中有多本地址簿，每本含自己的 name/address 表」。

但实际上它被用来表示单个地址簿的变化值—— book 原子扮演的角色与 addrT 中 time 原子的角色完全相同。 这就从逻辑层面解释了 2.4 节「加轨迹只需给 Book 加个排序」为什么行得通： Book 本来就是时间维度的化身。

作者还补充：当模型只关心单个对象及其变化的值时，可以用一组原子表示该对象在不同时刻的值。

配方 ③　原子无解释 → 用关系赋予性质

虽然原子是无解释的，你可以通过引入它们之间的关系来赋予它们性质。

例：网络协议的序列号

序列号可以表示为集合 SeqNumber = {(N0), (N1), …} 的原子，并用关系 precedes 排序—— 当序列号 N0 在 N1 之前时，它包含元组 (N0, N1)。

例：2.4 节的 book 原子

那些 book 原子被排序为 B0, B1, …， B0 表示书的初始值，B1 表示一步之后的值，以此类推。 这个排序是通过导入一个库模块施加的，该模块包含一个关系 next，把 B0 映射到 B1、B1 映射到 B2，等等。

例：图像编辑程序（Adobe Photoshop）——抽象层次的示范

图像编辑程序允许你对图像施加颜色变换。若要探索某个特定变换的性质， 你需要一个关于颜色和变换函数的详细模型。

但若要探索支撑这类方案的抽象——把变换施加到部分图像选区、 把变换与图层结合、撤销与重做变换等等——采取一个更抽象的视角可能就足够了： 图像只是「从像素位置到 RGB 值的映射」，颜色变换只是「从 RGB 值到 RGB 值的函数」。

// 交换 RGB0 与 RGB1 的变换
transform = {(RGB0, RGB1), (RGB1, RGB0)}

→ 这是全书关于「抽象层次选择」最好的示范： 你想探索什么问题，决定了你需要多细的模型。第 2.5 节「十行模型就很有用」的论断在此得到具体支撑。

Discussion · 关于原子与关系的九个问答

Q1：原子的名字有意义吗？

没有。原子名从不出现在模型中；它们只用于描述模拟或检查所产生的实例。 Alloy Analyzer 允许你为每个集合的原子指定自己的名字，但默认使用集合的全名—— 所以 Book 的原子是 Book0、Book1…，而不是 B0、B1…。 （这解释了第 2 章图里为什么是 Name0、Group1。）

Q2：像 {(N0, D0), (N1, D1)} 这样的表达式是什么意思？

它是传统数学语言中的表达式。这里它表示由两个元组构成的集合， 第一个元组以 N0 为第一元素、D0 为第二元素，第二个以 N1、D1 为元素。 术语 N0、N1、D0、D1 是原子的名字。

这些都不属于逻辑本身；作者只是用它来解释基本概念的含义。 在 Alloy 中，你完全无法显式地引用原子。 不过你可以声明标量变量 N0、N1、D0、D1，然后（后面会看到）这个关系可以用表达式 N0 -> D0 + N1 -> D1 来表示。

必须记住的一条硬规则

「In Alloy, you can't refer to atoms explicitly at all.」——在 Alloy 中你根本不能显式引用原子。 没有 Name0 这样的字面量。要指涉特定原子，只能通过声明标量变量或用 one/lone 重数让工具去选。 这条规则是「模型不依赖具体实例」的保证，也是 Alloy 能做到符号执行的前提。

Q3：为什么集合表达式 {(N0)} 里要多一层括号？

在 Alloy 中所有结构都是关系，而集合不过是一种所有元组都只含一个元素的关系。 集合 {N0} 在 Alloy 中会被建模成这个关系；它无法被直接表示。

因为这类表达式从不出现在模型里，多出的括号语法并不造成不便。 恰恰相反，集合与关系的统一让语法更简单——因为不需要在集合与关系之间、或标量与集合之间做转换。

Q4：关系能包含关系吗？

不能。我们的关系是平坦的（flat）或一阶的（first order）， 意味着条目永远是原子，绝不本身是关系。

拿 addr 举例（用来建模「地址簿包含 name/address 映射」这个想法）。在平坦表示下，它的值是一个三元关系：

addr = {(B0, N0, D0), (B0, N1, D1), (B1, N1, D2), (B1, N2, D2)}

// 更传统的（高阶）写法：从地址簿到「从名字到地址集合的函数」的函数
addrC =
  {(B0, {(N0, {D0}), (N1, {D1, D2})}),
   (B1, {(N1, {D2}), (N2, {D2})})}

addrC 无法在 Alloy 中直接表示。 本章后面（3.4.3）会看到：书 b 的 name/address 映射（传统上写作 addrC(b)）在 Alloy 中写作 b.addr。

Q5：为什么不允许高阶关系？

限制为平坦关系让逻辑对分析更可控（more tractable）。 正如关系数据库社区已经发现的，平坦关系对几乎所有应用都足够有表达力， 而且它们的简单性和统一性很有吸引力。

上面 addrC 中对称性的缺失意味着它不能像从左访问那样容易地从右访问。对比一下：

表达式含义
addr.a从地址簿到「它们为地址 a 所用的名字」的映射
addr.n.Addr含有名字 n 的条目的那些地址簿的集合

对 addrC 而言，这两个都需要更复杂的构造。

Q6：限制为平坦关系会损失表达力吗？

会，但通常可以绕过去。几乎总是，一个看似需要高阶关系的情形都可以不用它而重新表述。

经典例子：大学课程的先修结构。每门课有一组先修课；要选修一门课， 学生需要修完该课的先修课集合中至少一组里的全部课程。高阶写法：

// 想修 C3，必须修过 (C0 和 C1) 或 (C0 和 C2)
prereqC = {(C3, {(C0), (C1)}), (C3, {(C0), (C2)})}

// 简单地把它压平是错的 —— 丢失了分组信息！
prereqBad = {(C3, C0), (C3, C1), (C3, C2)}

正确的解法：引入一组新原子来建模「先修组合」，再加一个把组合映射到其构成课程的关系：

prereq  = {(C3, P0), (C3, P1)}
courses = {(P0, C0), (P0, C1), (P1, C0), (P1, C2)}

这保留了本质结构：课程 C3 现在有两个可能的先修组合—— P0（由 C0 和 C1 组成）和 P1（由 C0 和 C2 组成）。

这是一个必须掌握的建模技巧：具体化（reification）

「引入一组新原子来代表原本嵌套的结构」是 Alloy（以及关系数据库设计）里最常用的重构手法。 它把「集合的集合」变成「一个实体 + 一个关系」。 记住这个模式：任何时候你想写 X -> set Y 且需要对 那个 set 本身施加约束时， 就引入一个新签名 G，写成 X -> some G 加 G -> some Y。

Q6-补：高阶关系还有另一个表达力优势

一个把 A 中原子映射到 B 中原子集合的函数，可以包含「从某原子到空集」的映射， 从而区分「一个原子被映射到 nothing」与「一个原子根本没有被映射」。 而 A 到 B 的二元关系无法做这种区分。替代办法是额外声明一个集合： 例如「映射为空的地址簿」属于集合 Book，但不被 addr 映射。

Q7：为什么不把复合对象作为语言构造包含进来？

传统规格说明语言如 VDM 和 Z 允许你直接用复合数学对象建模复合对象。 例如地址簿可能不表示为一个原子，而表示为一个「从名字到地址的关系」。 那么地址簿与另一个对象之间的关系就只能用高阶关系表达。 所以排除复合对象的理由，就是我们已给出的偏好平坦关系的理由。

此外还有一个理由：数学对象没有独立于其值的身份（no identity distinct from their value）。 如果你想谈论不同地址簿在不同时刻的值，你反正都得引入代表书的身份的原子。

Q8：真的能不用整数这类有解释的原子吗？

能，几乎一直能。而且事实证明，在大多数你以为需要整数的场合， 用一个无解释类型的原子加上一些关系来提供所需的解释，反而更干净、更抽象。

Alloy 确实支持整数，尽管方式有限：你可以取关系的大小、做加减、比较整数， 但不能做乘除。整数的处理见 3.7 与 4.8 节。

Q9：关系可以有无穷的大小和元数吗？

我们的逻辑并不排除无穷大小的关系，但对我们要看的所有模型， 只考虑有限实例化就够了。不过，关系的元数必须是有限的。

Q10：multirelation（多元关系）在实践中有用吗？

有用。因为关系是平坦而非嵌套的，元数大于二的关系非常常见。

  • 三元关系：要建模一个「状态涉及若干关系」的系统的执行轨迹，就需要三元关系—— 两列表示给定时刻的关系，再加一列表示时间。
  • 四元关系：较少见。例如网络路由表的状态可能关联： 表所在的主机(1)、传入包的期望目的地主机(2)、转发消息所用的端口(3)、 以及该表项存在的时刻(4)。
  • 五元及以上：罕见。
Q11：为什么关系的列没有名字？

如果你更熟悉关系数据库而非关系逻辑，可能会觉得奇怪：关系的列由位置而非名字标识。理由有三：

  1. 建模中关系的元数比数据库中的关系小得多；超过四列的关系很罕见。
  2. 在模型的约束中，join 倾向于以特定顺序作用于关系的特定列。
  3. 通过仔细安排列的顺序，几乎所有 join 都可以做成是在关系的第一列或最后一列上进行。

因此，按位置而非按名字处理列更方便，并产生更简洁自然的表达式。

解读：这条决定了 Alloy 的建模品味

「几乎所有 join 都在第一列或最后一列上进行」——这句话是 Alloy 建模的一条实用美学准则。 回头看第 2 章的 addr: names -> some Target：Book 在第一列，所以 b.addr 干净利落； Target 在最后一列，所以 addr.t（反查「谁指向 t」）也干净利落。 如果你发现自己在写 ~r 或复杂的 box join 才能表达一个自然的查询，往往是列的顺序设计错了。

Q12：如果列的顺序重要，那如何表示一个无序的关系？

无序关系可以用不同方式表示。最简单的办法是用一个关系 r（照常是有序的）， 再加一条约束 r = ~r 使它对称——正反两个方向相同。

spouse = ~spouse      // 你是我的配偶 ⟺ 我是你的配偶

作者坦率地评价：「This trick may be philosophically dubious, but in practice it's fine, and much easier than introducing additional constructs.」 ——这个技巧在哲学上可疑，但实践中没问题，而且比引入额外构造容易得多。

Q13：把标量和集合当作关系来处理，这是新想法吗？

不是。它可以追溯到 Tarski 关于关系演算的奠基性工作 [70]。 不过 Tarski 的所有关系都是二元的，所以他的编码没那么自然： 一个集合是「把集合中的每个原子映射到每一个可能的原子」的关系。 Rick Hehner 的「bunches」[27] 有类似的味道，但用一种新的代数结构统一了标量与集合。

Q14：把标量当作集合，不会让人困惑吗？

初次遇到这个想法时，有些人会感到不安。毕竟，集合与其元素之间的区分不就是集合论的根基吗？

但在一阶逻辑中（其中从不使用集合的集合），不会产生混淆。 而实践中，打破集合与标量的区分带来了很好的统一性：写导航表达式时， 你不必担心一个表达式代表集合还是标量。

// p 的（外）祖父们：点算子作用于标量 p，与作用于集合 p.parents 方式完全相同
p.parents.father

// p 的岳母/婆婆：不必担心 p 没有妻子时 p.wife 会「未定义」
p.wife.mother + p.husband.mother
// 等价写法
p.(wife + husband).mother

与「偏性」（partiality）的处理结合起来，我们就能这样写岳母， 而不必担心如果 p 没有妻子，表达式 p.wife 可能是未定义的。 → 这就是开篇所说的「消除了偏函数应用问题，因此不需要特殊的 undefined 值」的具体收益。

Q15：哪些术语是 Alloy 特有的，哪些是逻辑与集合论中的标准术语？

到目前为止引入的所有术语都是标准的， 除了两个：multirelation（超过两列的关系）和 option（空或单例的集合）。

Q16：Alloy 的 option 和 ML 语言的 option 一样吗？

不一样。大多数建模语言和编程语言不把 option 当作单例或空集合，而是用一种联合类型（union type）。 ML 的 option 就是这样一个联合：一个带标签的值，要么是一个标量，要么是某个特殊的 null 值。

对建模来说这更不方便，因为打标签会包裹住值并改变它的类型。举例： 一个邮件应用模型，标量 userAddress 表示用户地址，option replyAddress 表示用于 reply-to 的另一个地址。

  • 在 Alloy 中，这两个变量类型相同，可以用集合算子组合和比较： 
    userAddress = replyAddress
    当 replyAddress 有定义且等于 userAddress 时，此式为真。
  • 在传统做法中，两个变量类型不同，不先对 replyAddress 做投影就无法比较。
Q17：所以 Alloy 里其实没有标量？

按标准意义说，没有。传统语言会区分 a（标量）、{a}（含一个标量的单例集合）、(a)（元组）、{(a)}（关系）， 而 Alloy 把它们全部当作同一个东西，都表示为 {(a)}。

Q18：「option」这个词有什么用？每个 option 不都要么是标量要么为空吗？

这个术语用来描述一个值未知的变量，而不是某个特定的值—— 就像你提到「一辆车（vehicle）」时并不知道它是轿车还是卡车。 按定义，每个标量也是一个 option；两者都是集合；每个集合都是一个关系。 但通常你想用那个能告诉你最多信息的术语： 所以如果你知道它是集合就不叫它「关系」，如果你知道它是标量就不叫它「集合」。

一句话记住术语层级

scalar ⊂ option ⊂ set ⊂ relation
（标量 ⊂ option ⊂ 集合 ⊂ 关系；每个都是关系，用最能传递更多信息的那个词称呼它）

3.2.4 Functional and Injective Relations · 函数式与单射关系

functional（函数式）

一个二元关系，把每个原子至多映射到一个其他原子。这样的关系被称为函数（function）。

injective（单射的）

一个二元关系，至多把一个原子映射到每个原子（即每个目标至多有一个来源）。

四个示例值（对应原书 fig. 3.3–3.6）：

address1 = {(N0, D0), (N1, D1), (N2, D1)}
address2 = {(N0, D0), (N1, D1), (N1, D2)}
address3 = {(N0, D0), (N1, D1), (N2, D2)}
address4 = {(N0, D1), (N1, D1), (N1, D2)}

address1✓✗N1、N2 都映射到 D1（多对一）fig. 3.3
address2✗✓N1 映射到 D1 和 D2（一对多）fig. 3.4
address3✓✓—（一一对应）fig. 3.5

边界情形

空的二元关系既是 functional 的，也是 injective 的。（An empty binary relation is functional and injective.） 这在推理「至多一个」类性质时经常被忽略。

Discussion：把函数当作关系，这想法从哪来？标准吗？

这个想法在建模领域由规格说明语言 Z [65] 开创。它的使用至少可追溯到 Zermelo 和 Fraenkel 的集合论（这就是 Z 这个名字里「Z」的由来）。 Alloy 实际上比 Z 更极简：虽然 Z 不区分函数和关系， 但它确实区分标量、集合和元组；而在 Alloy 中，一切都是关系。

把函数当作关系是标准做法吗？不。大多数其他建模语言区分函数与其他关系。 例如在 UML 的约束语言 OCL [53] 中，沿一个关联导航可能产生空集合或未定义值， 取决于该关联的重数。→ 附录 E 有 OCL 的完整对比。

「injective relation」是 injection 吗？ 术语 injection（单射）传统上只用于既 functional 又 injective 的关系，所以作者尽量避免使用它。 遗憾的是，对一个 injective 关系没有通用的名字。

3.2.5 Domain and Range · 定义域与值域

定义

关系的 domain（定义域）是其第一列中原子的集合； range（值域）是最后一列中的集合。
更高元数的关系同样有 domain 和 range。

address = {(N0, D0), (N1, D1), (N2, D1)}
domain (address) = {(N0), (N1), (N2)}
range  (address) = {(D0), (D1)}

addr = {(B0, N0, D0), (B0, N1, D1), (B1, N2, D2)}
domain (addr) = {(B0), (B1)}          // 第一列
range  (addr) = {(D0), (D1), (D2)}    // 最后一列
Discussion：domain / range 是特殊算子吗？常用吗？

不是特殊算子，但它们作为函数在 Alloy 库中为二元关系预定义了。 用其他算子（后面介绍）很容易表达：二元关系 r 的 domain 和 range 分别是 r.univ 和 univ.r。

它们的使用不如 Z 等语言频繁，因为 Alloy 有丰富的声明语言（见 3.6）， 它鼓励你引入显式代表关系定义域与值域的集合。 → 第 2 章给 Book 加 names: set Name 字段正是这个思路。

Discussion：全函数（total）与偏函数（partial）呢？

「domain」一词常被用来指可能被一个关系或函数映射的原子集合。 在那种意义下，全函数是映射其定义域中每个成员的函数。 这个概念要求一个集合隐式地与一个关系相关联。 （另一种可能是：全函数关系映射宇宙中的每个原子，但这是很罕见的情况。）

我们的逻辑更简单：关系就是它的元组，关系的 domain 和 range 由这组元组决定。 作者说自己偶尔会非正式地使用「total」「partial」这两个词， 指的是一个关系在其声明中出现的那个集合上是全的还是偏的。

3.4Operators · 算子

算术语言由常量（0、1、2…）和算子（+、−、×）组成。同样，关系语言也有它自己的常量和算子。

算子的两大类别（务必分清）

· 集合算子（set operators）：关系的元组结构无关紧要——元组不妨被当作原子看待。
· 关系算子（relational operators）：元组结构是本质的——正是这些算子让关系变得强大。

3.4.1 Constants · 三个常量

常量含义元数
none空集（empty set）一元
univ全集（universal set）一元
iden恒等关系（identity）：含「把每个原子关联到它自己」的元组二元
none 和 univ 是一元的！

要表示空的二元关系，写 none -> none； 要表示把每个原子映射到每个原子的全关系，写 univ -> univ（使用 3.4.3 定义的箭头算子）。

// 给定两个集合
Name = {(N0), (N1), (N2)}
Addr = {(D0), (D1)}

// 三个常量的值：
none = {}
univ = {(N0), (N1), (N2), (D0), (D1)}
iden = {(N0, N0), (N1, N1), (N2, N2), (D0, D0), (D1, D1)}
一个必须记住的陷阱

「Note that iden relates all the atoms of the universe to themselves, not just the atoms of some subset.」
iden 关联的是宇宙中的所有原子，而不只是某个子集的原子。

Q：这些常量是隐式按类型参数化的吗？

不是。在某些建模语言里，这些常量实际上是常量的带索引族，必须通过某种方式（隐式或显式）选出合适的那个实例。 例如在 Z 中，恒等关系带一个显式的类型参数，而空关系是多态的。

在 Alloy 中，这些常量就是三个简单的常量，iden 和 univ 的值由所有已声明集合的值决定。 因此，很少会不加限定地使用 iden 和 univ；你通常会写 s <: iden 来得到集合 s 上的恒等关系（使用 3.4.3.6 定义的限制算子）。

如果忘了这么做，你可能会得到一些惊喜。例如 iden in r 不仅说关系 r 是自反的，还说它映射宇宙中的每一个原子—— 这很可能与 r 的声明不一致。

Q：这些常量有用吗？

恒等关系对关系演算风格是本质的。例如约束 no ^r & iden 表示关系 r 是无环的。 空关系的一个常见用途是给接受集合作为参数的谓词实例化（见 4.5.2）， 如第 6.2 节的框架条件（frame conditions）。

除这些情形外，常量很少被使用。更好的写法是：

  • 说一个关系空 / 非空，用表达式量词（3.5.2）而非常量 none： 写 no r 而不是 r = none——更可读。
  • 全关系通常限定在特定集合上：所以你会写 Name -> Addr 来表示「把所有名字映射到所有地址」的关系。
Q：常量增加了任何表达力吗？（语言设计者的细节问题）

你可能以为这些常量可以省略，改为在库模块中定义。但：

  • 全关系无法这样定义，因为所有量词和集合构造都需要显式的界（explicit bounds）。 你可以把全关系显式定义为「所有自由集合变量（顶层签名，见 4.2.1）的并集」， 但那样每引入一个新集合就得改定义。
  • 另两个常量事实上可以定义。例如恒等关系可以表示为集合构造 {x, y: univ | x = y}。

但它们被包含进来，是因为用常量比用库函数更方便， 而且分析器能更容易地利用它们的特殊性质。

3.4.2 Set Operators · 集合算子

算子名称定义

myName = yourName                    // false
yourName in none                     // false —— 「没有名字是你的名字」
Q：这里的集合等号和你之前用的等号是同一个吗？

不是。像 cacheAddr = {(A0, D0), (A1, D1)} 这样的语句只在本章中使用， 用于解释逻辑的含义，它左边永远是 Alloy 表达式，右边是（用传统数学记号写的）关系描述。 这里的等号是一个特殊的定义符号，而且不对称—— 写 {(A0, D0), (A1, D1)} = cacheAddr 是没有意义的。

另一方面，像 Name = Group + Alias 这样的语句是 Alloy 逻辑中的一个约束， 等号是本节定义的集合算子。这个相等概念是对称的，该语句等价于 Group + Alias = Name。 作者说：「我本可以用一个不同的符号表示定义性等号，但那显得有点学究气。」

Q：相等是结构相等还是引用相等？

这个区分在这里没有意义——它基于编程概念，而关系没有独立于其值的身份。 如果两个关系有相同的元组集合，它们不是两个关系：它们就是同一个关系。

原子除了它的身份之外什么都不是；两个原子相等当且仅当它们是同一个原子。 如果你有一组代表复合对象的原子（用一些关系把原子映射到其内容）， 你可以通过引入一个新关系来显式定义任何你想要的结构相等概念。 （对那些 C++ 程序员：不行，你不能在 Alloy 中重定义等号。）

Q：这些算子上没有类型约束吗？

没有传统那种。在某些简单类型化的语言里，比如 Z，集合算子的两个参数必须类型相同。 所以像 Book + Addr（地址簿集合与地址集合的并）这样的表达式是非法的。

在 Alloy 中，这类表达式一般并不非法，而且能被好好利用。例如建模一个类型为 C 的 Java 变量 v 的值， 你可以引入一个包含 null 引用的单例集合 Null，然后声明：

v: C + Null      // v 要么是 null，要么是集合 C 中的一个引用

在不允许这种形式的并集的类型系统里，很难用一个声明表达这个约束， 可能必须弱化它——允许引用任何类，或者区分不同类型的 null 值。 → 这正是第 1 章说的「有子类型和并集但不需要向下转型」的类型系统的具体体现，第 4.4 节详述。

不过 Alloy 确实施加了一些约束：

  • 参数的元数必须匹配，所以 addr + Name 是非法的。
  • 「可被 none 替换而无害」即为病态：如果仅从变量的声明就能证明， 某个表达式可以被空关系替换而不影响它所在约束的值， 那么这个表达式就被判定为格式不良（ill-formed），即使它的含义是清楚的。 例如 Name & Book 和 Name & (Alias + Book) 都是类型不良的—— 因为两者中 Book 的出现（以及第一个中的 Name）都可以被 none 替换而不影响含义。
解读：这条类型规则其实是个「死代码检测器」

「能被 none 替换而无害 ⇒ ill-formed」听起来古怪，但它极其有用： 它意味着类型检查器会主动抓出那些恒为空的表达式。Name & Book 恒空（两个签名不相交）， 所以包含它的约束要么恒假要么对它无感——两种情况都表明你写错了。 这是一种在设计期就生效的「静默 bug」防线，比编译器的类型检查敏锐得多。

Q：为什么用关键字 in？

关键字 in 是为它的歧义性而精心挑选的（carefully chosen for its ambiguity）。 因为标量被表示为单例集合，in 有时表示成员关系（标量与集合之间，或元组与关系之间，传统写作 ∈）， 有时表示子集（两个集合之间或两个关系之间，传统写作 ⊆）。

两个关系 p 和 q 的箭头积（或简称积）p -> q，是这样得到的关系： 取 p 的一个元组与 q 的一个元组的每一种组合，把它们拼接起来。

p、q 的形态p -> q 的形态

p 或 q 有一方 arity ≥ 2multirelation

// 标量情形
n = {(N0)}   n' = {(N1)}   d = {(D0)}   d' = {(D1)}
address = {(N0, D0), (N1, D1)}

n -> d = {(N0, D0)}                       // 把名字 n 映射到地址 d 的元组

3.4.3.2 Dot Join · 点连接（最重要的算子）

原文定位

「The quintessential relational operator is composition, or join.」 ——最典型的关系算子就是复合，即 join。

先看元组怎么 join。给定两个元组 s1 -> … -> sm 和 t1 -> … -> tn：

  1. 检查第一个元组的最后一个原子（即 sm）是否匹配第二个元组的第一个原子（即 t1）；
  2. 若不匹配，结果为空——没有 join；
  3. 若匹配，结果是这样一个元组：以第一个元组的原子开头，以第二个元组的原子结尾， 但恰好省略掉那个匹配的原子： 
    s1 -> … -> sm-1 -> t2 -> … -> tn
表达式结果说明
{(N0, A0)} . {(A0, D0)}{(N0, D0)}A0 匹配，被省略
{(N0, D0)} . {(N0, D0)}{}末列 D0 ≠ 首列 N0，不匹配
{(N0, D0)} . {(D1)}{}D0 ≠ D1
{(N0)} . {(N0, D0)}{(D0)}N0 匹配并被省略 → 结果是标量
{(N0, D0)} . {(D0)}{(N0)}join 可以向右「削掉」列
{(B0)} . {(B0, N0, D0)}{(N0, D0)}标量 join 三元关系 → 二元关系
关系的 dot join 定义

关系 p 和 q 的 dot join（或简称 join）p.q，是这样得到的关系： 取 p 中一个元组与 q 中一个元组的每一种组合，如果它们的 join 存在，就把它包含进来。

p 和 q 可以有任意元数，只要它们不都是一元的 （因为那会产生一个零元的关系——而 arity 必须 ≥ 1）。 当 p 和 q 都是二元关系时，p.q 就是它们的标准关系复合。

关键推论：join 的元数规律

arity(p.q) = arity(p) + arity(q) − 1
因为那一列被「丢掉了」（the dropped column）

示例：消息路由

to      = {(M0, N0), (M0, N2), (M1, N2), (M2, N3)}   // 消息 → 意图发送给的名字
address = {(N0, D0), (N0, D1), (N1, D1), (N1, D2), (N2, D3), (N4, D3)}

to.address = {(M0, D0), (M0, D1), (M0, D3), (M1, D3)}   // 消息 → 应发送到的地址
M0→N0→D0 M0→N0→D1 M0→N2→D3 M1→N2→D3
注意：N1、N4 没有消息指向它们；M2→N3 断了（N3 不在 address 的定义域中），所以 to.address 里没有 M2

函数复合

如果 p 和 q 是函数，p.q 也将是函数，此时 dot 等价于函数复合。

address = {(N0, D0), (N1, D0), (N2, D2)}   // 名字 → 地址
user    = {(D0, U0), (D1, U1), (D2, U2)}   // 地址 → 用户名部分
host    = {(D0, H0), (D1, H1), (D2, H2)}   // 地址 → 主机名部分

address.user = {(N0, U0), (N1, U0), (N2, U2)}
address.host = {(N0, H0), (N1, H0), (N2, H2)}

导航（navigation）——最常见的用法

s 是集合，r 是二元关系

s.r 是集合 s 在关系 r 下的像（image）： 对 s 的每个成员跟随关系 r，然后把所有得到的集合收集到一个集合里。 这也许是 dot 最常见的用法，在对象建模术语中称为导航。

x 是标量，r 是二元关系

x.r 是 x 所映射到的原子集合。 对函数 f 和定义域内的标量 x，x.f 就是 f 把 x 映射到的那个标量—— 此时 join 就像函数应用。

Alloy 没有未定义表达式

注意：当 x 不在 f 的定义域中时，x.f 将是空集。 传统上，函数在定义域外应用根本没有结果，因此涉及这种应用的表达式可能是未定义的。 在我们的逻辑中，没有未定义的表达式。（In our logic, there are no undefined expressions.）

双向导航

一个常被忽略的能力

你可以向两个方向导航：s.r 是集合 s 向前穿过 r 的像， 而 r.s 是向后的像。

address = {(G0, A0), (G0, A1), (A0, D0), (A1, D1)}
Alias = {(A0), (A1)}   Group = {(G0)}   Addr = {(D0), (D1), (D2)}
表达式结果含义
Alias.address{(D0), (D1)}在地址簿中查找任意别名所得结果的集合（向前）
Group.address{(A0), (A1)}查找任意组所得结果的集合（向前）
address.Group{}反向：查找后得到组的那些名字 → 空（没有谁指向 G0）
address.Alias{(G0)}反向：查找后得到别名的那些名字 → G0

高元数关系的 join

高元数关系的 join 也很常见，尤其是 x.q 和 q.x 这两种形式，其中 x 是标量，q 是 multirelation。

// ① 三元关系：书、名字、地址
b    = {(B0)}
addr = {(B0, N0, D0), (B0, N1, D1), (B1, N2, D2)}
b.addr = {(N0, D0), (N1, D1)}        // 书 b 的 name→address 映射

// ② 三元关系：名字、地址、时间（时间在最后一列）
t    = {(T1)}
addr = {(N0, D0, T0), (N0, D1, T1), (N1, D2, T0), (N1, D2, T1)}
addr.t = {(N0, D1), (N1, D2)}        // 时刻 t 的 name→address 映射（向后 join！）

// ③ 四元关系：书、名字、地址、时间
addr = {(B0,N0,D0,T0), (B0,N0,D1,T1), (B0,N1,D2,T0),
        (B0,N1,D2,T1), (B1,N2,D3,T0), (B1,N2,D4,T1)}
t = {(T1)}   b = {(B0)}
b.addr.t = {(N0, D1), (N1, D2)}      // 书 b 在时刻 t 的映射
括号在这里不必要

注意 b.addr.t 不需要括号来指明 join 的应用顺序。 表达式 b.(addr.t) 和 (b.addr).t 是等价的： 你可以先投影到特定的书、再投影到特定的时刻，也可以先选时刻、再选书。

Q：dot join 是结合的吗？

不是。表达式 (a.b).c 和 a.(b.c) 并不总是等价， 因为一个可能格式不良而另一个格式良好。

由于被丢掉的那一列，join 的元数总比其参数元数之和少一。 例如若 s、t 是一元的，r 是三元的：那么 t.r 是二元的，s.(t.r) 是一元的； 而 s.t 会是零元的，因此非法——所以 (s.t).r 同样非法，与 s.(t.r) 不等价。

但如果给一个 join 表达式加括号的两种方式都格式良好——如上面的例子—— 它们就是等价的。所以括号位置放错不会导致模型产生非预期的含义， 除非类型检查器抱怨，你可以忽略这个问题。 （作者感谢 Somesh Jha 指出这一点。）

Q：dot join 和数据库的 join 一样吗？

不完全一样。在关系数据库查询语言中，join 算子按名字而非位置匹配列， 而且匹配的那一列不会被丢掉。你可以如下定义一个更像数据库的 join：

// 令 id3 为三元恒等关系
id3 = {a, b, c: univ | a = b and b = c}

// 定义
p ⊙ q = p.id3.q

那么 p ⊙ q 像 dot join 一样拼接匹配的元组， 但像数据库 join 一样保留匹配的元素。 它还提供了一个很好的限制（restriction，见 3.4.3.6）简写： s <: r 和 r :> s 可以写成 s ⊙ r 和 r ⊙ s。 （作者感谢 Butler Lampson 的这一洞见。）

3.4.3.3 Box Join · 方框连接

定义

方框算子 [] 语义上与 join 完全相同，但以不同的顺序接受参数，并且有不同的优先级：

e1 [e2]　　≡　　e2.e1

例：给定从名字到地址的关系 address 和代表一个名字的标量 n， 表达式 address[n] 等价于 n.address，表示 n 被映射到的地址集合。

优先级：dot 比 box 结合得更紧

a.b.c [d]　　≡　　d.(a.b.c)

这个算子存在的理由：它允许做一个语法上的区分—— 区分「解引用一个复合对象的字段」（用 dot join）与「执行一次索引查找」（用 box join）， 尽管二者在语义上没有区别。

// 三元关系 addr 关联书、名字、地址
b.addr[n]     // 书 b 中与名字 n 关联的地址集合
≡ n.(b.addr)

// 选择方框是为了类比数组记法：
// 类 C 有一个数组值字段 f，用 x 解引用字段 f、再取索引 i 处的对象
x.f[i]        // 就像在 Java 中一样
≡ i.(x.f)

3.4.3.4 Transpose · 转置

二元关系 r 的转置 ~r 取它的镜像——通过反转每个元组中原子的顺序构成一个新关系。

address  = {(N0, D0), (N1, D0), (N2, D2)}    // 名字 → 它代表的地址
~address = {(D0, N0), (D0, N1), (D2, N2)}    // 每个地址 → 代表它的名字

symmetric（对称）

二元关系 r 是对称的，当它包含元组 a -> b 时也包含 b -> a。 更简洁地写成关系约束：

~r in r

对对称关系取转置没有效果。

symmetric closure（对称闭包）

r 的对称闭包是包含 r 且对称的最小关系，它等于：

r + ~r

例子：把主机映射到其网络邻居的关系 connects，如果连接是双向的，它就是对称的。 把男人映射到其妻子的关系 wife 的转置，是把女人映射到其丈夫的关系 husband； 其对称闭包是把每个人映射到其配偶的关系 spouse。

关于 transpose 的三个有用事实（原文列出，很实用）
事实说明
s.~r 等于 r.s是集合 s 向后穿过关系 r 的像
r.~r把 r 的定义域中映射到一个共同元素的两个原子关联起来的关系； 当 r 是函数时，r.~r 是「把有相同像的原子等同起来」的等价关系
r.~r in iden
~r.r in iden		前者说 r 是 injective（单射的）；后者说 r 是 functional（函数式的）

mother.~mother    // 兄弟姐妹关系：把孩子映射到其同胞（也映射到它自己）
Discussion：为什么写 ~r in r 而不是 ~r = r 来表示对称？

你可能预期是 ~r = r。两个条件是等价的，但作者偏好第一个，因为：

  1. 它更贴近非正式的表述；
  2. 它遵循自反性与传递性条件的模式（分别是 iden in r、r.r in r）；
  3. 从分析的角度看，把约束写成最弱的形式是个好习惯。

作者自嘲：「 admittedly, this is a bit pedantic, and it's not unreasonable to expect a definition of symmetry to be symmetric.」 ——诚然这有点学究气，而且期待「对称的定义本身是对称的」也不算不合理。

解读：「写成最弱形式」为什么对分析有好处

这条建议在 Alloy 里有实在的技术理由。~r in r 是 ~r = r 的弱化， 而弱化后的公式对 SAT 求解器更容易：等式约束会立即把大量布尔变量钉死， 而蕴含式允许求解器更早剪枝。更重要的是建模层面：写最弱形式意味着你只声明你真正需要的东西， 不给模型附加意外的限制——这正是第 2 章「加一条过强的约束导致 show 变成 inconsistent」的教训。 记住三个配套写法：iden in r（自反）、r.r in r（传递）、~r in r（对称）。

3.4.3.5 Transitive Closure · 传递闭包

transitive（传递）

二元关系是传递的，当它包含 a -> b 和 b -> c 时也包含 a -> c。 更简洁地写成关系约束：

r.r in r

reflexive（自反）

二元关系 r 是自反的，如果它对每个原子 a 都包含元组 a -> a：

iden in r
两个闭包的定义

传递闭包 ^r（transitive closure，简称 closure）是包含 r 且传递的最小关系。 可以这样计算它：取这个关系，加上它与自身的 join，再加上它与那个结果的 join，如此继续：

^r = r + r.r + r.r.r + …

自反传递闭包 *r 是包含 r 且既传递又自反的最小关系， 通过给传递闭包加上恒等关系得到：

*r = ^r + iden
图形视角（最重要的直觉）

把关系看作一张图，传递闭包代表可达性（reachability）。 由于关系本身代表长度为 1 的路径，它的平方代表长度为 2 的路径，以此类推， 所以闭包在两个原子之间存在一条任意长度（除零以外）的路径时，把它们关联起来。

而自反传递闭包在两个原子之间存在一条任意长度（包括零）的路径时把它们关联起来。

Q：为什么自反传递闭包会关联「不相关的」原子？

假设一个模型有书集合 Book、名字集合 Name、地址集合 Addr、一本书 b， 以及一个把书映射到其内容的关系 addr，取值如下：

Book = {(B0), (B1)}
Name = {(N0), (N1)}
Addr = {(D0), (D1)}
b    = {(B0)}
addr = {(B0, N0, N1), (B0, N1, D0), (B1, N1, D1)}

univ = {(B0), (B1), (N0), (N1), (D0), (D1)}
iden = {(B0,B0), (B1,B1), (N0,N0), (N1,N1), (D0,D0), (D1,D1)}

^(b.addr) = {(N0, N1), (N1, D0), (N0, D0)}   // 书 b 中名字的直接与间接映射

表达式 *(b.addr) 会包含这两个关系的元组。除了有预期的 (N0, N0) 这类元组外， 它还会包含 (B0, B0) 这类元组（书！）。

虽然这看起来奇怪，但它自然地由自反传递闭包和恒等关系的定义得出。 替代方案是让每个关系都隐式关联一些集合，代表其定义域和值域的可能成员——那会让逻辑复杂化。

实践中这不是问题。闭包常出现在导航表达式中，而那些不相关的自反元组会在 join 中消失。 例如从名字集合 friends 出发零步或多步可达的名字与地址写作 friends.*(b.addr)， 它不会包含任何书，因为 friends 和 Book 是不相交的。

如果你需要显式地去掉多余的元组，你总是可以写 s <: *r 来把闭包限制为只映射集合 s 中的原子。

Q：形成一个关系的闭包需要多少次迭代？

对有限宇宙，传递闭包只需要有限的展开，其上限由图中最长路径的长度决定。

对某些关系，即使宇宙很大，传递闭包也只需要极少的展开。 Stanley Milgram 的著名实验（让堪萨斯州的居民通过熟人把信送到波士顿的居民手中） 表明信件平均只需六步就能到达 [52]。如果六步真的足以连接任意两个人， 那就意味着 knows 关系的闭包就是全关系，而且六次展开就能得到它。

3.4.3.6 Domain and Range Restrictions · 定义域与值域限制

定义

限制算子用于把一个关系过滤到给定的定义域或值域：

  • s <: r（由集合 s 和关系 r 构成）包含 r 中以 s 中某个元素开头的那些元组；
  • r :> s 包含 r 中以 s 中某个元素结尾的那些元组。

限制可以应用于元数为二或以上的任意关系，但最常用于二元关系。

address = {(G0, A0), (G0, G1), (A0, D0), (G1, D0), (G1, A1), (A1, D1), (A2, D2)}
Alias = {(A0), (A1), (A2)}   Group = {(G0), (G1)}   Addr = {(D0), (D1), (D2)}
表达式结果含义
address :> Addr{(A0,D0), (G1,D0), (A1,D1), (A2,D2)}把名字映射到地址（而非其他名字）的条目
address :> Alias{(G0,A0), (G1,A1)}把名字映射到别名的条目
Group <: address{(G0,A0), (G0,G1), (G1,D0), (G1,A1)}由组出发的条目
限制 vs 像：差别就在「是否丢掉匹配的元素」

对二元关系应用限制就像取一个集合的像，但不丢掉匹配的元素。更形式化地， 若 r 是二元关系、s 是集合，则：

range (s <: r) = s.r
domain (r :> s) = r.s

另外：恒等关系映射宇宙中每个原子到自身，但我们常常想要的是 把某个集合 s 中每个原子映射到自身的关系，它可以写作 s <: iden。

3.4.3.7 Override · 覆盖

定义

关系 p 被关系 q 覆盖（override）的结果 p ++ q 像并集， 只是 q 的元组可以替换p 的元组，而不只是增补它们。 p 中任何「以与 q 中某元组相同的元素开头」的元组都会被丢弃。 p 和 q 可以有任意匹配的、二或以上的元数。

// 别名在家和在工作时的邮件地址
homeAddress = {(A0, D1), (A1, D2), (A2, D3)}
workAddress = {(A0, D0), (A1, D2)}

// 首选地址：有工作地址就用工作地址，否则用家庭地址
homeAddress ++ workAddress = {(A0, D0), (A1, D2), (A2, D3)}

注意 A0：home 给的是 D1，但被 work 的 D0 覆盖了； A2：work 里没有，所以保留 home 的 D3。

override 可以用更简单的算子定义

把 p 被 q 覆盖，等价于「取 q，并上 p 中去掉那些以 q 的定义域中元素开头的元组之后剩下的部分」：

p ++ q = p - (domain (q) <: p) + q

→ 这也顺便说明了 ++ 为什么排在优先级表的低位（它是「和算子」）。

override 的两大用途

「Override is useful for modeling insertions into map datatypes, and assignment-like statements in programs.」 ——override 适用于建模向 map 数据类型的插入，以及程序中类似赋值的语句。

// ① 向 hashmap 插入键 k 与值 v：m、m' 是插入前后的两个「键→值」关系
m' = m ++ k -> v

// ② Java 程序的环境 e：变量 → 对象引用的关系。赋值 x = y 的效果：
e' = e ++ x -> y.e

// ③ 堆状态：每个类的每个字段（实例变量）用一个关系表示。
//    setter 语句 x.f = y（x、y 是变量，f 是字段）描述为：
f' = f ++ x.e -> y.e
解读：这就是第 6.4 节「内存抽象」的技术基础

注意 ②③ 这两条：用 override 就能把命令式语言的赋值语义完整地关系化。 环境 e 处理「变量→引用」，字段关系 f 处理「对象→对象」，两者的更新都是 ++。 这意味着 Alloy 可以直接建模一个 Java 堆——第 6.4 节 Memory Abstractions 正是这么做的。 也解释了为什么作者说 none 的常见用途之一是「第 6.2 节的框架条件」： f' = f ++ ... 只描述了被修改的字段，其他字段的「不变」需要用别的方式说清楚。

Discussion：算子的优先级是什么？

算子有一个标准的优先级排序，使约束不会被大量括号破坏。这个排序遵循通常的约定：

  • 一元算子（闭包 ^ *、转置 ~）先于二元算子；
  • 积算子（如 dot . 和 arrow ->）先于和算子（+、-、&）；
  • 所有算子都左结合（All operators associate to the left）。

3.5Constraints · 约束

我们已经看过如何用比较算子 in 和 = 从两个表达式做出一个约束。 更大的约束通过两种方式构成：用标准逻辑算子组合较小的约束，以及把含自由变量的约束对绑定进行量化。

3.5.1 Logical Operators · 逻辑算子

每个逻辑算子有两种形式：简写形式和冗长形式（类似于编程语言中布尔表达式所用的算子）。 两者完全可互换。

名称简写冗长形式说明
negation 否定!not可与比较算子组合：a != b ≡ not a = b；也可写 a not = b
conjunction 合取&&and—
disjunction 析取||or—
implication 蕴含=>implies—
alternative 选择,else与 implies 配套使用，见下
bi-implication 双蕴含<=>iff—
else / 逗号：一个容易被忽略的算子 
F implies G else H　　≡　　(F and G) or ((not F) and H)

即：F 成立则要求 G，F 不成立则要求 H。这是「if-then-else」的公式版本。

嵌套蕴含的常见惯用法

// 逗号形式
C1 => F1 ,
C2 => F2 ,
C3 => F3

// 等价的关键字形式
C1 implies F1
else C2 implies F2
else C3 implies F3

含义：在条件 C1 下 F1 成立；如果不成立，那么在条件 C2 下 F2 成立；再不成立，那么在 C3 下 F3 成立。 这就是 Alloy 里写 case 分析（分情况讨论）的标准姿势。

隐式合取：花括号内换行即 and

约束的合取太常见了，所以我们经常省略 and 算子，把整组约束包在花括号里： {F G H} 等价于 F and G and H。

→ 这就是第 2 章 sig Book {…} { no n… ⟲ all a… } 那种写法的依据。

条件表达式（不同于条件公式）

有时用条件表达式比用条件公式更自然。形式为：

if C then E1 else E2

其中 C 是一个约束，E1 和 E2 是表达式；当 C 为真时它的值是 E1，否则是 E2。

示例：首选地址（两种等价写法）

设地址簿用三个关系建模：homeAddress 和 workAddress 把别名映射到家/工作邮件地址，address 把别名映射到首选地址。 要说「别名 a 的首选地址是工作地址（若存在），否则是家庭地址」：

// 写法一：条件公式（用 else / 逗号）
some a.workAddress =>
  a.address = a.workAddress ,
  a.address = a.homeAddress

// 写法二：条件表达式
a.address =
  if some a.workAddress then a.workAddress else a.homeAddress

3.5.2 Quantification · 量化

量化约束的形式是：

Q x: e | F

其中 F 是一个包含变量 x 的约束，e 是限定 x 的表达式（bounding expression），Q 是量词。

形式含义
all x: e | FF 对 e 中的每个 x 成立
some x: e | FF 对 e 中的某个 x 成立
no x: e | FF 对 e 中没有 x 成立
lone x: e | FF 对 e 中至多一个 x 成立
one x: e | FF 对 e 中恰好一个 x 成立
记忆技巧（原文提供）

要记住 lone 的含义，可以把它想成 「less than or equal to one」（小于等于一）的缩写。

多变量与 disj

// 同一个量词中绑定多个变量：存在恰好一组 (x, y) 的取值使 F 为真
one x: e, y: e | F

// 界相同的变量可以共享声明，等价写法：
one x, y: e | F

// disj：把绑定限制为「被绑变量彼此不相交」的那些组合
all disj x, y: e | F     // F 对 x 和 y 的任意不同取值组合都为真

示例：多级地址簿

// 给定：Address（邮件地址集合）、Name（名字集合）、address（把名字映射到名字和地址的关系）

some n: Name, a: Address | a in n.address
  // 某个名字映射到某个地址（即地址簿非空）

no n: Name | n in n.^address
  // 没有名字能通过查找从自身到达（即地址簿中无环）

all n: Name | lone d: Address | d in n.address
  // 每个名字至多映射到一个地址

all n: Name | no disj d, d': Address | d + d' in n.address
  // 同一件事的另一种说法：对每个名字，不存在一对不同的地址同时属于查找该名字的结果

量词也可以直接作用于表达式（不带 | F）

形式含义
some ee 有一些元组（非空）
no ee 没有元组（为空）
lone ee 至多一个元组
one ee 恰好一个元组
可读性优先于「等价」

注意 some e 和 no e 本可以写成 e != none 和 e = none， 但使用量词能让约束更可读。（这也呼应了 3.4.1 中「说关系空/非空用 no r 而非 r = none」的建议。）

some Name                        // 名字集合非空
some address                     // 地址簿非空：存在某个把名字映射到地址的 pair
no (address.Addr - Name)         // 除名字外没有东西被映射到地址
all n: Name | lone n.address     // 每个名字至多映射到一个地址（比上面的写法简洁）
all n: Name | one n.address or no n.address   // 同一件事

3.5.3 Higher-order Quantification · 高阶量化

重要警告

量化变量不必是标量；它们可以是集合，甚至是 multirelation。 允许这样的逻辑不再是「一阶」的，而成为「高阶」的。 Alloy 包含这类量化，但它们并不总能被分析（见 5.2.2）。

// 高阶量化常用于陈述关于「算子本身」的性质：

all s, t: set univ | s + t = t + s
  // 集合上的并算子是交换的

all p, q: univ lone -> lone univ | p.q: univ lone -> lone univ
  // 两个函数的 join 也是函数
Q：Alloy 允许独立的（freestanding）声明吗？

不允许。本节描述的声明形式可以用于量化变量和字段， 也可以用作公式。但不支持顶层的关系声明——尽管它们是不必要的 （在 4.2.2 之后的讨论中解释）。

Q：高阶量化什么时候可以被分析？

一般来说，Alloy Analyzer 无法处理涉及高阶量化的公式，所以不鼓励使用它们。 但在某些有用的情形下，高阶量词可以通过一种称为 「skolemization」（斯科伦化）的方案消除—— 它把一个量化变量变成一个自由变量，其值随后可由约束求解找到。 更多细节见 5.2.2。
→ 这正是前言致谢里提到的 Viktor Kuncak 的工作领域。

Q：lone p: some X | F 和 some p: lone X | F 有什么区别？

新手有时会被这两种量化的区别搞混。令人困惑的是，同样的关键字既用作量词、又用作限定表达式的重数。

量词重数含义
lone p: some X | Flone（至多一个）some（一个或更多） p 被约束为取自 X 的非空子集，且约束说 F 对至多一个这样的子集 p 成立。
→ 真·高阶量化。作者说「我从没遇到过需要它的场合」。
some p: lone X | Fsomelone 约束说 F 对某个 option p 成立，等价于： 
(some p: X | F) or (let p = none | F)
→ 因此它根本不算高阶量化，而且「偶尔有用」。

3.5.4 Let Expressions and Constraints · let 表达式与约束

当一个表达式反复出现，或者是一个更大、更复杂表达式的子表达式时，你可以把它提取出来。形式：

let x = e | A
语义（纯语法替换）

它是 A 的简写，其中变量 x 的每次出现都被表达式 e 替换。 let 的主体 A（从而整个形式）可以是约束，也可以是表达式。

// let 的主体是约束
all a: Alias |
  let w = a.workAddress |
    a.address = if some w then w else a.homeAddress

// let 的主体是表达式（等价写法）
all a: Alias |
  a.address =
    let w = a.workAddress |
      if some w then w else a.homeAddress
Discussion：let 绑定可以是递归的吗？

不可以。它们只提供一个方便的简写，不允许递归定义。 一个 let 在绑定左侧引入的变量，不能出现在同一绑定的右侧，也不能出现在同一 let 构造中先于它的那个绑定里。

3.5.5 Comprehensions · 集合构造

定义

Comprehension 从性质构造出关系。集合构造表达式

{x1: e1, x2: e2, …, xn: en | F}

构造出一个关系，它包含所有形如 x1 -> x2 -> … -> xn 的元组， 对这些元组约束 F 成立，且 xi 的值取自限定集合表达式 ei 的值。

限制

每个表达式 ei 必须表示一个集合，而不能是更高元数的关系。

// 多级地址簿：address 把 Name 中的名字映射到名字、也映射到 Addr 中的地址

{n: Name | no n.^address & Addr}
  // 解析不出任何实际地址的那些名字的集合

{n: Name, a: Addr | n -> a in ^address}
  // 一个把名字映射到地址的关系，对应「多级查找」的结果
解读：集合构造是「把断言变成数据」的工具

注意第二个例子：^address 是一个可达性关系，而 {n: Name, a: Addr | n -> a in ^address} 把它收窄成「只保留名字→地址那部分」。这与第 2 章 n.^(b.addr) & Addr 目的相同，但机制不同： 交集 & 是算子级的过滤，集合构造是公式级的过滤——后者能表达任意复杂的条件（例如 {n: Name | no n.^address & Addr} 这种「解析不出地址的名字」用交集写不出来）。 配合 3.1 节的问答（谓词演算风格常用于集合构造），这条就串起来了。

3.6Declarations and Multiplicity Constraints · 声明与重数约束

声明引入一个关系名。我们刚看过声明如何用于量化约束和集合构造。 独立的关系名声明也讲得通，尽管第 4 章会看到，在完整的 Alloy 语言中， 它们会被改为在「签名」内部声明。

为什么重数出现在「逻辑」章

作者说明：重数的概念与声明的概念紧密相连。 它对逻辑而言并非本质（not essential in a logic），但之所以放进本章， 是因为它太有用了，而且可以独立于 Alloy 的结构化机制来解释。

3.6.1 Declarations · 声明

形如下式的约束称为声明（declaration）：

relation-name : expression

它的含义几乎（马上有个但书）等于把冒号换成关键字 in， 于是它变成一个简单的约束，说左边命名的关系的值，是右边限定表达式值的一个子集。 限定表达式通常由一元关系和箭头算子构成，但任何表达式都可以用。

// 单个地址簿：名字 → 地址
address: Name -> Addr

// 一组地址簿：书 → 名字 → 地址
addr: Book -> Name -> Addr

// 多级地址簿：名字 → 名字和地址
address: Name -> (Name + Addr)
同一个关系可以有不同强度的声明

「The same relation can be declared in different ways, depending on how much information you want to put in the declaration.」

// 弱声明：别名和组都映射到地址、别名、组
address: (Alias + Group) -> (Addr + Alias + Group)

// 强声明：额外说明「别名（不同于组）总是直接映射到地址」
address: (Alias -> Addr) + (Group -> (Addr + Alias + Group))

→ 这正是「增量细化」的具体操作：把弱声明替换为强声明，模型的其他部分无需改动。

关系（不只是集合）也可以出现在声明的右侧：

// 地址簿用三个关系表示：家庭、工作、首选地址
workAddress, homeAddress: Alias -> Addr
prefAddress: workAddress + homeAddress   // ← 右侧是两个关系之和

3.6.2 Set Multiplicities · 集合重数

上一小节说声明 x: e 的含义几乎等同于子集约束 x in e。现在是那个但书：

但书

声明可以包含重数约束（multiplicity constraints），而且它们有时是隐式的。

重数关键字含义
setany number · 任意数量
oneexactly one · 恰好一个
lonezero or one · 零或一个
someone or more · 一个或更多
注意关键字复用

one、lone、some 与用于量化的关键字是同一批 （这正是 3.5.3 那个问答里「新手困惑」的根源）。区分方法：看它在冒号前（量词）还是在冒号后（重数）。

含义取决于限定表达式的元数

如果限定表达式表示一个集合（即是一元的），它可以在前面加一个重数关键字：

x: m e

它按 m 约束集合 x 的大小。

对于集合值的限定表达式，省略关键字等同于写 one。 所以如果没有关键字出现，声明使该变量成为一个标量。

声明含义
RecentlyUsed: set NameRecentlyUsed 是集合 Name 的一个子集
senderAddress: AddrsenderAddress 是 Addr 中的一个标量（默认 one）
senderName: lone NamesenderName 是一个 option：要么是 Name 中的一个标量，要么为空
receiverAddresses: some AddrreceiverAddresses 是 Addr 的一个非空子集
量化变量声明与自由变量声明形式完全相同

量化约束中变量的声明，是完全相同形式的声明，遵循相同的规则。 唯一的区别是：量词引入的变量在量化约束的主体内被绑定； 而我们看过的其他声明引入的是自由变量（free variables）。

some n: Name, a: Address | a in n.address   // 两个声明，绑定标量 n 和 a

3.6.3 Relation Multiplicities · 关系重数

一条硬规则

当限定表达式是一个关系（即元数大于一的关系）时， 它不可以在前面加重数关键字。但如果限定表达式是用箭头算子构造的，重数可以出现在它内部。

假设声明形如：

r: A m -> n B

其中 m 和 n 是重数关键字（A 和 B 暂时当作集合）。那么关系 r 被约束为：

n 在右边 → 管「A 的每个成员」

把 A 的每个成员映射到 B 的 n 个成员

m 在左边 → 管「B 的每个成员」

把 A 的 m 个成员映射到 B 的每个成员

这样的声明可以指出关系的定义域与值域（见 3.2.5），以及它是否 functional 或 injective（见 3.2.4）：

声明含义
r: A -> one B一个函数，其定义域是 A
r: A one -> B一个 injective 关系，其值域是 B
r: A -> lone B一个在定义域 A 上偏的函数
r: A one -> one B一个 injective 函数，定义域 A、值域 B——也称 A 到 B 的双射（bijection）
r: A some -> some B一个定义域为 A、值域为 B 的关系

示例

workAddress: Alias -> lone Addr
  // 函数：把 Alias 的每个成员映射至 Addr 的至多一个成员；每个别名代表至多一个工作地址

homeAddress: Alias -> one Addr
  // 每个别名代表恰好一个家庭地址

members: Group lone -> some Addr
  // 一个地址至多属于一个组，且一个组至少包含一个地址
重数只是糖：完整的展开式

重数只是简写，可以被标准约束替换。r: A m -> n B 中的重数约束可以写成：

all a: A | n a.r
all b: B | m r.b

但重数更可取，因为它们更简短、更易读。

// 上面最后一个声明
members: Group lone -> some Addr

// 可以替换为：
members: Group -> Addr
all g: Group | some g.members
all a: Addr  | lone members.a
推广：A 和 B 不必是集合，规则里的「成员」换成「元组」

表达式 A 和 B 可以是任意表达式，不必是关系名；它们也不必表示一元关系。 规则的推广方式很简单：把「member（成员）」换成「tuple（元组）」。于是

r: A m -> n B

表示 r 把 A 中的 m 个元组映射到 B 中的每个元组， 并把 A 中的每个元组映射到 B 中的 n 个元组。

addr: (Book -> Name) -> lone Addr
  // addr 为每个「地址簿 + 名字」的组合关联至多一个地址

3.6.4 Declaration Constraints · 声明式约束

声明不只用来引入新名字

声明通常引入新名字，但它们也可以用来对已经声明过的关系、或任意表达式施加约束。 在这种情况下，声明（用冒号算子）与普通约束（用子集算子 in）的唯一区别是： 声明会施加重数约束——对集合而言，即使没有重数关键字也会施加（因为有默认重数）。

// 地址簿由关系 address 表示，把组和别名映射到地址
address: (Group + Alias) -> Addr

// 一个额外的声明可以约束「每个别名至多映射到一个地址」
Alias <: address : Alias -> lone Addr
声明约束是普通公式，可以任意组合

声明约束像任何其他公式一样，可以用逻辑算子组合、放进量化的主体里，等等。

// addr 关联地址簿、名字、地址。约束「每本地址簿都是 injective 的」
//（即至多把一个名字映射到一个地址）可以写作：
all b: Book | b.addr: Name lone -> Addr

3.6.5 Nested Multiplicities · 嵌套重数

这是 Alloy 的一项「新意」（本章开篇提到过）

重数可以嵌套。假设有一个形如下式的声明：

r: A -> (B m -> n C)

这意味着：对 A 中的每个元组，B -> C 中对应的那些元组构成一个具有给定重数的关系。 当 A 是一个集合时，这个重数约束等价于：

all a: A | a.r : B m -> n C

类似地：

r: (A m -> n B) -> C　　≡　　all c: C | r.c : A m -> n B

示例：一个括号位置的差异导致完全不同的语义

// ① 对任何书，每个地址至多与一个名字关联
addr: Book -> (Name lone -> Addr)
// 等价于
all b: Book | b.addr: Name lone -> Addr

// ② 每个地址至多与一个「书/名字」组合关联
addr: (Book -> Name) lone -> Addr
关键区别（原文点明）

「The first allows an address to have different names in different books; the second does not.」
① 允许一个地址在不同的书中有不同的名字；② 不允许。
这是「嵌套重数」最实用的场景：区分「每个容器内唯一」与「全局唯一」。

3.7Cardinality Constraints · 基数约束

算子 # 作用于一个关系，给出它包含的元组数量，作为一个整数值。 下列算子可用于组合和比较整数：

+ plus
- minus
= equals
< less than
> greater than
=< less than or equal
>= greater than or equal
整数算子 · 正整数字面量可以作为常量出现
注意符号方向

「小于等于」写作 =<（等号在左），「大于等于」写作 >=（等号在右）。 这个不对称是 Alloy 的一个易错点。没有乘法和除法（见 3.2.3 的 Q8 与 4.8 节）。

// address 把组和别名映射到地址
address: (Group + Alias) -> Addr

// 约束「每个组关联的地址多于一个」
all g: Group | #g.address > 1

完整示例：把大组拆分成子组

假设一个邮件程序需要把地址组拆分成更小的子组。给定把组映射到其包含地址的关系， 以及把组映射到其子组的关系：

address: Group -> Addr
split:   Group -> Group

三条结构性约束

// ① 没有组是它自己的子组
no g: Group | g in g.split

// ② 一个组的子组包含它的全部地址
all g: split.Group | g.address = g.split.address

// ③ 子组之间互不相交
all g: Group, disj g1, g2: g.split | no g1.address & g2.address
解读：注意 ② 里的 split.Group

split.Group 是反向导航（3.4.3.2）：「那些有子组的组」， 即 split 的值域。约束 ② 只对被拆分的组要求「子组地址之和 = 原组地址」—— 没被拆分的组自然不受约束。这是用反向导航精准限定量化范围的典型手法。

三条基数约束

// ① 任何成员数超过 5 的组都要被拆分
all g: Group | #g.address > 5 implies some g.split

// ② 没有子组包含超过 5 个成员
all g: Group.split | #g.address =< 5

// ③ 子组大小大致相等（彼此相差不超过 1）
all g: Group, disj g1, g2: g.split |
  #g1.address < #g2.address implies #g2.address = #g1.address + 1

sum：整数求和

定义

表达式

sum x: e | ie

表示这样一个整数：对取自集合 e 的标量 x 的所有值，把整数表达式 ie 的值求和。

// 一个组的大小等于其各子组大小之和
all g: split.Group | #g.address = (sum g': g.split | #g'.address)

第 3 章小结

  1. 三种风格：谓词演算（太啰嗦，但适合微妙约束和集合构造）、导航表达式（最常用、表达力最强）、 关系演算（太隐晦，但适合无环性这类经典约束）。三者表达力不等价——传递闭包只在导航/关系演算侧有。
  2. 原子三性质：不可分、不可变、无解释。想建模复合对象 / 变化 / 有性质的东西？统统用关系解决： ① 组合 → 用关系绑定组件；② 变化 → 身份与值分离，加时间列；③ 性质 → 引入关系（如 precedes、next）。
  3. 关系是平坦的：条目永远是原子。需要「集合的集合」时，引入新原子做具体化（先修课例子）。
  4. 一切都是关系：scalar = 单例集合 = 单例关系 = 元组。所以没有 undefined， p.wife.mother 在 p 无妻时只是空集。这消灭了偏函数应用问题。
  5. functional（每个来源至多一个目标）与 injective（每个目标至多一个来源）是两个独立性质；空关系两者都满足。
  6. domain = 第一列，range = 最后一列；二元关系下即 r.univ 和 univ.r。
  7. 三个常量：none / univ / iden。 iden 覆盖整个宇宙，所以几乎总要限定，如 s <: iden。
  8. 九个关系算子中最重要的是 .（join，去掉匹配原子）、^ / *（闭包 = 可达性）、 ++（override，建模 map 插入与赋值）。[] 与 . 语义相同，只是参数顺序与优先级不同，用于区分「解引用」与「索引查找」。
  9. 重数是声明的一部分，可以嵌套（Book -> (Name lone -> Addr) 与 (Book -> Name) lone -> Addr 含义不同！）。 重数只是糖，可展开为 all 约束，但更简洁易读。
  10. 整数能力有限：可取基数、加减、比较，不可乘除。大多数场合用无解释原子 + 关系更干净。
