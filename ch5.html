5.1Scope-Complete Analysis · 作用域完备的分析

5.1.1 Instance Finding and Undecidability Compromises

两个问题其实是同一个问题

检验断言与运行谓词归结为同一个分析问题：找到某个把关系赋给变量的赋值，使约束为真。所以书中不再分别讨论，只谈「检验断言」。

Alloy 的关系逻辑是不可判定的（undecidable）。这意味着不可能造出一个自动工具，以完全可靠的程度告诉你一个断言是否有效（即是否对每个可能的赋值都成立）。因此某种妥协是必需的。

传统妥协：定理证明Alloy 的妥协：实例查找（instance finding）
做什么自动定理证明器尝试构造一个证明，说明断言成立不尝试构造证明，而是寻找反驳（refutation）：把断言与一大堆测试用例逐一对照，每个用例都是「关系→变量」的一种可能赋值
成功时断言有效（确定结论）找到反例 ⇒ 断言无效（确定结论），并给出具体场景
失败时断言可能有效也可能无效。而且很难分辨失败是因为断言有错、证明器本身的局限、还是用户缺乏恰当的引导断言仍可能不成立——它的反例可能比所考虑的任何测试用例都大
适用性需要巨大的人工引导投入更适合轻量级建模
为什么实例查找更契合轻量级建模

由于分析在抽象的开发过程中被反复、增量地应用，它最常遇到的就是无效的断言。实例查找非常适合分析无效断言，因为：

  1. 它生成反例，而反例通常可以轻松追溯回描述中的问题；
  2. 无效断言的分析速度往往远快于有效断言——有效断言要求覆盖整个可能实例空间，而无效断言只需找到第一个实例就能停止。

5.1.2 The Notion of Scope · 作用域的概念

为了让实例查找可行，定义一个作用域来限制所考虑实例的大小。分析实际上检查了作用域内的每一个实例，一个无效断言只有在其最小反例落在作用域之外时才会「溜过去」而未被反驳。

为什么不让分析器自动递增作用域

你可能觉得好策略是：分析器从小作用域开始，自动递增，直到找到反例或超过预设时限。但这预设了「作用域只是一个数字」。

事实证明更丰富的作用域概念更有用：每个 signature 单独设界，由用户控制。例如分析一个铁路道岔操作可能只需要两个状态（前后状态）和一个路口，但需要更多的轨道段和列车。

作用域定义了一个多维测试用例空间

每个维度对应一个特定 signature 的界限。即使很小的作用域通常也定义了巨大的空间。

以默认作用域 3 为例（每个 signature 界为 3）：每个二元关系为状态贡献 9 个比特（因为定义域的 3 个元素中的每一个，都可能也可能不与值域的 3 个元素中的每一个相关联）——也就是 2⁹ = 512 倍。

所以一个只有四个二元关系的微型模型，其空间就超过十亿个用例（512⁴ ≈ 6.9 × 10¹⁰）。

5.1.3 The Small Scope Hypothesis · 小作用域假设

「实例查找不就是测试吗？」

某种意义上是的：断言被对照一组有限的用例检验，而这组用例只占可能用例空间中无穷小的一部分。Dijkstra 的名言同样适用于实例查找：

「程序测试可以用来展示 bug 的存在，
但永远不能展示它们的不存在。」

—— Dijkstra [13]

但测试的弱点超出了「无法证明 bug 不存在」——它通常连「证明 bug 存在」都做不到。代码中的大多数 bug 都能逃过测试；编写测试套件的挑战是捕获更多确实存在的 bug，而不是证明没有 bug 残留（那是一个完全不同、甚至更难的问题）。

实例查找的覆盖面远比传统测试广泛，因此它在找 bug 上往往有效得多。简而言之：

小作用域假设（Small Scope Hypothesis）

「大多数 bug 都有小的反例。」
Most bugs have small counterexamples.

也就是说：如果一个断言无效，它很可能有一个小的反例。这带来一个令人鼓舞的推论：如果你检查了所有小的情形，你就很可能找到反例。

5.1 Discussion · 原文问答

Q：定理证明器在分析软件抽象中扮演什么角色？

定理证明器与实例查找器扮演互补的角色。一旦 Alloy Analyzer 未能找到某断言的反例，你可以用定理证明器去证明该断言在所有作用域下都成立。

但借助定理证明器完成一个证明，通常需要比之前的建模努力大一个数量级的投入，所以对大多数应用而言不划算。不过对于安全攸关（safety-critical）的抽象，从证明中获得的额外保证可能是值得的。

Q：分析依赖于拥有「完美的断言」吗？

不。有些人假设，如果没有捕获某种柏拉图式「高层规范」的断言，分析就不值得做。恰恰相反，即使简单形式的分析也是有益的。

简单的模拟谓词常常生成令人惊讶的场景；把基本的健全性检查（sanity checks）表述为断言，就能暴露深层错误。当然，如果你能用断言表达一个软件设计的关键性质，那你就能用分析检验它们，而「找不到反例」的分量就更重。

Q：分析的首要目的是揭露微妙的 bug 吗？

形式化方法的论证常常建立在「捕获逃过测试的微妙 bug」这一前景上。但在实践中，远更重要的是那些不那么光鲜的分析——它们在抽象开发过程中被反复应用，使形式化模型与设计者的意图保持一致。

软件与硬件不同，很少因为单个微小但致命的缺陷而失效。几乎所有情况下，软件失效是因为糟糕的抽象导致 bug 大量滋生，而其中恰好有一个引发了失效。

Q：是什么让这套逻辑不可判定？

一阶逻辑是不可判定的，除非对可写的约束施加严厉限制。例如：

  • 把逻辑限制到「一元（monadic）」谓词（只有一个参数的谓词）——在关系设定下这会消灭关系，只剩集合与标量；
  • 或限制量词的使用方式，例如只允许某些「前缀」模式，即所有量词都出现在断言开头、按特定的存在/全称量词模式排列。

然而消灭量词并不能让我们的逻辑变得可判定，因为关系演算本身就不可判定——它只由二元关系和我们的关系算子（尤其是点连接）构成。

简言之：似乎不存在一种既实用、又足够丰富到能刻画软件抽象、同时还可判定的逻辑。

入门读物：David Harel 的书 [25] 第 8 章；全面论述见 [6]，其中含一个很好的分类，也以短文形式在线可得 [20]。

Q：为什么用「实例（instance）」这个词？
在标准数学术语中，一个约束的实例叫做「模型（model）」，找模型的工具叫「模型查找器（model finder）」。但「model」这个词被严重重载了，所以最好避开它。
Q：作用域这个想法是新的吗？

不是。1980 年代发展出的「模型检查（model checking）」技术用于分析可表示为有限状态机的协议与硬件设计。它太有效了，很快就被应用到无界系统上——方法是构造一个描述，人为地（而且往往有点任意地）把系统变有限。事实上这个过程如今被视为模型检查的根本环节，以至于人们以为这就是它名字里「model」所指：无限系统的一个有限模型。（其实这个词本意是数学意义上的：分析检查该状态机是否是一个时序逻辑公式的「模型」。）所以「在有限界限内搜索、（至少隐式地）依赖小作用域假设来找 bug」并不是新想法。

Alloy 中也许是新的东西有两点：

  1. 把作用域说明与模型本体分离。这防止模型被分析方面的考虑污染，并且无需调整模型本身就能用不同作用域跑不同分析。
  2. 细粒度调整作用域的能力。它超越了静态配置参数（如网络中的进程数），延伸到动态分配数据的界限（如队列中的消息数、堆中的对象数）。
Q：一个「只在小作用域下才work」的设计有什么用？

这个问题暴露了对作用域概念的常见误解。当然，一个「只有当每个类型的元素不超过一小把时才能工作」的系统是没用的。

小作用域假设的要点是：在大实例上失效的系统，几乎总会在具有相似性质的小实例上同样失效——即使这样的小实例在实践中不会出现。所以通过检查所有小实例，我们实际上也在为大实例做检查。

Q：那资源分配上限怎么办？
实现中常内建资源分配上限，一旦越过就失效。这看似与小作用域假设矛盾，因为失效只发生在超过分配上限的巨大实例上。但抽象没有这些问题，因为资源分配要么被抽象掉（factored out），要么被更抽象地表示——或者用模型中一个可以被设得任意低的参数，或者用非确定性行为。
Q：你能证明小作用域假设吗？

不能——所以我才叫它「假设」。它是对实践中出现的断言做的断言，不是对「所有可能断言的空间」做的断言。人们完全可以构造一个无效断言，其最小反例刚好超出任何给定的作用域。幸运的是，无意中的错误在实践中很少如此狡猾。

但仍须牢记：实例查找是一种不完备的分析，有时找到某个 bug 所需的作用域比直觉所暗示的更大。

如果存在一个足以找到任何无效断言反例的作用域，或者哪怕存在一种「逐断言计算出足够大作用域」的方法，那么（至少原则上）就能判定一个断言是否有效。这会与逻辑的不可判定性矛盾，所以做不到。

尽管如此，一阶逻辑的某些子集有「小模型定理（small model theorem）」，允许从断言的结构确定一个充分的作用域：与建模相关的一个例子是集合值字段的理论 [45]。

5.2Instances, Examples, and Counterexamples

5.2.1 Analysis Constraints and Variables · 分析约束与变量

当你 run 一个谓词或 check 一个断言时，分析器搜索的是一个「分析约束」的实例：给该约束的变量赋值，使约束求值为真。

分析约束 =找到的实例叫含义
run PP 的约束 ∧ 模型的所有 fact
（既包括 fact 段落里的显式 fact，也包括隐含在声明里的 fact）		例子（example）fact 与谓词同时成立的场景
check A¬(A 的约束) ∧ 模型的所有 fact反例（counterexample）fact 成立但断言不成立的场景（等价地：断言未能由 fact 推出的场景）
实例中被赋值的变量包括
  • 与各 signature 关联的集合；
  • 与各字段关联的关系；
  • 以及（对谓词而言）它的参数。

贯穿本章的例子：地址簿（fig. 5.1）

module analysis/addressBook
abstract sig Target {}
sig Addr extends Target {}
sig Name extends Target {}
sig Book {addr: Name -> Target}
fact Acyclic {all b: Book | no n: Name | n in n.^(b.addr)}
pred add (b, b': Book, n: Name, t: Target) {
  b'.addr = b.addr + n -> t
}
run add for 3 but 2 Book
fun lookup (b: Book, n: Name): set Addr {n.^(b.addr) & Addr}
assert addLocal {
  all b,b': Book, n,n': Name, t: Target |
    add (b,b',n,t) and n != n' => lookup (b,n') = lookup (b',n')
}
check addLocal for 3 but 2 Book
fig. 5.1 地址簿例子。作者选它是因为它包含了每一种基本语言构件。每个地址簿 b 有一个映射 b.addr，把名字不仅映射到地址，也映射到名字（从而允许多层间接）；Target 就是为这个泛化而声明的。fact 说这些间接永不形成环。add 只是加一条「名字→目标」的映射。lookup 返回从该名字可达的地址集合——即树的叶子。断言 addLocal 做出（错误的）声明：为名字 n 做一次添加，只影响对 n 本身的查找。

run add：分析约束的完整展开

对命令 run add，分析变量是：signature Target、Addr、Name、Book；字段 addr；以及 add 谓词的四个参数 b、b'、n、t。分析约束是下列各项的合取：

// ① signature 隐含的约束
Name in Target
Addr in Target
no Name & Addr
Target in Name + Addr      // 因为 Target 是 abstract
no Book & Target            // 因为两者都是顶层 signature

// ② 字段与参数声明隐含的约束
addr : Book -> Name -> Target
b: Book
n: Name
t: Target

// ③ 显式 fact（这里只有 Acyclic）
all b: Book | no n: Name | n in n.^(b.addr)

// ④ 被 run 的谓词的体
b'.addr = b.addr + n -> t
解读 · 这一段为什么重要

这是全书第一次把「一段 Alloy 代码」完整地翻译成「一条真正被求解的逻辑公式」。请注意：你写的每一个 extends、abstract、每一个重数关键字，都变成了合取式中的一项。理解了这一点，你就能预测分析器的行为——也能理解为什么「声明即约束」是 Alloy 的核心哲学。

还有一个细节：b' 虽然是谓词参数，但它不是「b 的后继」这种带语义的东西——对分析器来说它只是一个普通变量（见下面的 Discussion）。

第一个生成的实例

书中格式（第 3 章风格，元素加括号）

Target = {(Addr_0), (Name_0)}
Addr   = {(Addr_0)}
Name   = {(Name_0)}
Book   = {(Book_0), (Book_1)}
addr   = {(Book_0, Name_0, Addr_0),
          (Book_1, Name_0, Addr_0)}
b      = {(Book_0)}
b'     = {(Book_0)}
n      = {(Name_0)}
t      = {(Addr_0)}

这是「添加一个已经存在的 名字/地址 对」的情形。集合元素加括号是为了提醒读者：从语义角度看，集合在 Alloy 中是以关系表示的。

Analyzer 的文本 / 树形输出

    {Book_0 -> Name_0 -> Addr_0,

Analyzer 提供三种输出形式：文本形式、树形、图形（fig. 5.2）。它的格式更常规也稍友好，用关系的声明来决定如何排版。

check addLocal：反例的产生

对命令 check addLocal，变量包括各 signature 和字段 addr，但没有谓词参数。分析约束是「signature 与字段声明隐含的约束 + 显式 fact」（同前），再加上断言的否定：

some b,b': Book, n,n': Name, a: Addr |
  add (b,b',n,a) and n != n'
  and not lookup (b,n') = lookup (b',n')

把谓词 add 和函数 lookup 展开后变成：

some b,b': Book, n,n': Name, a: Addr |
  b'.addr = b.addr + n -> t
  and n != n'
  and not n.^(b.addr) & Addr = n'.^(b'.addr) & Addr

fig. 5.3 用三种不同的视图展示了一个反例（通过 Analyzer 中不同的可视化选择、并使用 3.3 节描述的投影设施得到）：默认设置的图形视图、投影到 Book 集合上的视图、以及只显示 Book 原子的视图。

见证者标签（witness labels）

注意那些标明「哪些原子是量化变量的见证者」的标签：例如 addLocal_b 就是 addLocal 中变量 b 的见证者。这些是 Skolem 常量，在 5.2.2 解释。反例中的绑定是：

addLocal_b  = Book_0
addLocal_b' = Book_1
addLocal_n  = Name_0
addLocal_n' = Name_1
addLocal_t  = Addr_0

5.2.1 Discussion

Q：处理前状态和后状态，不是需要一个变量的多个值吗？

不，不，不！在 addLocal 的分析变量中，b 和 b' 是不同的变量；就分析器而言，它们的共同点不比任何其他一对变量多——尽管它们碰巧代表一个地址簿的前值和后值。

Q：所以变量其实不「变」？

对。我们的变量像数学与物理学中的变量（而不像命令式程序中的变量），只在「可以被赋予多种值」这个意义上变化。工程中的标准做法是用不同的名字描述不同时间点的现象；这正是让代数操作式推理成为可能的原因。在计算机科学中，用不同名字描述前后状态的做法至少可以追溯到 Hoare 逻辑中辅助变量（auxiliary variables）的使用。

Q：为什么字段的后状态值没有带撇号的变量？

大多数建模语言（尤其是 Z [65]）采用那种做法。本书采取的做法更像物理学：把一个随时间变化的现象建模为一个从时刻到值的函数。例如 addr 字段可看作一个函数，对每本书 x 都有一个值 x.addr。多个地址簿可能代表某一时刻的不同簿子，或者——如本例——代表同一个簿子在不同时刻的状态。

在第 6 章的领导者选举和酒店门锁例子中，时间被完全显式化：一个随时间变化的状态组件被建模为一个字段 f，时刻放在最后一列，于是 f.t 表示在时刻 t 的值。

Q：Alloy 是第一个用这种做法的语言吗？
不是。这种做法由 John McCarthy 在其 situation calculus（情境演算）中首创 [51]。
Q：分析究竟是怎么工作的？

每次分析都涉及求解一个约束：要么找实例（run），要么找反例（check）。所以 Alloy Analyzer 是 Alloy 逻辑的一个约束求解器。但在实现上，它更像一个编译器：它不直接求解约束，而是把约束翻译成一个布尔公式，然后用现成的 SAT 求解器求解。

SAT = satisfiability（可满足性）：布尔公式的一个解，是给公式的布尔变量赋值使其「满足」该公式。过去十年 SAT 求解技术进展巨大，最先进的 SAT 求解器常常能求解含数千个布尔变量、数百万个子句的公式。Alloy Analyzer 捆绑了若干 SAT 求解器，其中最快的是 Chaff [55] 与 Berkmin [19]，可通过偏好设置选择用哪个。

翻译到布尔公式：概念上非常简单

考虑一个从集合 A 到集合 B 的二元关系 r 的某个特定值。这个值可以表示为一个由 0 和 1 组成的邻接矩阵：当 A 的第 i 个元素被映射到 B 的第 j 个元素时，第 i 行第 j 列为 1。

于是 r 的所有可能值的空间，可以表示为一个「元素不是布尔值、而是布尔变量」的矩阵：在每个位置放一个变量 ri,j。矩阵的维度由作用域决定：如果作用域把 A 界为 3、B 界为 4，那么 r 就是一个 3×4 的矩阵，含 12 个布尔变量，有 2¹² 种可能的值。

Alloy 构造翻译结果
关系表达式 p + q构造一个元素为布尔表达式的矩阵：第 i 行第 j 列是 pi,j ∨ qi,j（因为 Ai 被 p+q 关联到 Bj，当且仅当它被 p 或被 q 关联）
关系公式 p in q构造一个布尔公式：对所有 i、j 取 pi,j ⇒ qi,j 的合取（因为 p in q 成立，就是「只要 p 把 Ai 关联到 Bj，q 也如此」）

得到的布尔公式交给 SAT 求解器。找不到解 ⇒ Analyzer 只报告「没有找到实例/反例」。找到解 ⇒ 解被映射回一个实例：例如若变量 ri,j 为真，就把「关联 A 的第 i 个元素与 B 的第 j 个元素」的那个元组放进关系 r 的值里。

对称破缺（symmetry breaking）——最重要的优化

在从 Alloy 逻辑翻译到布尔公式时，Analyzer 应用了多种优化，其中最重要也最有趣的是对称破缺。

因为原子是无解释的（见 3.2），每个 Alloy 模型都有天然的对称性：你可以取一个命令的任意实例，通过置换原子造出另一个实例。这意味着当分析约束有一个解时，它实际上有一整组解，对应于该解的原子可以被置换的所有方式。

概念上，我们可以把赋值（可能解）的空间划分成等价类：两个赋值属于同一类，当且仅当其中一个可以被置换成另一个。求解器于是只需查看每个等价类中的一个赋值。由于置换数量极多，等价类非常大，这样限制搜索可以极大地提升性能。

事实上 Analyzer 只间接影响搜索：它从模型生成对称破缺约束，并把它们合取到分析约束上。如果这些约束是完美的，就会排除每个等价类中除一个以外的所有赋值——但那需要非常大的对称破缺约束，反而会压垮求解器、实际损害性能。所以 Analyzer 生成一个小得多的约束，只破除部分对称性，但在实践中消除了超过 99% 的赋值。

最简单的对称破缺：util/ordering

当模型使用 util/ordering 时，对称破缺最简单。这个库模块用来给一个 signature 施加排序，它在被排序的 signature 上声明一个关系 next。由于被排序的原子是可互换的，它们可以按自然的字典序排序而不失一般性。

这就是为什么用 util/ordering 给 signature S 排序，总会把它的元素排成 S0、S1、S2……这不仅对性能好（其他顺序不被考虑），也对可视化好。

历史脉络
  • 「用关系逻辑写模型、用约束求解器分析」的想法最早是为 Alloy 的前身 Nitpick [35] 开发的。Nitpick 的工具靠枚举完整的关系值工作，有一套相当精细的对称破缺方案 [34, 36]。
  • 用「归约到可满足性」求解 Nitpick 公式的方案不太成功 [11]，因为它用 BDD 表示布尔公式——这种数据结构在其他领域效果很好，但与关系逻辑不匹配。
  • Alloy→SAT 的基本翻译方案于 1997 年开发 [31, 32]，效果好得多，很大程度上归功于（Greg Nelson 建议的）从 BDD 转向 SAT。
  • 当前版本 Analyzer 的算法主要由 Ilya Shlyakhter 开发 [64]，特别是这套对称破缺方案 [63]，以及一个检测生成公式中共享机会的优化。

5.2.2 Skolemization · Skolem 化

如果分析约束含有存在量词，分析器通常（取决于约束的确切形式）能提供一个见证者（witness）：一个使存在量化公式的体为真的量化变量值。这是通过把实例中绑定的变量集合扩展到包含量化变量做到的，所用的变换叫 Skolem 化。

先看「不做 Skolem 化」时存在量词怎么处理

假设分析约束形如 some x: S | F，S 是 signature，F 是含 x 的任意约束。如果作用域给 S 分配界限 k，它就可以用原子 S1, S2, …, Sk 表示，量化可以展开为：

F[S0/x] or F[S1/x] or … or F[Sn/x]

其中 F[Si/x] 是把 Si 代入 x 的约束 F。注意变量 x 不再显式出现在这个新约束里，所以当生成实例时，可能不清楚哪个析取项为真。

Skolem 化的做法

取原分析约束，不展开量词，而是把绑定变量替换成一个自由变量：

(sx: S) and F[sx/x]

其中 sx 是一个新的自由变量。容易看出：新分析约束在旧约束有实例时也有实例，但它的实例更有帮助，因为它会给 sx 赋一个值。

Skolem 化没有任何魔法。分析约束中的一个自由变量——比如一个 signature 或一个关系——被约束求解器当作存在量化的变量来处理。Skolem 化只是把一个隐式的存在量化变成显式的。

最外层量词：变量变成标量/集合/关系

// 原式（check addLocal 的分析约束的一部分）
some b,b': Book, n,n': Name, a: Addr |
  add (b,b',n,a) and n != n'
  and not lookup (b,n') = lookup (b',n')

// Skolem 化后
b: Book and b': Book and n: Name
  and n': Name and a: Addr
and add (b,b',n,a) and n != n'
and not lookup (b,n') = lookup (b',n')

嵌套量词：变量变成一个「函数」

// 原式
all x: S | some y: T | F

// Skolem 化后
(sy: S -> one T) and (all x: S | F[x.sy/y])

其中 F[x.sy/y] 是把 y 的每次出现替换成表达式 x.sy 的约束 F。

直觉仍然直白：如果原约束有实例，那么对 x 的每个值都存在一个使 F 为真的 y 值。这个 y 值可以被看作把函数 sy 应用到相应的 x 值得到的，所以对 y 的量化可以通过引入这样一个函数作为「待确定值的变量」来消除。

例：run show 的 Skolem 化

// 模型
sig Name, Address {}
sig Book {addr: Name -> Address}
pred show () { all b: Book | some n: Name | some b.addr[n] }
run show for 3

// Skolem 化后
(sn: Book -> one Name) and (all b: Book | some b.addr [b.sn])

其实例将包含一个变量 sn，它是一个关系，对每本书 b 展示一个它所映射的名字的见证者 b.sn。

Skolem 化也适用于集合与关系，不只标量

上面的论证没有任何一步要求存在量化的变量是标量。

  • 最外层量词的简单情形：引入的变量成为一个集合或关系。
  • 内层量词的情形：引入的变量不再是函数，而是一个关系（为得到集合）或一个多关系（multirelation）（为得到关系）。

例：对集合做 Skolem 化（BadUnionRule）

// 断言（4.5.3 中提到的错误恒等式）
assert BadUnionRule {
  all s, t, u: set univ | s = t + u  iff  s - t = u
}
check BadUnionRule

// 否定后 Skolem 化：
ss: set univ and
st: set univ and
su: set univ and
not (ss = st + su  iff  ss - st = su)

// 给出的反例展示了绑定变量的见证者，例如：
ss = {(U0)}
st = {(U0)}
su = {(U0)}
Skolem 常量如何命名

Skolem 常量的命名方式是：把相应的变量名前缀上它所在的谓词或函数的名字（如果同一词法作用域内某个名字被用了多次，再加一个额外的索引）。所以 addLocal 里的 b 变成 addLocal_b，add 里的 b 变成 add_b。

Q：Skolem 化有什么好处？
三个好处：
  1. 它为绑定变量生成见证者（如前所述与图示）。
  2. 它让许多高阶量化——比如断言 BadUnionRule 里的那种——变得可以分析，否则根本无从分析。
  3. 它往往即使对一阶量化也能提升分析性能，因为存在量词相关的展开会让约束急剧膨胀。

5.3Unbounded Universal Quantifiers · 无界全称量词

一个重要而微妙的局限

本节解释有限实例查找的一个重要而微妙的局限。幸运的是，它在实践中并不常出现，而且它导致的是令人惊讶的反例，而不是令人惊讶的遗漏（后者会糟糕得多）。

问题的根源：当一个 signature 被意图表示「某个复合结构的所有可能值」时。这与 Alloy 的语义相矛盾——在 Alloy 中，一个 signature 只表示「某个」值的集合。这个矛盾只在全称量化以特定方式使用时才变得明显。

5.3.1 Generator Axioms and Exploding Scopes · 生成器公理与作用域爆炸

假设我们想检验「集合对并运算封闭」——即任意两个集合的并也是一个集合。我们把集合表示为对象：

sig Set { elements: set Element }
sig Element {}

// 对任意一对集合 s0、s1，存在一个集合同时含有两者的元素：
assert Closed {
  all s0, s1: Set | some s2: Set |
    s2.elements = s0.elements + s1.elements
}
check Closed     // 默认作用域 3

结果给出这样的反例：

Set      = {(S0), (S1)}
Element  = {(E0), (E1)}
s0       = {(S0)}
s1       = {(S1)}
elements = {(S0, E0), (S1, E1)}

其中 s0 是含 E0 的原子 S0，s1 是含 E1 的原子 S1，而没有任何 Set 原子同时含有这两个元素。

出了什么问题？

粗略地说，分析器找到的反例没有给 signature Set 填充足够多的值：它缺少一个 Set 原子（比如 S2），被 elements 映射到 E0 和 E1。

补救办法：生成器公理 → 但作用域会爆炸

要解决所有这类问题，可以加一条生成器公理（generator axiom）强制 Set 被完全填充，例如写成一条结构归纳：存在一个没有元素的集合，并且对每个集合和每个元素，都存在一个「加上了该元素」的集合：

fact SetGenerator {
  some s: Set | no s.elements
  all s: Set, e: Element |
    some s': Set | s'.elements = s.elements + e
}
结构生成器公理的代价
集合
sig Set {elements: set Element}		 如果 Element 有 k 个原子，Set 就必须有 2ᵏ 个原子。反过来说：如果把 Set 界为 k，那么只有 Element 至多 log k 个原子的实例会被考虑。在这个微型例子里还能做些有用的分析：4 个元素 + 16 个集合的作用域应该足以分析一些有趣的断言。
图
sig Graph {adj: Node -> Node}		 k 个节点上共有 2k×k 个不同的图。所以要考察三节点的图，作用域应把 Graph 界为 512。
递归列表
abstract sig List + one sig EmptyList + sig NonEmptyList {element: Element, rest: List}		 更糟：某些情况下生成器公理会要求无穷多个原子。见下方。
 
// 强制所有可能的列表都存在：
fact ListGenerator {
  all l: List, e: Element |
    some l': List | l'.rest = l and l'.element = e
}
灾难性后果：模型变成「有效不一致」

除非 Element 为空，这条公理会让模型实际上不一致——因为唯一可能的实例将是无限的。于是任何断言都变成有效的，包括明显为假的那些，例如：

assert {all l: List | not l = l}   // 竟然「通过」了

这正是「令人惊讶的反例好过令人惊讶的遗漏」的反面案例：不一致的模型会让所有检查都假性通过，是最危险的情形。

5.3.1 Discussion

Q：在集合的例子中，为什么要声明 Element？

Set signature 本可以声明成「元素任意取自原子全集」：

sig Set {elements: set univ}

但这会允许集合包含集合，引入一个正交的复杂性。另一个（更好的）选择是把声明对元素 signature 参数化：

module analysis/paramSets [t]
sig Set {elements: set t}
Q：为什么要为集合引入一个 signature？

「集合对并封闭」这个断言本可以写成：

assert {
  all s0, s1: set univ | some s2: set univ | s2 = s0 + s1
}

完全不需要引入 signature。但这个例子本意是说明一般的复合结构，集合只是其中特别简单的一个例子，而其他结构（如列表和序列）并不像集合与关系那样内建在 Alloy 里。

顺带一提：即使断言写成这种形式，分析也不能很好地伸缩，因为分析器必须把内层量词「落地（ground out）」，导致与生成器公理同样的爆炸。

Q：递归定义的列表在 Alloy 模型中常见吗？

没有你可能以为的那么常见——尤其如果你受过 Lisp、ML、Haskell 这类函数式语言的影响（在那里列表是首要数据结构）。

在 Alloy 中，列表包含多余的结构（代表子列表的那些原子），所以使用列表常常标志着一次抽象的失败——特别是当元素的顺序无关紧要时，本该用一个简单的集合。

不过类列表结构偶尔有用：例如文件系统中的路径名可以表示为「一个前缀 + 一个目录名或文件名」，其中前缀像列表的尾部一样递归定义。

需要顺序时：用「索引 → 元素」的序列，而不是递归列表

当需要顺序时，如果不允许重复，一个简单的关系就够了；否则，把序列建模为一个「字段把索引映射到元素」的 signature 更好：

sig Seq { element: Index -> lone Element }

它比递归列表引入更少的多余结构。

对这类序列的全称量词可能遭遇与列表相同的问题。Alloy 库包含一个序列模块，其中有一个谓词强制所有长度不超过给定值（即 Index 的作用域）的序列都存在。这个谓词显然必须谨慎使用以避免作用域爆炸。没有「强制所有可能序列都存在」的谓词，因为那会引入矛盾。

5.3.2 Omitting the Generator Axiom · 省略生成器公理

看到上一节描绘的沮丧图景，你可能想问：那 Alloy 为什么还有用？生成器公理问题在实践中很少出现，有三个原因：

① 关系天生封闭

其他语言中生成器公理的动机是确保每个表达式都表示一个值。但关系按定义对它的所有算子都封闭，所以不需要显式生成器公理，Alloy 中每个关系表达式都有值。

② 大多签名是问题域对象

生成器公理是数学对象需要的，但大多数 signature 表示问题域中的对象。在文件系统模型中，你不会期望对代表目录的 signature 写一条生成器公理，说「对每一种可能的内容组合都存在一个目录」。

③ 即使合适也常可省略

只要每个全称量词都是有界的，且只使用某些表达式形式，分析器无论是否包含生成器公理都会给出相同结果。这就是有界全称规则（bounded-universal rule）。

「有界（bounded）」的准确含义

量化变量的界定表达式不提及「被生成的 signature」的名字（即那些我们本想为它们写生成器公理的 signature）。

允许的表达式形式排除关系转置（~），并且点连接只能是「左边一个集合、右边一个关系」。

这些限制确保：全称量化的约束只能「向内看」结构的内部——比如看进一个列表的子列表、一棵树的子树——因而无法分辨生成器公理有没有被应用。

❌ 不是有界全称形式

sig Set { elements: set Element }
assert Closed {
  all s0, s1: Set | some s2: Set |
    s2.elements = s0.elements + s1.elements
}

否定后变成：

some s0, s1: Set |
  all s2: Set |
    not s2.elements = s0.elements + s1.elements

这不在有界全称形式中，因为 s2 的量化不是有界的（它的界定表达式是 Set 本身，而 Set 正是「被生成的 signature」）。所以检验这个断言可能（而且确实）产生伪反例——如果为 Set 加上生成器公理，这些反例就不会存在。

✅ 是有界全称形式

sig Set { elements: set Element }
assert UnionCommutative {
  all s0, s1, s2: Set |
    s0.elements + s1.elements = s2.elements
    implies
    s1.elements + s0.elements = s2.elements
}

分析约束是：

some s0, s1, s2: Set |
  s0.elements + s1.elements = s2.elements
  and not s1.elements + s0.elements = s2.elements

这是有界全称形式，因为它根本不含全称量词。检验这个断言不会产生伪反例；即使没有生成器公理，它也有其原本的含义。

这个问题最严重的后果：前置条件断言通常无法检验

声明式描述风格非常强大，但它有一个缺点：无意的过度约束（inadvertent overconstraint）。一个本意只约束后状态值的操作规范，可能无意中同时约束了前状态和参数，以致该操作不是「全的（total）」、在某些上下文中无法被应用。

为缓解这个风险，你可能想断言：「对每个前状态，至少存在一个后状态使该操作的约束得到满足」。不幸的是，这种形式的断言不属于有界全称类别，因而可能产生伪反例。

例：add 操作的「全性」断言

sig Name, Addr {}
sig Book { addr: Name -> Addr }
pred add (b, b': Book, n: Name, a: Addr) {
  b'.addr = b.addr + n -> a
}
assert AddTotal {
  all b: Book, n: Name, a: Addr |
    some b': Book | add (b, b', n, a)
}
check AddTotal

你可能以为这是有效的——因为每个映射都能被一个新的键值对扩展。相反地，如果字段 addr 声明为 addr: Name -> lone Addr（每个名字至多关联一个地址），你就不再期望该操作是全的：如果给一个已存在的名字提供一个新地址，就无法在不违反重数约束的前提下扩展这个地址簿。

确实，在第二种情形下断言是无效的。令人惊讶的是，在第一种情形下它也是无效的，分析器会生成这样的反例：

b    = {(B0)}
n    = {(N0)}
a    = {(A0)}
addr = {(B0, N0, A1)}

其中不存在任何 Book 可以绑定给 b' 以满足操作约束。

为什么两条路都走不通

问题在于：要让断言有其原本的含义，我们需要确保所有可能的 Book 结构都存在。

  • 加公理不切实际：Name 与 Addr 作用域为 3 时，Book 需要作用域 512！
  • 省略公理也不可接受：因为该断言归约为 all b': Book | not b'.addr = b.addr + n -> a，不是有界全称公式。

5.3.2 Discussion

Q：有界全称规则是否允许「只考虑有限情形」来分析一个无限模型？

是的，这正是它允许的。不过这并不太令人惊讶，因为落在有界全称类别里的性质只「向下看」一个无限实例的有限部分。

Q：那是不是说，在有限作用域里的一次检查就自动适用于无限情形？

不。它的意思是：如果一个断言有反例，那么在某个作用域里存在一个有限的反例。你仍然可能因为作用域太小而漏掉反例。

对刚才讨论的例子而言，它的意思是：在所有有限作用域中检验这些断言，覆盖了一个假想分析的情形——那个分析包含生成器公理且作用域是无限的。所以简言之：省略公理、且不考虑无限作用域的情形，并不会让漏掉反例的可能性变得更大。

Q：不能通过加否定，把一个全称量词转成存在量词吗？
不能。有界全称规则假定公式处于一种范式：所有量词都在最外层，且没有被否定。一篇研究论文更详细地给出了这条规则，并在「代数数据类型 + 一阶逻辑」的一般设定下证明了它的可靠性 [44]。

5.4Scope Selection and Monotonicity · 作用域选择与单调性

作用域给每个顶层 signature 的大小设一个上界，可选地也给子签名设界（见 4.6）。一个实例在作用域之内，当且仅当被作用域约束的每个 signature 的元素个数都不超过其对应的界限。

剪枝与保证

为执行一次分析，分析器考虑作用域内的所有候选实例。当然，候选的数量通常大到显式枚举不可行。所以分析使用剪枝技术（pruning），一次排除掉整组的候选情形。

如果它没有找到实例，就保证在该作用域内确实不存在——尽管更大的作用域里可能存在。

5.4.1 Selecting a Scope · 选择作用域

选择一个合适的作用域可能需要一些仔细的思考。大多数情况下，从默认作用域开始是有意义的——它被选为「空间小到足以让分析快速终止，但又大到足以包含有趣的实例」。

如果找到了实例

它可能立刻就能达成目的：对断言来说是暴露一个问题；对谓词来说是展示一致性、说明一个预期（或意外）的情形。

但它也可能显得比必要的更复杂。在试图消化它之前，你可能想在更小的作用域上重复分析——这通常会给出一个更小、更易理解的例子。

如果没找到实例

你可能想增大作用域，以获得「确实不存在实例」的更大信心——即被检验的断言有效、或被运行的谓词不一致。

作用域越大，越有理由有信心，但分析耗时越长。到某个点分析会变得难以忍受地慢。如果这是一次结果攸关的分析，你可能想把它放到一边、通宵运行，也许在更大的机器上。不过通常，几分钟内就能在给出足够信心的作用域上完成一次会终止的分析。

四条粗略指引

① 界限要能容纳你声明的常量
确保一个 signature 的界限足以容纳你为它声明的任何常量。 
// 分析约束涉及图中的一条路径：
some disj start, end: Node | …

这要求 Node 至少有两个元素，以容纳 Skolem 变量 start 和 end。

② 尽量用 signature 重数声明来约束集合大小
因为分析器会利用重数，在作用域设置与 signature 声明互相矛盾时生成警告，或在需要时覆盖默认作用域。

✅ 会得到编译错误

sig Color {}
one sig Red, Green, Blue
  extends Color {}
pred show () {}
run show for 2

你会得到一个编译错误，告诉你 Color 的作用域 2 太低了，因为子签名声明要求它至少有三个孩子。

❌ 没有任何错误或警告

abstract sig Color {}
sig Red, Green, Blue
  extends Color {}
fact {one Red and one Green and one Blue}
pred show () {}
run show for 2

没有任何错误或警告消息，你需要执行命令才能发现模型是不一致的。

③ 如果所有相关值都被显式命名为变量，就没必要设更大的作用域

只需两本书

sig Name, Address {}
sig Alias, Group extends Name {}
sig Book {addr: Name -> Address}
pred add (b, b': Book, n: Name, a: Address) {
  b'.addr = b.addr + n -> a
}
run add for 3 but 2 Book

运行地址簿的 add 操作不需要超过两本书（因为只有 b 和 b' 两个变量涉及 Book）。

但不应限制为两个节点

sig Node {adj: Node}
fact {all n, n': Node | n' in n.*adj}
pred show () {some Node}
run show for 3

对这个图模型 show 谓词的分析不应被限制为两个节点，因为变量 n 和 n' 是对所有节点全称量化的。

④ 如果实例预期构成某个已知形状的结构，该形状的性质可以提示作用域约束
// 铁路模型：连接点与轨道段
sig Point {}
sig Segment {from, to: Point}

要包含「某个连接点处有一个道岔（junction）」的情形，看起来我们至少需要三条轨道段，因而总共至少四个连接点：一个用于道岔本身，另外每条轨道段的另一端各一个。

5.4.2 Scope Monotonicity · 作用域单调性

作用域单调性

作用域指定的是一个 signature 大小的上界，而不是它的确切大小。这给分析带来一个叫作用域单调性（scope monotonicity）的性质，简单地说就是：

如果一个分析约束在某个作用域内有实例，那么它在任何更大的作用域内也有实例。

作用域单调性在实践中非常重要，因为它意味着：如果一个断言在某个作用域内看起来是有效的（即没有反例），那么在更小的作用域里重复分析不会有任何收获。

exactly 会破坏单调性

exactly 关键字（4.6 节）让你指定一个 signature 有某个确切数量的元素，因此它的使用违反了作用域单调性，应当极其小心地使用。

  • 在模拟（simulation）中，它提供了一种简单办法来强制生成更有趣的实例；
  • 但在检验（checking）中，不推荐使用它。

5.4 Discussion

Q：实践中多大的作用域是可行的？

在一台配置普通的机器上（比如 1 GHz PowerMac、1 GB 内存），使用最新版本（2005 年）的 Alloy Analyzer，对一个含约 20 个 signature、20～30 个字段的模型，作用域 5 到 10 的分析通常是可行的。

在模型的增量开发过程中，作用域 3 的分析通常就足够，并且在一分钟内终止。

Q：signature 不是笛卡尔积吗？那不会让作用域爆炸吗？

许多 signature（但不是全部）是作为「构造元组的手段」被引入的。例如：

sig Coord {x: X, y: Y}   // 表示二维空间中的坐标

如果 signature X 和 Y 的大小分别是 scope(X) 与 scope(Y)，那么要表示所有可能的坐标对，就需要至少 scope(X) × scope(Y) 个 Coord 值。

你可能以为这应当决定 Coord 的作用域，而如果真是这样，几乎没有任何分析是可行的。

这里的误解

作用域并不约束「可能值的集合」的大小，它约束的是「可以出现在实例中的值的集合」的大小。

如果被检验的断言有一个只涉及一个坐标的反例，那么它会在作用域 1 中被找到，无论 Coord 的字段组合能取多少种可能的值。类似地，如果分析约束涉及两条直线的交点，那么 Coord 的作用域 5 可能就够了，因为它足以包含两条直线的端点及其交点所需的坐标。

「一个结构可能取的值集合」与「出现在实例中的值集合」之间的这个区别，正是 5.3 节讨论的实质。

Q：作用域为零可能吗？

可能，作用域设为零是被允许的，而且并不一定是胡闹。命令

run P for 0

问的是：是否存在一个 P 的实例，其中宇宙是空的。实践中这很少见——例如每个文件系统至少有一个根。

但「对集合非空做尽可能少的假设」是一个好的设计原则。例如一个客户-服务器系统应当能处理「没有任何客户」的情形。

「集合能不能为空」这个问题常常暴露设计中的根本问题。例如大多数文本排版程序都假设样式表至少包含一个样式。其实完全可以设计一个排版程序，不是所有段落都有样式，于是样式表可以为空。这会让「删除一个样式」的情形更容易处理：程序可以简单保留该段落的所有格式，只是不给它指派任何样式。

第 5 章小结

  1. 分析的三重价值：探索时给具体例子强化直觉；开发中让你保持诚实（写下的就是你以为的）；揭示微妙缺陷。核心机制是作用域 + 作用域内穷尽搜索。
  2. 逻辑不可判定，必须妥协。定理证明尝试构造证明（成功⇒有效；失败⇒结论不明，且难以分辨是断言错、证明器弱、还是引导不足）。实例查找尝试寻找反驳（找到反例⇒无效且给出场景；找不到⇒仍可能无效）。后者更契合轻量级建模：因为开发中最常见的是无效断言，而无效断言分析得更快（找到第一个实例即可停），且反例易于追溯回描述中的问题。
  3. 作用域不是一个数字，而是多维的：每个 signature 单独设界、由用户控制（铁路例子：2 个状态、1 个路口、多个轨道段与列车）。默认作用域 3 下，每个二元关系贡献 9 比特 = 512 倍，四个关系的微型模型就有超过十亿个用例。
  4. 小作用域假设：「大多数 bug 都有小的反例。」它是假设，不能被证明（否则会与不可判定性矛盾）；它针对的是实践中的断言而非所有可能断言。在大实例上失效的系统，几乎总会在性质相似的小实例上同样失效——所以检查所有小实例，等于也在为大实例做检查。资源分配上限类的失效不构成反例，因为抽象中资源分配要么被抽象掉，要么用可任意调低的参数或非确定性表示。
  5. run 与 check 的对称结构：run P 的分析约束是 P ∧ 所有 fact（含声明隐含的），实例叫例子；check A 的分析约束是 ¬A ∧ 所有 fact，实例叫反例。被赋值的变量 = 各 signature 的集合 + 各字段的关系 +（谓词的）参数。
  6. 变量不「变」：b 与 b' 只是两个普通变量，对分析器而言毫无特殊关联。这继承数学/物理的传统（不同时刻用不同名字，才使代数推理成为可能），可上溯到 Hoare 逻辑的辅助变量与 McCarthy 的 situation calculus。本书不用 Z 式的「字段加撇号」，而把随时间变化的现象建模为「从时刻到值的函数」；第 6 章进一步把时刻放在关系的最后一列，于是 f.t 就是时刻 t 的值。
  7. Analyzer 实际上是一个编译器 + SAT 求解器：把关系表示为布尔变量组成的邻接矩阵（作用域 A=3、B=4 ⇒ 3×4 矩阵、12 个变量、2¹² 种值）；关系表达式⇒布尔表达式矩阵（p+q ⇒ pi,j ∨ qi,j），关系公式⇒布尔公式（p in q ⇒ 全部 pi,j ⇒ qi,j 的合取）。求解后把真变量映射回元组。捆绑的求解器中 Chaff 与 Berkmin 最快。
  8. 对称破缺是最重要的优化：因为原子无解释，置换原子可从任一实例造出另一实例，所以解空间天然分成巨大的等价类。Analyzer 间接影响搜索——生成较小的对称破缺约束合取上去，只破除部分对称性，却消除了超过 99% 的赋值（完美的约束太大反而拖慢求解器）。最简单的例子是 util/ordering：被排序原子可互换，故按字典序排定 ⇒ 元素总是 S0、S1、S2…，兼顾性能与可视化。
  9. Skolem 化：把绑定变量换成自由变量，从而产生见证者。最外层量词 ⇒ 引入标量/集合/关系变量；内层量词 ⇒ 引入函数（sy: S -> one T，把 y 替换为 x.sy），对集合/关系则引入关系或多关系。命名规则是「所在谓词/函数名 + _ + 变量名」（addLocal_b）。三个好处：生成见证者、让高阶量化变得可分析、避免存在量词展开导致的约束膨胀（提升性能）。
  10. 无界全称量词是有限实例查找的主要微妙局限。当 signature 被意图表示「某复合结构的所有可能值」时，与 Alloy 语义（signature 只表示某个集合）矛盾。补生成器公理会导致作用域爆炸：集合需 2ᵏ、k 节点的图需 2k×k（三节点⇒512）、递归列表的公理甚至要求无穷原子 ⇒ 模型有效不一致 ⇒ 连 all l: List | not l = l 都会「通过」。
  11. 有界全称规则（bounded-universal rule）是出路：只要每个全称量词都是有界的（界定表达式不提及被生成的 signature 名）、不用转置 ~、点连接只以「集合 . 关系」形式出现，那么加不加生成器公理结果相同。直觉：这类约束只能「向内看」结构内部（子列表、子树），无法察觉公理是否被应用。Closed（all s0,s1 | some s2）❌ 非有界全称，会产生伪反例；UnionCommutative（否定后无全称量词）✅ 有界全称，含义正确。
  12. 最严重的实践后果：全性/前置条件断言通常无法检验。声明式风格的代价是无意的过度约束；而「对每个前状态都存在一个后状态」这类断言不属于有界全称类别。AddTotal 在 addr: Name -> Addr（本应有效）下也会给出伪反例——加公理需要 Book 作用域 512，省略公理则公式不是有界全称。两条路都走不通，所以这类性质只能靠人工推理。
  13. 有界全称规则允许用有限情形分析无限模型：含义是「若断言有反例，则某个作用域内有有限反例」，不是「有限作用域的检查自动适用于无限情形」（作用域太小仍可能漏）。它保证的是：省略公理并不让漏掉反例的可能性变大。规则要求公式处于「所有量词最外层且未被否定」的范式；可靠性证明见 [44]。
  14. 作用域单调性：作用域是上界，故「某作用域内有实例 ⇒ 任何更大作用域内也有实例」。推论：断言在某作用域内无反例，就不必在更小作用域重跑。exactly 破坏单调性：模拟时可用它强制生成更有趣的实例，检验时不推荐。
  15. 作用域选择的四条指引：① 界限要能容纳声明的常量与 Skolem 变量（some disj start, end: Node ⇒ Node ≥ 2）；② 尽量用重数声明而非 fact 来约束大小，这样矛盾时编译期就报错（one sig Red,Green,Blue extends Color + for 2 ⇒ 编译错误；改用 fact 则静默不一致）；③ 值都被显式命名为变量时不必设更大界限（add 只需 2 个 Book；但全称量化的图模型不能只给 2 个 Node）；④ 按预期结构的形状推算（铁路道岔 ⇒ ≥3 段、≥4 点）。
  16. 可行规模（2005 年硬件）：约 20 个 signature、20–30 个字段的模型，作用域 5–10 通常可行；增量开发中作用域 3 通常足够，且一分钟内终止。找不到实例时增大作用域提升信心但耗时增长；攸关的分析可以放到大机器上通宵跑。
  17. 「signature 是笛卡尔积」的误解：sig Coord {x: X, y: Y} 的可能值有 scope(X)×scope(Y) 个，但作用域约束的是「能出现在实例中的值」而非「可能值的集合」。只涉及一个坐标的反例在作用域 1 就能找到；两条直线相交只需作用域约 5。这正是 5.3 节讨论的实质。
  18. 作用域为零是合法的（run P for 0 问「宇宙为空时 P 是否有实例」）。「对集合非空做尽可能少的假设」是好的设计原则——客户-服务器系统应能处理没有客户的情形。这个问题常暴露设计的根本问题：排版程序若允许「段落没有样式」，样式表就可为空，删除样式也因此更容易处理（保留格式、不指派样式）。
