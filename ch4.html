4Language · 语言

原书 p. 83–137 · 从逻辑到语言：signature、字段、模型图、类型系统、fact/pred/fun/assert、命令与作用域、模块与多态、整数。这一章把第 3 章的关系逻辑包装成一个可写、可复用、可与分析器对话的工程化语言。

为什么「逻辑」还不够

一种描述软件抽象的语言，不仅仅是逻辑。你还需要：组织模型的方式、把小模型组装成大模型的方式、抽取可复用组件的方式，以及一些让语言在实践中真正好用的小语法细节（比如声明的简写）。最后，还需要一种与分析器沟通的机制——指出要执行哪些分析。

Alloy 是一门很小的语言。它独有的特性只有两个：signature（签名）与作用域（scope）的概念。其余——模块、多态、参数化函数等——都是主流编程/建模语言的标准配置，并被刻意设计得尽可能符合惯例。

4.1An Example: Self-Grandpas · 一个例子

有一首流行歌曲叫 「I'm My Own Grandpa」（我是我自己的爷爷）。作者用 Alloy 来探究：这到底怎么可能是真的？这个例子的价值在于，它把一整章要讲的语言构件（module / sig / fact / fun / pred / assert / run / check / for）在一个 26 行的模型里全部用了一遍。

模型的宏观结构（gross structure）

module 头
给模块命名（第 1 行）。命名方式与 Java 相同：模块全名对应文件系统里的路径与文件名。默认扩展名 .als，所以这个模块存在 language/grandpa1.als。
sig 声明
每个 signature 代表一个原子集合，并可以引入若干字段，每个字段代表一个关系。
约束段落
由 fact / fun / pred 标记，记录各种形式的约束与表达式。
断言
由 assert 标记，记录期望成立的性质。
命令
由 run / check 标记，指示分析器执行特定分析。
1  module language/grandpa1
2  abstract sig Person {
3    father: lone Man,
4    mother: lone Woman
5  }
6  sig Man extends Person {
7    wife: lone Woman
8  }
9  sig Woman extends Person {
10   husband: lone Man
11 }
12 fact {
13   no p: Person | p in p.^(mother + father)   // 你不是你自己的祖先
14   wife = ~husband                             // 夫妻关系互为转置
15 }
16 assert NoSelfFather {
17   no m: Man | m = m.father
18 }
19 check NoSelfFather
20 fun grandpas (p: Person): set Person {
21   p.(mother + father).father
22 }
23 pred ownGrandpa (p: Person) {
24   p in grandpas (p)
25 }
26 run ownGrandpa for 4 Person
fig. 4.1 第一个完整 Alloy 模型：你能成为自己的爷爷吗？

逐段解读

构件这里做了什么背后的语言规则
abstract sig Person
sig Man extends Person
sig Woman extends Person		 建立分类层级：男人和女人是 Person 的互不相交的子集。 extends ⇒ 子集互不相交；abstract ⇒ 父集没有不属于任何扩展的元素。若省略 abstract，就会允许「既不是男人也不是女人」的人。
father: lone Man每人至多一个父亲。字段的定义域被限制在所属 signature 内，所以 father 关联的是 Person → Man。
fact { … }两条永远成立的假设。第 13 行用 p in p.^(mother+father) 表达「不能是自己的祖先」；第 14 行用转置表达夫妻对称。
assert NoSelfFather + check断言「没人是自己的父亲」；check 让分析器找反例。此断言有效，找不到反例。省略 for 时使用默认作用域 3。
fun grandpas定义可复用表达式。之后可以用 grandpas(p) 代替笨拙的 p.(mother+father).father。
pred ownGrandpa定义可复用约束。ownGrandpa(p) 代替 p in grandpas(p)。
run ownGrandpa for 4 Person让分析器找一个满足该谓词的实例。for 4 把搜索限制在「每个顶层集合最多 4 个元素」的宇宙内。

剧情：从「找不到」到「 socially acceptable 的解」

第一次尝试：什么也没发生

分析器在作用域 4 内找不到解。这可能意味着更大的作用域里有解，于是把 4 换成 10 再试——仍然没有。继续放大作用域，很快就会到达分析器无法在合理时间内穷尽可能性空间的地步。

于是换一种提法：把谓词改写成断言。

assert NoSelfGrandpa {
  no p: Person | p in grandpas (p)
}
check NoSelfGrandpa for 4 Person

当分析器找不到断言的反例时，它报告 success（与「谓词找不到实例」时的 failure 相反）。两者在分析机制上是同一件事，但报告的方向不同——这一点在 4.1 的 Discussion 与 4.6 里都有强调。

解读 · 这一步的方法论含义

「run 找不到解」和「check 找不到反例」都不等于命题被证明，只是「在作用域内穷尽了」。作者的巧妙之处是：当正面搜索失败时，不要立刻下结论说「不可能」，而是怀疑自己的定义。这里真正该被质疑的是 grandpas 的定义——它只考虑了生物学爷爷，没考虑婚姻带来的爷爷。

修正定义：把继父母算进「parent」

fun grandpas (p: Person): set Person {
  let parent = mother + father + father.wife + mother.husband |
    p.parent.parent & Man
}

let 把 parent 绑定到「母亲 + 父亲 + 父亲的妻子 + 母亲的丈夫」这个关系上。整体含义：你的爷爷 = 任何一个「是你父母的父母」的男人，其中「父母」现在包含继父母。

再跑 ownGrandpa，这次有解了（fig. 4.2）：只有两个人，Woman_0 和 Man_0，他们既是母子，又是夫妻。作者评了一句：「这不是一个适合写进流行歌曲的解。」

于是再加一条事实来排除乱伦：

no (wife + husband) & ^(mother + father)
关系式思维的示范

mother + father 关联「孩子 → 父母」；它的闭包关联「人 → 祖先」；wife + husband 关联「人 → 配偶」。 no p & q 表示两个关系不共享任何元组。整句：没有任何人的配偶同时是他的祖先。

再跑一次，得到一个更符合社会规范的解（fig. 4.3）：有两对夫妻，每对的妻子都是另一对丈夫的母亲。那个「自己当自己爷爷」的人 p，是通过让他的继子娶了他自己的母亲做到的。

module language/grandpa2
abstract sig Person { father: lone Man, mother: lone Woman }
sig Man extends Person { wife: lone Woman }
sig Woman extends Person { husband: lone Man }

fact Biology          { no p: Person | p in p.^(mother + father) }
fact Terminology      { wife = ~husband }
fact SocialConvention { no (wife + husband) & ^(mother + father) }

assert NoSelfFather { no m: Man | m = m.father }
check NoSelfFather

fun grandpas (p: Person): set Person {
  let parent = mother + father + father.wife + mother.husband |
    p.parent.parent & Man
}
pred ownGrandpa (p: Man) { p in grandpas (p) }
run ownGrandpa for 4 Person
fig. 4.4 Self-grandpas 最终版。作者把事实拆成多个段落并起了有提示性的名字（Biology / Terminology / SocialConvention），以示范「按角色或来源分组约束」是好习惯。

4.1 Discussion · 原文问答

Q：歌曲「I'm My Own Grandpa」从哪来？
最初是 Dwight Latham 和 Moe Jaffe 在 1930 年代广播节目里的一个短剧；Latham 把创意归功于一本马克·吐温的轶事集。后来扩写成歌，1948 年由「Lonzo and Oscar」（Ken Marvin 与 Rollin Sullivan）录制并走红。 顺便一提，歌里的情形和 Alloy 找到的解并不相同：歌中是「让继女嫁给自己的父亲」，而不是「让继子娶自己的母亲」。
Q：怎样构造关系式公式？

对新手来说关系式风格很难把握，但熟练后会非常自然。作者的建议是：想着「箭头的集合」，而不是「原子及其关系」。

以 no (wife + husband) & ^(mother + father) 为例，作者的思路链条是：

  1. 要表达的约束是「没人可以娶/嫁自己的父母、祖父母等等」——这是在禁止某些关系，即某些箭头不该存在 ⇒ 形式必为 no e。
  2. 被禁止的关系是「既是配偶，又是父母/祖父母/…」——这是个合取 ⇒ 取两个关系的交集：不该有一支箭头同时属于两者。
  3. 「是配偶」= 是妻子或丈夫 ⇒ wife + husband（并集）。
  4. 「父母、祖父母，等等」中的「等等」⇒ 对 parent 关系取传递闭包；而「父母」= 母亲或父亲 ⇒ 再一次并集。

拼起来就得到目标公式。

Q：如何确认约束真的是我想要的含义？

可以写一个断言，检验它与另一种表述等价。例如把关系式版本与导航式版本对照：

pred SocialConvention () {
  no (wife + husband) & ^(mother + father)
}
pred SocialConvention' () {
  let parent = mother + father {
    no m: Man | some m.wife and m.wife in m.*parent.mother
    no w: Woman |
      some w.husband and w.husband in w.*parent.father
  }
}
assert Same { SocialConvention () iff SocialConvention'() }
check Same

如果两种表述在作用域内不等价，分析器会生成一个反例，展示一个「满足其一却不满足另一个」的家庭。

Q：run 一个谓词和 check 一个断言，真的有区别吗？

从分析角度看没有本质区别：run 谓词是搜索其约束的实例；check 断言是搜索其约束否定的实例。所以「check 约束 C 的断言」等价于「run 约束 not C 的谓词」。

但这模糊了一个至关重要的方法论区分。在设计 Alloy 时，作者认为必须能把「被猜想可由其余部分推出的性质」单独抽出来。在模型中显式记录这些冗余、并标明它们是冗余——这个想法来自 John Guttag 与 Jim Horning，是 Larch 语言的一部分。

Q：如果分析器找不到断言的反例，是否说明该断言有效？
不一定。更大的作用域里可能存在反例。但在实践中，随着作用域增大，仍存在反例的概率确实会下降。所以你获得了一些保证，但不是绝对意义上的保证。

4.2Signatures and Fields · 签名与字段

4.2.1 Signatures

一个 signature 引入一个原子集合。sig A {} 引入名为 A 的集合。严格说 signature 不只是一个集合（它还能包含关系声明、还会隐式引入一个新类型），但书中宽松地把这个词同时用于「更大的结构」和「与之关联的集合」，比如说「signature 的元素」指集合里的原子。

声明形式含义隐含约束
sig A {}顶层 signature（独立声明，不依附他人）所有顶层 signature 互不相交
sig A1 extends A {}A1 是 A 的扩展 / 子签名，即子集同一父签名的各扩展互不相交；但不能推出 A = A1 + A2
abstract sig A {}A 没有不属于其扩展的元素加上 A1/A2 extends A ⇒ A in A1+A2，于是 A = A1 + A2，A1、A2 划分了 A
sig A3 in A {}子集 signature，用于表达正交的另一套分类子集 signature 不要求互不相交；再写 sig A4 in A {}，A3 与 A4 可以相交，除非另加约束
sig C in A + B {}C 的每个元素属于 A 或 B并集表达式可以列任意多个集合，但并集是唯一允许出现在这种位置的算子
m sig A {}前置重数关键字约束集合元素个数例如 abstract sig T {} + one sig A, B, C extends T {} ⇒ T 恰好有三个元素 A、B、C，即一个枚举
分类层级树 · 类型系统的来源

一组 signature 声明（部分顶层、部分扩展）的效果是引入一个分类层级（classification hierarchy）。 再加上常量 univ（全集，可视为一个隐式的抽象签名，所有顶层签名都扩展它），这个层级就形成一棵树：根是 univ，往下一层是顶层签名，再往下是它们的扩展，依此类推。 这棵树给所有原子提供了一个「主分类」，并被类型系统所利用（见 4.4）。需要其他正交分类时，就用子集 signature（in）。

六个典型分类例子

地址簿的目标

abstract sig Target {}
abstract sig Name extends Target {}
sig Alias, Group extends Name {}
sig Addr extends Target {}

像素颜色

abstract sig Pixel {}
sig Red, Green, Blue extends Pixel {}

交通灯颜色（枚举）

abstract sig Color {}
one sig Red, Yellow, Green
  extends Color {}

文件系统（两套正交分类）

abstract sig Object {}
sig File, Dir extends Object {}
sig Alias extends File {}
sig Temp in Object {}   // 正交：可能是文件或目录

同上，但不显式声明 Object

sig File {}
sig Dir {}
one sig Root extends Dir {}
sig Alias extends File {}
sig Temp in File + Dir {}

茶叶（两层 + 交叉分类）

sig Tea {}
sig IndiaTea, ChinaTea extends Tea {}
sig Assam, Darjeeling extends IndiaTea {}
sig Keemun, Lapsang extends ChinaTea {}
// 伯爵茶可能是中国茶也可能是印度茶：
sig EarlGrey in ChinaTea + IndiaTea {}

4.2.1 Discussion

Q：Alloy 支持多重继承吗？

支持，但不能完全靠声明——需要一些显式 fact。例如想说「茉莉花茶既是加味茶又是中国茶」，两个关系中必须有一个写成 fact：

sig Tea {}
sig ChinaTea extends Tea {}
sig FlavoredTea in Tea {}
sig JasmineTea extends ChinaTea {}
fact { JasmineTea in FlavoredTea }

不要把声明里的并集误认为多重继承。sig EarlGrey in ChinaTea + IndiaTea {} 说的是「Earl Grey 是中国茶或印度茶」，它并不表达对伯爵茶原产国的不确定性。signature 代表的是一个集合——所有伯爵茶的集合——所以这句话是说：该集合的每个成员，要么是中国茶，要么是印度茶。

Q：单例 signature（one sig）对应原子吗？

单例 signature 代表单例集合——只含一个元素的集合。在某个实例中，这样的集合确实对应单个原子。但把单例看作与其他集合根本不同，是个错误。

某些建模记法把含单例的模型看成「模型/实例的混合体」，这是不必要的。模型与实例的区别在于：模型代表一组实例。所以在模型里，单例集合并不绑定到某个特定原子，在不同实例中它可以代表不同的原子。

例如文件系统模型里为根目录声明一个单例，它描述的是所有可能文件系统的集合，每个文件系统有自己的根，不同文件系统的根可以是不同的原子。当我们在这个模型里使用 Root 时，指的是「当前所描述的那个文件系统的根」，它可以随文件系统而变。

4.2.2 Basic Field Declarations · 基本字段声明

关系以字段的形式声明在 signature 内。sig A {f: e} 引入一个关系 f，定义域是 A，值域由表达式 e 给出，效果等同于在 fact 里写了声明约束：

f: A -> e

它也可以等价地写成：

all this: A | this.f : e
为什么第二种写法是「更好的理解方式」

因为它在加上重数符号后仍然给出正确含义（见 3.6）。对集合 e，声明 sig A {f: m e} 添加的约束是 all this: A | this.f : m e，意思是：对 A 中任意 this，this.f 拥有 m 个取自集合 e 的元素。

声明含义（对任意 this: A）
sig A {f: one e}this.f 有 1 个 e 中元素
sig A {f: some e}至少 1 个
sig A {f: lone e}至多 1 个
sig A {f: set e}任意个
sig A {f: e}默认省略的关键字是 one，故与 sig A {f: one e} 等价 ⇒ this.f 是标量
sig A {f: e1 m -> n e2}若 e 本身是关系（arity ≥ 2），其中可以含重数关键字，规则相同：all this: A | this.f : e1 m -> n e2

六个字段声明例子

茶与其唯一原产国

sig Tea {origin: Country}
sig Country {}

文件系统：目录含任意对象，别名指向恰好一个对象

abstract sig Object {}
sig Directory extends Object {contents: set Object}
one sig Root extends Directory {}
sig File extends Object {}
sig Alias extends File {to: Object}

天气预报：每城恰好一种天气

sig Forecast {weather: City -> one Weather}
sig City, Weather {}
one sig Rainy, Sunny, Cloudy extends Weather {}

地址簿：名字至多对应一个地址或名字

sig Name {address: lone Addr + Name}
sig Addr {}

Book 持有「名字 → 地址/名字」的偏函数

sig Book { addr: Name -> lone (Addr + Name) }
sig Name {}
sig Addr {}

交通灯：在给定时刻显示某种颜色组合

sig TrafficLight { color: Color some -> Time }
abstract sig Color {}
one sig Red, Green, Yellow extends Color {}
sig Time
行文约定

作者说：把 signature S 描述成「S 的元素的一个集合」太啰嗦了，所以从此以后用单数指代 signature 的元素——「一个 S」。只要记住：一个 signature 潜在地代表任意多个元素。

Q：所有关系都必须声明为字段吗？

是的：Alloy 没有顶层关系声明。如果你想声明一些不属于任何现有 signature 的关系，就把它们声明为一个单例 signature 的字段。例如文件系统模型中，一个「名字 → 对象」的 lookup 结果关系可以这样声明：

one sig Globals { lookup: Name -> Object }

然后用 Globals.lookup 引用。这是一个非常常用的「全局关系容器」惯用法。

4.2.3 Grouping Fields · 字段分组

字段可以分组以共享声明表达式。关键字 disj 与 part 表示这组字段互不相交，或构成一个划分：

写法隐含约束
sig A {disj f, g: e}all this: A | no this.f & this.g
sig A {part f, g: e}同上，外加 all this: A | e in this.f + this.g（覆盖 e 的全部）

猫有三个名字

sig Cat {
  disj daily, peculiar,
       ineffable: Name
}
sig Name {}

对任意猫 c，c.daily、c.peculiar、c.ineffable 是三个不同的名字。

非友即敌

sig Cat {
  part friends, enemies:
       set Cat
}

猫把所有不是朋友的猫都视为敌人——part 保证两者合起来覆盖全集。

路口的灯

sig Junction {
  northSouth, eastWest:
    LightState
}
sig LightState {
  color: Light -> one Color
}
sig Color, Light {}

路口在（概念上）每个方向有一盏灯，在给定状态下被赋予单一颜色。

4.2.4 Dependent Declarations · 依赖式声明

唯一的限制

字段声明的界定表达式可以是任意 Alloy 表达式，只有一个限制：如果该表达式出现在 signature X 的字段声明中，它只能提及 X 自身中先前声明的字段，或 X 的某个父类型 signature 中的字段。

用另一种方式让猫的三个名字互异

sig Cat {
  daily: Name,
  peculiar: Name - daily,
  ineffable: Name - (daily + peculiar)
}
sig Name {}

三个映射：家、公司、默认

sig Book {
  homeAddress, workAddress:
    Name -> lone Addr,
  address: homeAddress + workAddress
}
sig Name, Addr {}

address 的声明允许它把一个名字同时映射到家庭地址和工作地址；若要限制为一个，需要额外约束（例如写进 signature fact，见 4.5.1）。

电台拥有多个频率

sig RadioStation {
  owns: set Freq,
  freq: Location -> one owns
}

变焦镜头的最大光圈

sig Lens {apertures: set FStop}
sig ZoomLens extends Lens {
  maxTeleAperture: apertures
}
sig FStop {}

依赖式声明的展开规则

依赖式声明隐含的约束，比「界定表达式里只出现 signature」的简单声明要稍复杂一些。对 sig A {f: e}，约束是：

all this: A | this.f in e'

其中 e' 与 e 完全相同，只是把每个字段引用都展开：出现在 e 中的每个字段都被视为对 this 的解引用，所以字段 g 的每次出现都被替换成 this.g。

// 由镜头例子产生的约束是：
all this: ZoomLens | this.maxTeleAperture in this.apertures
Q：为什么依赖式声明不能提及任意字段？

这个限制让模型更容易做类型检查，也许也更容易阅读。它确实排除了一些有用的情形，例如想描述「某电台的频率是它所属类别所允许的频率之一」：

sig RadioStation {class: StationClass, freq: class.band}   // 非法
sig StationClass {band: set Freq}

如果允许相互依赖，就可能出现没有唯一类型的字段。例如「某人的姓是其父母之一的姓」：

sig Person {surname: parents.surname, parents: set Person}   // surname 的类型无法确定

不过这些情形都可以在声明之后补上约束（见 4.5.1）：

sig RadioStation {class: StationClass, freq: Freq}
  {freq in class.band}

sig Name {}
sig Person {surname: Name, parents: set Person}
  {surname in parents.surname}
Q：依赖式声明会不会把人搞糊涂？

会。一个常见错误出现在闭包上。假设要描述一个 P2P 网络，每个 peer 有一组直连朋友，以及一个可从朋友到达的「社区」。这样的声明尝试：

sig Peer { friends: set Peer, community: set *friends }   // 被拒绝

会被拒绝，因为 community 声明中对 friends 的提及被展开成 this.friends，那是一个集合而不是二元关系。

你可能想用特殊符号 @ 阻止展开：

sig Peer { friends: set Peer, community: *@friends }   // 能通过，但含义不对！

这会被接受，但不是你以为的意思：*@friends 表示一个二元关系，所以 community 会变成一个三元关系！正确做法是用保留字 this 指代那个特定的 peer：

sig Peer {
  friends: set Peer,
  community: set this.*@friends
}
// 隐含约束： all this: Peer | this.community in this.*friends
这一节的教训

不要那么拼命地把所有约束都塞进声明里，写一个显式约束更好：

sig Peer {friends, community: set Peer}
fact {community in *friends}

模型图声明一些集合与二元关系，并对它们施加一些基本约束。图是传达模型轮廓的好方式，但图的表达力不足以包含详细约束。有人喜欢先画图再写文本，有人偏好先写文本、把图当插图。Alloy Analyzer 可以从文本模型生成模型图——你可以用它帮助理解大型模型，或者看着模型随新 signature 的增加而生长。图记法见附录 D。

4.3.3 Expressions and Higher-Arity Relations

任何表示集合或二元关系的表达式都可以出现在模型图里——把表达式当作框或箭头的标签即可，而不必是集合名或关系名。

高 arity 关系怎么画

arity 大于 2 的关系无法直接展示。但通常你可以通过创建一条或多条弧、并给它们打上合适的表达式标签，把需要说的都说出来。假设有关系 R: A -> B -> C：

  • 画一条从 B 到 C 的弧，标签 A.R；
  • 或画一条从 A 到 B 的弧，标签 R.C。

但要展示 R 这样的关系的重数，你真正想展示的往往是一个原型表达式（archetypal expression），比如 a.R，其中 a 是集合 A 中的一个标量。

给关系弧打标签 all v: be | e，意思是：该弧因源集合、目标集合和重数而隐含的约束，对表达式 e 成立，其中 v 遍历 be 给出的集合。例如从 B 到 C 的弧上标 all a: A | a.R !，是说 a.R 是一个把每个 B 映射到一个 C 的函数，对每个 a 都如此，等同于文本中的：

all a: A | a.R : B -> one C
便捷简写 <S>

实践中，界几乎总是遍历一个具名集合，而这种记法有点笨拙。所以有个方便的简写：遍历集合 S 的变量直接写成 <S>。上例的标签就写成 <A>.R。fig. 4.7 的地址簿图里出现的 <Book>.addr? 与交通灯图里的 color.<Time>+ 就是这个记法。

4.3 Discussion · 原文问答

Q：为什么图记法不更直接地对应文本记法？

Alloy 的文本形式与图形形式之间存在根本差异。图记法是平坦的：一个关系并不更属于它的源而非它的目标，所以在两端都标重数是合理的。而文本记法把关系打包进 signature，鼓励把关系看作对象的字段，并且语法不允许你为 signature 自身的元素给出重数。

例如 sig S {r: lone T} 说 r 是一个偏函数（把每个 S 映射到至多一个 T），但它没有说有多少个 S 映射到每个 T。你可以加一条显式声明公式 fact {r : S lone -> lone T}，让 r 的转置也成为函数，但你无法在声明本身中表达这一点。图形形式不受这种不对称之苦。

文本与图形形式的精确对应曾是早期版本 Alloy 的设计目标，但在引入 signature 之后失去了。

Q：为什么不用 UML 的图语法？

UML 语法的优势是很多人熟悉。但 Alloy 自己的语法与文本语言有更直接的映射，而且不需要专用工具就更容易画（只用标准形状，不要求一条弧在不同位置携带标签）。

一个常见约定是：为互不相交的子集画一个共享的粗箭头头，为每一套正交分类画单独的箭头。只在纸上作画时这没问题，但如果想把这样的图转成 Alloy 文本，你必须指定其中一套分类为「主分类」，这样表达式才能有唯一类型。次级分类必须用标注 in 的子集箭头表达，其不相交性质必须显式写成 fact。

Q：为什么图中 set（*）是默认重数？

图形记法应当是单调的（monotonic）：随着你不断修饰它，你是在添加而非移除约束。否则，如果你在中途停下，手上的图就是错误的，因为它说了你并不想说的话。

写文本模型时很少会省略所有重数，但画图时先勾勒宏观结构、再填充细节是很常见的。有些图形记法违反了这个原则，例如用普通线端表示「恰好一个」、用更复杂的线端表示更弱的重数。

4.4Types and Type Checking · 类型与类型检查

类型系统的两个功能
  1. 在任何严肃分析开始之前捕获错误。核心思想是：一个表达式如果有错，是因为仅凭类型就能证明它是冗余的。这个错误概念虽然不合常规，但在实践中与直觉相当吻合——它接受和拒绝表达式的方式正如你所期望。
  2. 解析重载（overloading）。当不同 signature 有同名字段时，用表达式的类型来决定指的是哪一个字段。

4.4.1 Basic Types · 基本类型

  • 类型隐式地与 signature 关联。每个顶层 signature 和每个扩展 signature 都引入一个基本类型。
  • 当 A1 扩展 A 时，A1 关联的类型是 A 关联类型的子类型。
  • 子集 signature 没有自己的类型，它继承父类型；若声明为多个 signature 并集的子集，其类型是这些父类型的并。
  • 两个基本类型重叠（overlap），当且仅当其中一个是另一个的子类型。
// fig. 4.8 茶叶的类型层级
sig Tea {}
sig IndiaTea, ChinaTea extends Tea {}
sig Assam, Darjeeling extends IndiaTea {}
sig Keemun, Lapsang extends ChinaTea {}
//  ⇒  Tea ← IndiaTea ← {Assam, Darjeeling}；Tea ← ChinaTea ← {Keemun, Lapsang}

// fig. 4.9 文件系统的类型层级
sig Object {}
sig File, Directory extends Object {}
sig Temp in Object {}
//  ⇒  Object ← {File, Directory}；Temp --in--> Object（不引入新类型）
Temp 这个集合没有自己的类型，其元素属于类型 Object。类型 File 与 Object 重叠（因为有原子既是文件又是对象），但类型 File 与 Directory 不重叠。

4.4.2 Relational Types · 关系类型

每个表达式都有一个关系类型，由若干「积的并」构成：

A1 -> B1 -> …  +  A2 -> B2 -> …  +  …

其中每个 Ai、Bi 等都是基本类型。每个积项必须含有与该关系 arity 相同数量的基本类型。二元关系的类型形如 A1 -> B1 + A2 -> B2 + …，集合的类型形如 A1 + A2 + …。

类型本身就是一个 Alloy 表达式

类型是自动推断的，使得类型的值总是包含表达式的值——即它是一个过近似（overapproximation）。 这意味着：如果两个类型的交集为空，那么它们所来自的两个表达式的交集也必为空。这正是类型检查可靠（sound）的原因。

类型是如何确定的（三步）

第一步 · 基本类型层级
从 signature 声明得到。例：abstract sig Object / Directory extends Object / one sig Root extends Directory / File extends Object / Alias extends File / Temp in Object ⇒ 基本类型为 Object、File、Alias、Directory、Root；File 与 Directory 是 Object 的子类型，Alias 是 File 的子类型，Root 是 Directory 的子类型；signature Temp 被赋予类型 Object。
第二步 · 字段类型
给每个字段一个类型，方法是对声明右侧的界定表达式定类型。例：sig Directory extends Object {contents: set Object} 与 sig Alias extends File {to: Object} 中的字段分别得到 Directory -> Object 与 Alias -> Object。
第三步 · 检查模型约束
用 signature、字段的类型，以及量化变量的类型（其推断方式与字段完全相同）为每个表达式推断类型。例：在 all d: Directory - Root | some d.~contents 中，量化变量 d 得到类型 Directory，然后 d.~contents 也得到类型 Directory。

确定表达式类型是直截了当的：每个关系算子都有一条对应的规则。例如点连接的规则是：

若 p 的类型包含积 P1 -> … -> Pn，
且 q 的类型包含积 Q1 -> Q2 -> … -> Qm，
且基本类型 Pn 与 Q1 重叠，
则 p.q 的类型包含积 P1 -> … -> Pn-1 -> Q2 -> … -> Qm

注意这条规则与 join 本身的语义规则形式相同。这不奇怪，因为类型只是值的近似，用同样的方式计算，只是更粗糙。

4.4.3 Type Errors · 类型错误

第一类：混合 arity

因为逻辑假定所有关系有固定 arity，构造出混合 arity 关系的表达式是非法的。

sig Tea {origin: Country}
sig Country {}
// origin + Country 非法：
// origin 是 arity 2，Country 是 arity 1

第二类：可证冗余

如果一个表达式仅凭声明就能被证明是冗余的，或包含冗余子表达式，则非法。最简单常见的情形是表达式等于空关系。

// 文件系统语境下，以下均类型错误：
Directory & Alias   // 必为空：两个 signature 不相交
Alias.contents     // 必为空：contents 只映射目录，
                     // 而没有目录是别名
类型检查器只推理类型

它不把 signature 本身与同类型的其他表达式区分开。例如 Alias - Object（不是对象的别名）确实表示空集，但类型检查器不会拒绝它，因为形如 A - O 的表达式，当 A 的类型是 Alias、O 的类型是 Object 时，可能非空。

点连接的四种情形

只有一种被拒绝

在这个类型系统里，子类型层级主要用于判断类型是否不相交。熟悉编程语言子类型的人所期待的那种不对称性并不存在。特别地，形如 s.r（s 是集合、r 是关系）的表达式的定类型，只要求 s 与 r 的定义域重叠。

集合与关系的组合例子是否合法
精确匹配Directory.contents✅ 合法
子类型Root.contents✅ 合法
父类型Object.contents✅ 合法
不相交File.contents❌ 非法——这是唯一总是产生空集的情形

注意其他三种组合也可能产生空集，所以区分它们没什么意义。

子表达式不相交 ≠ 冗余

并集的参数当然可以——而且经常——是不相交的。虽然 File & Directory 类型错误，File + Directory 却是合法的。它可以用在这样一个文件系统版本里：不为「所有对象的集合」声明 signature。

sig Directory extends Object {contents: set File + Directory}
sig File {}
sig Alias {to: File + Directory}

还有一类更微妙的冗余型类型错误：表达式不等于空关系，但可以用空关系替换它而不影响外层表达式的含义。

(Directory + Alias).contents

类型错误——别名没有 contents，提及 Alias 是冗余的，该表达式本可等价地写成 Directory.contents。

Directory - Alias
Directory in Alias

都类型错误——没有目录是别名，所以提及 Alias 冗余。后者本可等价地写成 no Directory。

4.4.3 Discussion

Q：类型检查器会误报吗？

不会。每当你得到类型错误，你的模型里就确实存在某种冗余，而你几乎一定会想消除它。

如前所述，类型只是特定形式的关系表达式；对任意表达式 e，其类型表达式 Te 总是表示一个更大的关系（至少含相同元组，可能更多）。这正是类型检查可靠的原因：检查一个交集表达式时，如果结果类型为空，该表达式所表示的关系必为空——因此是错误。

另一方面，类型检查器不提供任何保证。编程语言的传统类型系统恰恰相反：它们保证运行时不会出现类型错误，但会对其实永远不会出错的程序抱怨。在建模中没有「运行时失败」的类比物，所以不清楚什么样的保证才有用。

Q：为什么 Alloy 允许把字段应用于父类型？

把一个声明在子类型里的字段应用于「只知属于父类型」的表达式，结果可能为空。但由于结果并不总是为空，Alloy 类型检查器不禁止它，也不要求某种强制转换（cast）。理由是：即使应用于子类型自身，结果也可能为空，所以背上 cast 的负担并不能带来额外收益。

在面向对象编程语言里情况完全不同：如果已知一个表达式求值为某类的对象，那么该类中声明的任何方法都能被成功调用，类型系统因此能做出保证。但在 Alloy 这样的建模语言里，问题是在关系上导航，而不是调用方法；因为关系可以是偏的，所以永远无法保证结果非空。而且空结果不一定是错误——这就是为什么 Alloy 类型系统只排除「总是为空」的表达式，而不排除「有时为空」的。

Q：哪里能了解更多类型系统细节？
Alloy 的类型系统在研究论文 [14] 中有详细描述与设计论证。Alloy 语言的一个重要性质是：理解一个模型的含义并不需要类型；该论文解释了如何通过对语义做一个简单扩展来做到这点——允许混合 arity 的关系，并把未解析的字段视为其所有可能解析结果的并。

4.4.4 Field Overloading · 字段重载

规则

一个 signature 为其声明定义了一个局部命名空间，所以你可以在不同 signature 中使用相同的字段名，每次出现指代不同的字段。唯一的限制是：如果两个 signature 共享一个字段名，它们就不能重叠（即不能因为一个是另一个的子类型而潜在地共享元素）。

字段引用自动解析：当一个字段名可能指代多个字段时，用候选字段的类型决定指的是哪个。如果仍有可能多于一个，就报错。

例：File 也有 contents

sig Object, Block {}
sig Directory extends Object {contents: set Object}
sig File extends Object {contents: set Block}

// 平凡解析：若指 Directory 的字段，f.contents 会是空
all f: File | some f.contents      // ✅

// 无法解析 ⇒ 约束被拒绝
all o: Object | some o.contents   // ❌

例：歌手和电台都有 band

sig Singer {band: Band}
sig RadioStation {band: set Freq}
sig Band, Freq {}

// 电台的频段不重叠：
no disj s, s': RadioStation | some s.band & s'.band
// 每个（歌唱）乐队至少有一个歌手：
all b: Band | some b.~band

注意：第一条约束里字段是用关系的第一列解析的，第二条是用第二列解析的。

重载解析利用了字段引用出现的整个上下文，对字段必须以何种语法形式出现没有任何限制。上例最后一条约束可以写成以下任意形式：

all b: Band | some b.~band
all b: Band | some band.b
all b: Band | some s: Singer | s->b in band

更微妙的例子

sig Object, Block {}
sig Directory extends Object {contents: set Object}
sig File extends Object {contents: set Block}

no o: Object | o in o.contents

这里的 contents 被解析为 Directory 的字段。假如它指的是 File 里的字段，o.contents 的类型会是 Block；而 o 的类型是 Object，Object 与 Block 不相交，于是约束 o in o.contents 会空洞地为假。

消歧的万能招：域限制 S <: f

偶尔一个重载字段名无法被解析，这时你需要通过细化它所在的表达式（而不改变含义）来消歧。一个总是有效的简单办法是使用域限制算子：想要 signature S 中的字段 f，就写 S <: f。

例：节点环 + 同名的 next

sig Node {next: Node, value: Value one -> Time}
sig Time {next: Time}
sig Value {}

// 节点构成一个环：
fact {all n: Node | Node in n.^next}

// 时间步也用 next 排序。想说它无环：
fact {no ^next & iden}          // ❌ 被拒绝：next 有歧义
no ^(Time <: next) & iden      // ✅ 修正

（实践中，时间步排序是一个常见惯用法，你会改用库模块，即 util/ordering。）

4.4.4 Discussion

Q：字段可以声明在子集 signature 里吗？

可以。但要记住：用 in 扩展一个 signature 时，这些扩展不是子类型，也不必不相交。根据「不重叠」规则，它们因此不能共享字段名。即使你碰巧知道它们事实上不相交（因为你写了某条 fact），类型检查器并不知道，仍会拒绝你的模型：

sig Name, Thing {}
sig Man in Thing {name: Name}      // 非法
sig Island in Thing {name: Name}   // 即使加上 fact {no Man & Island} 也非法
Q：为什么重叠的 signature 不能共享字段名？
这条规则的结果是：同名的两个字段，其第一列的类型必定不同。所以同名字段总是有不同类型，总存在某个上下文能把它们区分开。如果允许两个重叠 signature 用同一名字，就需要一条更复杂的规则，而且用域限制来解析字段引用的标准技巧将不再总是有效。
Q：Alloy 的重载处理与 Java 有何关系？

Java 这类语言用重载解析，让类内的字段名与方法名可以不顾其他类所选的名字。但其解析机制通常简单得多。

在 Java 里，字段引用可以重载，但它们要么是自引用（f 是 this.f 的简写），要么跟在点后面（如 x.f）。前一种情况默认解析为它所在类的字段；后一种用点前面表达式的类型解析。而且没有转置算子——你不能向后导航。

在 Alloy 中，我们希望能把 x.f 写成等价形式 f.~x，把 x.f 和 x.g 写成 x.(f + g)。这要求一个更灵活的重载方案，不依赖任何特定语法形式。因此 Alloy 的解析机制不仅依赖字段的类型和 arity，还依赖它出现的完整上下文。

Q：域限制算子是一个特殊的「强制转换」算子吗？

不是，别被误导。你完全可以写 (S -> univ) & f 来代替 S <: f（至少就重载而言——虽然这个形式一点也不吸引人！）。

这是 Alloy 类型系统设计的一个重要结果：它是隐式的，不给语言增加任何自己的语法。事实上，Alloy 可以被看作一门无类型语言。理解一个约束的含义并不真的需要解析重载：每个字段名都被当作它可能指代的所有字段的并；当名字无歧义时，这个并恰好等价于被解析出的那个字段。

所以：读 Alloy 模型不需要懂任何类型知识，但写 Alloy 模型需要懂一点。

4.5Facts, Predicates, Functions, and Assertions

段落化的约束组织

模型的约束被组织成段落（paragraph）：假设放进 fact 段落；待检验的蕴含放进 assert；需要在不同上下文中使用的约束打包成 pred；可复用的表达式打包成 fun。

4.5.1 Facts · 事实

被假定为永远成立的约束记录为 fact。一个模型可以有任意多个 fact，每个自成一段，用 fact 标记，由一组约束构成。fact 出现的顺序、以及一个 fact 内部约束的顺序都无关紧要。你可以给 fact 起一个唯一的、便于记忆的名字。

电台频段不重叠

sig RadioStation {band: set Freq}
fact NoOverlapping {
  no disj s, s': RadioStation |
    some s.band & s'.band
}

文件系统三条性质

fact {
  // 无目录环
  no d: Directory | d in d.^contents
  // 每个对象从根可达
  Object in Root.*contents
  // 每个对象至多一个父目录
  all o: Object | lone o.~contents
}

交通灯：每个路口必有红灯

sig LightState {
  color: Light -> one Color
}
sig Light {}
abstract sig Color {}
one sig Red, Yellow, Green
  extends Color {}
sig Junction {lights: set Light}
fact {
  all s: LightState, j: Junction |
    some s.color.Red & j.lights
}

模型图见 fig. 4.10：弧标签为 <LightState>.color !Light。

Signature facts · 签名事实

规则

很多 fact 是对 signature 集合的每个元素都成立的约束，这些可以更简洁地记录为 signature fact：紧跟在 signature 后面的约束被隐式地对其元素量化，且每个字段引用被隐式解引用，与字段声明中提及字段的处理方式完全相同。

即 sig A {…} {F} 等价于：

sig A {…}
fact {all this: A | F'}

其中 F' 与 F 相同，只是把出现在 A 或其父类型中的每个字段 g 替换为 this.g。

没有链路把主机连到自己

// 冗长版：
sig Host {}
sig Link {from, to: Host}
fact {all x: Link | x.from != x.to}

// 简洁版：
sig Host {}
sig Link {from, to: Host} {from != to}

每条链路都有反向链路（用 @ 阻止展开）

sig Host {}
sig Link {from, to: Host}
  {some x: Link | x.@from = to and x.@to = from}

它等价于：

all this: Link |
  some x: Link |
    x.from = this.to and x.to = this.from

若没有 @，它会等价于（注意 this.from 是个集合，用作下标）：

all this: Link |
  some x: Link |
    x.(this.from) = this.to and x.(this.to) = this.from

这甚至无法通过类型检查。

字段声明中隐含的约束，也可以把声明当作出现在 signature fact 里的一个公式来理解：

// 这两种写法等价
sig Book {
  homeAddress, workAddress: Name -> Addr,
  address: homeAddress + workAddress
}
sig Name, Addr {}

sig Book {
  homeAddress, workAddress, address: Name -> Addr
} {
  address: homeAddress + workAddress
}
sig Name, Addr {}

因此，在声明的界定表达式中也可以使用关键字 this 和符号 @，尽管这很少有必要。

Q：signature fact 类似面向对象语言里的类不变式吗？

是的，经常扮演同样的角色：表达关于集合中个体的约束。但 signature fact 更有表达力，因为 Alloy 的字段可以向任意方向导航（所以你能谈论「指向这个对象的那些对象」），也因为可以以任意方式量化。就上面两个链路的例子来说，第一个（「没有链路把主机连到自己」）像类不变式，第二个（「每条链路都有对应的反向链路」）不是。

最离谱也最令人困惑的例子

好的实践是：把 signature fact 的使用限制在「只适用于该 signature 集合元素」的约束上。否则 signature fact 中的隐式量化会带来意外后果，尤其是当你没有提及该 signature 的任何字段时：

sig A {} {some A}

你会惊讶地发现：这个模型存在 A 没有任何元素的实例。展开这条 fact 就明白了：

all this: A | some A

当 A 为空时它空洞地为真，与量化体是什么无关。教训：把想要的约束写进一个独立的 fact：

sig A {}
fact {some A}      // 现在含义正确：A 非空
// 或者等价地：
some sig A {}

4.5.2 Functions and Predicates · 函数与谓词

常常有些约束你不想记录为 fact：你可能想在包含/不包含某约束两种情况下分析模型；想检验某约束是否由其他约束推出；或者想声明一个可在不同上下文中复用的约束。谓词为这些目的打包表达式；函数为复用打包表达式。

fun = 具名表达式

有零或多个参数声明，以及一个结果的声明表达式。使用时必须为每个参数提供一个表达式；其含义就是函数的表达式，把每个参数替换为其实例化表达式。

abstract sig Color {}
one sig Red, Yellow, Green extends Color {}

// 交通灯允许的颜色变化方式：
fun colorSequence (): Color -> Color {
  Color <: iden
    + Red -> Green
    + Green -> Yellow
    + Yellow -> Red
}

Color <: iden 是「保持不变」，其余三条是红→绿→黄→红的循环。

pred = 具名约束

有零或多个参数声明。使用时必须为每个参数提供表达式；其含义就是谓词的约束，把每个参数替换为其实例化表达式。

sig Light {}
sig LightState {color: Light -> one Color}
sig Junction {lights: set Light}

fun redLights (s: LightState): set Light {
  s.color.Red
}
// 除至多一盏外，其余都显示红灯
pred mostlyRed (s: LightState, j: Junction) {
  lone j.lights - redLights(s)
}

用谓词表示「操作」——非确定性的示范

谓词可以用来表示一个操作（operation），它通过约束前状态与后状态之间的关系来描述一组状态迁移。

1 pred trans (s, s': LightState, j: Junction) {
2   lone x: j.lights | s.color[x] != s'.color[x]        // 至多一盏灯改变
3   all x: j.lights |
4     let step = s.color[x] -> s'.color[x] {
5       step in colorSequence ()                        // 按序变化
6       step in Red -> (Color - Red) => j.lights in redLights(s)
7     }                                                 // 从红转其他色 ⇒ 之前全红
8 }
这个操作展示了非确定性：路口的这组灯如何变色被约束了，但没有被完全决定。谓词允许所有灯保持同色，也没有说明「当所有灯都是红的时」哪一盏会变。
非确定性正是优点

如果能证明这个操作是安全的，我们就知道：任何按照给定约束来解析这些选择的操作也都是安全的。这正是「用最弱的规范描述操作」的价值——你不需要提前决定实现细节。

Receiver 语法（::）

Alloy 有一个类似面向对象语言「接收者（receiver）」约定的简写，用于第一个参数是标量的函数或谓词。与其写：

pred f (x: X, y: Y, …) {… x …}

你可以写：

pred X::f (y: Y, …) {… this …}

带一个由关键字 this 指代的隐式第一参数（函数同理）。无论谓词/函数是否以这种方式声明，它都可以用 x::f(y, …) 的形式使用，其中 x 作为第一个参数、y 作为第二个，依此类推。

// 与前面的 redLights / mostlyRed 等价：
fun LightState::redLights (): set Light {s.color.Red}
pred LightState::mostlyRed (j: Junction) {
  lone j.lights - s::redLights()
}
// 调用式 s::mostlyRed(j) 与 mostlyRed(s, j) 等价，无论 mostlyRed 如何声明

4.5.2 Discussion

Q：如何决定用谓词还是 fact？

回忆一下：谓词只在其被调用时成立；fact 永远成立。所以一般规则是「永远成立的假设放进 fact，其他约束放进谓词」。但这条规则有点天真：其一，你可以把约束打包成谓词、再把谓词包含进 fact；其二，你甚至可以完全弃用 fact，把本该是 fact 的内容作为谓词插入到各处。所以选择更微妙。

因为 fact 是全局的，它们非常方便：写在一处的约束到处适用，在每个谓词和断言中都被假定。缺点是失去控制。也许你想在不带这条约束的情况下检验某个断言。你当然可以在检验那个特定断言时把它在 fact 段落里注释掉，但那很笨拙：如果有两个断言，你想一个带约束、一个不带地检验，就得在分析过程中不断注释/取消注释。

因此一种更啰嗦的风格很有吸引力：极少甚至完全没有 fact，把约束在它适用的每个上下文中重复。通过把重复的约束打包成谓词，你只需重复谓词的名字，而不必重复约束本身。

小模型用 fact 更方便（让模型更简洁，且容易转成谓词）；大模型往往用后一种更成熟的办法效果最好。

Q：receiver 语法在实践中什么时候用？

它的好处在于表达式涉及一连串函数应用的时候。那时你不必写嵌套表达式：

h (g (f (x, arg1), arg2), arg3)   // 函数名以「应用的反序」出现，淹没在括号里

而可以写：

x::f(arg1)::g(arg2)::h(arg3)
Q：谓词和函数如何做类型检查？
方式很直白。检查谓词或函数的体时，类型检查器假定形式参数具有所声明的类型。检查一次调用时，检查器判断每个实际参数的类型与对应形式参数的类型是否重叠；如果它们不相交，就报错。

4.5.3 Assertions · 断言

断言是意图由模型的 fact 推出的约束。分析器检验断言。如果一个断言并非由 fact 推出，那么要么暴露了一个设计缺陷，要么表述有误。即使确实成立的断言也值得记录：一是因为它们以不同方式表达性质，二是因为它们像回归测试——如果后来引入了错误，检验断言可能就检测得到。

文件系统：三个断言，两真一假

abstract sig Object {}
sig Directory extends Object {contents: set Object}
one sig Root extends Directory {}
sig File extends Object {}
fact { Object in Root.*contents }   // 每个对象都从根可达

// ✅ 有效：除根以外每个对象都在某个目录里
assert SomeDir  { all o: Object - Root | some contents.o }

// ❌ 无效：没有对象包含根目录（Root 本身是 Directory，含自己即可反证）
assert RootTop  { no o: Object | Root in o.contents }

// ✅ 有效：每个文件都属于某个目录
assert FileInDir { all f: File | some contents.f }
自包含的断言 = 逻辑猜想

断言可以完全自包含，不依赖任何 fact（无论显式还是隐式），甚至可以在没有任何 signature 的模型中声明。此时断言是一个逻辑猜想，意图是一个重言式。这类断言可用来检验算子的数学性质，或试验一个约束的不同表述方式。

// ✅ 正确：点对二元关系是结合的
assert DotAssociative {
  all p, q, r: univ -> univ | (p.q).r = p.(q.r)
}
// ❌ 错误：以为并和差可以像算术里的加减那样操作
assert BadUnionRule {
  all p, q, r: univ -> univ | p = q + r  iff  p - q = r
}

这就是书中提到的 language/theorems 模块的用法——把 Alloy 当成一个可以试验逻辑恒等式的沙盒。

module language/lights
abstract sig Color {}
one sig Red, Yellow, Green extends Color {}

fun colorSequence (): Color -> Color {
  Color <: iden + Red -> Green + Green -> Yellow + Yellow -> Red
}
sig Light {}
sig LightState {color: Light -> one Color}
sig Junction {lights: set Light}

fun redLights (s: LightState): set Light {s.color.Red}
pred mostlyRed (s: LightState, j: Junction) {
  lone j.lights - redLights(s)
}
pred trans (s, s': LightState, j: Junction) {
  lone x: j.lights | s.color[x] != s'.color[x]
  all x: j.lights |
    let step = s.color[x] -> s'.color[x] {
      step in colorSequence ()
      step in Red -> (Color - Red) => j.lights in redLights(s)
    }
}
// 关键安全性质：迁移前后都保持「除一盏外全红」
assert Safe {
  all s, s': LightState, j: Junction |
    mostlyRed (s, j) and trans (s, s', j) => mostlyRed (s', j)
}
check Safe
fig. 4.11 交通灯模型，带安全断言。这是一个「三段式」的典范：状态表示（LightState）+ 操作（trans）+ 不变式（mostlyRed），断言检验不变式被操作保持。这个模式在第 6 章的三个案例中被反复使用。

4.5.3 Discussion

Q：断言在实践中用来做什么？

断言通常扮演两种不同角色。

① 表达本身并不有趣的平凡性质，纯粹用来探测模型缺陷。令人惊讶的是，即使只有几条这样的断言，也能极其有效地揭示微妙的缺陷。以交通灯系统为例：我们可能相信自己已经把系统规范到了「保证确定性（每个状态至多一个后继）」的详细程度。确定性本身不是一个有趣的性质，但通过检验它，我们会发现模型里的洞——细节缺失的地方。

② 表达真正本质的性质，有时比模型的 fact 更根本。作者说：「我常常发现，为一个设计找出正确的断言，会给我一个关于它究竟是什么的完全不同的视角，比我开始时的视角清晰、简单得多。」在交通灯系统里，有些性质是其运行的根本、并激发了整个设计——例如灯通过「绝不同时显示多于一个绿灯」来正确地守护穿行路口的车辆。

Q：断言必须有名字吗？
和 fact 一样，断言可以没有名字。但要检验一个断言，你需要在命令中引用它，所以很少让它匿名。
Q：模型可以只有断言而没有 fact 吗？
可以（如 language/theorems 所示）。即使没有显式 fact，通常也存在隐含在 signature 声明里的 fact。

4.6Commands and Scope · 命令与作用域

命令作用找不到时报告
run P搜索谓词 P 的一个实例failure（没有实例）
check A搜索断言 A 的一个反例success（找不到反例）

除了谓词/断言的名字，你还可以给出一个作用域（scope），用来限定将被考虑的实例或反例的大小。省略作用域时，工具使用默认作用域：每个顶层 signature 限制为 3 个元素。

作用域的写法

要显式指定作用域，你可以为每个对应一个基本类型的 signature 给出界限。你可以给顶层 signature、扩展 signature，甚至两者的混合设界，只要每当一个 signature 被给了界限，它的父签名以及同一父签名的任何其他扩展的界限都能被确定。

✅ 合法命令

check A for 5 Object
check A for 4 Directory, 3 File
check A for 5 Object, 3 Directory
check A for 3 Directory, 3 Alias, 5 File

基于这些声明：

abstract sig Object {}
sig Directory extends Object {}
sig File extends Object {}
sig Alias extends File {}

❌ 非法命令

check A for 3 Directory, 3 Alias

因为它把 File 的界限留成了未指定：已知 Directory=3、Alias=3，但 File 除 Alias 外还有多少元素无法确定。

默认 + 覆盖

你可以显式设定一个默认作用域，并把它与特定类型的显式界限混合，后者会覆盖并补充默认作用域：

check A for 5            // 所有顶层类型界为 5（这里只有 Object）
check A for 5 but 3 Directory
// ⇒ Directory 界为 3，File 由推论界为 2
两条容易忘记的规则
  1. 声明已确定大小的 signature 会隐式覆盖作用域。给定 fig. 4.11 的声明，check Safe for 2 会把 Junction、Light、LightState 限制为各 2 个原子，但会给 Color 分配恰好三个的大小（因为 one sig Red, Yellow, Green extends Color）。
  2. 作用域声明只给出大小的上界。若要规定确切大小，用关键字 exactly： 
    check A for exactly 3 Directory, exactly 3 Alias, 5 File
// File 至多 5 个；Directory 和 Alias 各恰好 3 个

4.6 Discussion

Q：作用域是由实际系统中实例的大小决定的吗？

通常不是。偶尔实际系统中存在一个资源上限影响作用域的选择。例如作者们对一个质子治疗装置所做的分析中，恰好有三个治疗室，所以把对应集合限制为三个元素是合理的。

但更典型的是，作用域纯粹由分析方面的考虑决定：估计需要多大的实例才能找到缺陷（同时仍允许可处理的搜索）。例如你可能在作用域 10 下检验一个文件系统，因为你相信这足以捕获几乎所有设计缺陷——任何坏场景很可能都能在一个含十个对象的文件系统里演示出来。

分析的力量来自于：含十个对象的可能文件系统数量是巨大的，而你的模型会对其中每一个都被检验。但你当然不打算让模型本身有这样的限制——一个只能容纳十个对象的文件系统没什么用。

Q：为什么作用域必须在每条命令里重复指定？

把作用域设置与模型本体分离，是一个重要的语言设计决定。它防止模型本身被分析方面的考虑所污染，并允许同一个模型在不同作用域下被分析。

作用域的概念并非 Alloy 独有，但在其他工具中往往处理得更不系统。许多模型检查器要么把作用域硬连线，要么使用全局常量。一个典型的交通灯系统描述会限制路口的灯数，所有分析都在同一限制内进行。更糟的是，模型往往会硬连线一个特定配置：一个有两盏灯的模型不会覆盖只有一盏灯的情形。

4.7Modules and Polymorphism · 模块与多态

Alloy 有一个简单的模块系统，让你把模型拆分到若干模块中，并使用预定义的库。模块与文件一一对应。每次分析应用于单个模块；任何其他含有相关模型片段的模块都必须被显式导入。每个模块有一个路径名，必须与其文件在文件系统中的路径匹配。路径相对于工具偏好设置中给出的一组根目录解释。

4.7.1 Module Declarations and Imports

module modulePathName          // 每个模块的第一行
open modulePathName            // 紧随其后的显式导入（最简形式）

库模块

module library/graphs
pred Acyclic (r: univ -> univ) {
  no ^r & iden
}

用于家庭模型

module family
open library/graphs
sig Person {parents: set Person}
fact {Acyclic (parents)}

用于文件系统模型

module fileSystem
open library/graphs
sig Object {}
sig Directory extends Object {
  contents: set Object
}
fact {Acyclic (contents)}

模块有自己的命名空间。不同模块的组件之间的名字冲突可以用限定名解决：路径名为 p 的模块中的 signature、谓词或函数 X，其限定名是 p/X。即使非限定名本就无歧义，也仍可使用限定名。

用限定名避免冲突

module family
open library/graphs
sig Person {parents: set Person}
pred Acyclic () {
  library/graphs/Acyclic (parents)
}

用别名缩短

module family
open library/graphs as g
sig Person {parents: set Person}
pred Acyclic () {g/Acyclic (parents)}

4.7.2 Parametric Modules · 参数化模块

纯语法机制

模块可以由一个或多个 signature 参数参数化，写成模块名后方括号里的标识符列表。任何导入模块都必须用某个 signature 的名字实例化每个参数。参数化只是一个语法机制：实例化一个模块的效果，等同于导入该模块的一份副本，并把参数在整个副本中替换为实例化的 signature 名。

参数化的图论库

module library/graphs [t]
pred Acyclic (r: t -> t) {no ^r & iden}

两处使用：

module family
open library/graphs [Person]
sig Person {parents: set Person}
fact {Acyclic (parents)}

module fileSystem
open library/graphs [Object]
sig Object {}
sig Directory extends Object {contents: set Object}
fact {Acyclic (contents)}

参数化的 list 模块（泛型数据结构）

module library/list [t]
sig List {}
sig NonEmptyList extends List {
  next: List, element: t
}
fact Canonical {
  no disj p, p': List |
    p.next = p'.next and p.element = p'.element
}
fun List::first (): t {this.element}
fun List::rest (): List {this.next}
fun List::addFront (e: t): List {
  {p: List | p.next = this and p.element = e}
}

参数化模块最常见的用途就是泛型数据结构：排序、队列、列表、树。类型参数代表数据结构所容纳元素的类型。

注意 addFront 的返回体是一个集合理解式——它不是「构造一个新对象」，而是描述那个已经存在的、满足条件的 List 原子。这是 Alloy 与命令式语言的根本差异。

参数 vs univ 的取舍

任何带参数声明的模块，本都可以不带参数、改用 univ 来声明。参数的优势是允许更强的类型检查；劣势是每次使用都需要一次单独的实例化。

4.7 Discussion

Q：模块别名什么时候有用？

当一个参数化模块被以不同的参数实例化多次导入时，别名最有用——这种情况下组件名总是需要被限定。例如一个由「资源」和「被分配资源的用户」参数化的资源分配模块：

module general/resourceAllocation [user, resource]
…
pred Allocate (…) {…}

在火车系统模型中两次使用：

module trainSystem
open general/resourceAllocation [Train, Track] as trainResource
open general/resourceAllocation [Track, Current] as trackResource

于是像 general/resourceAllocation[Train, Track]/Allocate 这样长的名字，用别名后就成了 trainResource/Allocate。

Q：signature 扩展能跨越模块边界吗？

能。导入模块可以扩展被导入模块中声明的 signature，反之亦然。下面这个模块给一个 signature 添加 name 字段：

module named [t]
sig named_t extends t {name: Name}
fact {all disj a, b: t | a.name != b.name}
fact {t = named_t}

现在只要写 open named [S]，对任意 signature S，S 的每个元素 x 都会拥有一个互不相同的名字 x.name。

三条 fact 的分工值得注意：第一条保证名字互异；第二条 t = named_t 保证每个 t 都真的有一个 named_t 包装（否则 t 中可能有元素不被覆盖）。

4.8Integers and Arithmetic · 整数与算术

3.7 节介绍过整数值表达式：#e 是一个整数，表示关系 e 中的元组数；这类表达式可以做加减、可以比较。

例：三条同花

sig Card {suit: Suit}
sig Suit {}
pred ThreeOfAKind (hand: set Card) {
  #hand.suit = 1 and #hand = 3
}

「一手牌是三条同花」= 它由三张牌组成（#hand = 3），且花色只有一种（#hand.suit = 1）。

Int 与 int：整数值 vs 整数原子

你可能会问：整数能作为关系中的原子出现吗？整数本身不是原子，但与每个整数值相关联，存在一个「持有该整数值」的整数原子，从而让整数实际上可以被包含在关系里。

记号含义类型
Int e对整数值表达式 e，表示持有 e 的整数值的那个整数原子int -> Int
int e对表示一组整数原子的表达式 e，表示这些原子的整数值之和Int -> int
Int关键字，表示所有整数原子的集合可当作一个预定义 signature，如同 univ

从类型检查的角度，有一个与整数值表达式关联的类型 int，和一个表示整数原子集合的类型 Int。

例：带权图，自连接权重为零

sig Node { adj: Node -> lone Int }
fact {
  all n: Node |
    let w = n.adj[n] |
      some w => int w = 0
}

字段 adj 把每个节点映射到它的相邻节点及其权重（权重是整数原子）。注意必须写 some w => …：因为 adj 是 lone，自连接可能不存在。

4.8 Discussion

Q：为什么把整数放到最后讲？

整数其实不太有用。如果你觉得自己需要它们，再想想；往往有一个更抽象、更贴合问题的描述。「整数出现在问题域里」并不意味着它就应该被如此建模。

要判断整数是否必要，问自己究竟依赖了哪些性质。例如一个给消息编号的通信协议，可能只依赖「编号互不相同」；或依赖「编号递增」；甚至可能是「全序」。这几种情况下都不应该使用整数（用无解释原子 + util/ordering 更好）。当然，如果是一个重度数值化的问题，你很可能需要整数（以及更多），但那时 Alloy 大概本来就不合适。

Q：Alloy 有乘法算子吗？
没有。幸运的是，结构模型中很少需要它。需要乘法的那类模型往往重度数值化，本来就不适合 Alloy。
Q：Alloy 中整数是如何定作用域的？

在作用域说明中，Int 的设置限制 Int 原子的个数，而 int 的设置给出整数的最大位宽。例如包含作用域

3 Int, 6 int

的命令，会把搜索限制为至多三个 Int 原子，并涉及 −31 到 +31 范围内的整数。

Q：Alloy 的 Int 像 Java 的 Integer 吗？

像。Alloy 中 Int 与 int 的区分，非常类似 Java 中「原始整数值」与「Integer 对象」的区分。但目的不同：如果把整数值当作原子处理，我们就需要为作用域内每一个可能的整数值准备一个原子，这会让分析更不可处理。

这个区分本可以在语法上隐藏起来（在 Int 与 int 之间做隐式强制转换），但那样我们就无法重载 + 和 - 算子了。

Q：整数对象对它们承载的值是唯一的吗？
是的。下面的断言是有效的： 
assert UniqueInts {all i, j: Int | int i = int j => i = j}
Q：那布尔值呢？Alloy 没有布尔类型吗？

Alloy 没有布尔类型。乍看之下这非常奇怪，尤其是对一门基于一阶逻辑的语言而言。当然，公式确实有布尔值，但表达式永远没有。

要明白为什么，假设 Alloy 有一个可用于此类声明的布尔类型：

sig Phone {offhook, ringing: boolean}

这样做的动机是能写出这样的约束：

all p: Phone | p.offhook => not p.ringing

但麻烦来了：像 p.ringing 这样的项一般表示一个布尔值的集合。那么当集合含零个或多于一个布尔值时，not p.ringing 的值是什么？没有好的出路。也许你可以拒绝这类表达式，只允许不出现它们的约束（如上面那条）？这不容易做到，因为它涉及对函数定义域的推理。或者你可以把标准逻辑算子的解释扩展到布尔值的集合上？

这些问题只是「偏函数及其应用」这一老问题的一个特例，而 Alloy 通过只提供关系映像、不提供函数应用避开了它（见 3.4.3 的讨论）。引入布尔类型会把所有那些复杂性重新带回来——因为布尔表达式涉及函数应用——而收益很小。

如果你真的要布尔值

你可以自己定义一个布尔类型：

module booleans
sig Boolean {}
one sig True, False extends Boolean {}

module phones
open booleans
sig Phone {offhook, ringing: Boolean}
fact {all p: Phone | p.offhook = True => not p.ringing = True}

「如果你是一个真正的自虐狂」，你甚至可以定义逻辑算子的扩展版本，比如这个「当 e 不是标量时把 Not e 给成 false」的否定：

fun Boolean::Not (): Boolean {if this = False then True else False}
// 然后可以写： fact {all p: Phone | Implies (p.offhook, Not (p.ringing)}

事实上 Alloy 库里就包含这样一个模块。当布尔值必须被精细建模时它有用，例如在推理代码时。但对于设计建模，这是错误的做法。

本章最重要的建模忠告：用子类型，不要用布尔属性

给对象分类的方式，不是用属性把它们与布尔值关联起来，而是声明子类型：

sig Phone {calling: set Phone}
sig Offhook, Ringing extends Phone {}

于是「摘机的电话不在响铃」这条约束就隐含在声明里了——你根本不用写。

对于动态分类，你可以为每个属性关联「它成立的那些时刻的集合」：

sig Phone {
  calling: Phone -> Time,
  offhook, ringing: set Time
}
// 约束变成：
all t: Time | no offhook.t & ringing.t

使用集合算子，约束比用布尔属性更简洁，而且没有任何那些复杂性。

第 4 章小结

  1. 模型的宏观结构有五种段落：module 头 → sig 声明（集合 + 字段）→ fact/fun/pred 约束段 → assert 断言 → run/check 命令。Alloy 独有的只有 signature 与 scope 两个概念。
  2. signature 构成一棵分类树：univ 是隐式根，顶层签名互不相交，extends 的兄弟互不相交，abstract 表示「父 = 各子之并」。正交分类用 in（子集签名，不必不相交，不引入新类型）。前置重数关键字（one sig A, B, C extends T）可构造枚举。
  3. 没有顶层关系声明——所有关系都是某个 signature 的字段；不属于任何 signature 的全局关系，用一个 one sig Globals {…} 容器承载。
  4. 字段声明 sig A {f: m e} 的准确含义是 all this: A | this.f : m e，省略重数关键字时默认为 one（⇒ 标量）。disj 表示互斥，part 表示划分（互斥 + 覆盖）。
  5. 依赖式声明只能引用「本签名或其父签名中先前声明的字段」，且引用会被展开为 this.g。用 @ 阻止展开；但不要拼命把约束塞进声明——闭包类约束写成独立 fact 更安全（*@friends 陷阱：会让字段变成三元关系）。
  6. 类型是「值的过近似」，类型本身就是 Alloy 表达式。类型检查的唯一判据是可证冗余：混合 arity，或（子）表达式必为空。s.r 的四种组合中只有「不相交」被拒绝；把子类型字段用于父类型是合法的（结果可能为空，但不总是为空）。类型检查器从不误报，也不提供任何保证；Alloy 实际上可视为无类型语言——读模型不需要懂类型，写模型需要懂一点。
  7. 重载解析依赖完整上下文，而非语法形式（因此 b.~band、band.b、s->b in band 都能正确解析）。同名字段的 signature 不得重叠；无法解析时用域限制 S <: f 消歧——它不是什么特殊的 cast，等价于 (S -> univ) & f。
  8. 四种约束段落各司其职：fact 全局永真（方便但失去控制）；pred 按需调用（大模型宜少用 fact、多用 pred）；fun 复用表达式；assert 记录「应由 fact 推出的冗余」，充当回归测试。signature fact（紧跟 sig 的 {…}）隐式 all this: 量化并展开字段——危险例子：sig A {} {some A} 在 A 为空时空洞为真。
  9. 断言的两种用途：① 平凡性质（如确定性）用来探测模型的洞；② 本质性质常常比 fact 更根本，写对断言会让人对设计产生更清晰简单的理解。自包含断言（无 sig 无 fact）可用来试验逻辑恒等式（如验证 dot 的结合律、证伪 p = q + r iff p - q = r）。
  10. 作用域与分析器沟通，与模型本体分离：默认每个顶层签名 3 个；for 5 but 3 Directory（but 覆盖并补充默认）；for exactly 3 X 规定确切大小；声明已确定大小的签名（如 one sig 枚举）会隐式覆盖。作用域通常由「多大实例足以暴露缺陷」决定，而非系统实际规模——分析的力量在于：十对象的文件系统数量巨大，模型对每一个都被检验。
  11. 模块 = 文件；module / open / open … as 别名 / 限定名 p/X。参数化模块是纯语法机制（等同于导入一份替换过的副本），用于泛型数据结构（list、ordering、queue、tree）；相比直接用 univ，好处是更强的类型检查，代价是每次使用需单独实例化。signature 扩展可以跨模块（named [t] 模式）。
  12. 整数：能力有限，且应尽量不用。只有 #、加减、比较，没有乘除。Int（整数原子集合，像预定义 signature）与 int（整数值）的区分，类比 Java 的 Integer/int，目的是避免为每个整数值准备原子并保留算子重载。作用域中 3 Int, 6 int ⇒ 至多 3 个整数原子、位宽 6（−31…+31）。
  13. Alloy 没有布尔类型，这是深思熟虑的：布尔表达式必然涉及函数应用，而偏函数应用正是 Alloy 通过「只有关系映像」刻意回避的难题。正确做法是声明子类型（sig Offhook, Ringing extends Phone {}），静态分类的约束就隐含在声明里；动态分类则为每个属性关联一个 set Time，用集合算子表达——更简洁，且没有任何复杂性。
